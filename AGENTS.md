# Repository Guidance

- Consult `DESIGN_PRINCIPLES.md` when changing module ownership, dependency direction, effect contracts, expected-failure handling, closed-family members, recurring boundary boilerplate, or an agent-facing schema or artifact. Apply its decision visibility, outer-glue ownership, plain-function, thematic symmetry, semantic-scaffold, and fixed-point stop rules as repository constraints.
- When delivering or changing a feature, use the narrative-parity method in `DESIGN_PRINCIPLES.md`: make one representative code path and its product overview tell the same ordered story, and change either code or documentation when they disagree.
- Before broad autonomous work begins, give the human one short declarative scope confirmation that names the intended outcome, the principal surfaces expected to be read and touched, the approximate magnitude, and any surprising exclusion. This confirms the interpretation without asking again for permission already granted or exposing an internal plan; pause only when the sentence reveals a product or scope choice the human has not made.
- Use Python 3.14.x syntax only. Keep `.python-version`, `requires-python`, Ruff `target-version`, Pyrefly, CI, and the uv lock aligned with the current stable 3.14 patch release.
- Use uv as the only Python dependency, environment, build, and installed-package entry point. Keep `uv.lock` checked in. jscpd is the sole non-Python development dependency: install its pinned native binary project-locally with `npm ci`, keep `package-lock.json` checked in, and do not add other npm packages without explicit scope.
- Do not inject `PYTHONPATH` or another import path, invoke an ambient Python interpreter, add requirements files, or run source files as a substitute for the installed package.
- Before a task that began as an answer, explanation, review, diagnosis, or other read-only request starts repository writes, or when accepted repository changes still need a human disposition, load and follow the review, checkout, and wrap-up procedure in `skills/pinboard/SKILL.md`. Keep the decision procedure there rather than duplicating it here.
- Match checks to the changed surface. When plugin or skill files change, run `uv run --locked python scripts/validate-metadata.py`; it is the repository-owned platform-compatible metadata check. Run any platform-supplied `quick_validate.py` through the same locked development environment. PyYAML is declared there for validation, so a missing `yaml` module is a broken environment to fix, not an expected limitation to report. Do not provision undeclared one-off dependencies for unrelated optional checks.
- Keep Ruff `UP` as the only pyupgrade authority. Do not add standalone pyupgrade, MyPy, Pyright, or redundant type-checking layers.
- Run `npm run duplication` after changing production Python. Treat a match as a refactoring prompt rather than an automatic defect: share code only when doing so gives behavior or a repeated decision one clearer owner, and do not move code across an ownership or layer boundary merely to reduce the count. Do not abstract independent tests, required boundary shapes, or exhaustive closed-family branches merely to silence the detector. CI uses the less-sensitive `npm run duplication:ci` profile, rejects new clones relative to `origin/main`, and enforces its recorded percentage ceiling. Lower that ceiling after accepted cleanup reduces the baseline; do not raise it merely to admit new duplication.
- Keep Pyrefly strict. Convert boundary values into exact validated types before domain use.
- Declare supported structured boundary shapes as frozen `msgspec.Struct` records with annotated field constraints and `forbid_unknown_fields=True`, then decode or convert directly into the declared record. This applies to JSON payloads and to mapping-shaped CLI, SQLite, YAML, and TOML values. Prefer a verbose record declaration over `JsonValue` trees, mapping walkers, primitive field validators, or serialize-then-validate round trips. Put cross-field invariants that cannot be expressed declaratively in the boundary record's post-init validation so decoding and instantiation remain one operation; do not repeat them after the value becomes a production command or domain model. Schema-tagged payloads with no shared shape may use `msgspec.Raw`. Hand-written parsing is acceptable only when the format is predominantly a custom grammar or relational validation makes a declarative codec less clear; document that reason at the owner. When Codex or a project tool is the only writer of a machine-consumed structured artifact, keep strict typed JSON canonical and derive human-readable Markdown as a non-authoritative projection. Separate models, exact errors, and behavior only when each has a coherent responsibility; fold ceremonial islands into the nearest real owner.
- Keep Python types concrete. Do not use `object` as an annotation escape hatch. When a boundary is genuinely untyped, use `Any`, then validate or narrow it before domain use. Prefer explicit branches over reflective `getattr` or `setattr` loops when the concrete variants are known. Model closed vocabularies without variant-specific data as plain `Enum` values inside the domain. Model closed variants that carry different data as flat dataclass unions rather than a fieldless enum coupled to a separate payload or a polymorphic class hierarchy. Convert strings only at parsing and rendering boundaries. Handle closed branching with exhaustive `match` cases and `typing.assert_never`; write the unreachable arm as `case _ as unreachable:` so the project coverage configuration excludes the statically impossible clause. Combine alternatives with an OR-pattern when they bind equivalent values and perform identical work; remove a named case when an existing general case already owns the same outcome. Do not merge the variants themselves merely because one consumer handles them alike. Do not construct invalid variants merely to execute `assert_never`. Do not use static handler or type dictionaries when the alternatives cannot change at runtime, and do not let a catch-all `else` silently stand for a known variant. Reserve registries and polymorphism for behavior that is genuinely open or runtime-extensible. Never use `StrEnum`.
- When a closed family repeats one classification through a tag, payload presence, collection membership, or conversion table, give that classification one canonical owner. Use a vocabulary value when every alternative has the same shape, a closed variant when alternatives carry different data, and an explicit decision when validity depends on surrounding state. Preserve required wire, storage, and presentation shapes through named exhaustive boundary conversions instead of leaking their redundancy into the domain. Recompute producers and consumers after each collapse, and stop when another fold would erase a product distinction or add more conversion machinery than invalid states and repeated decisions it removes. Report core decision points, explicit boundary conversion, import volume, and source-line change separately; none is a proxy for the others.
- Treat a command route and its variant-specific arguments as one closed hierarchy. The parser must select and decode an exact leaf command before dispatch; do not carry a general-purpose argument namespace, separate command and operation discriminators, or nullable fields whose valid combinations depend on those discriminators into handlers. Represent coupled option sets as separate flat union members, and require production consumers and reviews to match the resulting union exhaustively rather than reparsing or revalidating the route late.
- When changing a command or closed-variant flow, trace one representative value from its supported entry point to its effect and simulate adding one sibling. Count the places a developer must discover and edit. Keep an exhaustive branch only where that owner distinguishes alternatives or converts an independently required boundary shape; fold route enums, conversion tables, wrapper variants, and layer-by-layer matches that merely repeat an already selected fact. Do not replace a justified closed branch with reflection, a registry, callbacks, or polymorphism solely to reduce the count. Dynamic dispatch is valid at a deliberately open boundary or when the caller should not distinguish implementations, but keep its required surface and wiring visible and never supply a fallback handler, inherited default behavior, optional callback, or permissive lookup for an unsupported case.
- Parsing, deserialization, and post-deserialization structural or canonical validation may use typed exceptions locally while values remain boundary representations. When invalid input is an advertised outcome of an installed use case, the boundary owner catches the exact parser exception and returns that use case's typed failure. Once input has become a domain model, return expected domain and state-machine rejections as explicit values rather than raising exceptions. Do not model command, proposal, dispatch, or domain rejection families as exceptions. Express a concrete success value as `DecisionResult[T]`; when a caller only propagates its failure, use an early `isinstance(value, DecisionFailure)` return so static narrowing exposes `T`. Use exhaustive `match` only when distinct closed variants require distinct behavior. Use `DecisionFailure | None` when validation has no success value, and propagate it with a walrus `None` check when the failure is only returned. Infrastructure failures also remain exceptions.
- Keep read-only ledger lookup on `LedgerSnapshot` and return `None` for absence. The decision call site owns the operation-specific failure value; lookup helpers must not combine data access with hidden control flow.
- Model stable opaque string identifiers as distinct `typing.NewType` values. Convert validated external strings once at the owning boundary; do not let storage, Markdown, JSON, CLI, or filesystem representations enter pure decision signatures.
- Name concrete values for their product role or operation, such as `snapshot_items`; do not use architecture-layer prefixes such as `domain_` merely to distinguish them from boundary values.
- Do not introduce a named helper whose only behavior is reading one public attribute or reapplying a constructor or `NewType` that does not change the runtime representation when the caller can use the expression directly. A concretely typed callback helper remains appropriate when Python cannot annotate the equivalent lambda and strict Pyrefly would otherwise infer `Any`. Retain helpers that own validation, canonicalization, meaningful composite keys, stable protocols, or reused domain operations.
- Keep unshipped behavior without an installed entry point out of `src`. When a maintained design probe still provides useful evidence, isolate it under `tests/prototypes/` with a module header that names the deferred purpose and states that it is excluded from the installed package. Move it into production only with an accepted product brief and a real production consumer; otherwise delete it when the evidence is no longer useful.
- Tests must exercise observable behavior, rejection contracts, concurrency, recovery, or package/plugin integration rather than implementation constants. Do not copy production data, palettes, inventories, or configuration values into tests merely to freeze their current contents; assert the consumer-visible requirement or an independently owned external contract instead. Do not unit-test prose semantics by matching required or forbidden wording in Markdown, skill instructions, prompts, or other guidance files. Validate mechanical structure with the repository's metadata tools and assess meaning through review; add model-based regression evaluation only when the project has an explicit behavioral eval harness and accepted variability criteria.
- Do not make test outcomes depend on wall-clock passage or scheduler speed. Model time with fixed timestamps or a patched clock, and coordinate concurrent scenarios with events, barriers, or controlled fakes. Use bounded timeouts only to fail deadlocks, never as the behavior under test. Use real elapsed time only when an external system's timing is itself the supported contract, and document why deterministic control cannot represent it.
- During implementation and review, require every added observable behavior, blocking product claim, or mandatory tool, threshold, platform, compatibility, or hardening obligation to trace to accepted scope, an applicable repository rule, a reviewed product authority, or a named existing production consumer. Treat unsupported discoveries as upstream scope questions rather than silently implementing, requiring, or hardening them.
- Before treating a new closed domain state or mutation family as complete, prove one representative accepted value through the application-owned persistence boundary and reload it from a fresh store. Pure decision tests and separately constructed storage fixtures do not prove cross-layer compatibility; treat a mismatch between domain values, mutation projection, stored state, and schema as an architecture defect rather than normalizing or dropping facts in an adapter.
- Support macOS and Linux. Do not add cross-platform-looking branches without contention and filesystem evidence on the claimed platform.
- Preserve the observable transaction contract: a failed transition leaves the previous valid ledger intact, and concurrent stale actions are rejected.
- Treat Pinboard as a trusted local developer tool, not an adversarial multi-tenant service. Validate human-, agent-, import-, or environment-supplied values once at the boundary that turns them into typed canonical domain values. After an internal producer has established that contract, do not duplicate validation merely to defend against a human deliberately editing authoritative files or SQLite rows, recomputing forged digests, swapping symlinks during an operation, malware changing local state, or another process intentionally violating the repository protocol.
- Keep ordinary path containment at the single boundary that may perform a computed filesystem write, because malformed free-form input or an implementation bug must not accidentally write outside the project root. Do not add repeated path checks, symlink-race defenses, or tamper-proof readback throughout trusted internal layers unless a concrete supported boundary requires them.
- Security-style hardening requires a named threat or failure model and a supported entry path. Reopen stronger defenses when the product accepts untrusted external imports, serves mutually untrusted users, crosses a privilege boundary, shares writable authority remotely, or records an actual corruption incident. A hypothetical hostile local user, forged private ledger, or adversarial filesystem alone is not sufficient scope.
- Treat compatibility code as release-scoped, not permanent architecture. While no external users depend on an older format, use temporary isolated tooling to migrate the known local ledgers, preserve equivalence evidence, then delete the migrator, legacy readers, compatibility branches, and superseded tests before acceptance. Retain current schema detection and clean module boundaries; add a version-specific migration only when a real supported predecessor exists.
- Keep production source, public documentation, and code comments meaningful outside their delivery history. Describe current behavior, ownership, and invariants; keep implementation-plan task or checkpoint numbers, attempt names, milestone labels, and speculative future file paths in private planning artifacts.
- Use “Pinboard” in prose and `pinboard` for technical identifiers. Do not introduce another formal project name.
- Keep `README.md` human-facing and descriptive. Put imperative agent and contributor constraints here.
- Consult `ARCHITECTURE.md` whenever work may change architectural ownership or dependency direction. Record that impact in the work brief, and include every required `ARCHITECTURE.md` correction in the same implementation candidate; never defer it to a separate documentation cleanup.
