# Architecture

This is the current implementation map for maintainers and coding agents. It records who owns each responsibility, which way dependencies point, where durable state and stored formats live, the current limitations with their consequences and reopening conditions, and one ordered trace per representative flow. It names owners instead of restating them: field names, schema identifiers, result codes, rendering details and version lists live in the module named. Module paths are relative to `src/pinboard/` unless they start at the repository root.

## System overview

Pinboard is a local coordination system for one repository-owned work ledger. Two installed entries, the `pinboard` CLI and the local-stdio `pinboard-mcp` server, discover the project, open its work root and call the same application use cases over the same SQLite authority. MCP owns agent workflows: status and discovery reads, proposal intake, brief construction and publication, preparation and attempt authority, lifecycle transitions, dispatch, candidate observation and restoration, review publication, human-owned PR review, initiatives and the roadmap, saved priority, structural parallel preview, and the human-confirmed close, cancellation and consolidation routes. The CLI owns human maintenance: root discovery, initialization, summary status, diagnosis, full validation, generated-view repair, portable export, direct human closure, schema migration and its own static contract and code catalogs. Pinboard is an application and plugin, not a supported Python library: `python -m pinboard` and `python -m pinboard.mcp` alias the two entries, and internal modules and package exports are not extension APIs.

Codex is the primary, stress-tested integration. Codex (`.codex-plugin/plugin.json`), Claude Code (`.claude-plugin/plugin.json`, from a marketplace or `--plugin-dir`) and Antigravity (`.antigravity-plugin/plugin.json`) load the same repository root and share the launcher, MCP entry, skills, schemas and SQLite authority. Per-host differences stay in outer integration: MCP configuration files, the Claude and Antigravity hook adapters, runtime-specific identity sourcing, worktrees, subagents, permissions beyond Pinboard's own tool approval, waiting and optional messaging. None of them creates a separate application, domain or lifecycle policy, and no hook reads project state or grants lifecycle authority.

SQLite is authoritative for lifecycle, accepted scope, dependencies, route facts, mutation authority and history. Immutable artifacts hold accepted long-form bytes that SQLite references, and generated views are repairable projections. Attempt continuation is a read-only projection of current SQLite facts and verified artifacts. One work root has three durable roles:

```text
.pinboard/
  state.sqlite3   # authoritative lifecycle, dependency, authority, and history state
  artifacts/      # immutable long-form bytes referenced by SQLite
  views/          # repairable Markdown and HTML projections generated from SQLite
```

Each invocation resolves two Git-backed roots. The **source checkout root** is the selected checkout's exact top level, including a linked worktree, and owns project-file and authority reads for that attempt. The **shared repository root** comes from the Git common directory and owns shared Pinboard state and local Git exclusion. They are equal in a primary checkout and deliberately different in a linked worktree. `DurableRoots` alone derives the database path, and selecting an unused external work root does not require its parent to exist. Database-backed CLI commands cross one outer work-state boundary that validates the layout and constructs one `SQLiteWorkStore`; handlers receive their capabilities as required parameters and never import the concrete store. Composition uses no globals, optional fallbacks or dependency-injection framework.

Agent-facing instruction prose has one source owner per rule: the Markdown files in `skills/pinboard/sources/`, one per owner ID. `docs/pinboard-guidance-classification.json` records owner source selectors, includes, consumer relationships and implementing-test links. `scripts/generate-instructions.py` compiles the coordinator, worker and reviewer documents for each runtime plus the deduplicated action documents and their byte-identity catalog under `src/pinboard/instructions/`, enforcing coordinator startup at 16,000 UTF-8 bytes and the recorded worker and reviewer budgets beneath the 46,080-byte native-read ceiling. Generated copies are projections. `scripts/validate-metadata.py` requires implementing-test links on mechanized owners, verifies that each resolves to a test method, and checks generated freshness, relative links and actual coordinator startup composition. Prose meaning is reviewed rather than frozen by wording tests.

Route facts (`size_class`, `architecture_impact`, `external_effects`, `declares_checkpoints`) are recorded at intake with each classified definition. `ActionSemantics` in `domain/decision_models.py` owns whether an action needs them, and `domain/routing.py` applies that requirement. Each legal action returns one verified single-read instruction document selected from route facts, caller role and negotiated native runtime; protocol-only clients receive that disposition without an invented runtime. Recorded small work skips source planning and separate brief review, standard and campaign routes keep independent brief review, and campaign conduct applies only to declared checkpoints. External-effect facts describe a route and never authorize publication, merge or another external effect.

Skill behavior belongs to the skill sources, not to this map. The main Pinboard skill (`skills/pinboard/`) owns intent classification, status reporting, question policy, finding dispositions, assurance and repair responsibility, campaign suggestion, private adoption and repository wrap-up. Its intent rule keeps answers, explanations, review assessments and diagnoses inspection-only, routes an explicit human-owned PR review through its own evidence route, and requires an announced Pinboard-item or direct route before the first implementation write. Guidance neither intercepts nor authorizes repository writes, and private adoption keeps the default `.pinboard` behind its repository-local Git exclusion without writing adoption policy into a managed project's committed files. `skills/pinboard-deliver/` and `skills/pinboard-intake/` are its specialized callers. Technical Writing, Investigation Focus, Repository Readiness, Slop Cleanup and Maintaining Agent Guidance are independent guidance owners; each may use the others or Pinboard but needs neither for its baseline workflow. `DESIGN_PRINCIPLES.md` owns the supported-reality and canonical-naming rule that Slop Cleanup applies through its bundled inventory, where a private disposition ledger rather than any count or match decides production scope.

`evals/behavioral/` is a development-only behavioral harness outside the installed package. It evaluates an exported revision only as an external client, through that export's own launcher, skills and MCP server. `evals/behavioral/processes.py` owns its agent, Git and launcher subprocess effects, `evals/behavioral/board.py` its one MCP stdio client, `evals/behavioral/records.py` the strict run record, `evals/behavioral/spend.py` its spending boundaries and `evals/behavioral/runner.py` the paid-run preflights that stop before an agent turn when isolation evidence is missing or mismatched. Process environments, isolation probes, scoring, investigation trials and the startup pilot are described in [the harness guide](evals/behavioral/README.md), and decision rules in [CRITERIA.md](evals/behavioral/CRITERIA.md). Its evidence has fixed limits: live login evidence establishes the OS and local OAuth path, not every provider; a later probe cannot qualify earlier runs, and a version observation does not guarantee the executable stays unchanged during a run; Codex runs keep their coding-agent context and parent environment rather than a fully stripped one; scripted gaps and slowdown turns do not establish real compaction or live-input cancellation; unknown reviewer dollars or incomplete evidence make a comparison inconclusive; investigation recovery outcomes are descriptive and controlled tests claim no paid agent effectiveness; sparse pilot results remain formally inconclusive, and native workflow calls alone establish no committed effect. Unsupported record shapes reject strict decoding, and private output stores are never migrated or rewritten.

## Dependency direction

Pure decisions remain at the center:

```text
cli ──┐
      ├────────────> application ────────> domain
mcp ──┘                    ▲                  ▲
  └────────────────> adapters ───────────────┘
```

`domain` depends only on the Python standard library and `msgspec` for exact canonical records. `application` depends on domain values and storage-independent capability protocols. `adapters` implement those capabilities with SQLite, the filesystem and Git. `cli` and `mcp` are sibling outer boundaries: each decodes its transport, composes concrete adapters with shared application use cases, and presents transport-specific results without importing the other. Production dependency tests keep domain independent of outer layers, application independent of adapters, CLI and MCP, and adapters independent of both interfaces; they also keep CLI composition acyclic, constrain `cli/entrypoint.py` to routing and final error presentation, and verify both installed entries. The MCP package is acyclic.

The method used to preserve these boundaries, expose effects and stop decomposition at a useful fixed point is recorded in [the design principles](DESIGN_PRINCIPLES.md).

## Runtime ownership

### Launcher

`scripts/pinboard` resolves runtime state only below its own plugin-version or source root. Ordinary arguments select the CLI. Exact startup selectors choose independently installed entries: `--mcp`, `--claude-session-start`, `--claude-subagent-start`, `--claude-pre-tool-use`, `--antigravity-session-start` and `--antigravity-pre-tool-use`. Hook selectors reject additional arguments before effects. MCP accepts no additional arguments or the complete capture declaration `--capture-evidence-dir <existing-directory> --safe-to-persist-exactly`; anything else rejects before server startup.

A source checkout prepared by `scripts/prepare-worktree` uses its development `.venv`. Otherwise launch requires the `.pinboard-runtime/.pinboard-ready` marker plus the selected executable, so a runtime prepared before an entry existed must be prepared again before that entry runs. Explicit `scripts/pinboard --prepare-runtime` is the only path that invokes uv: it synchronizes locked production dependencies into `.pinboard-runtime`, verifies every entry executable and writes the ready marker last, and a version-local `.pinboard-runtime/.preparing` lock serializes all callers. An unprepared `--mcp` and the Claude and Antigravity SessionStart hooks reach uv only by re-invoking that path, and MCP starts only after runtime-ready. Missing uv, a held lock or a failed preparation returns one strict launcher result on stderr; a failed preparation names `.pinboard-runtime` as possibly changed. Protocol stdout stays clean: MCP writes nothing there, and Claude SubagentStart and PreToolUse recovery emit no decision, so Claude's normal flow decides. Claude SessionStart recovery is the exception because its stdout is the agent's context channel: it prepares in a child launcher and, on success, runs the parent entry with `PINBOARD_RUNTIME_PREPARED_NOW=1`, otherwise it emits one additional-context record naming the cause and the manual command. Antigravity SessionStart recovery emits the same facts as one system message with a new-session reconnect route. Antigravity PreToolUse recovery still answers on stdout, because Antigravity blocks any call whose hook fails: it gives the close decision recorded under [Known limitations](#known-limitations-and-operating-assumptions) and `ask` for everything else. Packaged code, skills and a ready runtime are immutable during ordinary commands; project data stays below the selected work root.

The launcher also owns exact CLI process capture: `scripts/pinboard --capture-evidence <file> --safe-to-persist-exactly -- <arguments>` runs the CLI or prestart path exactly once, forwards `HUP`, `INT` and `TERM`, preserves argv, stdout, stderr and exit status, publishes the capture privately and immutably, and reports a post-target publication failure as changed aftermath that forbids replay. Automatic capture follows the selected work root's contributor setting: the launcher seeds a missing mode before Python runs through the same Git-config lock protocol that `adapters/files/setting_resolution.py` uses, and invalid settings or an unusable destination reject before the target runs. Capture never accepts MCP or hook selectors and records no environment values.

### Domain

`domain` owns immutable identifiers, ledger values, canonical history records and pure decisions. It reads no files, issues no SQL, parses no command-line or JSON input, renders nothing and coordinates no transaction.

| Owner group | Responsibility |
| --- | --- |
| `domain/work_models.py`, `domain/ledger.py`, `domain/identifiers.py`, `domain/errors.py` | Work-ledger values, dependency targets and their satisfaction decision, artifact kinds, the read-only `LedgerSnapshot`, opaque identifiers, `DecisionFailure`, mismatch facts, effect and retry classification |
| `domain/decision_models.py`, `domain/decisions.py` | Closed item and attempt commands, lifecycle-change variants, `ActionSemantics`, and lifecycle, dependency, requirement and review legality |

| `domain/ordering.py`, `domain/consolidation.py`, `domain/initiatives.py` | Saved-order permutation, campaign consolidation graph and initiative legality |

`WorkItemId` identifies a work item and `TaskId` the acting task; public and stored `item_id` spellings are converted at their boundaries. Expected rejections return typed failure values: `DecisionFailure` in domain and stale-persistence paths, with application queries, dispatch and publication keeping their own exact failure families and effect and retry facts. Low-level decoders may raise while values are still external representations, but an installed use case converts its advertised invalid input into its typed result. Adapter exceptions stay at effect boundaries until a receiving use case gives them effect, retry, recovery or diagnostic meaning; persisted invariants and programming defects keep tracebacks.

### MCP

`mcp` owns one local-stdio boundary, not a CLI mirror. `mcp/server.py` is the SDK registration root. `mcp/execution.py` owns admission, cancellation, trace preflight and semantic capture; `mcp/host_profiles.py` connected-host identification; `mcp/common.py` root, store and view glue; `mcp/tool_names.py` the stable wire names; `mcp/contracts.py` the one closed catalog of strict request and result records; and `mcp/contract_schemas.py` the negotiated schemas derived from it. Each `*_operations.py` module owns one transport-to-application verb family: reads, mutations, jobs (dispatch and review), PR review, cancellation, consolidation, initiatives and obligation coverage. `mcp/instructions.py` supplies entry and discovery instructions. CLI and MCP compose the same use cases without importing each other, and full validation and maintenance stay CLI-only.

**Configuration.** Codex and Claude Code read `mcp-codex.json` and `mcp-claude.json`, selected by their manifests; Antigravity reads the fixed root `mcp_config.json` and `hooks.json`, which Codex and Claude Code never discover. All three start the same launcher entry, and `scripts/validate-metadata.py` checks every declaration, including the 65536-byte `tool_input_schema_max_bytes` budget that Codex needs for complete schemas. Package negotiation tests establish configured process startup, not native-plugin ingestion or model usability; reconnecting is needed only when a connection stays unavailable after preparation.

**Hooks.** `hooks/claude-hooks.json` registers Claude's three entries; Codex loads no Pinboard hook. Each entry decodes its typed projection of the host event, validates required fields and identity, and ignores unrelated additive fields; it never forwards cwd, transcript paths or ignored extensions. SessionStart samples `socket.gethostname()` and emits the parent's session identity and machine name as attribution, adding a check-tools hint after just-in-time preparation; SubagentStart emits only the worker's `agent_id`. Malformed input emits no attribution and only a payload-free diagnostic, and a failed machine source supplies no fallback host. Claude's PreToolUse entry exists because plugins cannot ship permission rules: it matches only `mcp__plugin_pinboard_pinboard__.*` and emits only `allow`, while Claude Code still applies every saved deny and ask rule, so the hook reads no settings and never emits another decision. The user allow rule `mcp__plugin_pinboard_pinboard__*` remains the fallback when the hook is unavailable, and users who prefer prompts save an ask rule or disable hooks. Antigravity routes every server's MCP call through one `call_mcp_tool` hook that cannot abstain, so its entry answers each well-formed call: the close decision recorded under limitations, `allow` for Pinboard's other tools and `ask` for other servers. Its SessionStart fires for the parent and each `invoke_subagent` child and injects that conversation's own `conversationId` as `task_id` with the machine name. Hook context is attribution, not authentication or mutation authority; a launched worker pairs its own runtime identity with its verified dispatch host. Parent attribution refreshes on each host SessionStart delivery; emission alone does not prove ingestion or adherence. Reopen this outer integration when a supported event fails to deliver current session or machine context or an ordinary run still misattributes it, without changing application identity or permission policy to mask it.

**Contracts and schemas.** `mcp/contracts.py` stays one closed catalog although its size triggers cohesion review: every tool shares its result records and schema generation consumes the whole family, so splitting it would add re-exports and a second assembly graph without separating a product effect. `mcp/contract_schemas.py` derives schemas, adds correlations JSON Schema cannot infer, and validates every emitted result against its advertised alternative. `mcp/server.py` applies one JavaScript- and RE2-compatible projection to every advertised pattern, which clients such as Codex and Antigravity need; canonical `msgspec` decoding stays independent of it. Most tools take one strict `request` object whose leaf selects role, operation or transition; the remaining tools, including `pinboard_close`, take ordinary arguments, and flat inputs have no fallback. The advertised transition schema and `decode_transition_request` share one membership owner, the `TransitionRequest` union. Close is its own tool with its own `CloseRequest`; `pinboard_transition` refuses a close receipt unchanged and names `pinboard_close`. Action discovery derives payload applicability from `action_payload_schema` in `application/action_models.py` and adds a typed `invocation` starter; starters grant no authority and leave freshness, human decisions and effect validation unchanged. The stable action field `effect` classifies only lifecycle transition input, which domain code names `LifecycleEffect`; dispatch, for example, may publish evidence while its lifecycle effect is unchanged. `dispatch_request_schema` inlines the dispatch request so the complete input fits Codex's schema limits; that budget is finite, so a native client-version change or schema growth reopens this compatibility check.

**Execution and capture.** Every call carries explicit project and work roots and opens invocation-local connections. Synchronous work runs in a process-lifetime executor with two workers and at most four unfinished operations; saturation rejects before preflight. One admitted slot covers optional trace preflight, the callback, strict result validation and trace publication. Cancellation removes queued work before effects and reaches a running callback at safe checkpoints; once source restoration, immutable publication or a SQLite mutation enters its effect section, the executor waits for terminal classification and never reports ambiguous cancellation, and cancellation or transport loss never rolls back committed work. Partial publication names exactly its durable surfaces and forbids replay; a generated-view failure is a committed warning with explicit rebuild recovery. Without a startup capture declaration, each capture-enabled call rereads the selected work root's trace setting and item override; enabled capture is fail-closed and a recognized settings or destination failure returns `TRACE_PREFLIGHT_FAILED` with `target_ran: false` and its settings effects reported separately. Settings and capture recovery are owned by `mcp/execution.py` and `adapters/files/setting_resolution.py`. The registrations listed in the contributor-capture limitation row bypass capture. Bounded metadata-only stderr diagnostics never share protocol stdout. When a call opens the ledger, the connection owner verifies the exact schema first; a mismatch returns a strict schema rejection with an unchanged ledger, and a supported predecessor names the CLI preview command, while neither path migrates.

**Presentation.** One `mcp/server.py` middleware compacts the SDK's JSON text companion only when it is provably equivalent to the structured content; another drops that companion from `pinboard_startup_text` for hosts whose profile is structured-only. Both use the locked SDK's public middleware seam, so an SDK upgrade requires native-client verification again. Overview registration emits `anthropic/alwaysLoad`, and `pinboard_close` registration emits `anthropic/requiresUserInteraction: true`; both are outer hints whose adoption needs separate observation. A headless Claude Code 2.1.285 run with an allow rule and the hook's `allow` still received `MCPTool requires permission.` for `pinboard_close`, and the board stayed unchanged. The close-confirmation consequences per host are recorded under [Known limitations](#known-limitations-and-operating-assumptions).

**Startup text and fixture review.** Startup documents are read natively and never through `pinboard_startup_text`, which serves only oversized evidence: it returns verified character pages of an accepted artifact or selected file with exact continuations. Its page budget comes from the connected host's profile in `mcp/host_profiles.py` and the user-owned `~/.config/pinboard/hosts.config`, seeded on first use through `adapters/files/host_settings.py`; the measured defaults and their assumptions are the limitation rows on page sizes. An unrecognized or missing client identity gets the unmeasured 8000-byte profile, which has no setting, and an unusable stored setting returns `HOST_PAGE_SETTING_UNAVAILABLE` naming the file and key without substituting another size. SDK reconstruction establishes exact bytes and envelope sizes, but supported native Codex delivery also needs version-bound observation that evidence text, continuations and diagnostics reach the model intact, and that evidence is still unresolved. EOF establishes delivery only. `pinboard_fixture_review` verifies two caller-selected files and pages a deterministic changed-field view from `application/fixture_review.py`; the view is non-authoritative presentation, and its record budget is not a host delivery ceiling.

**Verified inputs and launch recipes.** Verified-file leaves accept a selected path and raw SHA-256, read that file once through `read_verified_input` and enter the unchanged inline owner; they add no authentication, streaming or memory cap. Dispatch and review jobs return immutable prompt provenance and a strict per-runtime `native_launch` recipe naming the exact host tool and arguments: Codex `spawn_agent`, Claude `Agent` with `description` and `prompt` only, or Antigravity `invoke_subagent` with `TypeName: "self"`, `Role` and `Prompt`. No recipe requests a second worktree or workspace, because that would be a different source root. Prompt artifacts carry the exact accepted brief bytes and, for reviewers, mark candidate evidence as claims to verify. The caller adds no startup guidance. Pinboard creates no native task, and launch, acquisition, submission and release remain separate observable effects.

## Storage boundaries

### Authoritative SQLite state

`.pinboard/state.sqlite3` owns the project revision and host epoch; immutable definition revisions; item, attempt, dependency, requirement and proposal state; planned-replacement relations and temporary-retention dispositions; preparation and attempt authority; accepted artifact references with nonexclusive ownership; latest decision-batch references; initiative facts; and transition history. `adapters/sqlite/schema.sql` owns the exact `sqlite-v11` schema and its indexes. Relational dependency rows mirror each item's latest definition, and the normalized checkpoint-acceptance relation is written in the same transaction as its receipt by `append_history` in `adapters/sqlite/state.py`. Live items require genuine current definitions; terminal historical definitions contribute dependency facts without becoming current anchors, so terminal edges stay in cycle detection.

Mutable action receipts carry the selected subject's revision, and leased receipts also carry lease identity and generation; the project revision identifies committed state, not action freshness. An ordinary mutation opens one write transaction, reads its selected subject and direct relationships, allocates one revision and receipt, updates only the relations its closed mutation names, validates the changed facts and returns the receipt with affected identities. Stale, fencing and affected-row guards return typed rejections, and every failure rolls back without assembling complete state. A read-only database failure keeps its exact path at the connection owner; the outer boundary adds the operation and narrow permission recovery and reports the unchanged ledger as `do-not-retry` while keeping any earlier artifact publication as its own committed surface. Initialization creates the empty current schema directly; complete state enters storage code only through validation.

A human-owned PR review item lives in the same relations: state `review` without an attempt, with its brief, brief review, observed heads, rounds and human-directed close as append-only history inputs. An implementation attempt cannot use that route, and a review-only item cannot enter candidate review.

### Immutable artifacts

Accepted requirements, briefs, results, reviews, snapshots, packages, prompts and certificates are immutable project data below `.pinboard/artifacts/`, separate from the immutable code and skills in the installed plugin cache. Readers resolve them only through accepted references and verify their bytes; the files own no lifecycle state. Publication through `adapters/files/artifacts.py` reports whether this invocation created or reused each file, so concurrent callers attribute only their own effect, and a failure after linking returns a typed partial-publication failure carrying the published selector. `application/artifact_identity.py` derives bounded keys from canonical checkpoint and completion addresses, so long and ambiguous identities keep distinct addresses.

Review submission publishes one strict candidate snapshot binding attempt, item, candidate, branch, preimage, accepted base, time and exact binary diff before the review transition accepts its reference. Attempt inspection, review jobs, checkpoint acceptance, restoration and completion all read those same accepted bytes. `working_tree_identity` and `candidate_diffs_match` in `application/candidate_identity.py` own identity and currentness: only compatible object-ID prefixes in Git index headers may differ, so retained snapshots with abbreviated index IDs stay comparable without rewriting, while a binding kept only as a digest cannot be reidentified without its original patch. Candidate patch reads disable external diff, text conversion and color so configured presentation cannot change accepted bytes.

Terminal history certificates (`application/history_archives.py`) preserve retired evidence with its original authority and never authorize execution; validation and export verify every certificate against independently selected original references, bytes, receipts and definitions, and current validators still run inside archived closures. Each retained historical format and its removal condition is a row under [Known limitations](#known-limitations-and-operating-assumptions).

### Generated views

`.pinboard/views/` is human-readable output derived from SQLite and accepted artifacts, owned by `adapters/files/views.py` and `adapters/files/roadmap.py`. Declared selectors are item, attempt and immutable per-receipt history views, the live board `board.md` and offline `board.html`, and `roadmap.md` and `roadmap.html`. No runtime path reads generated Markdown for semantics, a successful commit is authoritative before refresh begins, and a refresh failure returns a committed view warning without undoing it. Equal bytes leave files untouched.

After a commit the outer boundary refreshes only the item, attempt and history selectors named by `CommittedEffect`, reading only their projection facts and any live brief they render, then regenerates both board projections and the roadmap. The **composed board read** has three steps: one SQLite read transaction returns the live items in saved order with their dependency targets and change times and, for open attempts and live items only, current brief references, the receipt at each subject revision, checkpoint acceptances, review-state snapshot references and every definition revision; outside any transaction the composition then reads, decodes and identity-checks each current brief and reads review-state `result.md` and `review.md` digests; one short transaction finally reads one keyed candidate-review reference per review-state attempt, verified with the shared ready-record decision in `adapters/review_operations.py`. It excludes terminal items, unrelated receipts, past briefs, preparation authority and other artifacts, and never runs the review-verdict walk. An exclusive `fcntl.flock` on `views/board.lock` spans the read and both replacements so overlapping refreshes leave the board on the later commit, with no SQLite transaction open during rendering. The roadmap refresh holds its own aggregate lock from snapshot to publication and reads complete initiative history with the relevant members. Board output renders no operation-time, timezone or locale value, so one snapshot yields the same bytes in any process, and validation derives the same bytes from its loaded snapshot. `pinboard views rebuild` reconciles every declared selector, and validation distinguishes authoritative defects from stale generated output.

A consumed pause or paused-rebind receipt whose outcome no longer decodes leaves its item view unwritten and is named: a post-commit refresh returns a warning, rebuild fails naming it, and validation reports `TRANSITION_RECEIPT_DAMAGED`. On the board, an undecodable latest receipt or an unreadable current brief affects only its own card.

### Codex project-write boundary

Pinboard writes project data only below the selected work root, and fresh default initialization is the only routine path that also writes Git metadata. The Codex permission profiles and the one narrow initialization approval are recorded in the limitation row on Codex protected project writes. The exclusion append locks the shared exclude file and rechecks it, so concurrent initialization from the primary checkout and a linked worktree adds exactly one line and only the appending invocation reports it; it never edits `.gitignore`.

Human-requested Git effects use the outer Codex runtime's exact-command approval route (`approval_policy = "on-request"`, with `approvals_reviewer` set to `"user"` or `"auto_review"`), separate from Pinboard commands and without persistent `.git` write access. Human authority, runtime approval and observed effect stay independent: the outer agent observes the changed commits, refs, worktrees or pushed destination before claiming success, and an unavailable approval or reviewer rejection stops the action unless a materially safer authorized alternative exists. Pinboard supplies no Git broker, approval policy or lifecycle authority for these effects.

### Project evidence boundary

Pinboard requires no companion notes directory. Investigation Focus may guide a caller-owned note in a selected home, which is neither ledger state nor a validated evidence graph. Manual capture stays private at its selected destination, and automatic contributor traces live in the selected work root's `invocation-traces/`. Placement inside a work root grants nothing: durable execution semantics enter Pinboard only through accepted artifact references created by an authorized operation.

## Representative flows

Each trace names the owners that perform its steps in order. State-changing flows share one grammar: decode an exact request, observe selected context, reread locked state, decide legality, commit one closed mutation, refresh replaceable views, present the result.

### Lifecycle transition

A structured pause is the representative state-changing path. `mcp/mutation_operations.py` decodes the exact project or own-leased worker pause leaf of `TransitionRequest`, validating the complete decision batch, before resolving roots or reading state. `adapters/lifecycle_operations.py` (`select_transition`) observes the named attempt's exact decision context and `adapters/transition_input.py` converts the validated payload into one domain command. Through `commit_direct_transition`, `application/service.py` (`decide_and_commit_transition`) rereads the scoped facts inside one write transaction, reselects current legality and authority with a freshly sampled clock, and rejects a relevant change as stale while ignoring unrelated commits. `domain/decisions.py` decides the pause; `application/mutations.py` projects its canonical questions into the receipt; `adapters/sqlite/persistence.py` allocates one project revision, applies the closed mutation and writes the receipt and the latest-batch reference together, returning `CommittedEffect`. After commit the boundary refreshes the affected item, attempt and history views and the board, then returns the receipt, effects and a fresh `pinboard-item-status` observation through `queries.project_item_status`. Resume follows the same path and must supply exactly one human answer or deferral with a reopening condition for each pending decision; a scope-changing answer first needs definition and brief replacement and a paused rebind, which resolves no decision.

Status, continuation, item views and the board read the latest structured decision batch through its stored reference, independently of the latest receipt: later plain pauses, rebinds and transitions keep that reference, a new structured pause replaces it, and full validation recomputes it from retained receipts. A pause reason lives in its own receipt, and a paused rebind copies it forward, so the latest receipt always carries the current reason; checkpoint acceptance pauses with checkpoint evidence instead. A view warning or failed status read after commit returns a committed result with repair or read-only recovery, and the caller must not replay the mutation.

### Proposal intake, revision and dependencies

`pinboard_proposal_create` decodes into the shared record in `application/proposals.py`, and `application/service.py` (`create_proposal`) commits the proposal, the same-identity ready item with definition revision 1, its queue position and any relation target in one transaction; prerequisite creation also revises the live related item's definition and dependency rows, and a planned replacement commits its next relation revision with the proposal. Creation makes an item eligible for preparation and creates no attempt. Repeating a proposal is an unchanged duplicate rejection.

Every item's highest contiguous definition revision is its sole current accepted definition. `revise-item` appends a complete revision after checking expected revision and digest, rejects removing declared checkpoints and missing or cyclic dependencies, replaces dependency rows in the same transaction and leaves lifecycle untouched. Attempts keep the definition identity from their accepted brief, so a revision makes them stale until they rebind to a matching brief. A dependency is either a bare item, satisfied by `done` or `superseded`, or an `{item, checkpoint}` target, also satisfied by a matching committed checkpoint acceptance on any attempt of that producer, which stays valid after brief changes, rebind or cancellation. `adapters/dependency_operations.py` and `application/dependency_authoring.py` verify a checkpoint target against the producer's declared checkpoints or its current accepted brief and recheck that pin under the write lock. Cycle detection follows producer identities for both forms.

An unresolved current planned replacement is a decision fact, not a state. It withholds dispatch, review submission, checkpoint and review acceptance, continuation and completion while leaving rebind, pause, block, blocker reporting, return for correction and the `record-replacement` and `retain-temporarily` decisions available, and paused or blocked attempts expose close. Withdrawal or a temporary-retention disposition restores the otherwise legal actions.

### Preparation and activation

Native preparation `start` samples its time, then `application/service.py` (`start_preparation`) opens one write transaction and selects initial acquisition or transfer of an inactive claim pinned to the item's current definition; a live conflicting claim, an unresolved replacement or a non-ready item rejects unchanged. While the preparer compiles and reviews the brief, the item stays `ready` and the live claim suppresses conflicting ready-item mutations. After brief publication, the preparer's `activate` transition carries only the accepted brief reference: `adapters/lifecycle_operations.py` (`resolve_activation`) decodes the brief, requires it to match the current definition and the source checkout's classification (primary checkout as `main`, a registered linked worktree of the same repository as `isolated`, anything else rejected), requires the preparer's live authority, compares the checkout's observed branch and HEAD with the brief and checks every reviewed authority. The locked activation decision then revalidates definition and preparation pin, consumes the claim, creates the attempt and moves the item to `active` atomically; any earlier failure leaves the item ready with its claim live. Expiry, release or revocation of a claim reopens the ready-item operations. For both authority families, `application/authority_operations.py` gives renewal, release and revocation separate use cases: renewal and release require the exact current lease and generation, revocation records project task and host attribution, and each committed reply carries the authority reread under the same write lock.

A new isolated worktree is prepared once with `scripts/prepare-worktree`, which runs the locked uv and npm installs into checkout-local `.venv` and `node_modules`. The runtime adapter owns [source-worktree setup recovery](skills/pinboard/references/runtime-adapters.md#source-worktree-setup-recovery), including the one runtime-reviewed retry after a diagnosed permission restriction.

### Brief construction and source preparation

`pinboard_brief_contract` returns the construction contract or a starter from `application/work_brief_contract.py`. A brief uses the local checkpoint shape only when the change keeps one owner and changes no behavior, dependency direction, stored or wire identity or independent consumer; otherwise it uses the cross-boundary shape. The agent completes the facts, plans sources with read-only `pinboard_brief_sources`, which resolves whole-file or heading selectors in the selected checkout and returns a reusable plan with selected digests, then emits verified batches that reread exactly the selected bytes. Plans and batches are capped at 16,000 bytes of complete JSON, and a separate `pinboard_brief_source_plan_output` tool publishes a plan to one explicit immutable destination. On Antigravity the reading step uses native `read_file` instead, as recorded in its limitation row. `pinboard_brief_publish` decodes the record before resource work, `application/work_briefs.py` (`publish_work_brief`) validates it against the exact current definition, including its declared checkpoints and the exactly-once mapping of every accepted obligation, and publishes canonical bytes, SQLite accepts the reference, and one refresh follows. If acceptance fails after publication, the result reports the committed selector and forbids blind replay; identical republication is unchanged reuse, and `pinboard_brief_lookup` recovers a lost receipt by its original identity. A negative brief review is a separate artifact keyed to the exact brief, checkpoint and authority-set digests; it never authorizes dispatch, and a corrected brief starts without review status.

### Dispatch and native launch

The outcome owner selects project-only dispatch for the stable checkpoint. `mcp/job_operations.py` decodes the `pinboard-dispatch` environment, which binds runtime, background disposition, checkout, branch, starting revision, host, required fresh context, lease interval and declared permissions, then discovers the exact dispatch action at the supplied receipt revision. `adapters/dispatch_operations.py` (`prepare_dispatch`) first calls `application/dispatch.py` (`select_dispatch`), which confirms that action is still the current dispatch action and selects its active attempt and accepted brief reference. `prepare_dispatch` then decodes the accepted brief and checks its attempt, item, accepted scope, branch, base revision, checkout and checkpoint against the attempt and environment, plus, for cross-boundary work, reviewed-authority digests read from the accepted base commit; a base mismatch rejects unchanged with all three observed revisions. `validate_executable_work_brief` in `application/work_briefs.py` requires the exact current accepted definition and the actual checkout classification recorded by the brief, and the review choice then requires, for standard and campaign cross-boundary work, the independent ready brief review. Dispatch publishes or reuses the immutable worker prompt with the exact brief bytes; after publication `recheck_dispatch_authority` rediscovers the dispatch action, and a mismatch keeps the committed surfaces and forbids replay. Success returns the prompt reference and native launch recipe. The runtime launches a fresh worker that verifies and reads the prompt, reads its one worker document, takes its own runtime identity (Codex `CODEX_THREAD_ID`, the Claude hook's `agent_id`, or the Antigravity child's `conversationId`) and acquires attempt authority through `application/authority_operations.py`. Lost responses recover through a fresh dispatch after inspecting native activity; byte-identical evidence is reused unchanged.

### Review submission and candidate review

The worker observes its candidate with `pinboard_candidate_observe`, which reports tracked identity and omitted untracked paths without changing anything, and submits through its own leased `submit-review` action, optionally declaring exact untracked paths it omits. `adapters/lifecycle_artifacts.py` compares the supplied identity with the actual HEAD and diff, rejecting a mismatch unchanged with the current identity, then publishes the candidate snapshot, and `application/service.py` (`decide_and_commit_review_submission`) accepts its reference with the review transition and protects the candidate. `pinboard_review_job` (`adapters/review_operations.py`, `prepare_review_job`) resolves the exact attempt, protected candidate, brief, current `result.md` and any caller-selected package or return in one focused read, refuses when a valid ready record already exists, and publishes a reviewer prompt keyed to attempt, candidate, snapshot, brief, result and prompt digests. The fresh reviewer verifies its prompt and treats evidence as claims; if no reviewer can be launched, the candidate stays in review as a resumable boundary. Its favorable verdict becomes durable only through the non-launching `record-ready` leaf (`record_ready_candidate_review`), which rereads the current evidence, rejects a reviewer equal to the owner or a prompt that `pinboard_review_job` never published, and publishes a candidate review carrying that prompt digest. Retained candidate reviews from before the commission link cannot be reconstructed and are never read as ready, so an attempt holding only one needs a new commissioned review. Item status reports `ready` only while the record matches current candidate, brief, result and review; a later change returns it to `none`. Inspection with a valid record returns `reconcile-repository`, and the outer coordinator's reconciliation observations select the resumed continuation under the phase rules owned by `AttemptReconciliation`. When a PR was published before local review, the owner still has the local candidate submitted and reviewed; GitHub state never implies protection.

### Correction and replacement readiness

`return-for-correction` records the canonical reason in its receipt, keeps the candidate there, clears protection and fences the worker. `pinboard_correction_context` checks the current return and accepted brief, refreshes reviewed source digests (verifying a tracked removal against the accepted base), verifies the starting snapshot and reports whether accepted coverage can be reused. Correction dispatch in `adapters/dispatch_operations.py` runs the ordinary dispatch selection and brief checks, then requires the return to be the attempt's latest review event with no later rebind, refreshes the reviewed sources, requires a concrete independent assessment bound to the returned or currently assessed candidate and verifies the starting snapshot; it repeats the return, snapshot and source checks after publishing the assessment and again after the prompt and authority recheck. After a rebind, `pinboard_return_context` reads the historical return and its exact submission snapshot as provenance, and the `replacement-readiness` dispatch leaf (`prepare_replacement_readiness`) publishes a proof binding that history to the assessed current candidate before a newly commissioned review. The returned-candidate lookup cost is a recorded limitation.

### Checkpoint acceptance

After current-action selection and decoding, `accept-checkpoint` in `adapters/lifecycle_artifacts.py` reads the attempt's current brief and requires its named continue checkpoint and, for cross-boundary work, the exact ready brief review. `application/service.py` (`preflight_checkpoint_candidate`) then makes one fresh exact-scope observation and revalidates the action before comparing candidates, so stale actions exit before a candidate mismatch. A mismatched protected candidate, checkpoint or diff exits before reading `result.md` or `review.md` or publishing. The adapter then publishes candidate evidence, result, implementation review and the current checkpoint package in that order, reporting only the selectors it created if a later step fails. `application/service.py` (`decide_and_commit_checkpoint_acceptance`) rereads under the write lock, reapplies legality, accepts all four references, appends the acceptance receipt with its normalized producer/checkpoint fact, pauses item and attempt and fences authority atomically. `pinboard_candidate_restore` can later apply the current accepted snapshot, never an archived candidate, into a caller-selected clean checkout with the recorded branch and preimage through `adapters/candidate_evidence.py`, changing no ledger state. Review acceptance with remaining work instead returns the attempt to active, records the accepted candidate in its receipt and fences the worker. The current checkpoint shown by the board and item status comes from one projection of the identity-checked current brief.

### Terminal completion

Completion is selected only by a terminal checkpoint disposition. Broad action discovery never offers it; focused discovery reads only the named attempt and its accepted brief, and a continuing checkpoint or missing candidate refuses with one read-only inspection. The reviewed-completion input requires the human's exact decision words, the protected candidate, result and review digests, an independent reviewer and one row per prior checkpoint receipt. `adapters/lifecycle_artifacts.py` verifies every checkpoint package closure, requires a commissioned ready candidate review for that exact subject and reviewer (otherwise `CANDIDATE_REVIEW_REQUIRED`, unchanged), has `application/service.py` (`preflight_covered_completion`) reject stale authority or wrong lifecycle before publication and, when `landed` names a local target, checks the reviewed diff there with the same Git content observer as item integration. It publishes result, final review and completion package; `application/service.py` (`decide_and_commit_covered_completion`) rechecks brief identity and terminal disposition under the lock, accepts the references, closes item and attempt and fences authority. A landed completion returns the attempt branch and its remove-or-retain disposition, and the owning chat performs any worktree and branch cleanup with its own Git permissions; a Git refusal leaves the terminal receipt committed and the chat open. Pinboard writes no Git state for completion.

### Close, cancellation and consolidation

`pinboard_close` decodes its own `CloseRequest`, which requires `human_decision`, and shares lifecycle selection, execution and result presentation with transitions; the CLI `close` records `--reason` as that decision. Close records `done` for eligible work without an accepted attempt; an unresolved planned replacement requires `superseded` instead, which needs an existing non-dropped target and no live dependents still waiting on the absorbed item, and commits a paused or blocked attempt to `done` with its authority fenced; inspection, branch-owner status and views then report that attempt as superseded, and the close claims no successful completion. `dropped` is not a close outcome: `pinboard_cancel` previews the item, attempt, authority and direct relations through `application/cancellation.py` with a digest binding, and confirmation rereads that selection under the write lock, commits one cancellation receipt with the human's exact words, drops the item, terminalizes its retained attempt and fences both authority families while keeping all evidence, repository files and branches; item status, continuation, branch-owner output and views name the cancellation. Whole-item dependents of a dropped item stay unsatisfied, while matching accepted checkpoints stay satisfied. `pinboard_consolidate` previews and confirms, through `application/consolidation.py`, one campaign that absorbs selected sources: `domain/consolidation.py` builds the campaign definition, carries every source obligation with its exact origin, turns internal prerequisites into campaign work and merges external ones, and one `ConsolidationMutation` commits creation or revision, consumer revisions, replacements and superseded source endings with one receipt. Active and review sources refuse. None of these routes grants worker launch, Git or completion authority.

### Reads and validation

Every installed operation belongs to one data-scope class, published for CLI leaves by `cli/tool_contract.py`:

| Scope class | Operations | Data boundary |
| --- | --- | --- |
| State-independent | CLI `root`, `tool-contract`, `code-catalog`; brief construction, source preparation, observer actions | No SQLite state; source tools read only selected checkout files or one saved plan |
| Exact ordinary | CLI `close`; item status item and integration leaves, definitions, attempt inspection, review jobs, verification, restoration, authority, exact or leased actions, selected preview, publication, intake, dispatch, transitions | Selected subjects, direct relationships, cycle-sensitive definitions only where required, exact accepted references and changed rows |
| Retained-attempt scan | Item-status branch leaf | Every retained attempt's identity, branch and state; see its limitation row |
| Bounded discovery | Overview | At most the requested compact live rows plus scalar context, within a complete serialized envelope of 8000 bytes |
| Current project | CLI `status`; broad project actions; all-safe parallel preview | Live portfolio facts only; see the live-portfolio limitation row |
| Explicit project-wide | `init` or reopen, `validate`, `diagnose`, `views rebuild`, `export` | The records their whole-project result needs |

An invocation that reads the ledger may also seed the trace setting and publish a private trace; those auxiliary effects grant no ledger authority. After a commit, the post-commit refresh adds the composed board read outside the decision scope.

The item-status item leaf is the representative focused read. `mcp/read_operations.py` decodes the `item` leaf and calls `application/queries.py` (`project_item_status`). It first reads, through `adapters/sqlite/store.py`, the item's keyed fields, current definition, at most its one nonterminal attempt and preparation identity, plus the pause receipt at the attempt's subject revision when paused. It then validates that active, paused and review items have one matching current attempt and returns `ITEM_STATUS_INCONSISTENT` with only `pinboard validate` as recovery otherwise; status never repairs state. Only then does `adapters/review_operations.py` read and identity-check the current brief once for both the current checkpoint and the review verdict, adding the bounded verdict walk and, for a review-state attempt, the keyed ready record. A damaged consumed receipt returns `TRANSITION_RECEIPT_DAMAGED` with diagnosis-only recovery. The integration leaf adds one verified snapshot read and the Git content read recorded as a limitation; it never runs the verdict walk. Overview (`read_overview_page`) selects queue keys by index before projecting compact rows, shortens title prefixes until the dual-representation envelope measured by `host_profiles.envelope_size` fits, and never silently skips an oversized row. Parallel preview supplies structural facts only, never readiness or launch permission. None of these reads changes SQLite, artifacts or views.

Every routine database open verifies fixed-size metadata, schema version and schema signature without scanning rows. `pinboard validate` (`cli/work_state_commands.py`, `validate_state`) additionally runs SQLite `quick_check` and `foreign_key_check` while loading complete stored state once, then `cli/work_state.py` (`validate_loaded_work_state`) validates it and verifies every accepted artifact reference, live brief, checkpoint package, completion closure and history certificate, and reports generated-view drift separately; it never repairs. `pinboard diagnose --json` runs that same validation, then projects unfinished work and at most the ten newest receipts, and reports roots, runtime, trace configuration, versions and diagnostics without writing anything. `pinboard export --json` reads exported relations in one transaction, verifies each referenced artifact, applies the package provenance validator and writes canonical portable JSON only after the full result is materialized.

### Initialization and reopen

`pinboard init` (`cli/work_state.py`, `initialize_work_state`) resolves the default `.pinboard` below the shared repository root, so initialization from a linked worktree reuses the repository ledger. It adds only `/.pinboard/` to the shared `.git/info/exclude` before creating the work root or SQLite, runs integrity checks on a staging database and publishes it, then ensures artifact directories and rebuilds views. A typed effect wrapper reports exactly the surfaces committed before any later failure: the exclusion alone before database publication, or the exclusion and ledger after it. A repeat that changes neither is unchanged. When the database exists, reopening verifies its exact schema, removes a same-file staging alias left after publication and rejects a different-file conflict. Only after a fresh successful initialization does the CLI print one optional repository-care pointer and, for the Codex runtime, a recommendation read from the user's Codex config; neither writes configuration.

### Human-owned PR review

For a ready item whose change already lives in a human-owned PR, `mcp/pr_review_operations.py` and `application/pr_reviews.py` record a brief bound to the current definition, the PR, requirement sources, expected behavior, consumers, owners and criteria, then a different reviewer's ready verdict. Each round cites one full commit observed by the coding harness, the reviewed brief, findings and dispositions of every prior finding; `adapters/sqlite/pr_review.py` compares the item's subject revision and appends the evidence in one transaction. A newer observed head is reported as unreviewed until another round or a human-directed close at the prior head; closing records final dispositions and residual concerns, and a zero-round close says no head was reviewed. The route creates no attempt, lease, candidate or Git effect.

### Initiative membership

`mcp/initiative_operations.py` decodes a `member-add` leaf with its expected subject revision and dated human reason. `application/initiatives.py` reads the initiative, item and active membership under the write lock, `domain/initiatives.py` rejects absent, duplicate or stale facts, and `adapters/sqlite/initiatives.py` records the episode and advances the initiative and project revisions atomically. The refresh then derives the global roadmap through `application/roadmap.py`, where only `done` members earn delivery credit and satisfied edges are removed before dropped prerequisites block descendants, and replaces the offline projections. `member-remove` ends only that episode, and re-adding creates another. Changing an initiative's goal or success signal creates a new evaluation context, and assessments keep the exact context they evaluated. Human attribution and supplied dates stay separate from task and host attribution and commit time, and item status, dependencies and lifecycle authority stay with their own owners.

### Obligation origins and coverage

An obligation may carry one exact origin: source item, retained definition revision and obligation ID. `application/service.py` reads only the named source revisions under the write lock, and `validate_origins` in `application/obligation_coverage.py` rejects unresolved origins before commit; origins live inside canonical definition JSON with no separate rows. `pinboard_obligation_coverage` selects the latest definitions of a named pair or the current planned replacement through `adapters/sqlite/obligation_coverage.py` and lists every source obligation with its exact carriers or `uncovered`; a retained older origin is provenance but does not cover revised scope. Close detail and cancellation preview call the same owner; coverage adds no veto to a legal human ending, and cancellation confirmation rejects when the bound coverage changed.

## Keeping this map current

This document describes implemented ownership, dependency direction, storage and format owners, current limitations and representative flows. Every implementation checkpoint declares its architecture impact before dispatch: `none` records why no architecture change occurs, `read-only` names the authority it must conform to, and a checkpoint that changes an owner or dependency direction is `update-required`, names this file and includes the coherent correction in the same candidate. Typed brief validation enforces the declaration shape, while brief and implementation review verify that it is true for the sources and final diff.

Make each correction by replacing the statement at its owning section, not by adding sentences beside it. Each fact has one home: a limitation lives in its row or in the list of further operating assumptions, a mechanism in its owner's section and a flow in its trace, and other sections point there. Record field names, schema identifiers, result codes and version lists in the owning code and point to it from here. A genuinely new owner or flow gets its own entry. A limitation accepted by the human under [the limitation method](DESIGN_PRINCIPLES.md#make-architectural-limitations-explicit) is recorded here as current truth, with its consequence and reopening condition, in the same candidate that implements or preserves it.

Future behavior belongs here only when its implementation is present. Delivery history, speculative modules and deferred redesigns stay in private planning evidence until they change the current architecture.
