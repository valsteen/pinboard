# Architecture

## System overview

Pinboard is a local coordination system for one repository-owned work ledger. The installed `pinboard` command discovers the project, opens its work root, reads and validates current state, computes legal actions, and applies accepted changes atomically. Pinboard is an installed application and plugin, not a supported Python library: its production interface is the `pinboard` CLI, with `python -m pinboard` as an alias to that same interface; internal modules and package exports are not public extension APIs.

Codex is the primary, stress-tested outer integration. Claude Code can load the same repository root experimentally through `.claude-plugin/plugin.json` and `--plugin-dir`; both integrations call the same launcher, Python entry point, skills, schemas, and SQLite authority. Runtime-specific identity, worktree, subagent, permission, waiting, and optional-messaging operations stay in the agent-facing runtime adapter rather than entering the Python dependency graph or creating another lifecycle.

SQLite is the authority for the repository work ledger. Attempt continuation and review jobs are read-only projections from current authoritative state and verified accepted artifacts; they add no lifecycle state or stored workflow owner.

Each invocation resolves two Git-backed roots with different owners. The source checkout root is the current or explicitly selected checkout's exact top level, including a linked worktree, and owns project-file and authority reads for that attempt. The shared repository root is derived from the Git common directory and owns repository-shared Pinboard state and local Git exclude configuration. In a primary checkout the two roots are equal; in a linked worktree they are intentionally different.

Root resolution produces the source checkout, shared repository, and intended work root without requiring an unused external work-root parent to exist. `DurableRoots` is the single owner that derives the authoritative database path. State-independent commands stop at lightweight selection. For a database-backed command, the outer work-state boundary validates one immutable durable layout, constructs one `SQLiteWorkStore`, and passes the same layout plus storage-independent required capabilities through the complete workflow; thematic handlers neither reconstruct infrastructure nor import the concrete store. This is explicit composition through ordinary required parameters, not global state, an optional fallback, or a dependency-injection framework.

Agent guidance has a separate dependency boundary from the Python runtime graph. Repository guidance routes a task to the installed Pinboard skill before read-only work becomes repository writes and while accepted repository work awaits human disposition; the Pinboard delivery and intake skills remain specialized callers. The main skill owns the shared threshold for user-relevant process detail, verified readable-artifact links on every item or evidence mention, human task-start routing, explicit review-actor language, current-responsibility routing, preparation start, project-specific Git baseline inference and checkout confirmation, bounded checkout-risk assessment, reconciliation of late accepted direction with the current brief and candidate, exact workflow-ending state reporting from item status, and human-authorized repository wrap-up. It also owns the assurance boundary: defects and accepted guarantees remain blocking, while a material new concurrency, durability, security, adversarial, platform, or compatibility guarantee without accepted product evidence becomes one concrete human scope decision before entering implementation or review. That wrap-up composes runtime-owned task occupancy, Git integration, worktree and local and remote branch cleanup, and Pinboard terminal transition without moving Git behavior into the Python dependency graph or adding lifecycle state. Cross-boundary preparation freezes accepted semantics, the supported assurance model, stable authorities, constraints, and explicit uncertainty without predicting the complete implementation file set. Delivery derives concrete impact from the candidate and reads outward when a changed relationship or uncertainty exposes another owner. Separate candidate review begins with changed and unclassified surfaces, reuses unchanged evidence, and widens for architecture, persistence, wire, lifecycle, dynamic-consumer, or demonstrated-blind-spot conditions. Specialized skills apply that shared flow and assurance decision at their concrete evidence points and retain distinctive evidence and blocking outcomes without creating separate narration policy, a hard-coded impact graph, persistent checkout ownership, Git subsystem, or wrap-up state.

The bundled repository-care skills are independent guidance owners. Repository Readiness owns assessment of whether an unfamiliar repository can be changed reliably, including its authority map, coverage modes, developer-navigation method, and storytelling lens. Slop Cleanup owns recursive removal of approved unsupported residue and its deletion fixed point. Maintaining Agent Guidance owns placement and reconciliation of durable AI-facing guidance. They may refer to one another or use Pinboard for coordination, but no sibling or ledger is required for their baseline workflow.

One work root has three durable roles:

```text
.codex/pinboard/
  state.sqlite3   # authoritative lifecycle, dependency, authority, and history state
  artifacts/      # immutable long-form bytes referenced by SQLite
  views/          # repairable Markdown projections generated from SQLite
```

The architecture map is semantic rather than an exhaustive file tree. It names the owners and dependency boundaries a contributor needs to preserve; leaf modules that do not change those relationships need not be listed individually.

## Dependency direction

Pure decisions remain at the center:

```text
interfaces ────────> application ────────> domain
     │                    ▲                  ▲
     └────────────> adapters ───────────────┘
```

`domain` depends only on the Python standard library and `msgspec` for exact canonical records. `application` depends on domain values and storage-independent capability protocols. `adapters` implement those capabilities with SQLite and the filesystem. `interfaces` decode external values, compose concrete adapters with application use cases, and present results. Production dependency tests keep domain independent of outer layers, application independent of adapters and interfaces, and adapters independent of interfaces. They also keep interface composition acyclic and constrain the CLI entry point to routing and final error presentation.

The method used to preserve these boundaries, expose effects, and stop decomposition at a useful fixed point is recorded in [the design principles](DESIGN_PRINCIPLES.md).

### Declarative generated boundaries

The replacement-family pilot has one development-time canonical source at `codegen/replacements/declaration.py`. Its closed projection operations, six ordered invariant roles, exact diagnostics, and field dispositions are compiled by `codegen/replacements/compiler.py` into layer-local ordinary Python: `application/_generated/replacement_projection.py` owns the handover conversion and `adapters/sqlite/_generated/replacement_validation.py` owns persisted cross-record rejection. Production imports those generated owners directly and never imports `codegen`, so the inward dependency direction is unchanged. Ruff and strict Pyrefly check both the compiler and generated Python; CI runs deterministic freshness before those checks.

The mechanical guarantee is bounded. The compiler recursively discovers both tuple members of `ReplacementRecords` and every reachable dataclass leaf, rejects missing projection dispositions, requires the closed ordered invariant roles, and rejects stale generated bytes. The installed handover and SQLite readers prove that their supported paths call the generated owners. `application.queries.project_overview` remains an explicit independent consumer because it answers a different product question. Reflection and deliberate dynamic access remain review concerns, and generation freshness cannot prove that an agent did not read an output file. Stop this pattern rather than adding a class/site allowlist, suppression mechanism, control-flow graph, call graph, interprocedural analysis, or whole-program semantic claim; converting another family is separate work evaluated from this pilot's measured costs.

## Runtime ownership

### Launcher

The plugin `scripts/pinboard` launcher prefers the package already installed in the plugin cache's ready environment. Packaged code and skill assets in that cache are immutable runtime inputs; project-owned SQLite, artifacts, and views live only below the selected work root. When executed from a source checkout without that installed environment, the launcher falls back to the repository's locked uv execution path. This keeps ordinary installed use independent of ambient uv cache selection while preserving one source-development route on macOS and Linux.

### Package root

Only distribution version lookup and command composition live at the package root.

| Location | Ownership |
| --- | --- |
| `pinboard/__init__.py` | Installed distribution version lookup |
| `pinboard/__main__.py` | `python -m pinboard` route to the CLI |

### Domain

`domain` owns immutable identifiers, ledger values, canonical history records, and pure decisions. It does not read files, issue SQL, parse command-line or JSON input, render views, or coordinate transactions.

| Owner group | Responsibility |
| --- | --- |
| `work_models.py`, `ledger.py`, `identifiers.py`, `errors.py` | Work-ledger values and canonical artifact kinds, read-only snapshot behavior, opaque identifiers, expected decision failures, exact mismatch facts, effect disposition, retry classification, and recovery-action receipts |
| `decision_models.py`, `decisions.py` | Closed item and attempt commands, explicit lifecycle-change variants, and lifecycle, dependency, requirement, and review legality, including the shared project-attempt action decision used by global and exact reads |
| `authority_models.py`, `authority_decisions.py` | Closed ready-item preparation and attempt authority operations, lifecycle, and fencing |
| `proposal_models.py`, `proposal_decisions.py` | Closed proposal intake values, intake queue placement, relation-derived dependency decisions, and versioned planned-replacement admission decisions that bind the new proposal item to its affected item and practical replacement cost |
| `history.py`, `definition_decisions.py` | Canonical work-item definition records and digests, immutable revision legality, dependency replacement and cycle decisions, and receipt relationships |

Expected rejections return typed failure values. Domain and stale-persistence paths use `DecisionFailure`; application-owned queries and dispatch selection use their own closed failures where the installed interface must preserve a more specific public error. The interface returns closed command, proposal, and dispatch failures through one CLI presenter. Low-level decoders may raise while values are still external representations, but an installed use case converts its exact advertised invalid-input outcomes into its typed result. Infrastructure failures, malformed persisted relationships, and programming-contract failures remain typed exceptions.

### Application

`application` owns use-case sequencing, persistence contracts, read models, and cross-capability workflows. Ordinary use cases request operation-owned facts through storage-independent protocols and commit only closed accepted mutations. Validation alone receives complete stored state; other project-wide workflows receive their complete declared projection or exported-fact batches.

| Owner group | Responsibility |
| --- | --- |
| `stored_state.py` | Complete typed read aggregate plus storage-specific vocabulary |
| `mutation_models.py`, `mutations.py`, `ports.py` | Closed exact mutation and committed-effect records, exhaustive decision-to-relational conversion, storage-independent transactional and exact-read capabilities, validation-only complete state, project-wide projection facts, and exported-fact batches |

SQLite rows are not active domain objects. `StoredWorkState` is the exact typed read aggregate without SQL handles or filesystem paths, while live mutations carry only the accepted decision, receipt, and affected auxiliary values. `LedgerSnapshot` remains the storage-independent decision input.

## Storage boundaries

### Authoritative SQLite state

`.codex/pinboard/state.sqlite3` owns project revision and host epoch; immutable work-item definition revisions; item, attempt, dependency, requirement, and proposal state; versioned planned-replacement relations and exact-revision temporary-retention dispositions; preparation and attempt authority; accepted artifact references; and transition history. Schema `sqlite-v6` includes a partial item-leading index for exact current-attempt and current-portfolio reads, a dependency-leading `(dependency_id, item_id)` index so a committed effect can discover only the live item views whose eligibility changed, and lease-identity indexes so leased action discovery reaches only current subjects selected by the supplied lease and generation. Every retained attempt or preparation lease must have its exact current generation anchor before application code can consume it. Relational dependency rows are the query-efficient projection of the current definition and must match it exactly. Mutable action receipts carry the selected item's, attempt's, or proposal's subject revision; leased receipts also carry the exact lease identity and generation. The project revision identifies committed state and history, not action freshness. An ordinary mutation opens one write transaction, reads the selected subject and direct decision relationships, allocates one project revision and receipt, updates only the relations named by the accepted closed mutation, validates exact changed facts, and returns the receipt plus affected item and attempt identities. Authority, subject-revision, commit-revision, and affected-row guards return typed stale or fencing rejections. Expected failures and infrastructure failures both roll back without assembling complete state before or after the effect. SQLite read-only failures retain the exact database path at the connection-and-transaction owner; the command boundary adds the exact operation and narrow Codex permission recovery derived from the database's parent work root, classifies the unchanged ledger as non-retryable, and preserves any earlier immutable-artifact publication as a separate committed surface. Initialization creates the exact empty current schema directly; complete state enters ordinary storage code only through validation.

### Immutable artifacts

Accepted requirements, briefs, results, reviews, and other evidence are immutable project data below `.codex/pinboard/artifacts/`; they are distinct from the immutable code and skill assets shipped in the installed plugin cache. Canonical v2 work briefs and independent brief reviews are strict JSON; SQLite stores each accepted artifact's kind, selector, revision, digest, and size. Attempts and history own the relationships they actually consume. The installed brief-publication path validates and canonicalizes a candidate, publishes immutable bytes, and accepts their reference without changing scheduling. The atomic filesystem primitive verifies an existing file against the requested bytes and returns whether this invocation created or reused it; the artifact owner couples that disposition with the verified reference, so concurrent callers attribute only their own committed effect. Pre-link failures remain unchanged I/O failures even when another identical artifact already exists. If directory synchronization fails after linking the destination, a typed partial-publication failure carries the just-published identity; brief and checkpoint presentation report that selector, and checkpoint presentation also retains every artifact published earlier in the same invocation. Activation, resume, and rebind validate their selected v2 brief identity against the locked ledger snapshot. Readers resolve artifacts through accepted references and verify their bytes. The files do not independently own lifecycle state.

### Codex project-write boundary

Fresh default initialization is the only ordinary setup path that also writes Git metadata: before it initializes the work root or SQLite, it idempotently adds the exact repository-local exclusion `/.codex/pinboard/` to the shared repository's `.git/info/exclude`. A read-only presence check lets returning initialization proceed without Git write authority. When the line is absent, the write path locks the shared file, rechecks it, and appends, so concurrent primary-checkout and linked-worktree initialization still adds exactly one line and only the appending invocation reports that surface. It never edits `.gitignore`, and it does not hide sibling `.codex` content. If a later initialization step fails, the interface reports every surface newly committed by that invocation. A pre-publication failure may name only the exact repository Git exclusion; a post-publication generated-view failure also names the ledger and its exact database path. A repeat that adds no exclusion and publishes no database reports an unchanged result. The caller grants that exact initialization command one narrow approval; no persistent `.git` write is required.

Routine commands write project data only below the selected work root. In a normal checkout at the default root, a Codex custom permission profile extends `:workspace` and reopens only the relative `.codex/pinboard` subtree. In a linked worktree, the same profile grants only the exact resolved absolute shared-repository `.codex/pinboard` directory; it does not add the shared repository as a workspace root. An explicit `--work-root` likewise requires a direct write rule for that exact selected directory. Structured read-only recovery chooses the relative rule only when the source checkout and shared repository are the same default checkout, otherwise it names the exact absolute work root derived from resolved root facts. Sibling `.codex`, `.git`, and the installed plugin cache remain read-only. Legacy sandbox settings override profiles and therefore must be removed when a profile owns access. This runtime boundary is an outer integration concern: Pinboard records declared dispatch permissions but does not grant or enforce them itself.

### Generated views

`.codex/pinboard/views/` is human-readable output derived from SQLite and accepted artifact references. Declared selectors are `items/<item-id>.md`, `attempts/<attempt-id>.md`, and immutable `history/<history-id>.md`; queue position lives in each item view and in explicit overview output. Aggregate `queue.md` and `history.md` are no longer declared projections. An ordinary commit returns exact affected identities, the interface reads only those projection facts and any selected live brief bytes, and atomic replacement compares bytes only at those selected paths. Equal bytes preserve the existing file, inode, and modification time. A live v2 attempt view contains a complete Markdown rendering of its canonical JSON brief; no runtime path reads generated Markdown for semantics. A successful SQLite commit is authoritative before refresh begins, and a refresh warning cannot undo it. Explicit `pinboard views rebuild` reads every declared item, attempt, and receipt projection but excludes unrelated authority history, state counters, proposal child collections, and artifact references; it removes the two legacy aggregates, reconciles every declared selector, and still preserves equal files. Validation distinguishes authoritative defects from stale or missing generated output.

### Project evidence boundary

Pinboard does not require or produce a companion notes directory. Project documentation and other human-owned notes remain outside the installed runtime contract. Durable execution semantics enter Pinboard only through accepted immutable artifact references.

## Representative flows

### Initialization and reopen

`pinboard init` resolves the default `.codex/pinboard` root below the shared repository root, then idempotently adds only `/.codex/pinboard/` to that repository's local Git exclude file before initializing the work root or SQLite. Invoking initialization from a linked worktree therefore reuses the repository ledger and does not create a worktree-local authority. It never edits a committed `.gitignore`, so unrelated `.codex` content remains visible. Fresh default initialization receives one exact command approval for its combined `.git` and `.codex/pinboard` writes; returning and routine commands do not retain `.git` authority. A typed effect wrapper spans storage, accepted-brief rendering, and generated-view refresh after those writes. JSON reports exactly the surfaces newly committed before a known later failure: `repository-git-exclude` with its exact path and entry, plus `ledger` with its database path when fresh database publication completed. Before publication, the authoritative ledger remains absent; after publication it remains available even when replaceable view refresh fails. A repeat that adds no exclusion and publishes no database reports an unchanged rejection. Interface-owned work-state composition creates the SQLite schema when `state.sqlite3` is absent. When the database exists, it verifies that exact schema before reconciling the fixed publication staging path: a same-file staging alias left after publication is removed, while a different-file conflict is rejected without replacement. It then ensures the artifact directories exist and rebuilds views. Routine recovery selects relative `.codex/pinboard` for a normal default checkout, the exact absolute shared-repository work root for a linked worktree, and the exact selected directory for an explicit `--work-root`. Only after a successful fresh initialization and its receipt, the outer work-state interface prints one optional repository-care pointer. The default Codex runtime may also read the user Codex config to recommend `body_after_prefix` when that user default is absent; the explicit Claude runtime suppresses only this Codex-specific line. The pointer starts no skill or work, and neither effect writes configuration. A trusted project's `.codex/config.toml` may override the Codex user default. Resume and failure paths print neither effect; unreadable or malformed user config suppresses only the setting recommendation.

The path does not read generated views or mutate SQLite, artifacts, lifecycle, or authority.

### Brief source planning

The installed `pinboard brief-sources` plan leaf reads a strict source manifest without opening work state. It resolves each source-checkout-relative whole-file or Markdown-heading selector in turn, rejects overlapping line spans, and returns a strict reusable plan containing normalized selected-source digests and segment metadata. The emit leaf accepts that plan rather than the manifest, then rereads and verifies only the selected source files represented by the requested bounded batch before returning their content. Its heading selection is also used by dispatch against the same selected source checkout when validating reviewed-authority digests. Both leaves are read-only and do not acquire authority or write project state; planning memory grows with the largest selected file plus plan metadata, while emission memory and file access grow only with the selected plan document and requested batch.

`pinboard tool-contract` is another state-independent read. It derives one complete index from the installed parser leaves, recursively expanded exact command union, closed action family, and closed brief-boundary family. A bare operation family with several leaves returns their exact selectors. A selected leaf projects exact installed CLI usage including optional global-root placement alongside its purpose, mutation class, exact acquisition or retained authority, subject, lifecycle precondition, generated strict schema, artifact contract, actual success receipt, and retry semantics. Selected actions add their exact execution-route family, preventing read-only runtime continuation or blocker evidence from being presented as payload-bearing lifecycle transitions. Brief publication includes typed unresolved local and cross-boundary starters, every applicable structural-union choice as an exact replacement template, canonical byte rules, relational rules, and its fact-validation boundary generated beside the canonical brief records. A boundary-specific starter projection omits the much larger validation schema while retaining one complete unresolved shape and every structural, relational, and fact rule needed to fill it. The starter's initial union members are syntactic templates rather than fixed semantic choices; identity and semantic values remain unresolved, so this discovery path cannot invent scope, authority, or verification. Publication validates the candidate record and its accepted Pinboard references, but it does not resolve branch or base-revision declarations against Git or prove source-derived semantic claims.

### Mutations and proposal intake

Each argparse leaf carries its selected parser and either an exact command model or one of the few named coupled-option decoders. The interface converts the raw namespace once and dispatches a closed command union; handlers never receive a general argument namespace or reparse command and operation strings. A transition handler parses the opaque CLI capability receipt, which contains the action identity and required subject revision plus exact lease identity and generation for leased mutations. It derives the exact selected subject scope, reads only that decision context, decodes strict JSON against the selected variant, and constructs the exact command. `application.service` repeats that exact scoped read inside one write transaction and reselects the action against current subject, related legality, and lease facts. A change to the selected subject or a dependency that determines legality rejects the action, while a commit concerning an unrelated subject does not. Acceptance allocates one project revision and receipt and commits one closed mutation. The SQLite adapter reads only the current rows needed by that mutation, exhaustively applies its targeted effects, validates the changed facts, advances revision and history, and returns `CommittedEffect` with the exact receipt, affected item and attempt identities, and any continuation attempt. A stale or failed effect rolls back; neither success nor failure assembles complete pre- or post-state. Proposal intake follows the same boundary and adds its exact relation target plus only the queue suffix whose positions change. Queue positions remain one-based and contiguous. Follow-up candidates depend on their related item; a prerequisite candidate becomes a dependency of its live related item. A planned-replacement proposal names the existing affected item and the practical cost of continuing it, while the new intake item becomes the replacement. The locked decision reads that affected item's current relation history and selects the next relation revision. SQLite then commits the proposal, intake item and definition, explicit planned-replacement relation, and affected-item subject-revision update together, or accepts none of them. That subject update makes an earlier action selected for the affected item stale. Intake never creates an attempt or activates work.

An unresolved current planned replacement is a decision fact, not a new lifecycle state. Project action discovery continues to offer `record-replacement` so the relation can be revised or withdrawn and `retain-temporarily` so a human can accept its exact current cost. Active work also retains rebind, pause, and block; its worker retains blocker reporting. Review retains return-for-correction. Definition revision, defer, and close remain available only where their existing lifecycle and preparation rules already permit them. Withdrawal or an exact-revision temporary-retention disposition resolves the guard and restores the otherwise legal lifecycle actions.

After a successful mutation, generated views refresh only the item, attempt, and new history selectors named by `CommittedEffect`. SQLite returns exact projection facts for those identities, and the filesystem boundary reads only the accepted live briefs those selected attempt views require. Transition JSON exposes the committed receipt's exact history ID so a later caller can select it without discovery. Transition presentation derives continuation for the effect's exact attempt identity through the same named-attempt reader as inspection. A view or continuation warning cannot undo the committed transition, and callers must not replay that mutation merely because projection needs repair or reinspection. When the Codex runtime denies a SQLite write, the database and transaction owners classify `SQLITE_READONLY` and retain the resolved database path; the CLI adds the attempted installed operation and narrow permission recovery selected from the resolved checkout, shared-repository, and work-root facts, reports `do-not-retry`, and preserves the unchanged ledger disposition.

Every work item has immutable `work_item_definition_revisions`; the highest contiguous revision is its current accepted definition and the sole owner of title, objective, hypothesis, evidence selectors, scope, non-scope, acceptance criteria, ordered dependencies, effect, and unlock. Proposal intake creates revision 1 from immutable proposal facts. Explicit proposal-acceptance dependencies, prerequisite intake, and `revise-item:<item>` append another complete revision and replace relational dependency rows in the same transaction. Revision decisions compare both expected revision and digest, validate the complete canonical definition, reject missing or cyclic dependencies, and leave lifecycle state untouched. Block operations only confirm dependencies already present in the current definition. Attempts retain the exact definition revision and digest from their accepted brief. Current-scope actions stay unavailable to stale attempts; an active or paused stale attempt can rebind to a matching current-definition brief and corrected Git lineage while preserving its lifecycle state and evidence and fencing worker authority.

A dependency-satisfied ready item may retain one renewable preparation claim pinned to its exact current definition. The item remains `ready` while a preparer compiles and reviews the canonical brief. Ordinary `preparation start` samples its operation time at the boundary, then opens one write transaction and selects the current definition together with either initial acquisition when no claim exists or transfer when the retained claim is inactive. A live conflicting claim, an unresolved planned replacement, or an item that is no longer ready is rejected without change. Exact low-level acquisition and transfer remain supported for recovery and contract diagnosis. Renew and release require the exact preparation token, while revocation records the invoking project task and host. A live claim suppresses conflicting ready-item lifecycle and definition mutations but does not hide `record-replacement` or `retain-temporarily`. If a replacement is recorded after preparation was selected, activation disappears and a stale activation receipt is rejected by the locked recheck. Otherwise activation is advertised only to the exact preparer, validates the accepted brief and definition pin inside the write transaction, consumes the claim, creates the attempt, and moves the item to `active` atomically. Expiry, release, or revocation makes the ready-item operations available again; a later ordinary start repins the current definition.

### Worker dispatch and review publication

`application.dispatch` returns expected selection, review-publication, and final-authority outcomes as typed results. `interfaces.dispatch_brief` composes those operations with artifact verification and prompt rendering, converting its advertised environment, identity, source, review, and prompt rejections into one closed dispatch result. An unresolved planned replacement withholds project continuation and dispatch and worker continuation and review submission; blocker reporting, rebind, pause, and block remain available. A previously selected action is rejected by the locked recheck after the affected-item subject revision advances. Dispatch requires the environment checkout to match the selected source checkout before decoding the strict record and checking attempt, item, branch, stable checkpoint ID, accepted scope, architecture impact, contracts, authorization bases, verification, reviewed-authority digests, coverage, lifecycle disposition, and independent ready review. Reviewed-authority digests are recomputed from that source checkout rather than the shared repository root. Accepted-scope authorization must match the reselected attempt; source-derived authorization must name one exact reviewed authority family. The independent reviewer verifies that each selected source truthfully serves its claimed product-authority, repository-policy, or existing-consumer role and that each mandatory check's tool, threshold, platform, compatibility obligation, or hardening target is supported by accepted scope or selected source bytes. The stable action JSON field named `effect` classifies lifecycle transition input, not every outer command effect: dispatch may publish or reuse immutable review evidence while leaving item and attempt lifecycle unchanged. Domain code names that narrower fact `LifecycleEffect`; the inspection boundary preserves the existing field and values.

The agent-facing runtime adapter maps the accepted checkout, permission declarations, native subagent launch, waiting, and optional messaging without changing this flow. Pinboard validates the dispatch record but grants no runtime capability and creates no worker.

Ready review evidence is strict JSON bound to the stable checkpoint ID, canonical checkpoint-record digest, and canonical ordered authority-set digest. The interface canonicalizes it, the application publishes and accepts it through the result-shaped artifact capability, and the interface verifies the accepted bytes before rendering the launch prompt. Publishing that evidence may advance the project revision without changing the attempt subject. Dispatch therefore rereads the attempt and reselects the subject-local action after publication; it needs no revision rewrite or exemption for its own artifact acceptance. If a planned replacement became unresolved after evidence publication, dispatch reports the published artifact as a committed surface, leaves lifecycle unchanged, and does not present replay as an unchanged retry. The launch prompt only points the worker to the canonical JSON brief and names the execution environment; it does not duplicate or reinterpret the task contract.

After a candidate is submitted, the read-only `review-job` command requires the exact protected candidate and current review continuation. Its strict v2 command has two independent dimensions: an initial or correction round, and an absent or caller-selected prior checkpoint package. One focused SQLite read transaction resolves the named attempt, exact supplied history primary keys, their linked package artifact when selected, and the accepted brief; it never discovers the latest evidence, scans retained history, assembles complete state, invokes validation or handover, or writes. The outcome owner runs full validation as a separate stop-on-failure preflight before supplying a package history identity. The interface verifies selected package bytes and canonical same-attempt v2 receipt linkage. A correction round separately requires a caller-selected return receipt whose canonical `return-for-correction/v1` input reason agrees with its preserved candidate and outcome reason, then binds that evidence to the mutable current `review.md` path and render-time digest. Historical generic-input return receipts remain readable ledger evidence but cannot supply typed correction context. The job also reads the current nonempty `result.md` and emits all identities in a bounded fresh-context prompt. The reviewer verifies those bytes, resolves and compares each historical candidate independently with the current candidate, and classifies every changed or unreviewed surface. Unchanged owner relationships may reuse evidence; changed relationships and documentation are revalidated; relationship-invalidated evidence becomes stale even when its source hash is unchanged. Review widens beyond that surface for architecture, persistence, wire, lifecycle, dynamic consumers, or demonstrated blind spots, and stops without a verdict when an identity, comparison, classification, or widening condition cannot be established. Review-job rendering does not publish evidence, mutate lifecycle, create a task, or transfer acceptance authority; the accepted brief's `owner_task_id` remains the exact outcome owner. The Codex runtime creates the subordinate reviewer. If that capability is unavailable, the candidate remains in review as a valid resumable boundary rather than being routed to another user-owned task.

### Checkpoint and terminal acceptance

An accepted nonterminal checkpoint uses the accepted brief's stable checkpoint ID, preserves exact result and implementation-review evidence, composes one strict `pinboard-checkpoint-review-package/v1`, pauses the same attempt, and fences its worker authority. The interface owns this cross-layer composition because it already knows the accepted brief, immutable artifact references, and applicable review boundary. A package contains portable artifact identities rather than SQLite row IDs. Local packages name the brief, result, and implementation review; cross-boundary packages additionally name the validated ready brief review and bind its canonical checkpoint and reviewed-authority-set digests.

After initial current-action selection and payload decoding, checkpoint acceptance makes one fresh exact-scope observation, revalidates the selected action, and only then applies the canonical candidate rule to those same facts. A stale or unavailable action therefore exits before candidate or checkpoint comparison; failure to read this preflight observation remains an unchanged infrastructure failure with its ordinary retry disposition. A mismatched protected candidate or accepted-brief checkpoint exits before reading `result.md` or `review.md` and before publishing immutable evidence. Cross-boundary acceptance also resolves and validates the exact accepted ready review before those evidence reads. An unresolved planned replacement withholds checkpoint acceptance, review acceptance and continuation, and completion, while return-for-correction and the relation-decision actions remain available. An exact checkpoint request publishes result, implementation review, then package. If the relation becomes unresolved only after those publications, the locked transaction reselects and rejects the stale acceptance without changing lifecycle or prior ledger relationships. Each immutable publication returns whether this invocation created or reused the revision, so that rejection reports only the selectors it actually created, in publication order, marks immutable artifacts as the committed surface, and is `do-not-retry`. A `SQLITE_READONLY` acceptance failure carries the same database path, operation, and resolved-root permission recovery alongside every newly published artifact identity, `do-not-retry`, committed-artifact surfaces, and unchanged ledger relationships.

The locked checkpoint-acceptance transaction rereads current facts, reapplies action and candidate legality, accepts all three checkpoint references, links the attempt to the result and the history receipt to the package, then pauses the item and attempt and fences authority atomically. Checkpoint acceptance alone emits `checkpoint-acceptance/v2`; its exact outcome binds candidate, checkpoint, evidence, and outcome. Existing `transition-receipt/v1` rows and every sibling transition remain unchanged and readable in SQLite v6; the out-of-band v5-to-v6 migration adds empty replacement tables and the nullable proposal cost column without historical backfill. Review continuation, correction return, resume, and rebind neither create nor rewrite accepted packages. Correction return now populates the receipt's existing optional candidate field alongside its durable reason before clearing candidate protection and fencing authority, and records the canonical reason under `return-for-correction/v1` input schema for future typed correction review. Explicit validation and handover validate package provenance from the historical linked receipt and immutable evidence rather than the attempt's current brief link. Review-job can consume one explicitly selected validated package and eligible correction receipt.

Terminal completion has two mutually exclusive leaves selected from a fresh same-attempt enumeration of accepted checkpoint receipts, and both require the planned replacement to remain resolved through their locked action recheck. Empty enumeration preserves direct completion from active or review: its exact evidence-only input, generic `decision/v1` input and `transition-receipt/v1` outcome, absent artifact link, unchanged result pointer, atomic close, and authority fence remain artifact-free. Nonempty enumeration requires covered completion from protected review. The strict `pinboard-covered-completion/v1` input names the exact candidate, current result and review digests, an independent reviewer, and one compact reused-or-revalidated row for every authoritative checkpoint history ID in ascending order. The outer interface verifies those mutable bytes and every checkpoint package closure before publication. It then publishes the terminal result, final review, and canonical `pinboard-completion-review-package/v1`; the locked transaction rereads the enumeration, authority, and action legality, accepts all three references, points the attempt at the terminal result, emits `completion-acceptance/v2` linked to the completion package, closes the item and attempt, and fences authority atomically. A replacement recorded after covered-completion publication therefore leaves the newly published artifacts intact but rejects lifecycle completion with the same committed-artifact, `do-not-retry` disposition. Direct-with-history and covered-without-history reject unchanged, so the direct leaf acquires no package implication. Completion validation resolves only covered receipts and their immutable closure; handover v5 appends their typed portable packages while retaining the generic history and artifact records.

When review accepts the protected candidate but the current attempt should continue, review acceptance returns the item and attempt to active, clears the protected candidate, preserves the accepted candidate and evidence in the transition receipt, and fences the prior worker authority. Late accepted direction uses these existing operations rather than another lifecycle state: definition revision makes an active attempt stale; review return clears a superseded protected candidate without calling its implementation defective; matching brief publication and rebind accept the revised target without changing active or paused state before another exact candidate and review. Terminal completion records accepted evidence and removes the item from live work only after the human has authorized repository disposition, any requested cleanup, and the terminal transition. The outer coding-agent workflow verifies that an exact isolated worktree is unoccupied and contains no needed uncommitted or unintegrated work before removing it and its explicitly authorized local and still-present remote branches; Pinboard adds no Git state or command. After each workflow-ending stage, exact item status remains the canonical current pair: checkpoint acceptance is `paused`, accepted continuation is `active`, submitted review is `review`, and terminal item status is `done` with no current attempt. A named historical terminal attempt comes from the transition continuation or exact attempt inspection. Direction after that terminal boundary becomes new work. Review return keeps the same attempt and evidence while fencing the rejected worker lease.

## Stored formats

The default `.codex/pinboard` path is current; explicit work roots remain supported at their selected paths. Proposal JSON uses `pinboard-proposal/v1`; complete definition replacement uses `pinboard-item-revision/v1` containing `pinboard-work-item-definition/v1`; accepted work briefs use `pinboard-work-brief/v2`; independent review evidence uses `pinboard-work-brief-review/v2`; accepted checkpoint packages use `pinboard-checkpoint-review-package/v1`; covered terminal packages use `pinboard-completion-review-package/v1`; review jobs use `pinboard-review-job/v2`; dispatch environments use `pinboard-dispatch/v1`; brief-source manifests and plans use `pinboard-brief-sources/v1` and `pinboard-brief-source-plan/v1`; static command discovery uses `pinboard-agent-tool-contract/v1`, `pinboard-agent-tool-operation-variants/v1`, and its selected operation, action, and presentation records; work-brief construction uses `pinboard-work-brief-contract/v1`; unsuccessful JSON output uses `pinboard-rejected-operation/v1`; and read projections include `pinboard-item-definition/v1`, `pinboard-item-definition-history/v1`, `pinboard-overview/v4`, and `pinboard-parallel-preview/v1`. Historical terminal v1 brief artifacts remain opaque immutable evidence rather than a supported input format. Atomic file publication uses private `.pinboard-stage-*` names.

## Keeping this map current

This document describes implemented ownership and dependency direction. Every implementation checkpoint declares its architecture impact before dispatch. A checkpoint that changes an owner or dependency direction names this file as `update-required` and includes the coherent documentation change in the same candidate. A `read-only` checkpoint names the authority it must conform to; `none` records why no architecture change occurs. Typed brief validation enforces the declaration shape, while brief and implementation review verify that the declaration is true for the sources and final diff.

Future behavior belongs here only when its implementation is present. Delivery history, speculative modules, and deferred redesigns remain in private planning evidence until they change the current architecture.
