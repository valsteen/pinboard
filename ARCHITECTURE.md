# Architecture

This is the current implementation map for maintainers and coding agents. Use it to locate an exact owner, trace a supported operation across boundaries, or evaluate a known limitation. It is semantically exhaustive rather than an exhaustive file tree; leaf modules appear only when they change an ownership or dependency relationship.

## System overview

Pinboard is a local coordination system for one repository-owned work ledger. The installed `pinboard` command and local-stdio `pinboard-mcp` server discover the project, open its work root, and use the same application contracts over the same SQLite authority. MCP owns agent workflows. The CLI owns root discovery, initialization, summary status, full validation, generated-view repair, portable human export, direct human closure and its own static diagnostics. MCP exposes item status, proposal creation, canonical brief publication, current overview, saved human priority, structural parallel preview, legal-action discovery, exact attempt inspection, immutable-artifact verification, preparation and attempt authority, lifecycle transition, worker dispatch, candidate-bound review publication, and restoration of an explicitly inspected protected candidate into a caller-selected clean checkout. Pinboard is an application and plugin, not a supported Python library: `python -m pinboard` aliases the CLI and `python -m pinboard.mcp` aliases the MCP server; internal modules and package exports are not public extension APIs.

Codex is the primary, stress-tested integration. Claude Code support is experimental and loads the same repository root through `.claude-plugin/plugin.json` and `--plugin-dir`. Both use the same launcher, MCP entry, skills, schemas, and SQLite authority. Claude's installed host-only startup boundary independently decodes SessionStart and SubagentStart records, validates required fields and ignores unrelated extensions. SessionStart supplies the current parent event's actual local session identity and the executing machine's stdlib hostname as native additional context. SubagentStart supplies only the launched worker's own identity; its verified dispatch host remains separate. Neither entry reads project state or grants authority. Runtime-specific identity sourcing, worktree, subagent, permission, waiting, and optional messaging remain outer integration responsibilities; they create no separate application, domain or lifecycle policy.

SQLite is authoritative for lifecycle, accepted scope, dependencies, mutation authority, and history. Attempt continuation is a read-only projection of current SQLite facts and verified artifacts. Review submission first publishes one strict immutable candidate snapshot, then atomically accepts its reference with the review transition. Attempt inspection and review jobs resolve that same verified snapshot; review jobs may publish an immutable reviewer prompt and accept its artifact reference, but they do not mutate lifecycle or candidate state, change attempt authority, write repository files, affect Git, or add another workflow owner.

Each invocation resolves two Git-backed roots. The **source checkout root** is the selected checkout's exact top level, including a linked worktree, and owns project-file and authority reads for that attempt. The **shared repository root** comes from the Git common directory and owns shared Pinboard state and local Git exclusion. The roots are equal in a primary checkout and deliberately different in a linked worktree. Activation observes the source checkout's current branch and full HEAD through the same file adapter, then the shared lifecycle adapter compares those facts and every reviewed authority with the accepted brief before constructing the domain command.

Root selection does not require an unused external work-root parent to exist. `DurableRoots` alone derives the database path. State-independent commands stop after lightweight selection. Database-backed CLI commands cross one outer work-state boundary that validates the immutable layout, constructs one `SQLiteWorkStore`, and supplies that layout and storage-independent capabilities to the workflow. Thematic handlers neither reconstruct infrastructure nor import the concrete store; composition uses required parameters rather than globals, optional fallbacks, or a dependency-injection framework.

Agent guidance is a separate dependency graph. Repository guidance routes qualifying work to the installed Pinboard skill before read-only work becomes repository writes and while accepted repository work awaits human disposition; intake and delivery remain specialized callers. The main skill owns shared interaction style, decision-sized collaboration, preservation of accepted and unresolved status, asking for input only when the answer can materially change the work, the threshold for user-relevant process detail, verified readable-artifact links on every item or evidence mention, human task starts, review-actor language, current-responsibility routing, preparation start, Git-baseline and checkout confirmation, bounded checkout-risk assessment, late-direction reconciliation, exact item-status reads for workflow endings, and human-authorized repository wrap-up. It classifies a request to read named context, get oriented, or wait as a bounded read; only revision or implementation enters lifecycle, authority, source planning, dispatch, and review.

The main skill also owns assurance. Defects and accepted guarantees remain blocking. A material new concurrency, durability, security, adversarial, platform, or compatibility guarantee needs accepted product evidence or one concrete human scope decision before it enters implementation or review. Repository wrap-up composes runtime-owned task occupancy, Git integration, worktree and local and remote branch cleanup, and the Pinboard terminal transition without moving Git behavior into Python or adding lifecycle state.

For cross-boundary work, preparation freezes accepted semantics, assurance, stable authorities, constraints, and uncertainty without predicting every implementation file. Delivery derives the concrete impact and reads outward when a changed relationship or uncertainty exposes another owner. Separate review starts from changed and unclassified surfaces, reuses unchanged evidence, and widens for architecture, persistence, wire, lifecycle, dynamic-consumer, or demonstrated-blind-spot conditions. Specialized skills retain their own evidence and blocking outcomes without duplicating narration policy, a hard-coded impact graph, checkout ownership, Git integration, or wrap-up state.

Technical Writing owns composition for substantial technical documents and human-facing artifacts. It uses collaborative composition while material choices remain open and quiet production when accepted facts are sufficient. Pinboard selects it automatically for clear document work and permits explicit selection for ambiguous cases; readable artifacts and pull-request descriptions use quiet mode during delivery and wrap-up. Routine status, intake, lifecycle, implementation, and review coordination do not load it. Existing document, repository, brief, review, and machine-consumed artifact owners remain authoritative for facts and structure.

The repository-care skills are independent guidance owners. Repository Readiness owns unfamiliar-repository assessment, authority mapping, coverage modes, developer navigation, and the storytelling lens. Slop Cleanup owns recursive removal of approved unsupported residue and its deletion fixed point. Maintaining Agent Guidance owns placement and reconciliation of durable AI-facing guidance. They may refer to one another or use Pinboard, but none requires a sibling skill or ledger for its baseline workflow.

One work root has three durable roles:

```text
.codex/pinboard/
  state.sqlite3   # authoritative lifecycle, dependency, authority, and history state
  artifacts/      # immutable long-form bytes referenced by SQLite
  views/          # repairable Markdown projections generated from SQLite
```

## Dependency direction

Pure decisions remain at the center:

```text
cli ──┐
      ├────────────> application ────────> domain
mcp ──┘                    ▲                  ▲
  └────────────────> adapters ───────────────┘
```

`domain` depends only on the Python standard library and `msgspec` for exact canonical records. `application` depends on domain values and storage-independent capability protocols. `adapters` implement those capabilities with SQLite and the filesystem. `cli` and `mcp` are sibling outer boundaries: each decodes its transport, composes concrete adapters with shared application use cases, and presents transport-specific results without importing the other. Production dependency tests keep domain independent of outer layers, application independent of adapters, CLI, and MCP, and adapters independent of both interfaces. They also keep CLI composition acyclic, constrain `cli.entrypoint` to routing and final error presentation, and verify both installed entries.

The method used to preserve these boundaries, expose effects, and stop decomposition at a useful fixed point is recorded in [the design principles](DESIGN_PRINCIPLES.md).

## Runtime ownership

### Launcher

The `scripts/pinboard` launcher resolves runtime state only below its own plugin-version or source root. Ordinary CLI arguments select `pinboard`. Exact startup selectors choose independently installed entries: `--mcp` selects `pinboard-mcp`, `--claude-session-start` selects `pinboard-claude-session-start`, and `--claude-subagent-start` selects `pinboard-claude-subagent-start`. All three selectors reject additional arguments before effects. A source checkout prepared by `scripts/prepare-worktree` uses its development `.venv` when the selected executable is available. Otherwise, ordinary launch requires `.pinboard-runtime/.pinboard-ready` and the selected private executable. Missing readiness returns one strict `pinboard-launcher-result/v1` preparation requirement without invoking uv or starting Pinboard. CLI prestart recovery uses stdout; MCP and Claude hook prestart recovery use stderr and leave their protocol stdout empty.

Explicit `scripts/pinboard --prepare-runtime` is the only launcher path that invokes uv: it synchronizes locked production dependencies into `.pinboard-runtime`, verifies the real CLI entry and availability of the MCP and both Claude startup executables, and writes the ready marker last. An existing marker is reusable only when all four executables remain available. Preparation does not run protocol or hook entries with `--version`, because they do not support that argument. Packaged code, skill assets, and a ready private runtime are immutable inputs during ordinary commands. Project-owned SQLite, artifacts, and views remain below the selected work root, separate from both Pinboard runtime environments.

### MCP

The Codex and experimental Claude manifests explicitly select separate root configuration files, `mcp-codex.json` and `mcp-claude.json`. Codex resolves the configured relative `cwd` under the plugin root and invokes `sh ./scripts/pinboard --mcp`; Claude expands `${CLAUDE_PLUGIN_ROOT}` in its absolute launcher command. Neither declaration depends on default `.mcp.json` discovery or shared-file precedence. Both select the same launcher/runtime owner and existing server entry. Runtime preparation remains manual; a client reconnect or reload follows successful preparation. Package negotiation tests establish configured process startup, not enabled native-plugin ingestion or model usability.

The Claude manifest explicitly registers `./hooks/claude-hooks.json`; the plugin supplies no shared default hook configuration for Codex discovery. Its native SessionStart and SubagentStart commands select independent entries through the same prepared launcher/runtime and host adapter. Each entry decodes its exact typed projection of the Claude-owned event: required fields, event kind and native identity remain validated, while unrelated additive host fields are ignored. SessionStart then samples `socket.gethostname()` and emits only the current event's `session_id`, machine name and concise attribution instruction through strict Pinboard-owned additional-context records. SubagentStart emits only the actual `agent_id` as worker context. Neither forwards cwd, transcript paths or ignored extensions. Missing or malformed required fields, an unsupported event kind or invalid identity emit no attribution and a payload-free diagnostic; a failed machine source supplies no fallback host. Pinboard-owned requests, outputs and artifacts continue to reject unknown fields regardless of sender. Hook registration does not grant client trust.

Parent attribution refreshes when the native host delivers SessionStart on startup, resume or another session refresh, rather than relying on a Remote Control alias or potentially stale MCP startup environment. Emission alone does not establish actual context ingestion or model adherence. Reopen this outer integration on an observed supported event that fails to deliver current session/machine context or an ordinary run that still misattributes it; do not change application identity or permission policy to mask that discrepancy. Native hook context is attribution, not authentication or mutation authority. A worker still uses its own SubagentStart identity and verified dispatch host, verifies its immutable prompt, reads the canonical brief, and acquires its own exact lease through MCP. Shared prompts and envelopes name the runtime-owned identity source rather than a Codex environment variable.

Exact attempt inspection includes verified current accepted snapshot identity and a native `pinboard_candidate_restore` invocation. It preserves exact work root and inspected candidate while leaving the caller-selected exact clean checkout unresolved. The native restore tool invokes `adapters.candidate_evidence` and existing Git effects. They require the current accepted snapshot context; paused checkpoint acceptance clears that context, and neither selects arbitrary archived candidates. An inspected candidate superseded by a newer submission rejects before Git.

`mcp` owns one local-stdio boundary, not a general CLI mirror. `server.py` registers exactly twenty tools: complete work-brief construction, verified source preparation, current item status, full item definition/history, proposal creation, canonical brief publication, independent negative brief-review publication/status, current overview, saved human priority, selected/all-safe structural parallel preview, legal-action discovery, exact attempt inspection, immutable-artifact verification, candidate observation and restoration, preparation authority, attempt authority, lifecycle transition, dispatch, and review-job. CLI and MCP compose the same application use cases and concrete adapters without importing each other. The CLI has no agent workflow counterparts.

The same SDK registration supplies concise entry and discovery instructions through standard MCP initialization, before deferred tool schemas. For intake or coordination, they route the client to the complete existing workflow skill before attributed-call construction: `pinboard-intake` for new work, or `pinboard` for coordination of existing work. Native skill loading or a complete read of the resolved skill file supplies that owner's sequencing and runtime identity instructions; transport text does not duplicate them. Discovery instructions direct the client to resolve each host's actual advertised full callable name before exact selection, use native keyword discovery for unresolved names, and reconcile no-match results with the advertised inventory. The coordinator follows supplied connection instructions or loads the shared runtime reference when they are absent or detailed request, startup or recovery contracts are needed. Initialization creates no worker, identity, lease, lifecycle effect or permission. Emitting instructions does not establish that a supported native client exposes or follows them; actual native use remains the evidence for usability.

Overview's existing registration also emits the optional vendor-specific `anthropic/alwaysLoad` tool metadata, requesting first-use schema loading for that read-only entry. The other nineteen registrations remain unmarked and use host-native deferred discovery. This loading hint belongs to outer SDK glue; it changes neither strict operation schemas nor workflow authority. SDK emission, actual client adoption and ordinary native usability require separate observations; the hint is not a universal MCP compatibility guarantee.

Native negotiated schemas and inline action contracts own operation construction; dispatch's registration description also exposes its three strict construction leaves when host callable metadata loses that detail. The negotiated schema and typed decoder remain authoritative. This presentation supplements missing consumer information without repairing the host's schema translator or changing validation.

Dispatch and review-job publication return independently required immutable `prompt_reference` provenance and a `native_launch.message` containing the fixed verification/startup envelope. Publication creates no worker or worker authority. The outer runtime adapter passes that message unchanged to the advertised host worker-message argument: Codex `spawn_agent.message` or Claude `Agent.prompt`. Neither an artifact reference nor its verified prompt body is an alternative launch input. Native execution, the launched worker's own acquisition and later submission/release remain separate observable effects; declaration and publication do not establish them.

`pinboard_candidate_observe` reads one named nonterminal attempt's validated branch/base context and observes its exact checkout. The existing Git reader supplies the tracked binary diff and the actual HEAD used by the application-owned full-state identity. The observer separately reads Git-visible nonignored untracked paths and reports their exclusion. It changes no source, index, evidence, ledger or authority and makes no readiness or acceptance decision. Only separately authorized intended-file preparation changes source participation; the worker then reobserves and uses existing leased submission. Submission independently compares current state and preserves the reader's exact preimage with its diff in the accepted snapshot. Observation neither freezes that snapshot nor adds an atomic filesystem guarantee. Clean exact-current-commit submission remains separate without another observer mode.

Definition current/history leaves invoke `application.queries` and preserve its exact complete accepted fields and descending bounded chain facts. Brief-review publish/status leaves invoke `application.work_briefs`: resolve the accepted brief reference, verify and decode canonical bytes, validate exact subject binding and reviewer independence, then either publish and accept the negative evidence or read the latest verified evidence for that subject. Publication reports created artifacts separately from accepted-reference/ledger effects. Status returns the exact accepted brief and verified findings with structured correction targets; absence never implies readiness. Neither operation acquires authority or changes lifecycle. MCP owns the strict transport envelopes and structured correction guidance.

Authority operations share `application.authority_operations`; the application service selects initial acquisition or inactive transfer from facts reread under the same write lock that commits the change. Renewal, release, and revocation each reach a separate required-argument use case for their authority family: expiry belongs only to renewal, project attribution only to revocation. Renewal and release enrich the supplied lease and generation from the current command claim selected by `LedgerSnapshot`; absence rejection remains with the use case. Each use case constructs its existing domain operation once, then the application service independently rereads locked facts and decides authorization and fencing before persistence. The returned authority is reloaded through a fresh authoritative read. Initial preparation acquisition and inactive transfer remain real closed domain operations selected by native start under the shared lock; they are not separate installed CLI routes.

`contracts.py` owns strict frozen request records and correlated result records. Transition discovery advertises 23 exact request leaves for 22 mutating action kinds: role, action kind, authority fields, and shared application payload shape are coupled in each leaf. Direct and covered completion remain separate leaves; continue, dispatch, inspect, and report-blocker are not transition inputs or successful transition identities. Successful results couple the action to its exact ledger and artifact-reference surfaces. The handler selects and converts the exact leaf before resolving roots or reading state. It resolves the source checkout once and passes it with the validated payload into shared lifecycle selection and execution. `adapters.lifecycle_operations` and `adapters.lifecycle_artifacts` compose accepted brief, candidate, checkpoint, and completion effects with the application decision and locked persistence. Final authorization samples an explicitly supplied clock after locked state is reread. Snapshot and receipt provenance retain the original operation timestamp; it never substitutes for the fresh authority check. Action discovery binds one structured kind-and-subject identity to its semantics, authority receipt, and payload contract. Transition results return committed receipts and effects; attempt inspection supplies the derived continuation, verified brief, and evidence. The server validates each emitted result against its advertised correlated schema.

Shared strict-record bases own committed-publication failure and authority warning invariants, while exact leaves retain schema, code, scope and status-enum identity. MCP-local claim, read-status, rejection-detail and receipt/warning conversions do not resolve resources or refresh views; callers keep that replaceable-view effect explicit. CLI maintenance routing and native successful action/surface correlation answer different questions and remain separate exhaustive owners.

Every call carries nonempty, NUL-free explicit project and work roots and uses invocation-local storage connections. Synchronous work runs in a process-lifetime executor with two workers and at most four unfinished operations. Queued cancellation removes work before effects; running cancellation cooperates at safe checkpoints. Once source restoration, immutable publication or a SQLite mutation enters its effect section, execution reaches terminal classification before cancellation is reported. Source restoration reports only actual source-checkout changes; post-mutation verification failure retains that effect and forbids replay. Partial publication names exactly the durable surfaces and forbids replay; cancellation or transport loss does not roll back committed work. Generated-view failure is a committed warning with explicit rebuild recovery. Bounded metadata-only stderr diagnostics never share protocol stdout.

`mcp/__main__.py` routes `python -m pinboard.mcp` to the same process entry as `pinboard-mcp`. Dispatch, review-job publication, explicit selected retained-v1 remedy and candidate restoration use shared composition owners through the native boundary. Full validation and maintenance remain CLI-only; lifecycle and lease mutations use the shared application and adapter owners.

## Storage boundaries

### Authoritative SQLite state

`.codex/pinboard/state.sqlite3` owns project revision and host epoch; immutable work-item definition revisions; item, attempt, dependency, requirement, and proposal state; versioned planned-replacement relations and exact-revision temporary-retention dispositions; preparation and attempt authority; accepted artifact references; and transition history. Schema `sqlite-v6` includes a partial item-leading index for exact current-attempt and current-portfolio reads, a dependency-leading `(dependency_id, item_id)` index so a committed effect can discover only the live item views whose eligibility changed, and lease-identity indexes so leased action discovery reaches only current subjects selected by the supplied lease and generation. Every retained attempt or preparation lease must have its exact current generation anchor before application code can consume it. Relational dependency rows are the query-efficient projection of the current definition and must match it exactly. Mutable action receipts carry the selected item's, attempt's, or proposal's subject revision; leased receipts also carry the exact lease identity and generation. The project revision identifies committed state and history, not action freshness. An ordinary mutation opens one write transaction, reads the selected subject and direct decision relationships, allocates one project revision and receipt, updates only the relations named by the accepted closed mutation, validates exact changed facts, and returns the receipt plus affected item and attempt identities. Authority, subject-revision, commit-revision, and affected-row guards return typed stale or fencing rejections. Expected failures and infrastructure failures both roll back without assembling complete state before or after the effect. SQLite read-only failures retain the exact database path at the connection-and-transaction owner; the command boundary adds the exact operation and narrow Codex permission recovery derived from the database's parent work root, classifies the unchanged ledger as non-retryable, and preserves any earlier immutable-artifact publication as a separate committed surface. Initialization creates the exact empty current schema directly; complete state enters ordinary storage code only through validation.

### Immutable artifacts

Review submission publishes one strict current working-tree v2 or unchanged commit v1 candidate-snapshot JSON artifact before changing lifecycle, then the SQLite transaction accepts its evidence reference with the review transition. The snapshot binds attempt, item, candidate kind and identity, branch, preimage, accepted base, recorded time, and exact binary diff. It reuses the existing history artifact relationship and current attempt candidate timestamp, so SQLite remains schema `sqlite-v6`. Validation and handover verify every retained snapshot relationship; attempt inspection, review jobs, checkpoint acceptance, and installed recovery all read the same accepted bytes.

Accepted requirements, briefs, results, reviews, and other evidence are immutable project data below `.codex/pinboard/artifacts/`; they are distinct from the immutable code and skill assets shipped in the installed plugin cache. Current `pinboard-work-item-definition/v2` records own checkout policy and a nonempty set of stable obligations; `pinboard-proposal/v2` transfers both facts atomically into the same-identity intake definition while proposal rows retain conversation provenance. Current `pinboard-work-brief/v3` records resolve checkout selection and map every accepted obligation exactly once to a contract, criterion, or permitted deferral. Publication validates those facts against the exact current definition before accepting the strict JSON artifact. SQLite remains `sqlite-v6` because definitions are stored as versioned canonical bytes and brief artifacts already have opaque immutable references. The atomic filesystem primitive verifies an existing file against the requested bytes and returns whether this invocation created or reused it; the artifact owner couples that disposition with the verified reference, so concurrent callers attribute only their own committed effect. Pre-link failures remain unchanged I/O failures even when another identical artifact already exists. If directory synchronization fails after linking the destination, a typed partial-publication failure carries the just-published identity; brief and checkpoint presentation report that selector, and checkpoint presentation also retains every artifact published earlier in the same invocation. Readers resolve artifacts through accepted references and verify their bytes. The files do not independently own lifecycle state.

A needs-correction review is a separate strict artifact bound to the accepted brief's full SHA-256, checkpoint-record SHA-256, ordered authority-set SHA-256, attempt ID, checkpoint ID, and caller-selected artifact revision. Its fixed-length immutable key is derived from the complete attempt, checkpoint, full brief digest, and checkpoint digest tuple, so valid long identities remain portable and a corrected brief or changed checkpoint begins a new evidence stream. The record retains the complete identity tuple for validation. Focused status reads only the latest accepted reference for that exact kind and key, verifies its bytes, and validates its relationships again. It does not scan artifact history and it does not change lifecycle state.

### Codex project-write boundary

Fresh default initialization is the only ordinary setup path that also writes Git metadata: before it initializes the work root or SQLite, it idempotently adds the exact repository-local exclusion `/.codex/pinboard/` to the shared repository's `.git/info/exclude`. A read-only presence check lets returning initialization proceed without Git write authority. When the line is absent, the write path locks the shared file, rechecks it, and appends, so concurrent primary-checkout and linked-worktree initialization still adds exactly one line and only the appending invocation reports that surface. It never edits `.gitignore`, and it does not hide sibling `.codex` content. If a later initialization step fails, the CLI reports every surface newly committed by that invocation. A pre-publication failure may name only the exact repository Git exclusion; a post-publication generated-view failure also names the ledger and its exact database path. A repeat that adds no exclusion and publishes no database reports an unchanged result. The caller grants that exact initialization command one narrow approval; no persistent `.git` write is required.

Routine commands write project data only below the selected work root. In a normal checkout at the default root, a Codex custom permission profile extends `:workspace` and reopens only the relative `.codex/pinboard` subtree. In a linked worktree, the same profile grants only the exact resolved absolute shared-repository `.codex/pinboard` directory; it does not add the shared repository as a workspace root. An explicit `--work-root` likewise requires a direct write rule for that exact selected directory. Structured read-only recovery chooses the relative rule only when the source checkout and shared repository are the same default checkout, otherwise it names the exact absolute work root derived from resolved root facts. Sibling `.codex`, `.git`, and the installed plugin cache remain read-only. Legacy sandbox settings override profiles and therefore must be removed when a profile owns access. This runtime boundary is an outer integration concern: Pinboard records declared dispatch permissions but does not grant or enforce them itself.

### Generated views

`.codex/pinboard/views/` is human-readable output derived from SQLite and accepted artifact references. Declared selectors are `items/<item-id>.md`, `attempts/<attempt-id>.md`, and immutable `history/<history-id>.md`; queue position lives in each item view and in explicit overview output. Aggregate `queue.md` and `history.md` are no longer declared projections. An ordinary commit returns exact affected identities, its outer boundary reads only those projection facts and any selected live brief bytes, and atomic replacement compares bytes only at those selected paths. Equal bytes preserve the existing file, inode, and modification time. A live attempt view contains a complete Markdown rendering of its canonical typed JSON brief, including current checkout and obligation correspondence when present; no runtime path reads generated Markdown for semantics. A successful SQLite commit is authoritative before refresh begins, and a refresh warning cannot undo it. Explicit `pinboard views rebuild` reads every declared item, attempt, and receipt projection but excludes unrelated authority history, state counters, proposal child collections, and artifact references; it removes the two legacy aggregates, reconciles every declared selector, and still preserves equal files. Validation distinguishes authoritative defects from stale or missing generated output.

### Project evidence boundary

Pinboard does not require or produce a companion notes directory. Project documentation and other human-owned notes remain outside the installed runtime contract. Durable execution semantics enter Pinboard only through accepted immutable artifact references.

## Representative flows

### Intent and ordinary attempt start

The main Pinboard skill classifies the human request before loading delivery mechanics. Named-context orientation and wait requests read only that context and leave accepted attempt, lease, review, and repository state untouched. Implementation and revision requests enter delivery normally.

When implementation selects a new isolated worktree, the repository-owned `scripts/prepare-worktree` command first checks its uv and npm host prerequisites, then runs `uv sync --locked` and `npm ci --prefer-offline --no-audit --no-fund` from that checkout. The resulting ignored `.venv` and `node_modules` directories remain checkout-local; only package-manager caches may be reused.

The runtime adapter owns [source-worktree setup recovery](skills/pinboard/references/runtime-adapters.md#source-worktree-setup-recovery). After bounded diagnosis identifies a sandbox permission restriction, already-authorized setup can request one runtime-reviewed retry of the same command without a separate conversational confirmation. Runtime approval controls execution. Denied or unavailable permission, genuine setup failures, failed retries, and scope changes return to the human for a bounded decision before Pinboard preparation or implementation-source work. This recovery leaves installed-runtime preparation and protected ledger-write contracts unchanged.

A task that changes this setup path or another tool needed to assess itself records successful base preparation before editing. Stable installed tooling may continue to coordinate Pinboard state, but only direct source or built-candidate execution supports the changed behavior.

Preparation selects a typed checkpoint before publication. A README edit plus its referenced image may use the local checkpoint when both retain one owner and change no behavior, dependency direction, stored or wire identity, or independent consumer; any failed condition selects the cross-boundary path and its independent brief review. Mandatory verification remains hierarchical prose evaluated against repository authority. If a required tool cannot be resolved, preparation stops for an explicit human choice to abort, authorize one investigation or retry, or revise the accepted scope and evidence contract; it does not infer a fallback.

After brief publication, activation accepts only the accepted brief reference. The outer transition boundary decodes the canonical current brief, requires its owner to match the preparer's live authority, derives attempt, branch, base, and owner facts, and validates every declared reviewed authority. A shared Git observer classifies the primary checkout as `main` regardless of its current branch and classifies only a registered linked worktree of the same common repository as `isolated`; unsupported layouts reject. Activation, rebind, replacement-brief resume, and dispatch require the brief's exact current definition and recorded checkout selection to match that observation while retaining their existing identity, lineage, and authority guards. Only then does the existing locked activation decision revalidate the definition and preparation pin and atomically create the attempt. A failure before that transaction leaves the item ready and the preparation claim live. The outcome owner then selects project-only dispatch for the stable checkpoint. Dispatch publishes or reuses the immutable worker prompt reference and returns the native launch envelope; local dispatch needs no brief-review evidence, while cross-boundary dispatch publishes or reuses its ready review, reselects current authority internally, and performs its independent source revalidation. The runtime launches a fresh worker, that worker verifies the accepted prompt bytes, loads the complete delivery skill and reads the complete canonical brief before action, then uses its post-launch identity to acquire attempt authority and select leased continuation. Exact definition v1 and brief v2 bytes remain readable, reviewable, projectable, validatable, and exportable under explicit legacy-unrecorded policy, but they cannot authorize these execution operations.

### Initialization and reopen

Invoking initialization from a linked worktree therefore reuses the repository ledger and does not create a worktree-local authority. It never edits a committed `.gitignore`, so unrelated `.codex` content remains visible. Fresh default initialization receives one exact command approval for its combined `.git` and `.codex/pinboard` writes; returning and routine commands do not retain `.git` authority. A typed effect wrapper spans storage, accepted-brief rendering, and generated-view refresh after those writes. JSON reports exactly the surfaces newly committed before a known later failure: `repository-git-exclude` with its exact path and entry, plus `ledger` with its database path when fresh database publication completed. Before publication, the authoritative ledger remains absent; after publication it remains available even when replaceable view refresh fails. A repeat that adds no exclusion and publishes no database reports an unchanged rejection. CLI-owned work-state composition creates the SQLite schema when `state.sqlite3` is absent. When the database exists, it verifies that exact schema before reconciling the fixed publication staging path: a same-file staging alias left after publication is removed, while a different-file conflict is rejected without replacement. It then ensures the artifact directories exist and rebuilds views. Routine recovery selects relative `.codex/pinboard` for a normal default checkout, the exact absolute shared-repository work root for a linked worktree, and the exact selected directory for an explicit `--work-root`. The default Codex runtime may also read the user Codex config to recommend `body_after_prefix` when that user default is absent; the explicit Claude runtime suppresses only this Codex-specific line. ### Mutations and proposal intake

Each retained argparse leaf carries its exact frozen command model. Intake creates no attempt and activates no work.
