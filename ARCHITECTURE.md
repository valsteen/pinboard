# Architecture

This is the current implementation map for maintainers and coding agents. Use it to locate an exact owner, trace a supported operation across boundaries, or evaluate a known limitation. It is semantically exhaustive rather than an exhaustive file tree; leaf modules appear only when they change an ownership or dependency relationship.

## System overview

Pinboard is a local coordination system for one repository-owned work ledger. The installed `pinboard` command and local-stdio `pinboard-mcp` server discover the project, open its work root, and use the same application contracts over the same SQLite authority. MCP owns agent workflows. The CLI owns root discovery, initialization, summary status, full validation, generated-view repair, portable human export, direct human closure and its own static diagnostics. MCP exposes item status, proposal creation, canonical brief publication, current overview, saved human priority, structural parallel preview, legal-action discovery, exact attempt inspection, correction context, immutable-artifact verification, preparation and attempt authority, lifecycle transition, worker dispatch, candidate-bound review publication, and restoration of an explicitly inspected protected candidate into a caller-selected clean checkout. Pinboard is an application and plugin, not a supported Python library: `python -m pinboard` aliases the CLI and `python -m pinboard.mcp` aliases the MCP server; internal modules and package exports are not public extension APIs.

Codex is the primary, stress-tested integration. Claude Code support loads the same repository root through `.claude-plugin/plugin.json`, whether installed from a marketplace or loaded with `--plugin-dir`. Both use the same launcher, MCP entry, skills, schemas, and SQLite authority. Claude's installed host-only hook boundary independently decodes SessionStart, SubagentStart and PreToolUse records, validates required fields and ignores unrelated extensions. SessionStart supplies the current parent event's actual local session identity and the executing machine's stdlib hostname as native additional context. SubagentStart supplies only the launched worker's own identity; its verified dispatch host remains separate. A third PreToolUse entry emits an allow decision only for a well-formed event naming one of Pinboard's own MCP tools and emits nothing otherwise; Claude Code evaluates deny and ask rules regardless of the hook. None of these entries reads project state, settings files or grants lifecycle authority. Runtime-specific identity sourcing, worktree, subagent, permissions beyond Pinboard's own tool approval, waiting, and optional messaging remain outer integration responsibilities; they create no separate application, domain or lifecycle policy.

SQLite is authoritative for lifecycle, accepted scope, dependencies, mutation authority, and history. Attempt continuation is a read-only projection of current SQLite facts and verified artifacts. Review submission first publishes one strict immutable candidate snapshot, then atomically accepts its reference with the review transition. Attempt inspection and review jobs resolve that same verified snapshot; review jobs may publish an immutable reviewer prompt and accept its artifact reference, but they do not mutate lifecycle or candidate state, change attempt authority, write repository files, affect Git, or add another workflow owner.

Each invocation resolves two Git-backed roots. The **source checkout root** is the selected checkout's exact top level, including a linked worktree, and owns project-file and authority reads for that attempt. The **shared repository root** comes from the Git common directory and owns shared Pinboard state and local Git exclusion. The roots are equal in a primary checkout and deliberately different in a linked worktree. Activation observes the source checkout's current branch and full HEAD through the same file adapter, then the shared lifecycle adapter compares those facts and every reviewed authority with the accepted brief before constructing the domain command.

Root selection does not require an unused external work-root parent to exist. `DurableRoots` alone derives the database path. State-independent commands stop after lightweight selection. Database-backed CLI commands cross one outer work-state boundary that validates the immutable layout, constructs one `SQLiteWorkStore`, and supplies that layout and storage-independent capabilities to the workflow. Thematic handlers neither reconstruct infrastructure nor import the concrete store; composition uses required parameters rather than globals, optional fallbacks, or a dependency-injection framework.

Agent guidance is a separate dependency graph. The nearest project `AGENTS.md` keeps passive answer, explanation, review assessment, and diagnosis requests inspection-only. An explicit human-owned PR review request may record review evidence through its separate route without authorizing implementation edits. After a human implementation change request, the route requires an advance announcement of the Pinboard-item or direct implementation path before the first implementation repository write. Pinboard's source repository carries this route. Guidance does not intercept or authorize repository writes; already authorized direct implementation remains available without repeat approval.

During requested Codex setup, the main skill selects its setup-and-transitions reference, which announces and adds or reconciles the same thin route in the target project. `pinboard init` only initializes the work root, and existing projects are not retrofitted automatically. The optional Maintaining Agent Guidance skill recommends route placement during read-only assessment and edits it only with guidance-edit authority.

Installed MCP entry instructions direct saved-work questions, including quick read-only status, through complete main-skill loading and the selected phase reference. The status phase reads the overview for the live picture, the exact item's `review_verdict` for current-attempt review claims, and the exact attempt's authority status before worker claims. The verdict describes the nonterminal attempt; a terminal item has no current attempt, so `none` does not deny historical exact coverage. Claims about an earlier candidate or merged commits use selected available evidence for that subject and time, preserving verified coverage and qualifying unavailable or conflicting coverage. Informal favorable notes do not replace commissioned ready recording or completion. Explicit human retention or deferral keeps its accepted effect even when the change remains outside the product. Replies distinguish unresolved landing choices from retained work and merged-but-unreviewed work from implementation in flight. Overview omits review verdicts and reports preparation authority separately; neither omission nor a preparation release or revocation establishes a worker or review fact. Rejected reads leave those facts unknown. The resulting reply states only observed product and review status, and each separate human decision carries its own recommendation or default. Loading and narration remain agent guidance; existing status outputs, schemas, callbacks and registrations retain their current contracts.

The main skill loads for planning or ideation about saved items and for product, roadmap or architecture discussion in a Pinboard-managed project. It coaches discussion points individually, parks unsettled points without treating acknowledgment as agreement, pauses questions and tools on a slowdown request, and asks conversationally after readiness. It carries settled decisions into accepted work without creating discussion-only items. The main question policy and its native runtime caller require long or context-heavy questions in concise ordinary chat, an ended turn, and stopped tool work until the human answers. Timed, countdown, and asynchronous popups are excluded for those questions; silence, expiry, preselection, and unread prompts supply no response or approval. Short optional clarifications retain permitted native questions and independent authorized work, subject to the host tool’s purpose, mode, and permission limits. The main skill owns route choice and the human's picture of commitments: the agreed outcome and where it lands, current activity, where results live and whether they reach users, and what remains open. One section keeps that picture visible through a start-and-change statement, a `Still open:` line only when something is open, status words that name their subject and review coverage, a check of what the human's message presupposes, and acknowledgement only for costly or hard-to-undo assumptions. It also owns shared interaction style, decision-sized collaboration, asking for input only when the answer can materially change the work, the single rule that keeps Pinboard mechanics out of replies, verified readable-artifact links on every item or evidence mention, human task starts, review-actor language, current-responsibility routing, exact item-status reads for workflow endings, and human-authorized repository wrap-up. Its always-loaded core supplies these conversation rules and a phase index. On-demand references own status and selection, setup and transitions, consolidation, preparation and dispatch, review and repository disposition, and invocation evidence. Parallel work and state recovery retain their existing reference owners. Preparation mechanics include Git-baseline and checkout confirmation and bounded checkout-risk assessment; late-direction reconciliation, definition and brief replacement, and repository wrap-up mechanics live with review and disposition. Approval stays bound to its originating question and effect across long gaps; human-waived agent gates are released while human-set scope stays fixed. Originating reports reach wrap-up, and planned fixes and follow-up-worthy observations require a verified fix, exact live linked owner, or human-agreed drop. Private runtime memory and terminal history are not owners. Favorable review directs agent-owned repository reconciliation before an unresolved human landing choice, and isolated changes have their product status stated before integration. Plain merge requests retain the repository-action route. Intake, delivery, and parallel-work guidance remain specialized callers that report through that owner.

The main skill also owns assurance. Defects and accepted guarantees remain blocking. A material new concurrency, durability, security, adversarial, platform, or compatibility guarantee needs accepted product evidence or one concrete human scope decision before it enters implementation or review. Beside the architecture checkpoint, an opportunity checkpoint has agents name, before implementation only, an agreement that blocks a clearly better outcome, who introduced it, and the gain and cost of revising it, as a suggestion that leaves accepted scope unchanged until the human decides. Repository wrap-up composes runtime-owned task occupancy, Git integration, worktree and local and remote branch cleanup, and the Pinboard terminal transition without moving Git behavior into Python or adding lifecycle state.

For cross-boundary work, preparation freezes accepted semantics, assurance, stable authorities, constraints, and uncertainty without predicting every implementation file. Delivery derives the concrete impact and reads outward when a changed relationship or uncertainty exposes another owner. Separate review starts from changed and unclassified surfaces, reuses unchanged evidence, and widens for architecture, persistence, wire, lifecycle, dynamic-consumer, or demonstrated-blind-spot conditions. Specialized skills retain their own evidence and blocking outcomes without duplicating narration policy, a hard-coded impact graph, checkout ownership, Git integration, or wrap-up state.

The development-only behavioral harness exports exact revisions, seeds disposable projects through their own launcher and MCP boundary, drives scripted CLI turns, records loaded context and replies, and applies the frozen blind scorer and maintained variability criteria. Its existing process owner constructs the clean Claude OS/login environment for agent, version, scorer and assessor calls. Real HOME retains local OAuth discovery and documented authentication-only ANTHROPIC_API_KEY passes when present; desktop, messaging and session variables are stripped and account connectors are forced off. Agent sessions retain the exact passed environment for a names-only inventory, then verify exported plugin, hook, MCP and skill provenance before scored replies are accepted. Credential values and Claude credential files are not evidence artifacts. Live login evidence establishes the OS/local OAuth path, not every provider. Before each paid Codex delivery run through `runner.codex_run`, including bounded coverage, the shared runner requires a complete CLI version observation and requires an already passing isolation probe for that version, exact export commit and skills digest, model and reasoning effort. Missing, failed, incomplete or mismatched evidence stops before an agent turn and directs the caller to the explicit probe command. A later probe cannot qualify earlier runs, and this observation does not guarantee the executable remains unchanged during a run. The separate investigation path observes the version, checks rendered context, and reaches `run_turn` without a prior-probe requirement. Its context checks remain distinct from delivery eligibility. Probe records retain their existing typed inventory shape. Codex retains its disposable-home, refusal and credential-settlement owners; its coding-agent context and parent environment are not described as fully stripped. Scripted gaps and slowdown turns do not establish actual compaction or live-input cancellation.

Technical Writing owns composition for substantial technical documents and human-facing artifacts. It uses collaborative composition while material choices remain open and quiet production when accepted facts are sufficient. Pinboard selects it automatically for clear document work and permits explicit selection for ambiguous cases; readable artifacts and pull-request descriptions use quiet mode during delivery and wrap-up. Routine status, intake, lifecycle, implementation, and review coordination do not load it. Existing document, repository, brief, review, and machine-consumed artifact owners remain authoritative for facts and structure.

The repository-care skills are independent guidance owners. Repository Readiness owns unfamiliar-repository assessment, authority mapping, coverage modes, developer navigation, and the storytelling lens. Slop Cleanup owns recursive removal of approved unsupported residue and its deletion fixed point. Maintaining Agent Guidance owns placement and reconciliation of durable AI-facing guidance. They may refer to one another or use Pinboard, but none requires a sibling skill or ledger for its baseline workflow.

`DESIGN_PRINCIPLES.md` owns the reusable supported-reality and canonical-naming rule. Slop Cleanup applies it through a semantic maintenance-cost pass and the bundled generic and Python-AST inventory. Both inventory modes use one ordered declaration of every supported product root plus the separate test root and must report the same input digest. The helper exposes mechanical candidates and explicit coverage limits; a private disposition ledger owns repository-specific producer, consumer, boundary, retained-data, protocol, exception, removal, and consolidation evidence. No count or match mutates production scope by itself.

One work root has three durable roles:

```text
.pinboard/
  state.sqlite3   # authoritative lifecycle, dependency, authority, and history state
  artifacts/      # immutable long-form bytes referenced by SQLite
  views/          # repairable Markdown and HTML projections generated from SQLite
```

## Dependency direction

Pure decisions remain at the center:

```text
cli ──┐
      ├────────────> application ────────> domain
mcp ──┘                    ▲                  ▲
  └────────────────> adapters ───────────────┘
```

`domain` depends only on the Python standard library and `msgspec` for exact canonical records. `application` depends on domain values and storage-independent capability protocols. `adapters` implement those capabilities with SQLite and the filesystem. `cli` and `mcp` are sibling outer boundaries: each decodes its transport, composes concrete adapters with shared application use cases, and presents transport-specific results without importing the other. Production dependency tests keep domain independent of outer layers, application independent of adapters, CLI, and MCP, and adapters independent of both interfaces. They also keep CLI composition acyclic, constrain `cli.entrypoint` to routing and final error presentation, and verify both installed entries.

The method used to preserve these boundaries, expose effects, and stop decomposition at a useful fixed point is recorded in [the design principles](DESIGN_PRINCIPLES.md).

## Runtime ownership

### Launcher

The `scripts/pinboard` launcher resolves runtime state only below its own plugin-version or source root. Ordinary CLI arguments select `pinboard`. Exact startup selectors choose independently installed entries: `--mcp` selects `pinboard-mcp`, `--claude-session-start` selects `pinboard-claude-session-start`, `--claude-subagent-start` selects `pinboard-claude-subagent-start`, and `--claude-pre-tool-use` selects `pinboard-claude-pre-tool-use`. Claude selectors reject additional arguments before effects. MCP accepts either no additional arguments or the complete explicit capture declaration `--capture-evidence-dir <existing-directory> --safe-to-persist-exactly`; every incomplete or invalid declaration rejects before server startup. A source checkout prepared by `scripts/prepare-worktree` uses its development `.venv` when the selected executable is available. Otherwise, ordinary launch requires `.pinboard-runtime/.pinboard-ready` plus only the selected private executable, so a ready marker written before `pinboard-claude-pre-tool-use` existed still serves `--mcp`, `--claude-session-start` and `--claude-subagent-start`, while `--claude-pre-tool-use` is not ready until `--prepare-runtime` installs its executable; `--prepare-runtime` verifies every entry before rewriting the marker. When uv is available, an unprepared `--mcp` invokes the same `--prepare-runtime` path, whose version-local `.pinboard-runtime/.preparing` lock serializes all preparation callers, and starts `pinboard-mcp` only after runtime-ready. Missing uv or a held lock returns one strict unchanged `pinboard-launcher-result/v1` result on stderr without starting Pinboard; a failed preparation or invalid readiness may have changed `.pinboard-runtime` and reports that surface. MCP stdout remains empty. CLI prestart recovery uses stdout; Claude SubagentStart and Claude PreToolUse prestart recovery use stderr and leave their protocol stdout empty, so an unprepared version emits no permission decision and Claude's normal flow decides. Claude SessionStart prestart recovery is the one exception: when uv is available it invokes the same explicit `--prepare-runtime` path in a child launcher and on `runtime-ready` executes the prepared parent entry with `PINBOARD_RUNTIME_PREPARED_NOW=1`. Without uv, with a held lock, or after a failed preparation it writes the stderr result and emits one strict SessionStart additional-context record on stdout naming the cause and the exact manual command, exiting 0, because that hook's stdout is the agent's context channel rather than a protocol stream.

Exact CLI process capture uses one launcher wrapper. The manual form is `scripts/pinboard --capture-evidence <file> --safe-to-persist-exactly -- <normal arguments>`. For a normal CLI call, the launcher resolves the selected work root's contributor setting and item override using Git's config grammar. Before Python preparation, it creates an absent settings file privately at mode `0600`, validates its existing keys, writes a missing project mode with a key-level Git config operation, and reads the stored mode. With a selected runtime, the installed CLI entry also owns project resolution and private destination checks; without one, the launcher applies those checks and captures the strict runtime-preparation-required result. Effective on selects a unique file in the selected root's private `invocation-traces/` directory and enters the same wrapper; off invokes the CLI directly. Invalid settings or an unusable private destination reject before the target runs. The wrapper rejects MCP and Claude hook startup selectors in manual mode, validates the absent selected file and existing parent, keeps sensitive staging in that parent, and reserves mode-`0600` publication. It invokes the CLI target or prestart launcher exactly once, preserving the original launcher argv, stdout and stderr bytes, and exit status. `HUP`, `INT`, and `TERM` are forwarded to the child. Successful publication links the file immutably, replays each stream once, and returns the original status. A post-target publication failure reports potentially changed aftermath and forbids replay. Automatic capture prunes older automatic files to the newest 100; manual destination and retention remain caller-owned. The wrapper records no environment values.

Explicit `scripts/pinboard --prepare-runtime` is the only launcher path that invokes uv; Codex `--mcp` and the Claude SessionStart hook reach uv only by re-invoking that path. It synchronizes locked production dependencies into `.pinboard-runtime`, verifies the real CLI entry and availability of the MCP executable and the three Claude hook executables, and writes the ready marker last. `--prepare-runtime`'s already-ready early exit reuses an existing marker only when all five executables are present and otherwise re-prepares. Preparation does not run protocol or hook entries with `--version`, because they do not support that argument. Packaged code, skill assets, and a ready private runtime are immutable inputs during ordinary commands. Project-owned SQLite, artifacts, and views remain below the selected work root, separate from both Pinboard runtime environments.

### Domain

`domain` owns immutable identifiers, ledger values, canonical history records, and pure decisions. It does not read files, issue SQL, parse command-line or JSON input, render views, or coordinate transactions.

`WorkItemId` is the domain identifier for a `WorkItem`. Action subjects and work-item changes use that type; `TaskId` identifies the acting task. Public and stored `item_id` spellings are converted at their respective boundaries.

| Owner group | Responsibility |
| --- | --- |
| `work_models.py`, `ledger.py`, `identifiers.py`, `errors.py` | Work-ledger values and canonical artifact kinds, read-only snapshot behavior, opaque identifiers, expected decision failures, exact mismatch facts, effect disposition, retry classification, and recovery-action receipts |
| `decision_models.py`, `decisions.py` | Closed item and attempt commands, explicit lifecycle-change variants, and lifecycle, dependency, requirement, and review legality, including the shared project-attempt action decision used by global and exact reads |
| `authority_models.py`, `authority_decisions.py` | Closed ready-item preparation and attempt authority operations, lifecycle, and fencing |
| `proposal_models.py`, `proposal_decisions.py` | Closed proposal creation values, ready queue placement, relation-derived dependency decisions, and versioned planned-replacement decisions that bind the new proposal item to its affected item and practical replacement cost |

Expected rejections return typed failure values. Domain and stale-persistence paths use `DecisionFailure`; application-owned queries and dispatch selection preserve their own exact failure families. Application publication also returns typed failures for classified acceptance and post-publication infrastructure faults, with exact effect and retry facts. MCP projects these into correlated native results and names the failing phase of immutable publication, reference acceptance, or dispatch authority recheck while retaining every invocation-owned published selector. The CLI presents command, work-brief, and committed-initialization failures through its outer presenter. Low-level decoders may raise while values remain external representations, but an installed use case converts its exact advertised invalid-input outcomes into its typed result. Adapter exceptions remain at effect boundaries until a receiving use case assigns effect, retry, recovery, or stable diagnostic meaning. Persisted invariants and programming defects retain traceback behavior.

### CLI

`cli` owns the installed human-maintenance boundary, not agent workflow discovery or execution. It composes application use cases and concrete adapters without owning lifecycle legality or persistence policy. Its twelve command names are `root`, `init`, `status`, `diagnose`, `validate`, `views rebuild`, `export`, `close`, `migrate-work-root`, `migrate-schema`, `tool-contract` and `code-catalog`. Each migration has preview, apply and reverse command forms, selected as exact typed leaves. Help, version and module entry remain available.

The `close` leaf decodes its public `item_id` into `WorkItemId` before selecting the action. Its result keeps the public `item_id` spelling.

The launcher's optional exact process capture remains outside this command grammar. It observes one complete normal CLI process, including parser rejection and prestart failure, without adding a command leaf or changing `entrypoint.py` output. MCP and Claude hook startup remain protocol-specific paths and cannot be selected through CLI capture.

| Owner group | Responsibility |
| --- | --- |
| `cli_commands.py`, `cli_parser.py` | Exact frozen leaf records, strict field constraints, one required resolved-root configuration and parser selection before dispatch; only CLI convenience options have defaults |
| `entrypoint.py`, `cli_output.py` | One exhaustive leaf route, process exit policy, canonical success output and exact structured failures; invalid or retired grammar rejects before root or storage work |
| `tool_contract.py` | State-independent CLI-only operation index and selected details derived from the installed leaves: actual syntax, data scope, effect and retry; unknown selectors reject without resolving roots |
| `code_catalog.py` | State-independent failure and event lookup assembled from typed code vocabularies, neutral MCP diagnostic declarations, and receipt emitters; code meanings live with their definitions, and generic recovery defers to each result's exact facts |
| `work_inspection.py` | Current-project summary status from bounded state counts and active-attempt identities, and the explicit project-wide diagnosis from full validation, unfinished work, and the ten newest transition receipts; its frozen read views live at this owner |

## Storage boundaries

### Authoritative SQLite state

`.pinboard/state.sqlite3` owns project revision and host epoch; immutable work-item definition revisions; item, attempt, dependency, requirement, and proposal state; versioned planned-replacement relations and exact-revision temporary-retention dispositions; preparation and attempt authority; accepted artifact references; and transition history. Schema `sqlite-v7` includes a partial item-leading index for exact current-attempt and current-portfolio reads, a dependency-leading `(dependency_id, item_id)` index so a committed effect can discover only the live item views whose eligibility changed, a checkpoint-history subject index for selected acceptance receipts, and lease-identity indexes so leased action discovery reaches only current subjects selected by the supplied lease and generation. Every retained attempt or preparation lease must have its exact current generation anchor before application code can consume it. Relational dependency rows are the query-efficient projection of the current definition and must match it exactly. Mutable action receipts carry the selected item's, attempt's, or proposal's subject revision; leased receipts also carry the exact lease identity and generation. The project revision identifies committed state and history, not action freshness. An ordinary mutation opens one write transaction, reads the selected subject and direct decision relationships, allocates one project revision and receipt, updates only the relations named by the accepted closed mutation, validates exact changed facts, and returns the receipt plus affected item and attempt identities. Authority, subject-revision, commit-revision, and affected-row guards return typed stale or fencing rejections. Expected failures and infrastructure failures both roll back without assembling complete state before or after the effect. SQLite read-only failures retain the exact database path at the connection-and-transaction owner; the command boundary adds the exact operation and narrow Codex permission recovery derived from the database's parent work root, classifies the unchanged ledger as non-retryable, and preserves any earlier immutable-artifact publication as a separate committed surface. Initialization creates the exact empty current schema directly; complete state enters ordinary storage code only through validation.

Human-owned PR review uses the existing sqlite-v7 item and transition-history relations. A review item has state `review` without an attempt. Its canonical brief, separate brief review, observed heads, rounds, and human-directed close are strict append-only history inputs. Each write advances the item's subject revision and project revision in one transaction. Focused item status and explicit validation check the review relations; export carries their original full commit identities and evidence. An implementation attempt cannot use this route, and a review-only item cannot enter candidate review.

### Generated views

`.pinboard/views/` is human-readable output derived from SQLite and accepted artifact references. Declared selectors are `items/<item-id>.md`, `attempts/<attempt-id>.md`, immutable `history/<history-id>.md`, and the two live-board projections `board.md` and `board.html`; queue position lives in each item view, the board projections, and explicit overview output. Aggregate `queue.md` and `history.md` are no longer declared projections. The only times the projections render come from the live item rows: each live item's stored `updated_at`, which changes on state changes, pauses, resumes, definition revisions, and dependency changes but not on reordering, and one board-updated time, the latest of those values among the live items shown, absent when no live item is shown. The board-updated time therefore ignores commits that change no item, such as artifact-only commits from dispatch, review jobs, and brief reviews, and may move earlier when the most recently changed item leaves the board. Neither time is a transition-receipt time or a strict last-state-transition time. The projections render no lease, preparation, or other operation-time value and no process-timezone or locale formatting, so one snapshot yields the same bytes at any operation time and in any writing process's timezone. `board.md` groups live items as paused or in review, in progress, ready, and blocked or deferred, with state, the item's change time, the dependency reasons of only the dependencies that still apply, meaning live items on the board, and a relative link to each item view, and states the board-updated time; it writes every time as absolute UTC with an explicit UTC label. `board.html` is one self-contained offline page with inline CSS, script, and board data; it embeds that data as JSON with `<`, `>`, `&`, U+2028, and U+2029 escaped, including the same times as UTC instants and every dependency of each item ordered with those that still apply first and solved terminal ones after, keeping stored order within each group, inserts item text only as text, offers text and state filtering, a tile preview that lists only the dependencies that still apply and nothing for an item whose dependencies are all solved, and item detail that lists every dependency in that order, and never changes board state. Each tile shows the title on the left and the state badge on the right in a column of one width shared by every state so titles line up across tiles, the item codename on its own line below the title, and the item's time right-aligned on that line with no static label. In the browser every time is shown in one page-wide form, initially a relative age computed against the browser clock, otherwise the absolute time in the browser's local timezone; each time's tooltip reads Last update followed by the form not currently visible. Clicking any time, including the board-updated time, switches every time on the page between the two forms together; the choice resets on reload, and neither filtering nor the page's about-once-a-minute re-render of relative ages, which needs no reload, changes it. Each board write holds an exclusive `fcntl.flock` lock on the undeclared `views/board.lock` from before the live-portfolio read until both files are replaced, so overlapping refreshes leave the board on the later commit; the kernel releases the lock when its holder exits, and no SQLite transaction stays open during rendering or file writes. Every item view presents the intake-time next action and notes only in an original-intake-context section, never as the current next action. Review-only item views render the recorded brief, its independent review, every observed head and round, and the human's final disposition from transition history. The native `pinboard_pr_review` status gives the structured current view, including a newer observed head that has not been reviewed.

### Project evidence boundary

Pinboard does not require a companion notes directory. Project documentation and other human-owned notes remain outside the installed runtime contract. The optional Investigation Focus skill can deliver a clear bounded request directly or guide a caller-owned inquiry note in a selected local home separate from evidence sources when continuity is needed. The note is neither accepted Pinboard ledger state nor an application-validated evidence graph. Manual caller-selected CLI or MCP capture remains private evidence at its selected destination. Contributor automatic traces live in the selected work root's `invocation-traces/` directory under a mode-`0700` directory and mode-`0600` files, with a 100-file retention limit. Both modes remain outside accepted ledger semantics; placement inside a work root alone grants no authority. Durable execution semantics enter Pinboard only through accepted immutable artifact references created by an existing authorized operation.

## Representative flows

### Human-owned PR review

For a ready item whose change is already authored in a human-owned PR, the native `pinboard_pr_review` route records a canonical brief bound to the current item definition, the PR, requirement sources, expected behavior, consumers, owners, and applicable repository criteria. A different reviewer records a ready verdict before the first round. The coding harness supplies a full observed commit and its provenance; a review round cites that observation, the reviewed brief, findings, limits, and dispositions of every finding from the previous round. The SQLite adapter compares the item's subject revision and appends the typed evidence in one transaction. Generated item and history views then expose the accepted facts, while explicit validation and export reread the same history. The route creates no worker, attempt, lease, candidate, or Git effect.

When the harness observes a newer head, native status identifies it as unreviewed. Another round reviews that exact head, or the human explicitly directs closure at the prior reviewed head. The human may also close before any round. Closure records every final finding disposition when findings exist, residual concerns, and any observed but unreviewed head. A zero-round close explicitly states that no PR head was reviewed. It terminally closes the item and prevents further rounds. The separate implementation flow below retains its own candidate review and authority rules.

### Intent and ordinary attempt start

The main Pinboard skill classifies the human request before loading delivery mechanics. Passive answers, explanations, review assessments, diagnoses, named-context orientation, and waits use bounded reads without implementation edits. An explicit human-owned PR review request follows its review-only flow above and may record review evidence. Implementation and revision requests enter delivery normally after advance disclosure of the implementation route.

When implementation selects a new isolated worktree, the repository-owned `scripts/prepare-worktree` command first checks its uv and npm host prerequisites, then runs `uv sync --locked` and `npm ci --prefer-offline --no-audit --no-fund` from that checkout. The resulting ignored `.venv` and `node_modules` directories remain checkout-local; only package-manager caches may be reused.

The runtime adapter owns [source-worktree setup recovery](skills/pinboard/references/runtime-adapters.md#source-worktree-setup-recovery). After bounded diagnosis identifies a sandbox permission restriction, already-authorized setup can request one runtime-reviewed retry of the same command without a separate conversational confirmation. Runtime approval controls execution. Denied or unavailable permission, genuine setup failures, failed retries, and scope changes return to the human for a bounded decision before Pinboard preparation or implementation-source work. This recovery leaves installed-runtime preparation and protected ledger-write contracts unchanged.

A task that changes this setup path or another tool needed to assess itself records successful base preparation before editing. Stable installed tooling may continue to coordinate Pinboard state, but only direct source or built-candidate execution supports the changed behavior.

Preparation selects a typed checkpoint before publication. A README edit plus its referenced image may use the local checkpoint when both retain one owner and change no behavior, dependency direction, stored or wire identity, or independent consumer; any failed condition selects the cross-boundary path and its independent brief review. Mandatory verification remains hierarchical prose evaluated against repository authority. If a required tool cannot be resolved, preparation stops for an explicit human choice to abort, authorize one investigation or retry, or revise the accepted scope and evidence contract; it does not infer a fallback.

After brief publication, activation accepts only the accepted brief reference. The outer transition boundary decodes the canonical current brief, requires its owner to match the preparer's live authority, derives attempt, branch, base, and owner facts, and validates every declared reviewed authority. A shared Git observer classifies the primary checkout as `main` regardless of its current branch and classifies only a registered linked worktree of the same common repository as `isolated`; unsupported layouts reject. Activation, rebind, replacement-brief resume, and dispatch require the brief's exact current definition and recorded checkout selection to match that observation while retaining their existing identity, lineage, and authority guards. Only then does the existing locked activation decision revalidate the definition and preparation pin and atomically create the attempt. A failure before that transaction leaves the item ready and the preparation claim live. The outcome owner then selects project-only dispatch for the stable checkpoint. Dispatch publishes or reuses the immutable worker prompt reference and returns the native launch envelope; local dispatch needs no brief-review evidence, while cross-boundary dispatch publishes or reuses its ready review, reselects current authority internally, and performs its independent source revalidation. The runtime launches a fresh worker, which verifies the accepted prompt publication, reads that exact prompt and canonical brief as its direct task, loads the complete delivery skill, then uses its post-launch identity to acquire attempt authority and select leased continuation. Exact definition v1 and brief v2 bytes remain readable, reviewable, projectable, validatable, and exportable under explicit legacy-unrecorded policy, but they cannot authorize these execution operations.

### Initialization and reopen

`pinboard init` resolves the default `.pinboard` root below the shared repository root, then idempotently adds only `/.pinboard/` to that repository's local Git exclude file before initializing the work root or SQLite. Invoking initialization from a linked worktree therefore reuses the repository ledger and does not create a worktree-local authority. It never edits a committed `.gitignore`, so unrelated `.codex` content remains visible. Fresh default initialization receives one exact command approval for its combined `.git` and `.pinboard` writes; returning and routine commands do not retain `.git` authority. A typed effect wrapper spans storage, accepted-brief rendering, and generated-view refresh after those writes. JSON reports exactly the surfaces newly committed before a known later failure: `repository-git-exclude` with its exact path and entry, plus `ledger` with its database path when fresh database publication completed. Before publication, the authoritative ledger remains absent; after publication it remains available even when replaceable view refresh fails. A repeat that adds no exclusion and publishes no database reports an unchanged rejection. CLI-owned work-state composition creates the SQLite schema when `state.sqlite3` is absent. When the database exists, it verifies that exact schema before reconciling the fixed publication staging path: a same-file staging alias left after publication is removed, while a different-file conflict is rejected without replacement. It then ensures the artifact directories exist and rebuilds views. Routine recovery selects relative `.pinboard` for a normal default checkout, the exact absolute shared-repository work root for a linked worktree, and the exact selected directory for an explicit `--work-root`. Only after a successful fresh initialization and its receipt, the outer work-state CLI module prints one optional repository-care pointer. The default Codex runtime may also read the user Codex config to recommend `body_after_prefix` when that user default is absent; the explicit Claude runtime suppresses only this Codex-specific line. The pointer starts no skill or work, and neither effect writes configuration. A trusted project's `.codex/config.toml` may override the Codex user default. Resume and failure paths print neither effect; unreadable or malformed user config suppresses only the setting recommendation.
