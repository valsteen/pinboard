# Architecture

## System overview

Pinboard is a local coordination system for one repository-owned work ledger. The installed `pinboard` command discovers the project, opens its work root, reads and validates current state, computes legal actions, and applies accepted changes atomically. Pinboard is an installed application and plugin, not a supported Python library: its production interface is the `pinboard` CLI, with `python -m pinboard` as an alias to that same interface; internal modules and package exports are not public extension APIs.

Codex is the primary, stress-tested outer integration. Claude Code can load the same repository root experimentally through `.claude-plugin/plugin.json` and `--plugin-dir`; both integrations call the same launcher, Python entry point, skills, schemas, and SQLite authority. Runtime-specific identity, worktree, subagent, permission, waiting, and optional-messaging operations stay in the agent-facing runtime adapter rather than entering the Python dependency graph or creating another lifecycle.

SQLite is the authority for the repository work ledger. Attempt continuation and review jobs are read-only projections from current authoritative state and verified accepted artifacts; they add no lifecycle state or stored workflow owner.

Each invocation resolves two Git-backed roots with different owners. The source checkout root is the current or explicitly selected checkout's exact top level, including a linked worktree, and owns project-file and authority reads for that attempt. The shared repository root is derived from the Git common directory and owns repository-shared Pinboard state and local Git exclude configuration. In a primary checkout the two roots are equal; in a linked worktree they are intentionally different.

Root resolution produces the source checkout, shared repository, and intended work root without requiring an unused external work-root parent to exist. `DurableRoots` is the single owner that derives the authoritative database path. State-independent commands stop at lightweight selection. For a database-backed command, the outer work-state boundary validates one immutable durable layout, constructs one `SQLiteWorkStore`, and passes the same layout plus storage-independent required capabilities through the complete workflow; thematic handlers neither reconstruct infrastructure nor import the concrete store. This is explicit composition through ordinary required parameters, not global state, an optional fallback, or a dependency-injection framework.

Agent guidance has a separate dependency boundary from the Python runtime graph. Repository guidance routes a task to the installed Pinboard skill before read-only work becomes repository writes and while accepted repository work awaits human disposition; the Pinboard delivery and intake skills remain specialized callers. The main skill owns the shared threshold for user-relevant process detail, human task-start routing, explicit review-actor language, current-responsibility routing, preparation start, project-specific Git baseline inference and checkout confirmation, bounded checkout-risk assessment, reconciliation of late accepted direction with the current brief and candidate, and human-approved repository wrap-up. Specialized skills retain their distinctive evidence and blocking outcomes without creating separate narration policy, persistent checkout ownership, or wrap-up state.

The bundled repository-care skills are independent guidance owners. Repository Readiness owns assessment of whether an unfamiliar repository can be changed reliably, including its authority map, coverage modes, developer-navigation method, and storytelling lens. Slop Cleanup owns recursive removal of approved unsupported residue and its deletion fixed point. Maintaining Agent Guidance owns placement and reconciliation of durable AI-facing guidance. They may refer to one another or use Pinboard for coordination, but no sibling or ledger is required for their baseline workflow.

One work root has three durable roles:

```text
.codex/pinboard/
  state.sqlite3   # authoritative lifecycle, dependency, authority, and history state
  artifacts/      # immutable long-form bytes referenced by SQLite
  views/          # repairable Markdown projections generated from SQLite
```

The architecture map is semantic rather than an exhaustive file tree. It names the owners and dependency boundaries a contributor needs to preserve; leaf modules that do not change those relationships need not be listed individually.

## Dependency direction

Pure decisions remain at the center:

```text
interfaces ────────> application ────────> domain
     │                    ▲                  ▲
     └────────────> adapters ───────────────┘
```

`domain` depends only on the Python standard library and `msgspec` for exact canonical records. `application` depends on domain values and storage-independent capability protocols. `adapters` implement those capabilities with SQLite and the filesystem. `interfaces` decode external values, compose concrete adapters with application use cases, and present results. Production dependency tests keep domain independent of outer layers, application independent of adapters and interfaces, and adapters independent of interfaces. They also keep interface composition acyclic and constrain the CLI entry point to routing and final error presentation.

The method used to preserve these boundaries, expose effects, and stop decomposition at a useful fixed point is recorded in [the design principles](DESIGN_PRINCIPLES.md).

## Runtime ownership

### Launcher

The plugin `scripts/pinboard` launcher prefers the package already installed in the plugin cache's ready environment. When executed from a source checkout without that installed environment, it falls back to the repository's locked uv execution path. This keeps ordinary installed use independent of ambient uv cache selection while preserving one source-development route on macOS and Linux.

### Package root

Only distribution version lookup and command composition live at the package root.

| Location | Ownership |
| --- | --- |
| `pinboard/__init__.py` | Installed distribution version lookup |
| `pinboard/__main__.py` | `python -m pinboard` route to the CLI |

### Domain

`domain` owns immutable identifiers, ledger values, canonical history records, and pure decisions. It does not read files, issue SQL, parse command-line or JSON input, render views, or coordinate transactions.

| Owner group | Responsibility |
| --- | --- |
| `work_models.py`, `ledger.py`, `identifiers.py`, `errors.py` | Work-ledger values and canonical artifact kinds, read-only snapshot behavior, opaque identifiers, expected decision failures, exact mismatch facts, effect disposition, retry classification, and recovery-action receipts |
| `decision_models.py`, `decisions.py` | Closed item and attempt commands, explicit lifecycle-change variants, and lifecycle, dependency, requirement, and review legality, including the shared project-attempt action decision used by global and exact reads |
| `authority_models.py`, `authority_decisions.py` | Closed ready-item preparation and attempt authority operations, lifecycle, and fencing |
| `proposal_models.py`, `proposal_decisions.py` | Closed proposal intake values, intake queue placement, and relation-derived dependency decisions |
| `history.py`, `definition_decisions.py` | Canonical work-item definition records and digests, immutable revision legality, dependency replacement and cycle decisions, and receipt relationships |

Expected rejections return typed failure values. Domain and stale-persistence paths use `DecisionFailure`; application-owned queries and dispatch selection use their own closed failures where the installed interface must preserve a more specific public error. The interface returns closed command, proposal, and dispatch failures through one CLI presenter. Low-level decoders may raise while values are still external representations, but an installed use case converts its exact advertised invalid-input outcomes into its typed result. Infrastructure failures, malformed persisted relationships, and programming-contract failures remain typed exceptions.

### Application

`application` owns use-case sequencing, persistence contracts, read models, and cross-capability workflows. Ordinary use cases request operation-owned facts through storage-independent protocols and commit only closed accepted mutations. Validation alone receives complete stored state; other project-wide workflows receive their complete declared projection or exported-fact batches.

| Owner group | Responsibility |
| --- | --- |
| `stored_state.py` | Complete typed read aggregate plus storage-specific vocabulary |
| `mutation_models.py`, `mutations.py`, `ports.py` | Closed exact mutation and committed-effect records, exhaustive decision-to-relational conversion, storage-independent transactional and exact-read capabilities, validation-only complete state, project-wide projection facts, and exported-fact batches |
| `service.py` | Exact-fact locked mutation orchestration for ordinary work |

| `artifacts.py`, `artifact_publication.py`, `dispatch_models.py`, `dispatch.py` | Immutable artifact references and typed brief identity, artifact-acceptance capabilities, activation, resume, and rebind brief guards, and result-shaped dispatch selection, review publication, and final authority confirmation |

SQLite rows are not active domain objects. `StoredWorkState` is the exact typed read aggregate without SQL handles or filesystem paths, while live mutations carry only the accepted decision, receipt, and affected auxiliary values. `LedgerSnapshot` remains the storage-independent decision input.

## Storage boundaries

### Authoritative SQLite state

`.codex/pinboard/state.sqlite3` owns project revision and host epoch; immutable work-item definition revisions; item, attempt, dependency, requirement, and proposal state; preparation and attempt authority; accepted artifact references; and transition history. Schema `sqlite-v5` includes a partial item-leading index for exact current-attempt and current-portfolio reads, a dependency-leading `(dependency_id, item_id)` index so a committed effect can discover only the live item views whose eligibility changed, and lease-identity indexes so leased action discovery reaches only current subjects selected by the supplied lease and generation. Every retained attempt or preparation lease must have its exact current generation anchor before application code can consume it. Relational dependency rows are the query-efficient projection of the current definition and must match it exactly. An ordinary mutation opens one write transaction, reads the selected subject and direct decision relationships, allocates one revision and receipt, updates only the relations named by the accepted closed mutation, validates exact changed facts, and returns the receipt plus affected item and attempt identities. Revision, authority, subject-revision, and affected-row guards return typed stale or fencing rejections. Expected failures and infrastructure failures both roll back without assembling complete state before or after the effect. Initialization creates the exact empty current schema directly; complete state enters ordinary storage code only through validation.

### Immutable artifacts

Accepted requirements, briefs, results, reviews, and other evidence are immutable files below `.codex/pinboard/artifacts/`. Canonical v2 work briefs and independent brief reviews are strict JSON; SQLite stores each accepted artifact's kind, selector, revision, digest, and size. Attempts and history own the relationships they actually consume. The installed brief-publication path validates and canonicalizes a candidate, publishes immutable bytes, and accepts their reference without changing scheduling. Activation, resume, and rebind validate their selected v2 brief identity against the locked ledger snapshot. Readers resolve artifacts through accepted references and verify their bytes. The files do not independently own lifecycle state.

### Generated views

`.codex/pinboard/views/` is human-readable output derived from SQLite and accepted artifact references. Declared selectors are `items/<item-id>.md`, `attempts/<attempt-id>.md`, and immutable `history/<history-id>.md`; queue position lives in each item view and in explicit overview output. Aggregate `queue.md` and `history.md` are no longer declared projections. An ordinary commit returns exact affected identities, the interface reads only those projection facts and any selected live brief bytes, and atomic replacement compares bytes only at those selected paths. Equal bytes preserve the existing file, inode, and modification time. A live v2 attempt view contains a complete Markdown rendering of its canonical JSON brief; no runtime path reads generated Markdown for semantics. A successful SQLite commit is authoritative before refresh begins, and a refresh warning cannot undo it. Explicit `pinboard views rebuild` reads every declared item, attempt, and receipt projection but excludes unrelated authority history, state counters, proposal child collections, and artifact references; it removes the two legacy aggregates, reconciles every declared selector, and still preserves equal files. Validation distinguishes authoritative defects from stale or missing generated output.

### Project evidence boundary

Pinboard does not require or produce a companion notes directory. Project documentation and other human-owned notes remain outside the installed runtime contract. Durable execution semantics enter Pinboard only through accepted immutable artifact references.

## Known limitations and operating assumptions

These are evidence-backed boundaries of the current implementation. They are architecture facts, not a backlog: each remains deliberate while its stated consequence is acceptable, and its reopening condition identifies the observation that would justify reconsidering it.

| Current boundary | Practical consequence and affected paths | Why it is deliberate | Reopen when |
| --- | --- | --- | --- |
| Current live-portfolio projections | `overview`, project-role `actions` without an exact action identity, and empty-selection all-safe `parallel preview` read the current live portfolio because their result or decision ranges over that portfolio. Their work can grow with live items, open attempts, direct dependencies, open proposals, and current authority, but not with terminal attempt bodies, retained definition history, artifacts, or transition receipts. Exact action identity reads only its named subject; leased worker or preparer discovery uses indexed lease identity to read only selected subjects; observer and unleased denied roles read no project state. `status` reads live active-attempt identities plus a fixed closed set of transactionally maintained item-state counters, so its compatibility counts do not scan retained items. | These commands explicitly answer project-current questions; selecting less data would change their advertised result. Exact item, attempt, action-ID, leased-action, and selected-preview routes remain available for focused work. The status counter is stored because recomputing it would make a routine summary grow with retained history. | Reconsider with an observed live-portfolio latency or memory problem, or when the public contract gains paging or a required selection. |
| Focused validation detects only consumed facts | Ordinary selected reads and mutations validate the exact facts and relationships their result or decision consumes. Corruption outside that selected context can remain undiscovered until explicit `pinboard validate`. | Scanning unrelated rows during ordinary work would defeat operation-owned dataflow; the dedicated validation command owns complete integrity diagnosis. | Reconsider when a supported ordinary result depends on a wider invariant, or an actual corruption incident shows that a specific missing relation belongs in that operation's selected context. |
| Current-schema-only reopen | Runtime commands open exactly `sqlite-v5` and reject older or structurally different ledgers without modifying them. A schema upgrade therefore requires a quiescent, recoverable out-of-band migration before v5-only callers take over. | Pinboard has no external compatibility obligation yet, so a permanent legacy reader or migration framework would add unsupported architecture and hide which schema is authoritative. | Reconsider when a released predecessor has external users, rolling upgrades become supported, or more than one retained schema needs a product-owned migration path. |
| Fully materialized handover result | `pinboard handover --json` reads every exported lifecycle and transition relation, pending proposal and its child facts, and accepted artifact reference and bytes, then encodes one final canonical JSON value in memory. It excludes local lease/counter state and disposed proposal collections. The persistence/application boundary accepts batches, but the current SQLite producer emits one exact batch and the outer result is fully materialized. Export time, memory, and output size grow with exported retained facts. The owners are `application.handover`, `interfaces.project_handover`, the exact SQLite handover reader, artifact repository, and CLI JSON presenter. | The installed command intentionally produces one portable, exact, tool-neutral project package as a single canonical result, while the batch seam keeps progressive storage or projection possible without changing ordinary decisions. | Reconsider when observed handover size or memory prevents a supported export, or a supported consumer requires progressive transfer rather than one complete result. |
| Dense live-queue suffix updates | Inserting at a selected position or removing a terminal item changes every following live queue position. The committed effect therefore names that live suffix and focused publication refreshes those per-item views plus the new receipt; work grows with the semantically changed suffix, never with retained history. | Contiguous one-based positions give the live queue one deterministic order without a second ranking scheme or sparse-position reconciliation. | Reconsider when measured queue depth makes front insertion, terminal removal, or its affected per-item publication materially slow or contended for supported use. |
| Retained history and artifacts without pruning | Transition receipts, definition revisions, terminal work, disposed proposal records and their evidence, authority-generation anchors, accepted immutable artifacts, and per-receipt generated history views accumulate. Ordinary commands read only selected or current rows. Explicit validation grows with every retained relation and artifact; view rebuild grows only with declared projections and their current presentation facts; handover grows only with exported lifecycle/history, pending proposals, and accepted artifacts. The owners are the SQLite schema and validation reader, exact handover reader, immutable artifact repository, and full generated-view projection. | Complete local provenance supports review, recovery, stale-action explanation, and reproducible accepted-scope and authority identity. | Reconsider when repository work-root growth or maintenance cost becomes material in real use, or when an accepted retention, archive, or deletion policy defines which evidence may be removed. |
| Complete materialization of one selected input | Commands that accept a proposal, transition payload, item revision, brief, review, dispatch environment, brief-source manifest, or brief-source plan read the selected file completely before strict decoding, canonicalization, or digest checks. Each individual input must fit in memory, although unrelated input files are not read. The owners are the thematic interface command and codec for that input. | Whole-value validation keeps each small local control artifact atomic, canonical, and exactly attributable to one command. | Reconsider when a supported input class becomes large enough for measured memory or latency to matter, or when a supported producer supplies progressive input that cannot be represented as one bounded file. |
| Trusted-local deployment | Pinboard assumes one trusted local developer authority over the repository, checkout, work root, SQLite database, and accepted artifacts. It validates external values and ordinary computed-write containment, but it does not defend against a hostile local user, deliberate database or artifact forgery, malware, or filesystem races by an actor with the same write authority. | This keeps the local developer tool focused on accidental invalid input, implementation defects, integrity, concurrency, and recoverable filesystem failure rather than unsupported multi-tenant security. | Reconsider when Pinboard accepts untrusted external imports, serves mutually untrusted users, crosses a privilege boundary, shares writable authority remotely, or records an actual corruption incident within a supported path. |

## Representative flows

### Initialization and reopen

`pinboard init` resolves the default `.codex/pinboard` root below the shared repository root and idempotently adds only `/.codex/pinboard/` to that repository's local Git exclude file. Invoking initialization from a linked worktree therefore reuses the repository ledger and does not create a worktree-local authority. It never edits a committed `.gitignore`, so unrelated `.codex` content remains visible. An explicit `--work-root` selects that exact path instead. Interface-owned work-state composition creates the SQLite schema when `state.sqlite3` is absent. When the database exists, it verifies that exact schema before reconciling the fixed publication staging path: a same-file staging alias left after publication is removed, while a different-file conflict is rejected without replacement. It then ensures the artifact directories exist and rebuilds views. Only after a successful fresh initialization and its receipt, the outer work-state interface prints one optional repository-care pointer. The default Codex runtime may also read the user Codex config to recommend `body_after_prefix` when that user default is absent; the explicit Claude runtime suppresses only this Codex-specific line. The pointer starts no skill or work, and neither effect writes configuration. A trusted project's `.codex/config.toml` may override the Codex user default. Resume and failure paths print neither effect; unreadable or malformed user config suppresses only the setting recommendation.

### Reads and validation

Every installed parser leaf belongs to one visible data-scope class. The static tool contract publishes that class in both its exhaustive operation index and selected operation detail, so a new parser leaf cannot remain silently unclassified. The exhaustive CLI router passes one resolved durable layout and, for database-backed commands, one composed store through these boundaries:

| Scope class | Installed operations | Data boundary |
| --- | --- | --- |
| State-independent | `root`, `input-contract`, `tool-contract`, `brief-sources`, observer `actions`, and unleased worker/preparer `actions` rejection | Read no SQLite state. Root discovery reads only Git and configured path facts; selected input commands read only their named input files; roles with no possible contextual selection resolve from the supplied role and authority fields. |
| Exact ordinary | `item status`, `item definition`, bounded `item definition-history`, `attempt status`, `attempt inspect`, `review-job`, `preparation status`, exact action-ID or leased worker/preparer `actions`, selected `parallel preview`, `brief publish`, `proposal`, every preparation and attempt authority command, `dispatch`, `close`, item revision, and every lifecycle action executed by exact action ID | Read selected subjects, only the direct liveness or reverse-dependent relationships each decision names, transitive definitions only for cycle-sensitive decisions, exact accepted references, and changed rows. Lease-only discovery first uses an indexed lease-and-generation lookup; exact action identity bypasses even that wider selected set. A committed effect names the affected item, attempt, receipt, and continuation subject needed afterward. |
| Current project | `status`, `overview`, project-role `actions` without an exact identity, empty-selection all-safe `parallel preview` | `status` reads active attempt identities plus the fixed state-count relation maintained by each item insertion or state transition. The other commands read current live semantic facts across the portfolio, excluding retained definition history, terminal attempt bodies, artifacts, and transition receipts. Project action discovery adds current proposals and command authority; all-safe preview omits proposals; overview reads its richer proposal and preparation presentation facts without loading action authority. |
| Explicit project-wide | `init` or reopen, `validate`, `views rebuild`, `handover` | Traverse the records required by their advertised whole-project result. Validation alone reads every authoritative relation. Initialization and rebuild read every declared view projection but omit unrelated stored state. Handover reads every exported relation and artifact but omits local authority/counter facts and disposed proposals. Their application seams receive projection facts or export batches and do not leak project-wide capability into ordinary decision signatures. |

Exact action discovery and execution cover every closed lifecycle sibling because the selected action kind and subject create one `DecisionScope` before the boundary reads. Leased discovery without an action identity uses indexed lease and generation facts to find only the current selected subjects, then reads the same exact contexts. That application-owned scope distinguishes primary subjects, existence-only related identities, cycle-sensitive dependency closure roots, direct live-dependent roots, attempts, proposals, and artifact references. SQLite does not infer a broader relationship: ordinary dependency checks read direct liveness only, closing reads direct live dependents through the reverse index, and only proposal acceptance or item revision follows transitive definitions to reject cycles. Item status reads keyed item fields, its current definition, at most its one indexed nonterminal attempt, and optional preparation identity; retained terminal attempts require their exact attempt identity and never ride on status. Definition history uses the item-and-revision primary key and fetches at most the requested page plus one row. Named-attempt inspection reads a closed terminal or nonterminal fact variant; only the nonterminal variant adds current Git/scope, item, direct dependencies, and one accepted brief. `review-job` additionally reads only that attempt's current `result.md`. Selected parallel preview reads only requested items and their direct launch constraints. Expected absence, malformed supported input, or unavailable selection returns a typed result. Artifact integrity and I/O failures remain exceptional. These paths never parse generated Markdown.

Every routine database open verifies fixed-size application metadata, schema version, and the installed schema signature without scanning stored rows. Explicit `pinboard validate` additionally runs SQLite `quick_check` and `foreign_key_check`, reads and validates the complete stored state, verifies every accepted artifact reference and live v2 brief, keeps historical terminal brief bytes opaque, and reports generated-view drift separately. Fresh initialization runs the integrity checks against its constant-size staging database before publication.

`pinboard handover --json` opens one read transaction for the exact exported lifecycle, history, pending-proposal, and artifact-reference facts. It excludes local authority generations and counters, fixed state counts, and disposed proposal collections. The application boundary accepts export batches so a future SQLite producer can page without changing projection semantics; the current producer supplies one batch. The interface verifies and reads each referenced artifact through the filesystem adapter, rejects suffixes outside the installed media vocabulary before output, and writes canonical JSON only after the full package is materialized. The path does not read generated views or mutate SQLite, artifacts, lifecycle, or authority.

### Brief source planning

The installed `pinboard brief-sources` plan leaf reads a strict source manifest without opening work state. It resolves each source-checkout-relative whole-file or Markdown-heading selector in turn, rejects overlapping line spans, and returns a strict reusable plan containing normalized selected-source digests and segment metadata. The emit leaf accepts that plan rather than the manifest, then rereads and verifies only the selected source files represented by the requested bounded batch before returning their content. Its heading selection is also used by dispatch against the same selected source checkout when validating reviewed-authority digests. Both leaves are read-only and do not acquire authority or write project state; planning memory grows with the largest selected file plus plan metadata, while emission memory and file access grow only with the selected plan document and requested batch.

`pinboard tool-contract` is another state-independent read. It derives one complete index from the installed parser leaves, recursively expanded exact command union, closed action family, and closed brief-boundary family. A bare operation family with several leaves returns their exact selectors. A selected leaf projects exact installed CLI usage including optional global-root placement alongside its purpose, mutation class, exact acquisition or retained authority, subject, lifecycle precondition, generated strict schema, artifact contract, actual success receipt, and retry semantics. Selected actions add their exact execution-route family, preventing read-only runtime continuation or blocker evidence from being presented as payload-bearing lifecycle transitions. Brief publication includes typed unresolved local and cross-boundary starters, every applicable structural-union choice as an exact replacement template, canonical byte rules, relational rules, and its fact-validation boundary generated beside the canonical brief records. A boundary-specific starter projection omits the much larger validation schema while retaining one complete unresolved shape and every structural, relational, and fact rule needed to fill it. The starter's initial union members are syntactic templates rather than fixed semantic choices; identity and semantic values remain unresolved, so this discovery path cannot invent scope, authority, or verification. Publication validates the candidate record and its accepted Pinboard references, but it does not resolve branch or base-revision declarations against Git or prove source-derived semantic claims.

### Mutations and proposal intake

Each argparse leaf carries its selected parser and either an exact command model or one of the few named coupled-option decoders. The interface converts the raw namespace once and dispatches a closed command union; handlers never receive a general argument namespace or reparse command and operation strings. A transition handler parses the opaque CLI capability receipt, derives the exact selected subject scope, reads only that decision context, decodes strict JSON against the selected variant, and constructs the exact command. `application.service` repeats that exact scoped read inside one write transaction, validates current authority and legality, allocates one revision and receipt, and commits one closed mutation. The SQLite adapter reads only the current rows needed by that mutation, exhaustively applies its targeted effects, validates the changed facts, advances revision and history, and returns `CommittedEffect` with the exact receipt, affected item and attempt identities, and any continuation attempt. A stale or failed effect rolls back; neither success nor failure assembles complete pre- or post-state. Proposal intake follows the same boundary and adds its exact relation target plus only the queue suffix whose positions change. Queue positions remain one-based and contiguous. Follow-up candidates depend on their related item; a prerequisite candidate becomes a dependency of its live related item. Intake never creates an attempt or activates work.

After a successful mutation, generated views refresh only the item, attempt, and new history selectors named by `CommittedEffect`. SQLite returns exact projection facts for those identities, and the filesystem boundary reads only the accepted live briefs those selected attempt views require. Transition presentation derives continuation for the effect's exact attempt identity through the same named-attempt reader as inspection. A view or continuation warning cannot undo the committed transition, and callers must not replay that mutation merely because projection needs repair or reinspection.

Every work item has immutable `work_item_definition_revisions`; the highest contiguous revision is its current accepted definition and the sole owner of title, objective, hypothesis, evidence selectors, scope, non-scope, acceptance criteria, ordered dependencies, effect, and unlock. Proposal intake creates revision 1 from immutable proposal facts. Explicit proposal-acceptance dependencies, prerequisite intake, and `revise-item:<item>` append another complete revision and replace relational dependency rows in the same transaction. Revision decisions compare both expected revision and digest, validate the complete canonical definition, reject missing or cyclic dependencies, and leave lifecycle state untouched. Block operations only confirm dependencies already present in the current definition. Attempts retain the exact definition revision and digest from their accepted brief. Current-scope actions stay unavailable to stale attempts; an active or paused stale attempt can rebind to a matching current-definition brief and corrected Git lineage while preserving its lifecycle state and evidence and fencing worker authority.

A dependency-satisfied ready item may retain one renewable preparation claim pinned to its exact current definition. The item remains `ready` while a preparer compiles and reviews the canonical brief. Ordinary `preparation start` samples its operation time at the boundary, then opens one write transaction and selects the current definition together with either initial acquisition when no claim exists or transfer when the retained claim is inactive. A live conflicting claim or an item that is no longer ready is rejected without change. Exact low-level acquisition and transfer remain supported for recovery and contract diagnosis. Renew and release require the exact preparation token, while revocation records the invoking project task and host. A live claim suppresses conflicting ready-item lifecycle and definition mutations. Activation is advertised only to its exact preparer, validates the accepted brief and definition pin inside the write transaction, consumes the claim, creates the attempt, and moves the item to `active` atomically. Expiry, release, or revocation makes the ready-item operations available again; a later ordinary start repins the current definition.

### Worker dispatch and review publication

`application.dispatch` returns expected selection, review-publication, and final-authority outcomes as typed results. `interfaces.dispatch_brief` composes those operations with artifact verification and prompt rendering, converting its advertised environment, identity, source, review, and prompt rejections into one closed dispatch result. It requires the dispatch environment checkout to match the selected source checkout before decoding the strict record and checking attempt, item, branch, stable checkpoint ID, accepted scope, architecture impact, contracts, authorization bases, verification, reviewed-authority digests, coverage, lifecycle disposition, and independent ready review. Reviewed-authority digests are recomputed from that source checkout rather than the shared repository root. Accepted-scope authorization must match the reselected attempt; source-derived authorization must name one exact reviewed authority family. The independent reviewer verifies that each selected source truthfully serves its claimed product-authority, repository-policy, or existing-consumer role and that each mandatory check's tool, threshold, platform, compatibility obligation, or hardening target is supported by accepted scope or selected source bytes. The stable action JSON field named `effect` classifies lifecycle transition input, not every outer command effect: dispatch may publish or reuse immutable review evidence while leaving item and attempt lifecycle unchanged. Domain code names that narrower fact `LifecycleEffect`; the inspection boundary preserves the existing field and values.

The agent-facing runtime adapter maps the accepted checkout, permission declarations, native subagent launch, waiting, and optional messaging without changing this flow. Pinboard validates the dispatch record but grants no runtime capability and creates no worker.

Ready review evidence is strict JSON bound to the stable checkpoint ID, canonical checkpoint-record digest, and canonical ordered authority-set digest. The interface canonicalizes it, the application publishes and accepts it through the result-shaped artifact capability, and the interface verifies the accepted bytes before rendering the launch prompt. The launch prompt only points the worker to the canonical JSON brief and names the execution environment; it does not duplicate or reinterpret the task contract.

After a candidate is submitted, the read-only `review-job` command requires the exact protected candidate and current review continuation. It obtains that continuation from the named-attempt reader, verifies and resolves only the selected accepted brief, reads canonical `result.md` bytes from that attempt directory, rejects missing or empty evidence, and emits a bounded fresh-context prompt with the brief and result paths and render-time SHA-256 digests. The reviewer must verify those bytes and the candidate identity immediately before use. Review-job rendering does not publish evidence, mutate lifecycle, create a task, or transfer acceptance authority; the accepted brief's `owner_task_id` remains the exact outcome owner. The Codex runtime creates the subordinate reviewer. If that capability is unavailable, the candidate remains in review as a valid resumable boundary rather than being routed to another user-owned task.

### Checkpoint and terminal acceptance

An accepted nonterminal checkpoint uses the brief's stable checkpoint ID, preserves exact result and review evidence, pauses the same attempt, and fences its worker authority. Checkpoint evidence is published before the locked acceptance transaction. If locked rejection or infrastructure failure follows a newly published immutable revision, the CLI reports a committed-effect outcome naming that surface while the prior ledger relationships remain intact; replay is not presented as an unchanged retry. When review accepts the protected candidate but the current attempt should continue, review acceptance returns the item and attempt to active, clears the protected candidate, preserves the accepted candidate and evidence in the transition receipt, and fences the prior worker authority. Late accepted direction uses these existing operations rather than another lifecycle state: definition revision makes an active attempt stale; review return clears a superseded protected candidate without calling its implementation defective; matching brief publication and rebind accept the revised target without changing active or paused state before another exact candidate and review. Terminal completion records accepted evidence and removes the item from live work only after the human has chosen repository disposition and confirmed completion. Direction after that terminal boundary becomes new work. Review return keeps the same attempt and evidence while fencing the rejected worker lease.

## Stored formats

The default `.codex/pinboard` path is current; explicit work roots remain supported at their selected paths. This document describes implemented ownership and dependency direction. Every implementation checkpoint declares its architecture impact before dispatch.
