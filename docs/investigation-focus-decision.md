# Investigation focus: contract and design decision basis

## Decision at this checkpoint

An investigation should remain one continuing inquiry while its questions, evidence and intended audiences change. A bounded pass should leave enough state for another session to resume, challenge a conclusion and produce a different document without searching everything again. This is a proposed product contract, not an installed Pinboard capability. This record recommends a falsifiable comparison before choosing its final implementation. Checkpoints 2 through 6 remain open.

The accepted location decision is a caller-selected local investigation directory separate from the repositories and other material being examined. Git is optional for that directory. The human has not selected a final application architecture, an aggregate paid-run budget, per-batch ceilings or an exact runnable Luna-high model. Any route below that would introduce a material product or architecture limitation needs the human's agreement before dependent implementation.

## Current boundary and proposed use

Pinboard currently coordinates one repository-owned work ledger through a selected Git checkout and a shared work root. Its work item preserves a repository delivery decision across attempts; an attempt executes an accepted brief toward one candidate and review. SQLite owns lifecycle and accepted references, immutable artifacts hold accepted bytes, and generated Markdown views are repairable projections. Existing application owners handle briefs, queries, dispatch and artifact publication for that workflow. None is an installed continuing investigation state or a general source connector. The current brief source adapter reads a selector under one `source_checkout_root`; it cannot acquire evidence from arbitrary repositories by changing the selector. The existing work root's protection and trusted-local assumptions apply to current Pinboard paths, not automatically to a new investigation directory.

The proposed inquiry has a different lifetime and result. It starts with an imperfect question, accumulates findings across bounded passes, and may yield several independently versioned outputs. An inquiry is not a work item, each pass is not an implementation attempt, and an output revision is not a review candidate for repository delivery. An investigation may recommend a code change, incident action or policy, but those remain proposals until a person authorizes the corresponding effect through its own workflow.

### State that must survive a pass

The inquiry needs one stable local identity independent of Git and a recorded purpose that can change by explicit human direction without rewriting earlier observations. Each pass needs its question, planned bounds, source access actually available, discoveries, failed or exhausted leads, remaining unknowns, next useful question, interruption point and reason for stopping. A pass can stop when its agreed time or effort budget is spent, a useful answer is available with stated limits, further accessible evidence has diminishing value, a necessary source is unavailable, or urgent evidence calls for human attention. An urgent finding should be surfaced promptly with its basis and uncertainty; it does not grant authority to remediate, message others or start delivery work.

Before a pass, the human sets its question, permitted source scope, effort or time bound, and authorized destinations. While the human is away, the agent may discover and read sources within that scope, reconcile evidence, and save findings and draft outputs in the inquiry home until the bound is reached. It pauses with a recoverable account of completed work and the next useful question when a new source or output destination needs authority, the human must choose between materially different directions, a necessary source is unavailable, the bound is reached, or urgent evidence needs human attention. Silence does not enlarge the pass or authorize remediation, external messages or writes to evidence sources.

Evidence must distinguish source material observed at a named version or time from an inference drawn from it, a proposal for action, a human agreement, a contradiction between sources, and an unresolved question. Preserve provenance sufficiently to revisit a claim: source identity, selected location or query, relevant revision or time window, observation time, excerpt or reproducible locator, access and coverage limits, and any transformation into a finding. A later source revision should make freshness visible without silently replacing the earlier observation. A source that was inaccessible, withheld or not searched is a gap, not a negative finding. Contradictions should retain both sides and their provenance until resolved or explicitly left open.

Outputs are separately identified and versioned by audience and purpose. Each output cites or otherwise resolves to the inquiry evidence it uses, states which claims are observed, inferred, proposed, agreed or unknown, and names material gaps. Revising a leadership summary should not silently revise a technical note, the underlying evidence or a previous agreement. Reusing one evidence set for a new audience may change emphasis and detail, but cannot promote an inferred cause into an observation. The existing Technical Writing guidance can shape prose from accepted facts; it does not provide inquiry identity, source acquisition, evidence persistence or output-version authority.

### Home, access and effects

The caller selects a local directory to hold the continuing inquiry and its private evidence and outputs. That directory is the proposed state home even when it is not a Git repository. Source repositories, supplied files and other permitted sources are read inputs. Opening or revising inquiry state in its home and writing a derived document to a chosen destination are separate effects; permission to read a source does not imply permission to write to it or export its contents. A requested output outside the inquiry home needs separate destination authority. The workflow should record a denied or unavailable source as limited coverage and resume from that state, rather than claim it inspected the source.

Private transcripts, company logs and other confidential originals stay in the caller's local inquiry home or their original source locations. They do not enter this public repository, its examples, ordinary commits or published documentation. A future work-computer trial keeps raw evidence there; only a human-reviewed sanitized package may return to this development item. The current trusted-local model supplies no adversarial protection for that new home. If a supported use requires shared remote state, cross-machine synchronization, untrusted imports or stronger isolation, the design must reopen the home and trust decision before implementation.

### Representative inquiry and recovery

Consider a fictional service, Harbor, whose checkout jobs became slower after a deployment. The initial question is “Did the deployment cause it?” Within the permitted synthetic sources, the first bounded pass searches the service catalog for Harbor's checkout job, follows its deployment identifier into repository history, and checks the available trace and dashboard indexes for the same time window. This yields candidate deployment records, checkout traces, latency and queue dashboards, and a team note. The pass selects the deployment record, a trace sample and the latency dashboard because they cover the job and agreed window. The queue dashboard is listed but inaccessible; the team note is discoverable but left unsearched at the effort bound. Both remain explicit coverage gaps, with their discovery paths and access status recorded.

The selected dashboard shows a rise after deployment, while the trace sample covers only one region. The observation is temporal correlation; deployment causation remains an inference. A lead in the deployment notes is exhausted when the changed code does not touch the slow operation. The pass ends at its effort bound with a technical note version 1, an explicit next question about queue depth and a locator for each observation.

The session is interrupted before the queue source is available. On resume, the inquiry reloads the same question, observations, inference, exhausted lead, missing metric, source windows and note version. The human then changes direction: investigate whether an upstream retry policy is amplifying load, and prepare a leadership decision summary as a second output. A second pass reads a newly available queue snapshot, a synthetic retry-policy change record and the previously deferred team note. The queue snapshot supports a rise in backlog but covers a later window; it neither verifies nor erases the earlier deployment hypothesis. A retry count contradicts the team's “no retry change” note, so both claims remain visible. The leadership summary version 1 states observed slowdown and backlog, labels retry amplification as a plausible inference, names the conflicting note and mismatched windows, and proposes a limited measurement before any policy change. The technical note remains version 1 until deliberately revised. An urgent new observation, such as ongoing error growth, triggers a human alert with its source and freshness; it does not change production settings.

This trace is a contract example, not evidence that the proposed workflow works. A synthetic world and then a real multi-session trial must test whether a fresh session can recover these distinctions without relying on hidden chat context.

## Design routes to test

All three routes need the accepted inquiry home, source-read versus output-write distinction, private-data boundary and explicit human authority for downstream effects. They differ in where continuity and validation live. Present application ownership remains `domain` for pure decisions, `application` for use-case sequencing and storage-independent contracts, adapters for filesystem or storage effects, and CLI/MCP for transport and presentation. Reusing that direction does not mean reusing the repository attempt lifecycle for an inquiry.

| Route | Exact unlock and current owner relationship | Cheapest falsifying observation | Reversible first step and possible durable footprint | Material limitation and reopening condition |
| --- | --- | --- | --- | --- |
| Skill-only guidance | A focus skill tells the agent how to keep an inquiry note and derive outputs in the caller-selected directory. It can reuse Technical Writing for prose, while current Pinboard application modules remain unchanged. | Resume a held-out synthetic inquiry in a fresh session after an interruption and changed human direction. Reject this route if provenance, contradiction, unknowns, source windows or output relationships are lost despite the supplied note. | Write an experimental skill and sample notes outside installed production, then discard them if they fail. A durable version would need a shipped skill, user instructions and evaluation scenarios; no authoritative machine check is implied. | Recovery and consistency depend on agent adherence and legible files; the note is not authoritative Pinboard state merely because it is Markdown. Reopen for structured validation when observed resumption or cross-output errors exceed what a clearer note can correct. |
| Structured local artifacts | Versioned typed inquiry, pass, evidence and output-relation records in the selected home make status, provenance and recovery inspectable. This introduces new application-owned contracts and a storage adapter; existing work-brief and artifact owners are examples of strict publication, not inquiry consumers. | Feed two interrupted, contradictory synthetic passes into a minimal validator and fresh-session reader. Reject or revise the shape if valid uncertainty cannot be represented, or if an invalid relationship passes undetected. | Prototype one strict record and round-trip validation against synthetic files without installing a command. A durable path would likely span models, validation, local persistence, one entry path, docs and tests: more than five files and more than one production owner, so it needs an explicit implementation decision. | Shape checks do not establish truth, discover sources, or make a document useful. Separate local state adds a new recovery and write boundary. Reopen for application sequencing when experiments show repeatable cross-record or pass-control failures that file validation alone cannot own. |
| Application-backed support | An installed use case could own inquiry lifecycle, bounded-pass decisions, source inventory, evidence relations, resume and output registration, exposed through a narrow CLI or MCP surface. It would add separate domain/application owners and adapters while preserving existing repository delivery. | Prototype only the failing mechanic shown by the first two routes, then run the same held-out recovery and authority scenarios. Reject the extra machinery if it adds no measurable protection or reduces useful human effort less than it costs. | Begin with one isolated application path over synthetic local sources; keep it outside the installed package until a supported entry is chosen. A durable path crosses domain, application, filesystem/storage, CLI/MCP, tests and product docs, with significant code and architecture footprint. | A local application still lacks universal connectors, authenticated principals and automatic remote sharing. Reopen each missing capability only on a named supported source or observed failure; do not turn the first implementation into a general platform. |

The cheapest next route is to build checkpoint 2's fictional investigation world, then compare an ordinary agent pass with a skill-only focus and a structured-artifact prototype under the same source access, human intervention and resource bounds. The structured prototype should prove or disprove recoverable representation before an installed application is chosen. Application support is warranted only for an observed failure that needs an enforceable owner, such as stable evidence identity, valid relations or pass transitions. This is an experimental recommendation, not a selection of the final architecture or authorization for paid calls.

The comparison should inspect grounded conclusions, useful source discovery, contradiction and unknown retention, provenance and source-window correctness, resumption after interruption, repeated work, human effort, document usefulness, stopping behavior, latency and known versus unavailable spend. A seemingly shorter answer is not success if it omits a material inaccessible source or upgrades inference to fact. Reopen the recommendation if held-out synthetic cases show the guidance route handles continuity reliably, structured files fail to represent real direction changes, or a narrow application prototype materially improves a measured failure. The human must agree to any material product or architecture choice, including a new inquiry state contract, installed entry path, material limitation or changed write boundary, before implementation depends on it.
