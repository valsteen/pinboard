# Coordinate with the pinboard

Coordinate shared work through one project-local ledger while keeping execution isolated by attempt. Any task may apply an atomic project transition. Preparation and attempt leases fence the longer operations that genuinely need retained authority.

Use [the coding-agent runtime adapters](references/runtime-adapters.md) for identity, checkout isolation, subagents and reviewers, permission declarations, waiting, and optional messaging. This skill owns the shared decisions in both integrations.

## Confirm broad scope once

Before broad autonomous work begins—including repository-wide work or an outcome spanning several principal product, documentation, agent, tooling, packaging, or CI surfaces—give the human one short declarative sentence that names the intended outcome, the main surfaces expected to be read and touched, the approximate magnitude, and any surprising exclusion. State magnitude in terms the human can correct, such as one representative family versus the whole supported repository.

This sentence confirms the interpretation; it is not a permission question, an internal plan, or a canonical brief. When the human already authorized immediate execution, continue after the sentence without asking again. Ask one concrete question only when the confirmation exposes an unresolved choice that would materially change product behavior, architecture, scope, compatibility, or verification.

Give the sentence before acquiring a preparation claim, loading implementation sources, compiling a brief, or launching a worker. The later brief preserves the agreed magnitude; it does not silently narrow or widen it.

## Resolve material architecture limitations before preparation

Before acquiring a preparation claim for any relevant refinement or change, inspect the project's current limitations owner and apply its reusable limitation method. Distinguish an acknowledged existing limitation, an introduced or widened limitation, a defect against accepted behavior, and a speculative risk. Trace a proposed local remedy to its foundation so a compensating layer does not preserve, mask, or deepen an unacknowledged material limitation.

When the proposed work crosses a previously acknowledged limitation without materially changing its consequence, preserve that accepted boundary without asking again. When it would introduce, widen, preserve, mask, or deepen an unacknowledged material limitation, resolve the decision before claiming preparation authority. Generic task permission and silence are insufficient.

Present the decision in this information order:

**Architecture checkpoint**

1. Explain the concrete behavior, affected supported paths, consequences, and observable reopening condition.
2. Separate the exact unlock from work that remains outside scope.
3. Give the recommendation and its evidence.

**Practical consequence: state plainly what accepting this exact limitation means for the product and future work.**

Ask an ordinary approval question about that exact decision. An explicit natural-language answer is sufficient; never require a recited acknowledgement phrase. Approval authorizes only the stated limitation, not related implementation or hardening beyond accepted scope. Record the resolved assessment in the complete accepted definition and existing brief fields. Do not acquire or retain a preparation lease while waiting for this decision.

## Keep assurance inside accepted product scope

Before making an assurance obligation mandatory in preparation, implementation, or review, classify it as an in-scope defect, an accepted assurance obligation, a material new assurance obligation, or a speculative risk. A mandatory obligation or blocking finding must trace to accepted scope or an exact accepted brief contract or criterion, an applicable repository policy, an exact reviewed product-authority family, a named existing production consumer, or an observed failure on a supported path. A broad appeal to correctness, an exploratory failing test, public product prose, or guidance written by the current change cannot authorize a new guarantee by itself.

Fix defects and enforce accepted assurance without asking the human to confirm scope again. Keep speculative risks non-blocking. When a finding would materially add a concurrency, durability, security, adversarial, platform, or compatibility guarantee without one of the accepted bases above, stop only the affected preparation, implementation, or review disposition. The task that owns the outcome presents one concise decision containing the current product behavior, proposed new guarantee, triggering scenario, evidence gap, likely implementation and verification footprint, recommendation, and practical consequence. Ask one ordinary question about that exact expansion; silence and generic task authority are insufficient.

Use the current definition and canonical brief fields to preserve the decision and its provenance. If those fields cannot express the distinction, stop before changing the schema and state the exact schema, codec, projection, tool-contract, review-job, compatibility, and architecture footprint that would be required. Newly accepted assurance then follows the ordinary definition, brief, candidate, and review replacement path; an unaccepted expansion does not become implementation work or a blocking review defect.

## Match detail to the question

Keep Pinboard operationally invisible when it is working normally. User-facing progress and receipts describe the user's tasks, decisions, confidence, blockers, and next actions. Do not volunteer the storage backend, command mechanics, generated-view mechanics, revisions, leases, routing, transport, validation steps, or unchanged project state. Include an implementation or process detail only when it changes the result, confidence, risk, requested action, or next step, or when the user asks to inspect or troubleshoot Pinboard itself.

Apply an engaged, neutral collaboration style whenever Pinboard is active, regardless of which repository or product the user is discussing. Advance product reasoning in decision-sized increments. Make the smallest useful move, preserve the difference between a proposal, an accepted decision, an assumption, and an unresolved question, then stop only where the user's answer can materially change scope, meaning, emphasis, or structure. Resolve obvious wording, organization, and routine workflow choices without asking. Do not jump from an early idea to a complete polished plan that nobody has accepted.

When a Pinboard-managed request clearly creates or substantially revises a technical document, report, RFC, design note, investigation or decision record, pull-request description, or comparable human-facing project artifact, also use `$technical-writing`. An explicit invocation selects it for ambiguous document work. Do not load or announce it for routine status, intake, lifecycle, implementation, or review coordination merely because Pinboard itself produces readable views or receipts. The writing skill owns document composition and editing; this skill retains accepted decisions and the surrounding interaction.

Do not narrate successful generated-view refreshes, rebuilds, or routine retries. Report recovery only when it fails or materially changes the outcome, confidence, risk, or required user action.

Usable artifacts and delivery links are outcome context, not internal mechanics. Whenever a Pinboard-facing response or permitted task message mentions a Pinboard item or another user-relevant fact with confirmed readable Markdown, make the human-facing name or purpose a native clickable link on that mention, even when the same artifact was linked earlier or its contents are unchanged. This includes accepted-definition summaries, full briefs and attempt views, implementation results, blockers, complete independent reviews, history evidence, commits, pull requests, and comparable durable results. For a local readable artifact, use the actual supported item, attempt, or history selector or named evidence path exposed by the selected work root, and verify that it exists before linking; never synthesize a target from an assumed directory or filename convention. If readable Markdown is unavailable, mention the item or fact accurately without a guessed link and surface the absence only when it materially affects the result or next action. Announce a newly available or materially refreshed artifact promptly with its purpose, say what remains in progress, and continue; later contextual references still link it every time without repeating its contents or generating standalone unchanged-status notices. Keep canonical JSON, receipts, leases, immutable storage copies, and routine mechanics silent unless the user asks or they are needed to explain a material change.

Do not suppress a higher-level instruction that requires disclosing the first use of a selected skill. Keep that required disclosure to one concise, outcome-oriented acknowledgment for each selected skill. Do not add a separate Pinboard-authored explanation of companion-skill selection, internal routing, or healthy task state.

The presence of a disjoint ready or active item is not a user-facing event. Start the current task normally without naming another task's ownership. Mention another task only when observed write overlap, live contention, changed priority, or required user action affects the current outcome.

Treat a stale action or expired or replaced preparation or attempt lease as routine internal control flow when retained state is safe and the authorized workflow can refresh or reacquire the exact capability. Do not send commentary merely because a command rejected stale authority or rendered that expected race as an error. Refresh and retry silently within the applicable bounded recovery rule. Report only when recovery is exhausted, state is unsafe or inconsistent, work is blocked, the requested outcome changes, or a user decision or new authority is required. Name the holder or expiry only when the user asks to troubleshoot or decide revocation.

Default “where do we stand?”, “what remains?”, “quick status”, and equivalent orientation questions to the single `overview` result. Report active attempts, ordered live items, eligibility, dependency reasons, review flags, and immediate choices. Present every mentioned item through its confirmed item-view link under the readable-artifact rule above. Intake candidates already appear in that order; there is no separate hidden inbox to inspect. Retain the revision stamp privately as freshness evidence; show it only when the user asks for it or when it materially explains stale or conflicting state. Do not read history, project notes, GitHub, branches, CI, delivery state, or old decisions for this default answer. Do not acquire a lease merely to explain the live picture.

On the first conversational mention of a task, include one short practical explanation using its overview title, effect, and unlock. Omit that explanation only when the same task was just discussed and the immediate context already supplies it. When the overview includes a planned-replacement warning, state the exact replacement item and practical replacement cost; do not infer replacement from similar titles or prose. Ask the human whether to revise or withdraw the relation, stop the affected work, or retain it temporarily; never select the outcome on their behalf. Temporary retention records only the rationale the human supplies and the exact displayed replacement cost.

Keep inspection, validation, repair, and handover claims distinct. `pinboard_item_status` and both `pinboard_item_definition` leaves read only the named item facts. Use definition operation `current` for complete accepted fields and revision/digest identity, never a title or status substitute. Use operation `history` only when history is requested, with an explicit 1–100 limit and `before_revision: null` initially; continue with the returned exclusive `next_before_revision` only while it is non-null. These reads require no lease. Direct attempt- and preparation-authority status likewise read only their named authority facts.

Those selected SQLite facts share one focused read transaction. The tool may then publish an immutable reviewer prompt, accept its artifact reference, and advance the ledger; it does not mutate lifecycle or candidate state, change attempt authority, write repository files, or affect Git. Run full validation separately before supplying package evidence. `pinboard_parallel_preview` with explicit selected `item_ids` reads only those current items, their direct launch constraints, and applicable authority, while its explicit all-safe leaf is intentionally project-wide. retained CLI `status`, `pinboard_overview`, `pinboard_actions`, and that all-safe preview each report a projection from one current SQLite snapshot; they do not validate accepted artifacts or generated views. The action's inline input contract describes its selected payload. Use `<launcher-root>/scripts/pinboard validate` when integrity matters: it verifies the SQLite snapshot and accepted artifact bytes, validates each v2-linked checkpoint or covered-completion package against its historical receipt and immutable evidence, then reports generated-view drift as repairable warnings. When continuing work from another coding-agent task, extract every named Pinboard item for which that task claims terminal completion and verify each claim through `pinboard_item_status` with exact roots and item before treating it as complete. Then use `overview` only to identify remaining live work. Absence from `overview` means only that the item is not currently live; never use that absence to report an item as missing, unrecorded, or unfinished without the exact item-status lookup. Exact item status proves the recorded item and attempt state, not acceptance of a nonterminal checkpoint.

Make the user's next move frictionless at a genuine decision edge. Ask only when the answer changes the next action; reuse authority already granted rather than creating another confirmation. Prefer an available native structured-question tool when its current instructions permit this question. Give concise choices with their practical consequences and recommend the best-supported option when evidence supports one. Follow the runtime adapter for host-specific tool selection and restrictions.

When no native tool is available or permitted, ask in ordinary text. When two to four useful alternatives remain, recommend the best-supported next step in a natural sentence and follow it with a shortcut such as `Quick reply: 1 investigate freshness · 2 admit it · 3 revise it`. All `Quick reply:` examples below are text fallbacks; do not repeat a native widget's choices in a second menu. Accept the visible number, a short phrase, or an ordinary sentence as the same intent. The numbers belong only to the visible offer and are never global application commands. Omit shortcuts when the result is terminal with no follow-up, the user's exact requested action has completed, only one sensible next move exists, or extra options would be filler.

A state-changing choice authorizes only its described effect; resolve current action availability and gather missing semantic input before executing it. While an answer is pending, continue independent authorized work, but keep answer-dependent work pending. A preselected option, silence, or elapsed time grants no approval. Leave the unresolved choice resumable; never interpret silence as completion, deletion, or abandonment. Use the runtime's actual permission mechanism for execution escalation; a question widget cannot replace it.

## Route human task starts through Pinboard

Humans do not need to know the preparation boundary before asking Pinboard to start work. If a human invokes `$pinboard-deliver` to begin a named item without an already prepared active attempt, treat the request as Pinboard start intent rather than a lifecycle error. Give one gentle, non-blocking clarification: `$pinboard-deliver` is the implementer route after Pinboard prepares an active attempt; ordinary wording such as “Use Pinboard to work on <item>” is the intended start. Then continue through the normal Pinboard route when the item and requested outcome are clear. Ask one concrete question only when the intended item or outcome is genuinely ambiguous.

Do not blame the human, lecture about internal routing, expose backend or unrelated task state, or stop after the clarification when Pinboard can continue.

Keep `$pinboard-intake` and `$pinboard-deliver` as thin specialized callers of this interaction owner. Their additional instructions decide how to preserve or implement work; they do not replace the collaboration style above.

End every compact overview with one short, explicit offer to expand the useful layers: recommendation and item context; completed decisions; delivery and CI; or full history. Phrase the offer as a natural continuation of the conversation, such as “If useful, I can explain why X should come next, recap decisions we already closed, check what shipped and whether CI is green, or reconstruct the full project history.” Use the question presentation above; the text fallback is `Quick reply: 1 why next · 2 decisions · 3 delivery/CI · 4 full history`.

Do not invent slash commands for these follow-ups. `$pinboard` is an explicit entry point for invoking the skill in a new or unrelated context, where terse prompts such as `$pinboard quick status` or `$pinboard full history` are valid. It is not a required subcommand inside an ongoing pinboard conversation.

Fetch only the selected expansion:

- For a recommendation or deeper rationale, use the overview itself when it contains enough evidence. Otherwise read only the exact live item records that are plausible choices. Apply the ordering below only then.
- For completed decisions, read terminal item history only. Do not add GitHub or delivery checks.
- For delivery or CI, inspect Git and GitHub only. Do not reconstruct ledger history.
- For full history, say that the answer will be slower, then read the complete relevant ledger and accepted artifact context. Add delivery state only if the user includes it.

When an expansion needs several known project files or headings, plan their selected sizes with `pinboard_brief_sources` before loading their bodies, then read each non-overlapping emitted batch once. For other known facts, use a bounded batch when the available tool supports it. If output truncates, continue at the first unread boundary without replaying returned content. Do not turn one requested layer into an exploratory command-per-item walk. If the user explicitly asks for a zero-tool or last-known answer, reuse the most recent overview from the current conversation and label it as not refreshed. Never present it as current. A requested expansion is not permission to preload the other layers.

This proportional behavior applies to mutation as well as status. After a successful command returns a revision-stamped receipt, do not run a redundant overview merely to confirm what the command already proved. Run broader verification only when the operation lacks a sufficient postcondition or the user asks for it.

## Ownership

- Let `state.sqlite3` own lifecycle, dependencies, attempts, preparation and attempt leases, proposals, history, and accepted artifact references.
- Let `views/` remain generated human-readable output. Never edit it as authority.
- Let accepted brief and evidence artifacts own execution semantics and review receipts; resolve them through their SQLite artifact references.
- Let proposal fact columns preserve the original intake evidence while disposition columns record the later decision and same-identity items own queue state and position.
- Let public project documentation own stable architecture and domain truth.

Project transitions are direct atomic SQLite changes with task and host audit attribution supplied by the invoking trusted local task. Those strings are not authenticated credentials. Disjoint preparation leases reserve exact ready-item definitions before activation, and disjoint attempt leases authorize active item-local work concurrently. Expiry, release, revocation, and higher fencing generations invalidate retained leased actions.

## Coordinate review responsibility and checkout use

Route frozen candidates to the task that owns the outcome, not by conversational ancestry. That task commissions one fresh-context, candidate-read-only review subagent after the candidate is stable. The result returns automatically, and the owning task processes the complete accept-or-correct verdict. Keep the reviewer independent, commission one reviewer by default, and do not duplicate the full review or add reviewers without a concrete risk.

For a correction, require the current `result.md` to map the exact prior findings, intervening candidate delta, affected owner-consumer relationships, and each evidence family as reused, revalidated, or stale. Every semantic reread or verification rerun needs the changed relationship or accepted widening reason that requires it. The outcome owner checks this map before rendering the correction review job, and the reviewer reports the same dispositions while still returning one complete verdict. An unchanged source hash does not preserve evidence whose owner-consumer relationship changed.

Before commissioning review, inspect the attempt continuation and call `pinboard_review_job` with exact roots and a structured review leaf containing `attempt_id` and `candidate_revision`. Use `kind: initial` without histories, `package-initial` with `checkpoint_history_id`, `correction` with `correction_history_id`, or `package-correction` with both. Before supplying a package history, run `<launcher-root>/scripts/pinboard validate --json` separately and stop on failure. Copy exact same-attempt history identities from checkpoint output, explicit handover, or the selected return receipt; neither is discovered automatically. Only canonical `return-for-correction/v1` reason input can supply correction context. Current nonempty `review.md` remains independently bound to its render-time digest, and may describe a newer candidate than a selected package. Give the fresh reviewer only the returned native envelope and follow its exact interface-owned verifier before reading the immutable prompt. The job binds the exact protected snapshot, accepted brief owner and digest, nonempty `result.md`, and selected historical bytes. The reviewer verifies every selected byte and Git identity, compares each historical candidate independently, reuses unchanged owner relationships, revalidates changed relationships and documentation, classifies unreviewed changed surfaces, and marks relationship-invalidated evidence stale despite unchanged source hashes. Widen only for architecture, persistence, wire, lifecycle, dynamic-consumer, or demonstrated-blind-spot conditions. Stop without a verdict if an identity, comparison, classification, or required widening cannot be resolved. Publication may change immutable-artifact, accepted-reference, and ledger surfaces; it neither runs full validation nor mutates lifecycle, authority, or native tasks. The outcome owner applies the reviewed result.

Use [the coding-agent runtime adapters](references/runtime-adapters.md) for the native fresh-reviewer launch and wait operations. The exact review job and review responsibility remain shared.

Name the actor and expected next action in every user-facing review update. Describe the default path as `review by a separate Codex reviewer` or `review by a separate Claude Code reviewer`, matching the current runtime and including whether that review is ready, underway, accepted, or returned for correction. Say `ready for your review — <decision requested>` only when the human is actually expected to review or decide something. Do not use bare `independent review` as a user-facing destination when the actor would be unclear.

Do not use or wake another coding-agent task to review or receive the same outcome. Dispatching work, clarifying or widening scope, or sending a prior message does not establish current responsibility. A separate task owns a genuinely independent outcome and reports in its own conversation; it is never a subordinate return path.

If the runtime adapter establishes that the current runtime cannot create a subagent, keep the exact candidate in review, preserve the durable result and accepted brief, and state that review is waiting for a runtime with subagent capability. Do not create or wake a user-owned task, return routine ownership to a parent task, substitute the implementer as reviewer, or imply that the human must review unless the human explicitly chooses that route.

Treat an explicit user choice of the main checkout or an isolated worktree as settled. Do not ask again. For an explicit worktree choice, use that worktree without a generic warning about possible later integration conflicts. Discuss integration risk only when observed overlap or conflict makes it concrete, or when the later repository-disposition decision requires it.

After selecting a newly created implementation worktree for repository writes, follow the repository's exact worktree-preparation command before Pinboard preparation or implementation source work. Run it once for that checkout; do not substitute global installs or another checkout's mutable dependency directories. If setup fails, follow the runtime adapter's [source-worktree setup recovery](references/runtime-adapters.md#source-worktree-setup-recovery). When the task changes its own preparation or verification tool, preserve base setup as bootstrap evidence, keep stable installed tooling only for coordination, and verify the changed candidate directly.

Before repository writes or worktree creation, infer the likely integration baseline from project Git evidence rather than treating `main`, `origin`, or `upstream` as universal names.
