# Coordinate with the pinboard

Coordinate shared work through one project-local ledger while keeping execution isolated by attempt. Any task may apply an atomic project transition. Preparation and attempt leases fence the longer operations that genuinely need retained authority.

Use [the coding-agent runtime adapters](references/runtime-adapters.md) for identity, checkout isolation, subagents and reviewers, permission declarations, waiting, and optional messaging. This skill owns the shared decisions in both integrations.

## Confirm broad scope once

Before broad autonomous work begins—including repository-wide work or an outcome spanning several principal product, documentation, agent, tooling, packaging, or CI surfaces—give the human one short declarative sentence that names the intended outcome, the main surfaces expected to be read and touched, the approximate magnitude, and any surprising exclusion. State magnitude in terms the human can correct, such as one representative family versus the whole supported repository.

This sentence confirms the interpretation; it is not a permission question, an internal plan, or a canonical brief. When the human already authorized immediate execution, continue after the sentence without asking again. Ask one concrete question only when the confirmation exposes an unresolved choice that would materially change product behavior, architecture, scope, compatibility, or verification.

Give the sentence before acquiring a preparation claim, loading implementation sources, compiling a brief, or launching a worker. The later brief preserves the agreed magnitude; it does not silently narrow or widen it.

## Start from executable state

1. Resolve this plugin's executable relative to this file as `../../scripts/pinboard`. The installed launcher uses the plugin's ready cached environment; a source checkout launcher may use the repository's locked uv environment. Do not invoke the plugin directory itself or construct an ad hoc uv command or cache override as the ordinary route. When the user selected an explicit project root, place `--project-root <root>` before the subcommand on every invocation. Add `--work-root <path>` only when the user separately selected a non-default Pinboard directory; never reuse the project root as the work root. Keep every selected root option before the subcommand and never silently fall back to the current directory's default board.
2. For ordinary orientation, run `pinboard overview --json` from the repository checkout and treat its revision-stamped result as the complete default input. When the user has already supplied an exact mutation and its semantic inputs, do not add an overview preflight merely because this skill triggered; use the narrow canonical command or action query directly.
3. If the default `.codex/pinboard` root is absent, report `WORKFLOW_UNAVAILABLE`. Initialize it with `pinboard init --json` only when the user explicitly requests coordinated-work setup. An explicit `--work-root` remains an exact user-selected exception. When a successful fresh initialization reports optional repository-care skills, relay them once in the user-facing result by presenting `$repository-readiness`, `$slop-cleanup`, and `$maintaining-agent-guidance` as optional next steps. The pointer and Codex setting recommendation are advice only: do not invoke a skill, create work, edit configuration, infer that a repository-care recommendation applies, or infer the effective project setting from them.
4. Require the returned authority to be exactly `sqlite-v4`. If validation fails or another authority is reported, stop state-consuming work and use the recovery procedure in `references/state-and-recovery.md`; never infer a fallback from generated views or archived files.
5. Inspecting SQLite state needs no lease. For one project transition, prepare its semantic payload first, using `pinboard input-contract <action-kind> --json` when the fields are not already known. `input-contract` accepts lifecycle action kinds such as `accept-proposal`; it does not accept CLI operation names such as `proposal`, whose command contract comes from `tool-contract --operation proposal --json`. Query the exact action as Role.PROJECT, then run `pinboard transition` with the returned receipt plus the invoking task and host identity. SQLite checks and commits the complete transition atomically. The `close` convenience command applies the same direct project authority for terminal human decisions.
6. Preparation and attempt work use their own renewable leases. Begin ordinary preparation with `pinboard preparation start --item-id <item> --task-id <task> --host-id <host> --ttl-seconds <seconds> --json`; it selects the current definition and either creates the first claim or transfers an inactive retained claim in one transaction. Use exact low-level acquire, transfer, renew, release, and revoke operations for recovery and explicit authority maintenance, not for an ordinary start. Inspect an attempt with `pinboard attempt inspect --attempt-id <attempt> --json`, and follow its derived continuation rather than reconstructing ownership or the next lifecycle action from conversation. Lifecycle state alone does not prove that user input is required; ask only when the recorded condition exposes a product choice the human has not made. If a required precondition is unavailable through a supported read, preserve that missing path as a product defect instead of inventing a value or reading raw SQLite state.

When an invocation, role, authority requirement, artifact shape, or retry rule is not already known, run `pinboard tool-contract --json`, then request only the returned exact operation or action selector. This contract is static and does not need an initialized ledger. The selected operation includes its exact installed `cli_usage`, including the position of optional global roots; follow that grammar instead of guessing flags from neighboring commands. An action's `execution_route` distinguishes lifecycle input for `transition` from `dispatch`, installed inspection, runtime continuation, and runtime blocker evidence. Never pass an advisory action with a null payload schema to `transition`. Do not inspect Pinboard source, reconstruct a command from help prose, or carry a general argument namespace past the selected leaf. For brief construction, choose the boundary from accepted work and run `pinboard tool-contract --brief-starter <local|cross-boundary> --json`. Copy its complete `starter` object, replace every semantic `null` from accepted scope and reviewed evidence, preserve every other field, and apply its canonical byte rule, relational constraints, and fact-validation boundary. Query `--operation brief/publish` only when the full generated validation schema or publication operation facts are needed. Never publish an unresolved, partial, or invented value. Publication does not verify declared Git facts or prove semantic claims.

For a new concern in a newly initialized or existing board, use this ordinary sequence without substituting low-level authority commands: create the strict proposal file and run `proposal --json`; accept it through a freshly queried project action; run `preparation start --json`; compile, independently review, and publish the brief; activate through a freshly queried preparer action; acquire the attempt; dispatch and deliver; submit the candidate for review; then follow `attempt inspect --json` and `review-job --json`. Query a fresh action immediately before every mutation and use the returned receipt as an opaque unit. This sequence applies only after the user has authorized preserving and working the concern; it does not manufacture scope or bypass the detailed preparation and review rules below.

For commands that support `--json`, treat `pinboard-rejected-operation/v1` as the recovery boundary. `status: rejected` and `state_changed: false` mean this invocation committed no Pinboard effect; correct the input, reacquire authority, or use one returned fresh action exactly as classified. `status: committed-effect` names durable surfaces already changed before the operation stopped; inspect current state and do not replay the mutation. A recovery action with `generation: null` uses direct project authority, while a non-null generation and lease must be copied together. Do not infer success or safety from the prose message when these fields are present.

One coding-agent task owns one outcome through final human disposition. Keep product, scope, approval, review, and repository-disposition decisions in that task. Use subagents for bounded research, implementation, verification, and review whose results should return to it automatically. Create another task only for a genuinely independent outcome the human intends to follow in that task's own conversation; it is not a subordinate worker or return destination.

Tell the user which task to follow only when another task was created or responsibility would otherwise be unclear. In multi-task use, recommend one task per distinct independent outcome.

Do not infer work from arbitrary Markdown, historical plans, unchecked boxes, branch names, or transcript memory. Do not directly edit canonical lifecycle fields when the executable can perform the transition.

## Match detail to the question

Keep Pinboard operationally invisible when it is working normally. User-facing progress and receipts describe the user's tasks, decisions, confidence, blockers, and next actions. Do not volunteer the storage backend, command mechanics, generated-view mechanics, revisions, leases, routing, transport, validation steps, or unchanged project state. Include an implementation or process detail only when it changes the result, confidence, risk, requested action, or next step, or when the user asks to inspect or troubleshoot Pinboard itself.

Do not narrate successful generated-view refreshes, rebuilds, or routine retries. Report recovery only when it fails or materially changes the outcome, confidence, risk, or required user action.

Usable artifacts and delivery links are outcome context, not internal mechanics. As soon as an accepted-definition summary, full brief, implementation result, blocker, complete independent review, commit, pull request, or comparable durable result becomes available or materially refreshed, announce it with its purpose and one native clickable link. For a local readable artifact, use the actual supported artifact or generated-view path exposed by current state and verify that it exists before announcing it; never synthesize a target from an assumed directory or filename convention. Do not wait for later verification or bookkeeping; say what remains in progress and continue from the announced result. Link each version once, do not repeat its contents, and report again only when later work changes the result, confidence, risk, or next action. Keep canonical JSON, receipts, leases, immutable storage copies, and queue, current, or history views silent unless the user asks or they are needed to explain such a change.

Do not suppress a higher-level instruction that requires disclosing the first use of a selected skill. Keep that required disclosure to one concise, outcome-oriented acknowledgment for each selected skill. Do not add a separate Pinboard-authored explanation of companion-skill selection, internal routing, or healthy task state.

The presence of a disjoint ready or active item is not a user-facing event. Start the current task normally without naming another task's ownership. Mention another task only when observed write overlap, live contention, changed priority, or required user action affects the current outcome.

Treat a stale action or expired or replaced preparation or attempt lease as routine internal control flow when retained state is safe and the authorized workflow can refresh or reacquire the exact capability. Do not send commentary merely because a command rejected stale authority or rendered that expected race as an error. Refresh and retry silently within the applicable bounded recovery rule. Report only when recovery is exhausted, state is unsafe or inconsistent, work is blocked, the requested outcome changes, or a user decision or new authority is required. Name the holder or expiry only when the user asks to troubleshoot or decide revocation.

Default “where do we stand?”, “what remains?”, “quick status”, and equivalent orientation questions to the single `overview` result. Report active attempts, ordered live items, eligibility, dependency reasons, review flags, and immediate choices. Intake candidates already appear in that order; there is no separate hidden inbox to inspect. Retain the revision stamp privately as freshness evidence; show it only when the user asks for it or when it materially explains stale or conflicting state. Do not read history, project notes, GitHub, branches, CI, delivery state, or old decisions for this default answer. Do not acquire a lease merely to explain the live picture.

Keep inspection, validation, repair, and handover claims distinct. `status`, `overview`, exact item reads, `actions`, and `parallel preview` each report a projection from one current SQLite snapshot; they do not validate accepted artifacts or generated views. `input-contract` is a static description of one action kind and does not read project state. Use `pinboard validate` when integrity matters: it verifies the SQLite snapshot and accepted artifact bytes, then reports generated-view drift as repairable warnings. Validation does not repair; use `pinboard views rebuild` for that separate write. Use `pinboard handover --json` only to materialize one revision-stamped package of the supported project-facts subset from one snapshot and verified artifacts. Preparation and attempt authority remains local. The command does not choose, contact, or write to a receiving tool.

When continuing work from another coding-agent task, extract every named Pinboard item for which that task claims terminal completion and verify each claim with `pinboard item status --item-id <item-id> --json` before treating it as complete. Then use `overview` only to identify remaining live work. Absence from `overview` means only that the item is not currently live; never use that absence to report an item as missing, unrecorded, or unfinished without the exact item-status lookup. Exact item status proves the recorded item and attempt state, not acceptance of a nonterminal checkpoint.

Make the user's next move frictionless at a genuine decision edge. When a response leaves an unresolved item or project state with two to four useful ways to continue, end with one natural sentence that recommends the best-supported next step when evidence supports one and offers the alternatives. Follow it with a shortcut line such as `Quick reply: 1 investigate freshness · 2 admit it · 3 revise it`. Use this pattern especially after item-detail answers, priority or admission choices, and blockers that require user direction. Put the recommendation first when practical. Accept the visible number, a short phrase, or an ordinary sentence as the same intent.

Keep the conversational sentence primary and the shortcut line secondary; do not present bare option names as a robotic command menu. The numbers belong only to the visible offer and are never global application commands. A state-changing option must name its practical effect clearly, and selecting it authorizes only that described effect; resolve current action availability and gather any missing semantic input before executing it. Omit shortcuts when the result is terminal with no follow-up, the user's exact requested action has completed, only one sensible next move exists, or extra options would be filler.

Silence leaves the repository and Pinboard state unchanged and resumable. Never interpret it as completion, deletion, or abandonment.

## Route human task starts through Pinboard

Humans do not need to know the preparation boundary before asking Pinboard to start work. If a human invokes `$pinboard-deliver` to begin a named item without an already prepared active attempt, treat the request as Pinboard start intent rather than a lifecycle error. Give one gentle, non-blocking clarification: `$pinboard-deliver` is the implementer route after Pinboard prepares an active attempt; ordinary wording such as “Use Pinboard to work on <item>” is the intended start. Then continue through the normal Pinboard route when the item and requested outcome are clear. Ask one concrete question only when the intended item or outcome is genuinely ambiguous.

Do not blame the human, lecture about internal routing, expose backend or unrelated task state, or stop after the clarification when Pinboard can continue.

End every compact overview with one short, explicit offer to expand the useful layers: recommendation and item context; completed decisions; delivery and CI; or full history. Phrase the offer as a natural continuation of the conversation, such as “If useful, I can explain why X should come next, recap decisions we already closed, check what shipped and whether CI is green, or reconstruct the full project history.” Follow it with `Quick reply: 1 why next · 2 decisions · 3 delivery/CI · 4 full history`.

Do not invent slash commands for these follow-ups. `$pinboard` is an explicit entry point for invoking the skill in a new or unrelated context, where terse prompts such as `$pinboard quick status` or `$pinboard full history` are valid. It is not a required subcommand inside an ongoing pinboard conversation.

Fetch only the selected expansion:

- For a recommendation or deeper rationale, use the overview itself when it contains enough evidence. Otherwise read only the exact live item records that are plausible choices. Apply the ordering below only then.
- For completed decisions, read terminal item history only. Do not add GitHub or delivery checks.
- For delivery or CI, inspect Git and GitHub only. Do not reconstruct ledger history.
- For full history, say that the answer will be slower, then read the complete relevant ledger and accepted artifact context. Add delivery state only if the user includes it.

When an expansion needs several known project files or headings, inspect their selected sizes with `pinboard brief-sources` before loading their bodies, then read each non-overlapping emitted batch once. For other known facts, use a bounded batch when the available tool supports it. If output truncates, continue at the first unread boundary without replaying returned content. Do not turn one requested layer into an exploratory command-per-item walk. If the user explicitly asks for a zero-tool or last-known answer, reuse the most recent overview from the current conversation and label it as not refreshed. Never present it as current. A requested expansion is not permission to preload the other layers.

This proportional behavior applies to mutation as well as status. After a successful command returns a revision-stamped receipt, do not run a redundant overview merely to confirm what the command already proved. Run broader verification only when the operation lacks a sufficient postcondition or the user asks for it.

## Ownership

- Let `state.sqlite3` own lifecycle, dependencies, attempts, preparation and attempt leases, proposals, history, and accepted artifact references.
- Let `views/` remain generated human-readable output. Never edit it as authority.
- Let accepted brief and evidence artifacts own execution semantics and review receipts; resolve them through their SQLite artifact references.
- Let proposal fact columns preserve the original intake evidence while disposition columns record the later decision and same-identity items own queue state and position.
- Let public project documentation own stable architecture and domain truth.

Project transitions are direct atomic SQLite changes with task and host audit attribution supplied by the invoking trusted local task. Those strings are not authenticated credentials. Disjoint preparation leases reserve exact ready-item definitions before activation, and disjoint attempt leases authorize active item-local work concurrently. Expiry, release, revocation, and higher fencing generations invalidate retained leased actions.

## Coordinate review responsibility and checkout use

Route frozen candidates to the task that owns the outcome, not by conversational ancestry. That task commissions one fresh-context, candidate-read-only review subagent after the candidate is stable. The result returns automatically, and the owning task processes the complete accept-or-correct verdict. Keep the reviewer independent, commission one reviewer by default, and do not duplicate the full review or add reviewers without a concrete risk.

Before commissioning that review, inspect the attempt continuation and run `pinboard review-job --attempt-id <attempt> --candidate-revision <candidate> --json`. Use its prompt unchanged. The read-only job binds the exact protected candidate, accepted brief owner and digest, and the current nonempty `result.md` path and render-time digest. The fresh reviewer must verify those bytes and identities immediately before use and stop if they changed. Rendering a review job does not submit, accept, complete, or otherwise mutate the attempt; the outcome-owning task remains responsible for applying the reviewed result.

Use [the coding-agent runtime adapters](references/runtime-adapters.md) for the native fresh-reviewer launch and wait operations. The exact review job and review responsibility remain shared.

Name the actor and expected next action in every user-facing review update. Describe the default path as `review by a separate Codex reviewer` or `review by a separate Claude Code reviewer`, matching the current runtime and including whether that review is ready, underway, accepted, or returned for correction. Say `ready for your review — <decision requested>` only when the human is actually expected to review or decide something. Do not use bare `independent review` as a user-facing destination when the actor would be unclear.

Do not use or wake another coding-agent task to review or receive the same outcome. Dispatching work, clarifying or widening scope, or sending a prior message does not establish current responsibility. A separate task owns a genuinely independent outcome and reports in its own conversation; it is never a subordinate return path.

If the current runtime cannot create a subagent, keep the exact candidate in review, preserve the durable result and accepted brief, and state that review is waiting for a runtime with subagent capability. Do not create or wake a user-owned task, return routine ownership to a parent task, substitute the implementer as reviewer, or imply that the human must review unless the human explicitly chooses that route.

Treat an explicit user choice of the main checkout or an isolated worktree as settled. Do not ask again. For an explicit worktree choice, use that worktree without a generic warning about possible later integration conflicts. Discuss integration risk only when observed overlap or conflict makes it concrete, or when the later repository-disposition decision requires it.

Before repository writes or worktree creation, infer the likely integration baseline from project Git evidence rather than treating `main`, `origin`, or `upstream` as universal names. Prefer a uniquely resolved remote default branch supported by its symbolic remote head and current tracking or ancestry evidence. Refresh the relevant remote reference when network authority is already available and freshness matters; a local default branch may be stale after remote-only merges. Keep the evidence and inference private when it is strong and the selected checkout already matches.

Treat weaker evidence as a hypothesis. If the selected main checkout is on another branch, its current commit is behind or divergent from the likely baseline, several remotes or targets remain plausible, or no strong project-specific clue exists, pause before writes and state the practical mismatch in one sentence. Ask the smallest confirmation with project-specific choices, recommending the best-supported baseline first; for example, `Quick reply: 1 use <remote>/<default> · 2 keep <current branch>`. Never silently redefine “main checkout” to mean whatever branch happens to be checked out.

When an active or paused attempt has a confirmed branch or base mismatch, an older accepted definition, or both, publish a replacement brief for that same attempt that matches the item's current definition and corrected Git lineage. Then use the supported `rebind-attempt:<attempt>` project action with the corrected branch, base revision, and accepted brief reference. Rebinding atomically replaces the attempt's accepted-scope identity and Git lineage, preserves its active or paused state and evidence, fences the previous worker generation, and never changes the checkout. Acquire fresh attempt authority before continuation or dispatch in the corrected environment.

Before repository writes begin in the main checkout, establish that it is available for the current task. Use current coding-agent task occupancy together with the exact active Pinboard attempt and its dispatch checkout as the existing ownership evidence; do not create persistent checkout ownership state. A matching current task, attempt, and dispatch checkout establishes availability for that task. Another writing task in the main checkout means it is occupied; name that task with its real title when available.

When the user has not chosen a checkout, inspect main-checkout occupancy first, then ask one concise question. Base the recommendation on the observed context: prefer the main checkout when it is available and no concurrent isolation is useful; prefer an isolated worktree for independent concurrent work. End with `Quick reply: 1 main checkout · 2 isolated worktree`.

When the main checkout is occupied, make a bounded overlap assessment from:

- target-checkout or worktree occupancy;
- the intended write paths;
- currently changed filenames; and
- at most the active brief's named owners or source selectors.

Separate direct observations from uncertainty and limitations. Recommend waiting when the intended files overlap or unresolved uncertainty makes waiting safest; otherwise recommend an isolated worktree. Ask one concise question and end with `Quick reply: 1 wait for main checkout · 2 isolated worktree`.

Stop after the bounded recommendation unless further evidence is necessary for the user's decision. Do not turn this assessment into a full-diff review, history walk, test run, open-ended investigation, persistent checkout registry, or generic resource-lock subsystem without concrete evidence that the bounded path fails.

## Prepare delegated attempts

When the owning task prepares and launches a delegated attempt:

1. Run `pinboard preparation start --item-id <item> --task-id <task> --host-id <host> --ttl-seconds <seconds> --json` before loading implementation sources or compiling a brief. The ordinary start chooses the current definition and either creates the first claim or transfers an inactive retained claim inside the same write transaction; a live conflicting claim or no-longer-ready item is rejected without change. The item remains ready. Renew the returned exact lease before it expires throughout source closure, compilation, publication, correction, and review. If work stops, release it. After expiry, release, or revocation, run ordinary `preparation start` again, then re-read the definition and revalidate every applicable closed source receipt against the current checkout. Reuse prior preparation only when both the returned pin and those receipts remain exact; otherwise discard stale draft or review evidence and rerun the affected source closure, brief publication, and review before activation. Reserve low-level `preparation acquire` and `preparation transfer` for exact recovery or contract diagnosis.
2. Open one strict `pinboard-work-brief/v2` JSON candidate pinned to the preparation claim's exact definition revision and digest. Do not publish it until its checkpoint shape, named source selectors, criteria, and exact checks have completed the applicable preparation below.
3. Give every checkpoint a stable kebab-case ID, separate human title, and one typed `local` or `cross-boundary` variant. Use `local` only when ownership and dependency direction, stored and wire identities, and independently owned consumers remain unchanged, and one production entry point can observe the complete changed path. Use `cross-boundary` whenever any of those conditions is false. Local checkpoints retain their lightweight path.
4. Give every checkpoint exactly one tagged architecture-impact value. Use `none` when ownership and dependency direction are unchanged, `read-only` when implementation must conform to a named project-relative authority, and `update-required` when the same candidate must update that authority. Do not defer an architecture update to a separate work item.
5. For a cross-boundary checkpoint, read and follow [references/brief-preservation.md](references/brief-preservation.md) completely: close and challenge the draft authority set, then compile its exact contracts, coverage, verification, and lifecycle disposition. Start from the machine-readable brief contract rather than a remembered field inventory. Publish the prepared brief with `pinboard brief publish --file <candidate> --json`; its accepted `.json` artifact is the sole semantic brief, and its generated Markdown attempt view is read-only convenience output that must never be edited or parsed as authority. Commission the required fresh-context review and prepare its digest-bound ready-evidence candidate for dispatch. Resolve incomplete coverage or authorization through the reference's fixed-point correction path before implementation; do not restart a fresh full review merely because corrected artifact bytes changed, and do not file a code defect for code that does not exist. A local checkpoint skips the cross-boundary procedure but uses the same contract, publication command, and artifact ownership.
   When the accepted item or brief explicitly selects the optional engineering-health baseline, also read [references/engineering-health-baseline.md](references/engineering-health-baseline.md) and preserve its representative contract proof in the brief's authorized contracts and verification. Do not load it because work merely appears complex or cross-boundary, and do not turn it into a default requirement.
6. Select the exact `activate:<item>` action as Role.PREPARER with the preparation lease identity and generation. Activate with the reviewed brief reference; the transaction rechecks its complete identity, consumes the preparation claim, and creates the attempt. After activation or resume makes the live attempt Markdown available, resolve the actual generated-view path from current Pinboard state, apply the readable-link rule above, and mention it once as the full work brief before implementation dispatch. A revised or resumed brief is announced again only when it materially changes. Only after the returned state is active, acquire the attempt lease and select the exact `dispatch:<attempt>` action. Record only `schema`, `checkout`, `branch`, `starting_revision`, and `permissions` in a `pinboard-dispatch/v1` environment JSON file. Permission values are `repository-read`, `repository-write`, `network`, `external-write`, and `live-application`. They declare limits already authorized by the user and execution environment; Pinboard validates and forwards the vocabulary but neither grants nor enforces those capabilities.
7. Run `pinboard dispatch` with the action tokens, stable checkpoint ID, and environment file. For a cross-boundary checkpoint, pass the prepared evidence candidate and review ID so dispatch validates and publishes the evidence before returning the prompt. Dispatch prepares that prompt; it does not create a task. Launch the worker separately as a subagent with the rendered prompt unchanged so its result returns automatically to the owning task. Use `--prompt` to verify a prompt received through another transport before launch. Never dispatch a ready item or a claimless start.
8. Retain the worker identifier and its attempt lease. Do not edit the worker's checkout or review candidate while it is still changing.
9. Wait until the worker finishes or needs attention. A wait timeout, progress update, or successful launch is not a terminal result.
10. After completion, read `result.md` or `blocker.md`, inspect the stable candidate, and mention the new implementation result or blocker with one purpose-labelled clickable link. A corrected candidate gets one new notice for its materially refreshed result; do not repeat an unchanged result or blocker link. Run `pinboard attempt inspect --attempt-id <attempt> --json` and follow its continuation. When it names review, render the exact candidate-bound `review-job` and commission that prompt as a fresh-context subagent from this outcome-owning task. Then process the complete returned verdict through the current-responsibility review route above.

The dispatch prompt identifies the canonical brief, checkpoint, and execution environment. It must not repeat acceptance semantics, checks, deferrals, or source-reading instructions. Change the attempt first when its contract is wrong.

Do not end the owning turn merely because implementation started. End with a running worker only when the user explicitly requested background execution; report that review by a separate reviewer in the current coding agent remains pending and perform it before any acceptance transition.

The responsible task reviews the frozen candidate, then applies the review outcome as one direct project transition. Use `complete:<attempt>` only when the entire work-item outcome is accepted. When an independently buildable checkpoint is accepted and the canonical brief records remaining work, use `accept-checkpoint:<attempt>` with the stable checkpoint ID, exact candidate identity, and nonempty review evidence. That transition archives the exact current `result.md` and `review.md`, pauses the same item and attempt, and fences worker authority. Publish the revised canonical JSON brief at its next artifact revision, then use the ordinary `resume:<item>` with that accepted reference before dispatch. When the protected candidate is accepted but work should continue within the same active attempt, use `accept-review-and-continue:<attempt>` with that exact candidate identity and nonempty acceptance evidence. This distinct transition returns the item and attempt to active, clears the protected candidate, records the accepted candidate and evidence without a checkpoint, sets the next action to continue, and fences the previous worker authority before a worker reacquires it. When review finds an actionable defect, use `return-for-correction:<attempt>` with one concise reason that identifies the durable review evidence. The transition preserves the same attempt and evidence, fences its previous worker authority, and leaves it ready for an explicitly selected worker to reacquire.

## Interpret the available actions

Translate executable actions into ordinary repository and product language. Retain the exact action record privately for execution.

When selecting work, explain:

1. the current product or repository trajectory;
2. what changed after the last accepted item;
3. which items are ready and why;
4. which items are blocked and the exact unresolved condition;
5. which ordering is mechanically determined by dependencies;
6. which choice genuinely requires human priority;
7. the recommended next item and why now.

Prefer, in order:

1. evidence preservation or avoidance of an irreversible transition;
2. prerequisites required by the current product objective;
3. runtime, consumer, or user-visible product evidence;
4. foundation work that is concretely cheaper now;
5. optional hardening only after its recorded reopen condition occurs.

Do not turn that ordering into a score. A recommendation remains an explanation, not an automatic product decision.

## Preview and launch independent work

When the user asks what can run in parallel, asks to choose a batch, or explicitly asks to launch independent work, read `references/parallel-work.md` and follow it completely.

Use `pinboard parallel preview` as read-only structural evidence. It does not authorize task creation or decide product priority. Keep these outcomes distinct:

- listing or previewing creates no tasks;
- an exact selected subset or “all safe work” is launch authority for that batch only;
- each external creation receives a fresh structural check and an explainable separate-task or subagent recommendation.

Never describe a partial external launch as complete. Report one result per requested item and retain the current repository work as the main topic.

## Apply a transition

1. Identify one action as `<kind>:<subject>`. Read its returned `use_case`, `effect`, `permitted_roles`, `subject_kind`, `lifecycle_precondition`, and `practical_result` instead of inferring from the verb. The stable `effect` field says whether the action accepts a lifecycle transition payload; it does not summarize every outer command effect, and dispatch may publish or reuse review evidence while leaving lifecycle unchanged. Treat the exact action record's `authorization` as the runtime authority to forward; the kind-level permitted roles do not replace it. When semantic input is not already settled, run `pinboard input-contract <kind> --json` and prepare the payload before selecting the action. `revise-item:<item>` replaces one complete definition after exact revision-and-digest matching; never synthesize a partial patch. `report-blocker:<attempt>` is a worker advisory with no mutation payload; `block:<attempt>` is the project transition for an active attempt; `block-item:<item>` is the project transition for an unstarted intake item. Blocking may name only dependencies already accepted in the current definition and never changes dependencies itself.
2. For one project change, query only the exact action with `pinboard actions --role project --action-id <kind:subject> --json`. Treat the returned record as one opaque capability receipt and supply the invoking task and host identity to `pinboard transition`.
3. For an attempt- or preparation-local change, query only the exact action with `pinboard actions --role <worker|preparer> --lease-id <lease> --generation <generation> --action-id <kind:subject> --json`. Treat the returned action record as one opaque capability receipt. Forward its `action_id`, `expected_revision`, `generation`, `authorization`, and every non-empty `subject_revision` and `lease_id` value verbatim. Do not infer authorization from the current role, reuse fields from another action, or reconstruct a partial token from prose.
4. Run `pinboard transition` with those exact token fields and the prepared payload file. Prefer `--json` when continuation matters: after a successful commit it reloads current canonical state and includes the derived attempt continuation. A generated-view refresh warning does not undo the authoritative transition. If continuation rendering itself is unavailable after commit, preserve the receipt, inspect the attempt afresh, and do not replay the transition.
5. On `STALE_ACTION`, discard the retained receipt, reselect only the same exact action, and retry silently while its semantics and payload remain unchanged, retained state is safe, and existing authorization can refresh or reacquire the required capability. Never reuse the stale token. Stop when the action disappears, its semantics, required role, or payload changes, authority cannot be refreshed, state is invalid, or the current lease or turn deadline cannot accommodate another attempt; report only the resulting blocker, changed outcome, unsafe state, or required decision. If the exact freshly selected receipt is rejected without an intervening ledger revision, preserve the evidence and report an executable contradiction.
6. On `ACTION_NOT_AVAILABLE`, do not replay the same command, switch roles, or skip to another lifecycle state. Validate once and refresh only the same exact action under fresh authority. If it disappeared, follow the resulting state and report it only when the user's outcome or next action changed. If it is now available, apply its fresh receipt once under the `STALE_ACTION` rule; treat only an unexplained rejection without an intervening ledger revision as an executable contradiction.
7. If a task is interrupted before a receipt is visible, never replay its retained action. Follow the interrupted-transition recovery in `references/state-and-recovery.md`; authoritative state distinguishes no change from one complete committed transition, and a fresh lease generation fences the abandoned action.
8. Report the practical effect of the returned transition. Keep its internal revision and command receipt private unless they materially affect confidence or the user's next action. Run `pinboard validate` immediately after any non-tool edit to supporting attempt artifacts.

The executable rejects stale definition identities, expired or replaced lease holders, illegal states, invalid dependencies, and inconsistent references. Actions that require current accepted scope remain unavailable to attempts pinned to an older definition; rebind is the explicit active-or-paused recovery that accepts a matching current-definition brief and corrected Git lineage together. It does not decide whether evidence is true, whether work is valuable, or what product behavior should mean.

For an explicit terminal human decision about non-active live work, use one `pinboard close <item> --outcome <done|dropped> --reason <text> --task-id <current-task> --host-id <current-host>` invocation instead of manufacturing intake, ready, active, or attempt states. The command applies one direct atomic project transition. Do not precede this exact command with overview or action-list reads. Use `done` when the recorded decision or outcome is complete and may satisfy dependents. Use `dropped` only when the work is intentionally abandoned and has no live dependents. Never use `close` to bypass review for active or review work; keep the normal evidence-backed completion transition there. The returned revision is the durable receipt, so do not create a temporary payload file or re-read status after success.

## Safe boundaries

Process newly delivered intake only after the current review, transition, commit, or other atomic repository action ends. Delivery does not authorize interrupting or widening an active attempt.

Intake persists immutable proposal facts and a same-identity intake item. It appends at the back by default or uses an explicitly requested one-based position, and relation semantics may add a dependency or review flag. It does not mark the item ready, create or activate an attempt, pause current work, or complete anything. When intake is embedded in ongoing work, keep a compact continuation anchor in the current task context before invoking it:

- the pre-intake objective;
- the next action already promised;
- the exact active or paused item, attempt, proposal, or durable selector that owns the facts after context compaction.

After persistence and optional notification handling, return to that anchor in the same turn. Re-read the durable selector when compaction made conversational memory uncertain; do not create a scheduler or recovery record. Before the final response, reconcile every announced pending action as completed, durably deferred at an exact owner, or blocked by one exact decision.

Conditional follow-up language such as “if this is a production defect, follow it up” authorizes one bounded disposition only after the named condition is proved by current evidence. Evaluate the condition first. If it is false or unproved, make no ledger write. If the exact observation and consequence are already recorded, reuse that owner and make no new write. If the condition is proved and the exact concern is new, create at most one `follow-up` or `independent` intake proposal through `$pinboard-intake`, choosing the relation from the evidence. Never turn this conditional authority into a prerequisite, admission, preparation, activation, implementation, notification, or unrelated intake. Record the evidence, relation to current work, and smallest useful next decision; then return to the continuation anchor.

Deliberate steering is distinct from intake. Insert a genuine prerequisite only at a safe boundary, pause or block the displaced objective through its legal transition, and name the ordinary `resume:<item>` action that restores it. Recovery is for interrupted or inconsistent state, not the normal route back to preserved work.

### Reconcile material concerns before reporting them

Before presenting a discovered out-of-scope concern as planned, preserved, covered, queued, deferred, or future work, determine the disposition of that exact concern. A broader item with a compatible theme is not exact coverage.

Use one of these durable dispositions:

- `already recorded`: the exact observation and its consequence were durable before the current report;
- `recorded now`: the exact observation was absent and this turn added it to its authoritative item context or created an intake proposal;
- `not recorded`: no exact durable owner exists, persistence was not authorized, or persistence failed.

When the concern belongs to an existing admitted item but its accepted semantics are incomplete, read the current definition and use `pinboard item revise` with one complete replacement, exact expected identity, source task, and reason. A retained attempt then remains pinned and stale; use its legal review-correction path when a candidate is protected, publish a matching revised canonical brief, and rebind the active or paused attempt before continuation. When no admitted item owns the concern, use `$pinboard-intake` if the user has explicitly authorized preservation.

Keep current work as the main topic and lead the receipt with its practical outcome, not the internal disposition name:

- For `already recorded`, say `Saved for later — <concern> is already in <exact owner and state>; current work <continues | is blocked by it>.` For `recorded now`, say `Saved for later — <concern> is now in <exact owner and state>; current work <continues | is blocked by it>.`
- For an explicit dismissal, say `Not saved — <concern> was dismissed at your request; no follow-up remains.`
- For completed work, say `Completed — <result>; no follow-up needed.` Do not introduce completed or dismissed work as a durable concern or saved follow-up.

A material `not recorded` disposition is unresolved and must not end as a bare receipt. State the concern, exact cause, durable state, current-work impact, and next action owner. Then produce exactly one resolution:

- If preservation lacks authorization, ask one concrete preserve-or-dismiss question: `This needs a decision — <concern> is not saved because <cause>. Current work <impact>. Should I preserve it for later or dismiss it?`
- If a safe retry needs no new authority and does not change the outcome, retry silently before the terminal response. If that retry cannot finish, report the persistence failure and its current-work impact once.
- If retry needs new authority, changes scope, or overrides another owner, ask one concrete approval question that names the action and consequence.
- If persistence still fails after the permitted retry, report the same four facts and ask the one decision that can actually resolve it. Never leave `not recorded` as a terminal aside.

Let `recorded now` mean this turn before the update. For `already recorded`, include the earlier durable selector or timestamp. Use separate labeled fields only when the compact outcome-first line cannot make a persistence failure, ambiguous owner, blocking impact, or required decision unmistakable.

Never use a later edit to imply earlier coverage. If a broad item existed before the report but the exact observation was added only after a question or challenge, say both facts explicitly.

When an active attempt discovers a prerequisite:

1. preserve its current result and verification;
2. use `$pinboard-intake` to propose the prerequisite;
3. report the advisory `report-blocker:<attempt>` from the worker context, then have the owning task select the exact project transition: use `block:<attempt>` only when its named dependencies already exist in the current definition, or `pause:<attempt>` when preserving work without such a condition; revise the complete definition first when a newly accepted dependency is required, and never use the intake-only `block-item:<item>` action for active work;
4. implement the accepted prerequisite independently from the current integration base;
5. resume the preserved attempt only after its freshness check passes.

Never absorb the prerequisite silently into the current attempt.

## Review and completion

Treat worker completion as a review request, not acceptance. Compare the attempt brief, diff or commit, result receipt, and fresh proportionate verification. Check the architecture declaration against the final owner and dependency-direction diff: `none` must be truthful, `read-only` must conform to its named authority, and `update-required` must include a coherent same-candidate authority change. For a reviewed cross-boundary brief, reuse its compiled authority map and account for every acceptance criterion, Contract row and authorization basis, coverage row, and lifecycle sibling row. When the checkpoint invokes the [developer-navigation lens](../repository-readiness/references/developer-navigation.md), verify the final representative trace, sibling edit sites, retained exhaustive owners, and dynamic-wiring failure mode against the frozen candidate. Every piece of blocking review feedback must cite an accepted Contract row, criterion, reviewed authority, or applicable repository rule. Classify it as an implementation defect, brief omission, authority contradiction, product decision, or new capability. A correction review may reuse exact unchanged selector digests and owners, but it must re-read changed owners and sweep every changed or neighboring row before returning one complete correction package. Complete the item only when every acceptance criterion is satisfied and current knowledge owners are reconciled.

The owning task owns review publication. After the candidate-read-only reviewer returns a complete verdict, write that verdict to the active attempt's `review.md`, then mention its purpose with one native clickable link before announcing or applying the outcome. Use this same order for acceptance, return for correction, accepted checkpoints, accept-review-and-continue, and terminal completion. Do not separately link immutable copies archived by acceptance transitions, and do not re-announce an unchanged verdict during repository disposition.

Before presenting a candidate, accepting review, offering repository disposition, or wrapping up, account for every user direction and repository change after the current accepted brief or exact candidate was established. Distinguish work that implements the current brief from a change to accepted semantics. When semantics changed, do not present, submit, accept, or complete against the superseded identity: replace the complete item definition, publish a matching canonical brief, rebind the active or paused attempt to that current scope and its accepted Git lineage, produce a new exact candidate, and obtain a new exact-candidate review.

Use the existing lifecycle route that matches the current state. Before submission, revision makes the active attempt stale; publish the matching brief and rebind it without changing its active state. While a candidate remains in review—even after a favorable reviewer verdict—return it for correction with a reason that says accepted scope superseded the candidate rather than calling the implementation defective, then revise, publish, rebind, implement, submit, and review again. After `accept-review-and-continue` has already returned the attempt to active, revise, publish, and rebind without a review-state return. A paused attempt follows the same publication and rebind path while remaining paused, even when live dependencies keep resume unavailable. After terminal completion, preserve the terminal history and treat later direction as new work.

At every workflow-ending reply after implementation, review, repository disposition, follow-up, or terminal confirmation, state whether the coding agent is finished. When a user action remains, invite exactly one applicable next action: review the result, merge or publish the accepted candidate, answer one unresolved follow-up, or confirm closure. Once terminal confirmation has completed the last action, state that no further action remains. Keep immediate artifact announcements visible, but do not treat them as this closure statement. Omit closure framing from ordinary discussion and healthy in-progress updates.

After a repository candidate is accepted, keep its code acceptance, Pinboard state, commit state, branch integration, remote publication, and deliberate deferral distinct. Before asking the human to wrap up, refresh only the decision-relevant facts: review outcome; dirty or committed state; current branch and checkout or worktree; intended target; known filename overlap or conflict risk; and remote delivery status when it affects the choice. State observations, uncertainty, and limitations. A separate worktree avoids competing writes in one checkout but does not make later integration conflict-free.

Recommend the best-supported next action and offer two to four concrete alternatives whose repository effects are explicit. End with a numbered `Quick reply:` line. When remote publication is available, include `commit the candidate, push its branch, and open a draft PR` as one choice alongside any useful commit-only, named-branch integration, or publication choices. Do not imply that the draft-PR path is required. Perform only the action the human selects. Do not routinely offer leaving the candidate unchanged, uncommitted, or isolated, or leaving the work for later. If the human explicitly asks to leave it for later, acknowledge that deliberate deferral. Otherwise, an accepted candidate with no acknowledged repository disposition remains a concise conversational obligation: mention the unresolved choice in later responses, even after a topic change, until the human chooses a concrete disposition. Keep this obligation in the active conversation; do not create a scheduler, reminder store, or persistent checkout owner.

After the selected administrative action, refresh the same bounded repository facts. When they show that an exact isolated worktree is disposable, first verify that no active coding-agent task or Pinboard attempt uses it, that it has no needed uncommitted changes, and that it has no needed unintegrated branch work; then suggest removing that exact path as part of closure. Do not suggest deletion when any check fails or remains unknown, and do not treat merge status alone as sufficient evidence. Ask the human to confirm whether the task can be considered done. Do not perform the terminal completion transition before that explicit confirmation, and do not manufacture integration or publication as a prerequisite when the human knowingly accepts another disposition.

For an accepted intermediate checkpoint, use the checkpoint acceptance path above. Its paused item and attempt remain nonterminal, checkpoint evidence remains immutable under the same attempt, and terminal item history remains absent until a later full-outcome completion. For an accepted intermediate review inside an unfinished checkpoint, use `accept-review-and-continue:<attempt>` instead; it records the passing review without accepting the checkpoint and leaves the fenced attempt ready to continue after a worker reacquires it.

Use `return-for-correction:<attempt>` for an implementation defect against an accepted owner or when newly accepted semantics supersede the protected review candidate. In the second case, record scope supersession rather than calling the implementation defective, then follow the complete definition-and-brief replacement route above. For a brief omission, authority contradiction, unresolved product decision, or new capability that has not become accepted scope, preserve the review evidence and stop before any lifecycle transition until the existing upstream owner resolves it; do not turn the review feedback into implementation scope or invent a state, transition, or alternate acceptance path. For an implementation defect, record the exact correction reason instead of completing the item, manufacturing a new attempt, or editing lifecycle files. Report the outcome compactly: `Returned for correction — <reason>; the same attempt and review evidence are preserved and ready for a named worker to reacquire. No acceptance occurred.` If the executable does not offer that action for a valid review return, preserve the review evidence and report the workflow blocker; do not bypass the missing transition.

Move terminal scheduling state out of the live queue in the same transition that preserves its history receipt. Do not manufacture follow-up work when the honest result is no follow-up.

Read `references/state-and-recovery.md` only for lease revocation, invalid SQLite state, or interrupted transitions.
