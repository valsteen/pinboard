# Work-item consolidation

Load this phase only when the human requests combining saved work. The [main conversation core](../SKILL.md) owns decisions and replies. The preview below is read-only until separately approved.

## Preview work-item consolidation

When a user wants to combine saved work, first ask them to identify the live items to compare if the selection is not already explicit. An optional proposed owner is part of that selection. Keep this first pass read-only: it recommends a smaller backlog but changes no item, relation, priority, proposal, attempt, or accepted artifact. Do not use `merge-proposal` to combine accepted work-item definitions; it only disposes an intake proposal.

1. Read the current overview for live order, direct dependencies, planned replacements, preparation, and attempts, plus the complete current definition and exact status of each selected item and optional owner. Report each item's ID, definition revision and digest, lifecycle state, and sampled project revision; a missing or terminal selection cannot support a current preview. These reads are not one atomic snapshot: reconcile their project revisions, refresh changed selections and affected live relationships, or label the comparison stale and stop short of an assured recommendation. Do not read unrelated retained history or use generated item views as definition authority.
2. Compare the selected objectives, effects, obligations, scope, criteria, exclusions, dependencies, evidence, and stopping or reopening conditions. Give every obligation and distinct material scope fact one source key such as `item-id@definition-revision/obligation/obligation-id` or `item-id@definition-revision/scope/1`, with exactly one proposed disposition: owner outcome, named checkpoint, retained independent item, already covered item, or explicit dismissal. Coverage names the exact destination and evidence; a similar title or broad theme is insufficient. Keep conflicting claims, uncertain evidence, and unmatched facts visible, and retain a concern independently while its disposition is uncertain.
3. Recommend one owner only for one concrete product outcome. A checkpoint must deliver independent value and leave nonempty work toward that outcome. Keep separate ownership for different consumers, stopping conditions, uncertainty, or reopening triggers. If no coherent owner exists, say so and show the completed map rather than forcing a merge.
4. Show what applying the map would do to every affected dependency edge and live queue position, including downstream items found through the overview, with each planned-replacement cost and any preparation claim or active, paused, or review attempt that constrains revision or closure; proposed absorption cannot bypass current work, its pinned definition, or independent review. Name the exact action IDs currently available for each affected subject and a conditional order for later application; `revise-item`, `record-replacement`, `rebind-attempt`, `close`, and the review or completion actions each retain their own legality. For an unavailable action, explain the prerequisite instead of inventing a consolidation mutation.
5. Present the concern map and impacts as a proposal and ask for a separate decision before any application. After approval, reread exact current definitions, statuses, overview relationships, and fresh action receipts; changed identities require a revised map. Apply only the approved changes through their existing actions in the stated order, checking each committed effect before the next action.

A retrospective portfolio comparison can illustrate a recommendation, but label its historical definitions and lifecycle facts as retrospective. Dogfood the procedure separately on an explicit current live cohort and record whether the ledger revision stayed unchanged during that preview; concurrent work may advance the revision, so attribute only observed effects rather than treating equal revisions as the sole proof.
