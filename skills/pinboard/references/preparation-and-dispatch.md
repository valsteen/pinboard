# Preparation and dispatch

Load this phase when authorized work starts or resumes and before preparing or dispatching it. The [main conversation core](../SKILL.md) owns scope, limitations, opportunity suggestions and the human picture. Load [brief preservation](brief-preservation.md) only for a cross-boundary checkpoint.

For brief construction, choose the boundary from accepted work and call `pinboard_brief_contract` operation `starter` with exact roots and that boundary. Copy its complete `starter`, choose one returned structural variant at every applicable `selection_path`, replace only those values with complete templates, then fill each semantic `null` from accepted scope and reviewed evidence. Preserve the remaining fields and apply its canonical byte rule, relational constraints and fact-validation boundary. Use operation `full` when the generated schema is needed. Never publish unresolved, partial or invented values. Publication does not verify declared Git facts or prove semantic claims.

Publication verifies the current accepted definition, complete obligation correspondence, and fixed checkout-policy agreement. Activation additionally verifies the brief's owner, branch, base revision, actual checkout classification, and declared source authorities against the exact selected checkout before lifecycle mutation.

For an authorized new concern, load the complete intake skill through the runtime's advertised native skill loader (`Skill` for `pinboard:pinboard-intake` in Claude) before proposal construction. If that loader is unavailable, read the actual sibling `../../pinboard-intake/SKILL.md` completely; unavailable complete content stops intake. Follow that owner through persistence and its immediate-start continuation.

For immediate-start continuation after proposal persistence, start preparation for the same-identity ready item through `pinboard_preparation_authority`. When the accepted checkout policy is isolated, create or select the actual isolated checkout through the runtime adapter before constructing or publishing the brief. Use that checkout as `project_root`, keep the exact shared `work_root`, and read its branch and full base revision there. Do not publish an isolated brief from the original checkout or change the brief to main merely because no worktree exists yet. Publish through `pinboard_brief_publish`, commissioning independent brief review for a cross-boundary checkpoint; activate through the fresh preparer receipt and accepted brief reference. Select project dispatch and call `pinboard_dispatch` to publish the immutable prompt and native envelope. The fresh worker follows the runtime adapter's verifier and startup contract. Submit the candidate through the fresh worker receipt and `pinboard_transition`; inspect its continuation through `pinboard_attempt_inspect` with explicit reconciliation observations or `null`, then follow the one returned operation. Query a fresh action before every transition and copy its receipt as an opaque unit. This sequence does not manufacture scope or bypass the preparation rules below and [review rules](review-and-disposition.md).

## Checkout and baseline

Treat an explicit user choice of the main checkout or an isolated worktree as settled. For requested isolation, select the actual isolated checkout—not a feature branch in the original checkout—before recording the brief's branch and base revision, activating, or dispatching; if an existing attempt's recorded Git lineage must change, use the same-attempt replacement-brief and rebind route below first. Discuss integration risk only when observed overlap or conflict makes it concrete or the repository decision requires it.

After selecting a newly created implementation worktree for repository writes, follow the repository's exact worktree-preparation command before Pinboard preparation or implementation source work. Run it once for that checkout; do not substitute global installs or another checkout's mutable dependency directories. If setup fails, follow the runtime adapter's [source-worktree setup recovery](runtime-adapters.md#source-worktree-setup-recovery). When the task changes its own preparation or verification tool, preserve base setup as bootstrap evidence, keep stable installed tooling only for coordination, and verify the changed candidate directly.

Before repository writes or worktree creation, infer the likely integration baseline from project Git evidence rather than assuming `main`, `origin`, or `upstream` are universal: prefer a uniquely resolved remote default branch supported by its symbolic remote head and current tracking or ancestry evidence, refreshing the remote reference when network authority exists and freshness matters, since a local default branch may be stale. Keep strong evidence private when the selected checkout already matches.

Treat weaker evidence as a hypothesis. If the main checkout is on another branch, behind or divergent from the likely baseline, several targets remain plausible, or no strong project clue exists, pause before writes, state the mismatch in one sentence, and ask the smallest confirmation with the best-supported baseline first, for example `Quick reply: 1 use <remote>/<default> · 2 keep <current branch>`. Never silently redefine “main checkout” as whatever branch is checked out.

When an active or paused attempt has a confirmed branch or base mismatch, an older accepted definition, or both, publish a replacement brief for that same attempt that matches the item's current definition and corrected Git lineage. Then use the supported `rebind-attempt:<attempt>` project action with the corrected branch, base revision, and accepted brief reference. Rebinding atomically replaces the attempt's accepted-scope identity and Git lineage, preserves its active or paused state and evidence, fences the previous worker generation, and never changes the checkout. Resume a paused attempt after rebinding. If replacement supersedes an outstanding correction, follow [replacement-brief review recovery](review-and-disposition.md#recover-after-a-brief-replacement) before dispatch. Otherwise, in the corrected environment, select project dispatch, publish or reuse the immutable prompt reference, launch a fresh worker, and require prompt verification before that worker acquires fresh attempt authority and selects leased continuation. The fresh reviewed dispatch checks reviewed authorities against the accepted base commit, so uncommitted authority edits from the attempt do not prevent relaunch. Correction dispatch continues to check the current checkout and requires fresh correction source review when those edits affect reviewed authorities.

Before repository writes begin in the main checkout, establish that it is available: a matching current coding-agent task, exact active attempt, and dispatch checkout establish availability without persistent checkout ownership state, while another writing task there means it is occupied, named by its real title when available.

When the user authorized immediate work without choosing a checkout, select the main checkout without asking when its baseline is strongly resolved, it is available, and isolation has no concrete benefit. Prefer an isolated worktree when independent concurrent work makes isolation useful; otherwise ask the smallest checkout question the baseline or contention evidence supports, with text fallback `Quick reply: 1 main checkout · 2 isolated worktree`.

When the main checkout is occupied, assess overlap only from target-checkout or worktree occupancy, intended write paths, currently changed filenames, and at most the active brief's named owners or source selectors. Separate observations from uncertainty; recommend waiting when files overlap or uncertainty makes waiting safest, otherwise an isolated worktree, and ask one concise question with text fallback `Quick reply: 1 wait for main checkout · 2 isolated worktree`.

Stop after the bounded recommendation unless further evidence is necessary for the user's decision. Do not turn this assessment into a full-diff review, history walk, test run, open-ended investigation, persistent checkout registry, or generic resource-lock subsystem without concrete evidence that the bounded path fails.

## Prepare delegated attempts

For a newly created implementation worktree, complete the repository-owned preparation command described above before acquiring preparation authority or reading implementation sources. Record that successful base setup in the brief's bootstrap when the task changes the preparation command, dependency locks, package-manager contract, launcher, validator, or another tool needed to assess itself. The worker must exercise the changed candidate separately; stable installed tooling remains coordination infrastructure.

Before the owning task publishes either a local or cross-boundary brief, resolve every executable, package, or module named by mandatory verification to a repository-owned entry point, a declared dependency or toolchain, or documented runtime or standard-library support. Resolution is necessary but not sufficient: separately confirm that the exact command is appropriate for this repository's guidance and supported consumers. Apply the main skill's [repair responsibility](../SKILL.md#keep-assurance-inside-accepted-product-scope) to an available-tool defect or agent-selected unsuitable invocation, correcting it under existing authority while preserving the required evidence. If a required capability cannot be resolved or remains degraded, stop its affected preparation without guessing, substituting, repeatedly recovering, or silently omitting the check. Ask the human only for missing authority or a revised scope and evidence contract; runtime permission recovery remains with the runtime adapter.

When a cross-boundary outcome remains materially broad because it contains multiple independently valuable product effects or distinct required outcomes, regardless of file or command count, make its delivery shape explicit before publication. Record independently useful checkpoints with nonempty required remaining work, or one concrete reason the outcome is indivisible. Measurement, source enumeration, and report-only artifacts are evidence, not independently useful delivery checkpoints. Preserve complete accepted scope across the sequence and keep later required work nonoptional.

When composing any brief for a change that adds an agent-facing output, a failure path, or a multi-step effect, check the managed project's recorded readiness tier or equivalent repository policy. This readiness hook is mandatory only under that existing policy: map the affected capability to a brief contract or criterion sized to it, preserving the exact authority and verification. Use the [agentic-readiness method](../../repository-readiness/references/agentic-readiness.md) to identify the capability, not to create a new guarantee. Without that policy, keep the hook non-blocking. An explicitly accepted readiness obligation still applies through the general assurance rule above; it does not activate this automatic hook. Guidance written by the current change supplies no retroactive basis, and the hook does not select the optional engineering-health baseline.

Prepare and launch the delegated attempt as follows:

1. After the [material-limitation assessment](../SKILL.md#resolve-material-architecture-limitations-before-preparation) is resolved and recorded in the accepted definition, call `pinboard_preparation_authority` with exact roots, operation `start`, item, task, host, and TTL before loading implementation sources or compiling a brief. The ordinary start chooses the current definition and either creates the first claim or transfers an inactive retained claim in the same write transaction; a live conflicting claim or no-longer-ready item is rejected without change, and the item remains ready. Renew the exact lease before it expires throughout authority selection, compilation, publication, correction, and review, and release it if work stops. After expiry, release, or revocation, inspect preparation `status`, call ordinary `start` again with your own task and host, re-read the definition, and revalidate every applicable reviewed-source receipt against the current checkout. Reuse prior preparation only when the returned pin and those receipts remain exact; otherwise discard stale draft or review evidence and rerun the affected selection, publication, and review before activation. A live conflicting holder is never permission to transfer or revoke it.
2. Open one strict `pinboard-work-brief/v4` JSON candidate pinned to the preparation claim's exact definition revision and digest. Resolve the accepted definition's checkout policy to `main` or `isolated`; `coordinator-selected` permits either after the ordinary occupancy decision. Record exactly one correspondence row for every stable accepted implementation obligation, targeting an existing contract, criterion, or permitted deferral without replacement prose. Put `remaining_work` only inside a `continue` checkpoint disposition; use the fieldless `terminal` disposition only when reviewed completion may close the item. Candidate scope, criteria, verification and any continuing work describe only the product or repository state that the worker must produce for independent review. Never put independent review, integration, publication, disposable checkout or branch cleanup, or terminal Pinboard closure into that worker contract; those are later effects retained by the owning coordinator under the repository-disposition authority. Do not publish until the selected checkout exists, the correspondence is complete, and the checkpoint shape, named source selectors, criteria, and exact checks have completed the applicable preparation below.
3. Give every checkpoint a stable kebab-case ID, separate human title, and one typed `local` or `cross-boundary` variant. Use `local` only when ownership and dependency direction, stored and wire identities, and independently owned consumers remain unchanged, and one production entry point can observe the complete changed path. A README edit plus its referenced image is a representative local family when both remain under the same owner and the edit changes no behavior, dependency, stored or wire identity, or independent consumer. Use `cross-boundary` whenever any condition is false. Local checkpoints retain their lightweight path.
4. Give every checkpoint exactly one tagged architecture-impact value. Use `none` when ownership and dependency direction are unchanged, `read-only` when implementation must conform to a named project-relative authority, and `update-required` when the same candidate must update that authority. Do not defer an architecture update to a separate work item.
5. For a cross-boundary checkpoint, read and follow [references/brief-preservation.md](brief-preservation.md) completely: freeze the accepted outcome, assurance model, constraints, stable authorities, and explicit uncertainty, then select the smallest evidence set that can challenge the planned change and compile its exact contracts, coverage, verification, lifecycle disposition, and obligation correspondence. The brief names semantic owners and acceptance boundaries, not every implementation file; start from the machine-readable brief contract rather than a remembered field inventory. Publish the complete structured brief through `pinboard_brief_publish` with exact roots; its accepted `.json` artifact is the sole semantic brief, and its generated Markdown attempt view is read-only convenience output never edited or parsed as authority. Publication checks structural correspondence completeness and forbidden deferrals; independent review owns whether each selected target truthfully discharges its obligation. Commission the required fresh-context review and prepare its digest-bound ready-evidence candidate for dispatch. When the reviewer finds blocking defects, publish its complete `pinboard-work-brief-review-needs-correction/v1` evidence through `pinboard_brief_review` operation `publish` with that exact `brief_artifact_ref_id`; operation `status` on the same reference recovers the canonical brief, latest verified review and findings, and structured correction targets. Correct and republish before independent reassessment under the reference's bounded-correction policy; a changed canonical digest begins a new negative-evidence stream but does not itself require a fresh reviewer. Needs-correction evidence never authorizes dispatch, changes lifecycle, or acquires authority, and its absence says nothing about ready-review evidence. Resolve incomplete semantics, authority roles, coverage, correspondence, or explicit uncertainty through that bounded correction before implementation, and do not file a code defect for code that does not exist. A local checkpoint skips the cross-boundary procedure but uses the same contract, MCP publication tool, and artifact ownership.
   When several implementation sources need a reusable plan, call `pinboard_brief_source_plan_output` operation `plan-to-file` with the structured manifest, explicit destination, positive batch ceiling and exact roots. The tool writes the same canonical `pinboard-brief-source-plan/v1` bytes that stdout planning would return and emits only a compact receipt; then read every batch in order through read-only `pinboard_brief_sources` operation `emit-file` with that plan path and batch index. Keep operation `plan` for cases where the complete plan itself is the requested inspection result. Never overwrite a differing destination. Treat a committed selected-output failure as non-replayable and inspect its exact path before choosing a new explicit destination.
   When the accepted item or brief explicitly selects the optional engineering-health baseline, also read [references/engineering-health-baseline.md](engineering-health-baseline.md) and preserve its representative contract proof in the brief's authorized contracts and verification. Do not load it because work merely appears complex or cross-boundary, and do not turn it into a default requirement.
6. Call `pinboard_actions` for exact `activate:<item>` as preparer with its lease and generation, then `pinboard_transition` with that receipt, the same authority, and only `brief_artifact_ref_id` in the payload. The shared boundary reads the accepted brief, requires its owner to match the preparer, and verifies the exact current definition, checkout classification, branch, HEAD, and reviewed authorities; the primary checkout is `main` regardless of its current branch, and only a registered linked worktree of the same common repository is `isolated`. The locked transaction rechecks the live definition pin, consumes the preparation claim, and creates the attempt; rebind and replacement-brief resume repeat the definition and checkout check. Announce the brief link after activation or resume. Once active, select exact project-only `dispatch:<attempt>` without worker authority and build the structured `pinboard-dispatch/v2` environment: runtime, background disposition, checkout, branch, starting revision, host, required fresh context, bounded lease TTL, and already-authorized permissions. Dispatch rechecks the current definition and actual checkout classification; Pinboard validates these declarations but neither grants nor enforces runtime access.
7. Call `pinboard_dispatch` with exact roots and `dispatch.kind: ordinary` for a local launch, or `reviewed` with the independent `brief_review` object and `review_id` for initial cross-boundary work, carrying the fresh project `receipt`, stable `checkpoint_id`, structured `environment`, and explicit `prompt: null`. After return-for-correction, use `kind: local-correction` for a local checkpoint with an independent review bound to the accepted brief, or `kind: correction` for a cross-boundary checkpoint with a fresh effective contract review; both require the exact selected `correction_history_id`, returned candidate, and canonical reason, and cross-boundary correction refreshes source receipts from the implementation checkout. Dispatch rechecks selected bytes before publication and returns immutable prompt identity, publication accounting, and one exact runtime-specific native launch recipe; it creates no task or worker authority. Call exactly `native_launch.tool` with exactly `native_launch.arguments`: never add, remove, shorten, reformat, or reconstruct an argument from `prompt_reference` or prompt bytes, and never copy the prompt body into the launch call. A supplied `prompt` only checks exact canonical bytes. A worker launched from different arguments is invalid: stop it and use a fresh context with the returned recipe instead of coaching or resuming it. Never dispatch a ready item or require authority before the worker exists.
8. The worker follows the runtime adapter's prompt-verification and startup contract: verify and read the exact named prompt, use its complete canonical brief and bootstrap, obtain its own trusted post-launch runtime identity, use the verified host, acquire own authority, and select the leased continuation. Retain that identity and returned lease and generation. Successful delivery continues through current result evidence, candidate observation, own-leased submission, protected-review confirmation and lease release; do not coach a worker that returns after only editing source. Never substitute a parent/session identity, invent a pre-launch worker identity, or edit its changing checkout or review candidate.
9. Wait until the worker finishes or needs attention. A wait timeout, progress update, or successful launch is not a terminal result.
10. After completion, read `result.md` or `blocker.md`, inspect the stable candidate, and announce the new or materially refreshed result or blocker under the readable-artifact rule. Call `pinboard_attempt_inspect` with exact roots, attempt, and either `reconciliation: null` or fresh outer-owned reconciliation observations, then follow its one continuation. An incomplete worker return or blocker does not transfer implementation, submission, or review ownership to the coordinator; preserve it and follow the returned continuation or fix the supported product blocker before a fresh launch. When inspection names review, render the exact candidate-bound `review-job` and commission its returned native envelope as a fresh-context subagent from this outcome-owning task. A rejected review job publishes no reviewer prompt: correct its stated precondition, and never construct a substitute prompt or direct the reviewer toward approval. After a favorable verdict, record its exact candidate-bound ready identity before resumed inspection can select repository work. Then process the complete returned verdict through the [current-responsibility review route](review-and-disposition.md#coordinate-review-responsibility-and-checkout-use).

The canonical dispatch prompt identifies the brief, checkpoint, declared environment, trusted worker identity source, and result or blocker paths. It includes the exact accepted brief bytes rather than a restatement, so every acceptance semantic, check and deferral reaches the worker without an indirect instruction fetch. The transport-owned envelope adds the exact verifier, acquisition, continuation and successful-return instructions. Change the attempt first when its contract is wrong.

Do not end the owning turn merely because implementation started. End with a running worker only when the user explicitly requested background execution; report that review by a separate reviewer in the current coding agent remains pending and perform it before any acceptance transition.
