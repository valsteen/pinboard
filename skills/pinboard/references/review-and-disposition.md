# Review and repository disposition

Load this phase for commissioning or processing review, correction, brief replacement, integration, repository cleanup or completion. The [main conversation core](../SKILL.md) owns human authority, product status, review-actor language and replies. Load [runtime adapters](runtime-adapters.md) for native launch and exact request contracts.

## Coordinate review responsibility and checkout use

For a human-owned PR whose author is not a Pinboard worker, use `pinboard_pr_review` on its ready item. Record a canonical brief tied to the current definition, exact requirement sources, expected behavior, consumers, owners, PR, and applicable repository criteria. Have a different task review that brief before recording a round. The coding harness supplies each full observed PR commit and observation source; Pinboard does not verify remote freshness or hosted checks. Record every round against that observation with findings, verification limits, and a disposition for each prior finding. Report the findings to the human in conversation after each round, including the exact reviewed head and any unverified or newer observed head. If a newer head appears, review it in another round or ask the human whether to stop at the earlier reviewed head. Close only on explicit human direction, including when no round was completed. Preserve residual concerns and any observed but unreviewed head in the final record and report; when no round was completed, say explicitly that no PR head was reviewed. Review-only work uses no implementation attempt, worker lease, candidate submission, or ordinary close, defer, block, resume, or replacement action. Definition revision makes the prior brief stale until it is prepared and reviewed again.

Route frozen candidates to the task that owns the outcome, not by conversational ancestry. When the recorded owner session is unavailable and the human asks a session that inherited its work to continue, that session owns the outcome under [inherited sessions](state-and-recovery.md#inherited-sessions). That task commissions one fresh-context, candidate-read-only review subagent after the candidate is stable. The result returns automatically, and the owning task processes the complete accept-or-correct verdict. Keep the reviewer independent, commission one reviewer by default, and do not duplicate the full review or add reviewers without a concrete risk.

Under an active implementation request, commission this review and dispatch its in-scope corrections without asking for general reviewer approval. An explicit pause or an unresolved scope, capability, access, integration or closure decision retains its separate boundary. Recover a lost review-job response or failed pre-verification launch through [fresh launch-response recovery](preparation-and-dispatch.md#recover-a-worker-or-reviewer-launch-response); stop an invalid launch and use the new exact recipe in a fresh context.

If a Pinboard-managed pull request was published before local review, inspect the actual attempt before reporting delivery. A published PR supplies neither a protected candidate nor review evidence. For an active attempt without a candidate, dispatch or continue a worker that verifies the exact local candidate, updates `result.md`, and submits it through its own lease. For a paused attempt with stale accepted scope or Git lineage, publish a replacement brief and rebind the same attempt before selecting its legal resume action. Then inspect the protected candidate and commission the separate reviewer through `pinboard_review_job`. If any state transition, worker authority, or reviewer capability is unavailable, preserve the pending attempt and report that exact blocker. The ordinary sequence still reviews the protected candidate before repository disposition.

For a correction, require the current `result.md` to map the exact prior findings, intervening candidate delta, affected owner-consumer relationships, and each evidence family as reused, revalidated, or stale. Every semantic reread or verification rerun needs the changed relationship or accepted widening reason that requires it. The outcome owner checks this map before rendering the correction review job, and the reviewer reports the same dispositions while still returning one complete verdict. An unchanged source hash does not preserve evidence whose owner-consumer relationship changed.

Before commissioning review, inspect the attempt continuation and call `pinboard_review_job` with exact roots and a structured review leaf containing `attempt_id` and `candidate_revision`. Use `kind: initial` without histories, `package-initial` with `checkpoint_history_id`, `correction` with `correction_history_id`, or `package-correction` with both. Before supplying a package history, run `<launcher-root>/scripts/pinboard validate --json` separately and stop on failure. Copy exact same-attempt history identities from checkpoint output, an explicit project export, or the selected return receipt; neither is discovered automatically. Only canonical `return-for-correction/v1` reason input can supply correction context. Current nonempty `review.md` remains independently bound to its render-time digest, and may describe a newer candidate than a selected package. Give the fresh reviewer only the returned native envelope. Its direct prompt contains the exact published task and complete accepted brief; follow its interface-owned verifier to confirm provenance rather than fetching a second instruction source. The job binds the exact protected snapshot, accepted brief owner and digest, nonempty `result.md`, and selected historical bytes. The reviewer verifies every selected byte and Git identity, compares each historical candidate independently, reuses unchanged owner relationships, revalidates changed relationships and documentation, classifies unreviewed changed surfaces, and marks relationship-invalidated evidence stale despite unchanged source hashes. Widen only for architecture, persistence, wire, lifecycle, dynamic-consumer, or demonstrated-blind-spot conditions. Stop without a verdict if an identity, comparison, classification, or required widening cannot be resolved. Publication may change immutable-artifact, accepted-reference, and ledger surfaces; it neither runs full validation nor mutates lifecycle, authority, or native tasks. The outcome owner applies the reviewed result.

After a favorable reviewer verdict, call the `record-ready` review leaf with the exact candidate revision, candidate-snapshot digest, accepted-brief digest, current `result.md` and `review.md` digests, `reviewer_prompt_sha256` copied from the `prompt_reference.sha256` that the review job returned for this exact candidate and `result.md`, the task identity of the reviewer launched from that prompt, `verdict: ready`, and nonempty acceptance evidence; it has no runtime or background fields and launches nothing. `REVIEWER_PROMPT_NOT_COMMISSIONED` means no reviewer prompt was published for that subject—for example `result.md` changed after the launch—so run the review job for the current candidate first, then record the verdict of the reviewer it launched. On every later resume, inspect with fresh reconciliation observations. Missing or invalid ready identity selects review first; otherwise target-stale selects refresh, residual or diverged selects correction, the first denied or unknown required effect in source-checkout, shared-work-root, git-metadata order selects permission recovery, pending candidates select repository disposition, integrated cleanup selects repository cleanup, and integrated terminal selects completion. A favorably reviewed working-tree candidate may become a clean commit without another review when Pinboard verifies the recorded branch, the snapshot's accepted-base correlation, and an exact binary diff from its preimage to current HEAD. This proves local code identity only; revalidate changed accepted semantics or reviewed owner-consumer relationships before reusing the review. A mismatch requires proportionate correction or review of the current candidate, and an unreadable Git observation blocks disposition with its exact read failure. Follow only the returned operation.

Use [the coding-agent runtime adapters](runtime-adapters.md) for the native fresh-reviewer launch and wait operations. The exact review job and review responsibility remain shared.

Do not use or wake another coding-agent task to review or receive the same outcome. Dispatching work, clarifying or widening scope, or sending a prior message does not establish current responsibility. A separate task owns a genuinely independent outcome and reports in its own conversation; it is never a subordinate return path.

If the runtime adapter establishes that the current runtime cannot create a subagent, keep the exact candidate in review, preserve the durable result and accepted brief, and state that review is waiting for a runtime with subagent capability. Do not create or wake a user-owned task, return routine ownership to a parent task, substitute the implementer as reviewer, or imply that the human must review unless the human explicitly chooses that route.

### Recover after a brief replacement

When an accepted brief is replaced while a returned candidate still awaits correction, its old correction request is historical context, not authority for the new target. This recovery does not apply to ordinary initial briefs, new checkpoints, or rebinds without an outstanding superseded correction.

1. Bind the replacement brief.
2. For a cross-boundary replacement, independently assess the complete current canonical brief against current authority bytes and the actual current candidate binding on its accepted base, including every moved, removed and newly added authority. Read `pinboard_return_context` with exact roots, attempt, and `selection: {kind: historical, return_history_id: <selected original return>}`. Verify its exact original receipt, accepted returned snapshot and canonical reason separately as historical context; a genuine rebase may change the current base and candidate without changing those original bytes. While the attempt is active and its latest return is historical after rebind, use `pinboard_dispatch` with `kind: replacement-readiness`, its fresh project dispatch receipt, exact checkpoint, `review_id`, selected `correction_history_id`, full `pinboard-correction-source-review/v1` as `brief_review`, and `current_candidate` naming the assessed commit or complete working-tree identity. The source review binds the current full canonical contract review, historical accepted snapshot and reason, and a concrete independent source assessment for the current candidate. This establishes replacement-brief readiness; reserve the complete implementation verdict for the protected candidate review in step 4. Pass no environment or prompt.
3. Verify the returned proof and plain ready-review identities, then protect the returned `candidate_revision` using your own current attempt authority. The proof binds the historical review context and assessed current candidate; plain readiness belongs to the replacement brief and is consumed independently by checkpoint acceptance. Publication verifies current sources and accepted binding, rechecks the exact current candidate after each publication, and produces no worker prompt, launch, lease or lifecycle mutation. Identical bytes reuse; differing evidence preserves collision evidence. After a committed partial failure, inspect the named surfaces and current continuation rather than replaying the operation. Local replacements keep their existing preparation rules.
4. Commission one fresh complete implementation review against the replacement brief and protected current candidate. Supply the selected previous return and checkpoint as independently verified historical context. Retain every prior finding with an evidence-backed disposition; replacing the brief does not erase findings or make the old verdict current.
5. Preserve the complete new verdict. If it requests changes, apply one new `return-for-correction` and retain its actual canonical history identity.
6. Independently review the current correction sources, then dispatch correction using that new return on the same reviewed brief binding. Preserve the accepted plain readiness record through corrected submission, review, and checkpoint acceptance. If another genuine brief replacement becomes necessary, repeat fresh review against it rather than transferring the old verdict.

Review-job may select an older return as context; correction dispatch requires the current canonical return. Do not replay completed transitions, relax stale-return checks, or add storage machinery to preserve the old request.

The responsible task reviews the frozen candidate, then applies the review outcome through the state-appropriate project transition. Use `complete:<attempt>` only when the human has authorized the entire work-item outcome and its named completion boundary is satisfied, the current v4 checkpoint disposition is `terminal`, the exact candidate is protected and independently reviewed, and every already-authorized repository disposition and cleanup effect has succeeded; keep a favorable final candidate in review while those effects run. When an independently buildable checkpoint is accepted and the canonical brief disposition is `continue`, use `accept-checkpoint:<attempt>` with the stable checkpoint ID, exact candidate identity, and review evidence written as a [human-read record](setup-and-transitions.md#write-human-read-records); it archives the exact current `result.md` and `review.md`, pauses the same item and attempt, and fences worker authority. Publish the revised canonical JSON brief at its next artifact revision, then use the ordinary `resume:<item>` with that accepted reference before dispatch. When the protected candidate is accepted but accepted checkpoint work remains within the same active attempt, use `accept-review-and-continue:<attempt>` with that exact candidate identity and acceptance evidence written as a [human-read record](setup-and-transitions.md#write-human-read-records); it returns the item and attempt to active, clears the protected candidate, records the accepted candidate and evidence without a checkpoint, sets the next action to continue, and fences the previous worker authority. When review finds an actionable defect, use `return-for-correction:<attempt>` with a reason written as a [human-read record](setup-and-transitions.md#write-human-read-records) that identifies the durable review evidence, and capture the successful transition's exact `history_id`. Select project dispatch again and commission a fresh independent source review—bound to the accepted brief for a local checkpoint, or to the effective checkpoint and its current contract review for a cross-boundary one—and pass it with the selected return to the matching correction dispatch leaf before launching the fresh correction worker. The same attempt and evidence remain; the new worker reacquires at a higher generation through the rooted MCP calls in its generated prompt.

Treat the paused state produced by an accepted intermediate checkpoint as an internal evidence boundary when the human has already authorized continued execution, the brief records remaining work, and no blocker or unresolved human-owned decision exists. Report the accepted milestone, then continue the owning turn through any already-selected repository disposition, next brief publication and binding, resume, fresh worker acquisition, and delivery. Preserve the pause, immutable evidence archive, and authority fence; stop only for an explicit request to pause, a genuine blocker, missing authority, or an unresolved human-owned decision.

## Review and completion

Before terminal completion, identify the human's actual whole-item completion instruction and verify that its named boundary is satisfied. Reuse an earlier explicit instruction when it still applies; do not ask again merely because review or repository effects have since finished. If the instruction makes completion conditional on a merge, keep the item nonterminal until that condition is verified. A knowingly selected isolated result can be the final outcome without a merge.

Candidate readiness and human terminal authority answer separate questions. A terminal brief, favorable review, draft publication, no remaining code work, or an acknowledgment such as “this step is done” supplies no missing whole-item decision. Keep remaining accepted work within the same item; do not reclassify it as follow-ups to manufacture completion. Use checkpoint acceptance or reviewed continuation when their accepted work remains. Continue already-authorized same-item work through its checkpoint route without another general approval.

Record the human's exact completion words through the currently advertised native completion contract: use `human_decision` when it declares that field, otherwise preserve the words in its declared evidence field. Source instructions describing a newer field do not change an installed callable or authorize installation. If the advertised contract cannot represent a required condition, report that exact gap; do not invent a field or another execution route. If no applicable instruction exists or its boundary remains unsatisfied, report that precise pending decision or condition before completion. The text records attribution within Pinboard's trusted-local boundary; it does not authenticate the human or prove the meaning of their words. Supplying it relaxes no commissioned-review, terminal-disposition, replacement or freshness condition.

Keep a favorably reviewed candidate protected while read-only investigation or explicit retention settles the existing accepted work. Record that decision in separate private evidence and cite it in completion evidence. Preserve the accepted brief and the bound result and review bytes. Use `accept-review-and-continue` only when accepted checkpoint work remains; it clears candidate protection and requires another submission. A material change to any accepted worker deliverable or acceptance requirement follows the complete definition-and-brief replacement route below and requires review of the new exact candidate. A newly required investigation or report can change accepted scope even when source code is unchanged.

Treat a refused closure as a bounded diagnosis. Report the actual accepted remaining work or missing current candidate, review, or evidence, then follow its focused inspection to establish what remains. Closure does not authorize reconstructing a candidate or launching implementation. Keep already-cleared or rebound history as history; it supplies no current approval. Reuse a valid current commissioned ready review when its exact candidate and evidence still satisfy completion.

Retired patch-only working-tree v1 snapshots remain exact readable/exportable terminal bytes under independently verified archive source, receipt and definition closure. They provide no restoration, integration, review or correction authority. Current complete commit v1, working-tree v2 and declared v3 snapshots retain their exact independent checks and correction-context formats; retired checkpoint v2 packages retain exact non-executable patch-only terminal history under independent certificate closure.

For a reviewed candidate whose starting checkout still matches its returned snapshot, call `pinboard_correction_context` with the exact attempt and return history ID before commissioning the independent source reviewer. Supply the returned effective brief, reviewed-authority identities and hashes, canonical reason, accepted starting candidate identity, and coverage-reuse eligibility to that reviewer. If the accepted brief, every reviewed source, and accepted ready review are unchanged, a cross-boundary reviewer makes a fresh candidate-bound assessment in `ReusedCoverageCorrectionReview` and dispatch uses `reuse-correction`. A reported blocker selects the full `CorrectionSourceReview` and `correction` route. A local reviewer uses `LocalCorrectionSourceReview`. Dispatch recomputes and rechecks these identities. Report a blocker and its next supported action without repeating unchanged status. An earlier ready review or a different starting snapshot cannot replace the fresh correction assessment. Substituting a different host application still requires its own human approval.

When tracked changes or new untracked names have drifted from a current returned checkout, use `pinboard_return_context` with `selection: {kind: current-candidate, return_history_id: <current return>}`. Give the reviewer its plain `review_context` and exact `current_candidate` binding. A fresh independent assessment must explain the drift and bind the observed tracked candidate plus omitted path names. Dispatch uses `kind: candidate-correction` and a strict `pinboard-current-correction-source-review/v1` wrapper: `boundary: cross-boundary` carries a full `CorrectionSourceReview` in `source_review`; `boundary: local` carries a `LocalCorrectionSourceReview`. Both carry the exact `current_candidate` record. Valid unchanged evidence may inform that assessment, but the existing `reuse-correction` leaf remains an exact-return route. Candidate-bound correction permits reviewed diff and path drift while retaining the returned branch, HEAD, accepted base and current return. It neither includes omitted bytes in identity nor turns a historical return after rebind into correction authority. Reobserve and reassess a changed binding; after committed publication failure, inspect effects before any continuation.

When hosted CI finds an ordinary implementation defect after a draft PR was published, continue correction in the same attempt through a fresh candidate submission and separate review. If repository publication of the corrected commit is already authorized, update the same draft PR and verify hosted checks on that exact head. Ask the human only for an actual missing repository authorization or a material product, architecture, compatibility, scope, or risk decision; routine correction within the accepted brief needs no new decision.

Report repository publication and local review as separate facts, naming review as not started, underway, favorable, blocked, or returned for correction from fresh attempt state and actual reviewer evidence. A published PR makes review neither favorable nor the item complete. If the human explicitly chooses to proceed before review, name that choice and keep the review pending. A locally matching protected commit verifies no remote PR, push, merge, or hosted-CI head; apply the review-provenance rule in [the human's picture](../SKILL.md#keep-the-humans-picture-current).

For an agent-authored Pinboard PR, create or keep it draft while any accepted agent-side work remains, including implementation checkpoints, corrections, independent review, and required hosted checks. If an existing ready PR needs an unfinished new head, convert it to draft and verify the remote draft state before pushing that head; if conversion cannot be confirmed, hold the push and report the blocker. Continue authorized corrections on the same draft PR.

After every accepted agent-side step is complete, observe the PR's current remote head and confirm that independent review and every required check cover that exact head. Then mark the draft PR ready for human review and verify its state and head again. If the head changed or coverage cannot be confirmed, keep or return the PR to draft and continue the missing work. A push, green CI result, or locally reviewed candidate alone does not trigger readiness. Pinboard does not certify remote head or hosted checks; the outcome owner reports the observations, and the human retains the merge decision.

At publication, check, review, and wrap-up updates, briefly name the PR's draft state, the agent work still pending, and the planned ready transition. Once it is ready, name the observed head and its review and required-check coverage, leaving the merge to the human. Report hosted checks and remote state as unverified when they were not observed.

Before commissioning a caller-selected checkpoint review, require accepted candidate bytes as well as the package reference. A current v3 package carries a portable canonical snapshot with its actual preimage and exact diff. Retired v1/v2 packages are non-executable terminal archive history; selecting them rejects before prompt publication. Keep current v3 package review and current restoration independent of archive membership. Historical patch assurance cannot authorize a new complete-state correction start.

Checkpoint acceptance for a new candidate verifies its protected identity before publishing candidate, result, implementation review, and the v3 package as one evidence closure. A working-tree candidate binds the actual full HEAD revision and exact `git diff --binary HEAD` bytes; a commit candidate binds the full current HEAD with a clean working tree and the exact `git diff --binary <accepted-brief-base> <current-HEAD>` bytes. Validation, review, project export, and covered completion stop when the current package's candidate reference, identity, or canonical bytes are missing or mismatched. Retired patch-only working-tree v1 snapshots remain non-executable terminal history under verified archive closure. Retired checkpoint v2 bytes and captured labels keep exact patch-only assurance under independent certificate closure; full commit labels establish no complete preimage.

Treat worker completion as a review request, not acceptance. Compare the attempt brief, diff or commit, result receipt, and fresh proportionate verification. Start with the changed and explicitly uncertain semantic surface: reuse unchanged reviewed relationships, revalidate changed relationships and documentation, and classify every changed file or contract preparation did not cover. Widen only for architecture, persistence, wire, lifecycle, dynamic-consumer, or demonstrated-blind-spot evidence, not merely because the checkpoint is cross-boundary. Check the architecture declaration against the final owner and dependency-direction diff: `none` must be truthful, `read-only` must conform to its named authority, and `update-required` must include a coherent same-candidate authority change. Account for every acceptance criterion, Contract row and authorization basis, coverage row, and lifecycle sibling row. When the brief carries a requirement from the readiness hook, verify its affected capability and proportionate evidence against the recorded project tier or equivalent policy. Without that policy the hook remains non-blocking; separately accepted readiness obligations retain their own basis under the general assurance rule. Apply the brief-composition rule without adding retroactive guarantees. When the checkpoint invokes the [developer-navigation lens](../../repository-readiness/references/developer-navigation.md), verify the final representative trace, sibling edit sites, retained exhaustive owners, and dynamic-wiring failure mode against the frozen candidate. Apply the [assurance classification](../SKILL.md#keep-assurance-inside-accepted-product-scope): every blocking finding cites accepted scope or an exact brief contract or criterion, an applicable repository rule, an exact reviewed product-authority family, a named production consumer, or an observed supported-path failure, never broad correctness prose, an exploratory failure, public narrative, or newly written guidance. Fix defects and enforce accepted hardening without redundant confirmation, and route a materially broader unsupported guarantee to the [one human assurance decision](../SKILL.md#keep-assurance-inside-accepted-product-scope). Classify each finding as an implementation defect, brief omission, authority contradiction, product decision, or new capability. A correction review may reuse package evidence only when its owner and relevant relationships remain valid; it revalidates changed owners, marks relationship-invalidated neighbors stale even with unchanged hashes, and resolves every prior finding before one complete verdict. Complete the item only when every acceptance criterion is satisfied and current knowledge owners are reconciled. A `continue` checkpoint may be accepted or returned to active reviewed work, never terminally completed. A `terminal` checkpoint may complete only from protected review with the exact candidate, current result and review digests, independent reviewer identity, and one ascending compact reused-or-revalidated row for every enumerated checkpoint, including an empty row set when none was previously accepted. Pinboard refuses completion with `CANDIDATE_REVIEW_REQUIRED`, unchanged and before publishing any completion evidence, unless it holds a ready review recorded through `record-ready` for that exact candidate, snapshot, brief, `result.md` and `review.md`, commissioned by a reviewer prompt `pinboard_review_job` published for that subject, and naming the same `reviewer_task_id` as the completion. Never choose or invent a reviewer identity. If the required record is absent, report the missing review and inspect the exact round before offering its commissioned review route; the closure warning itself launches nothing. Follow the review procedure above only with review authority, then complete with the recorded reviewer's identity. A retained `pinboard-candidate-review/v1` record carries no commission link and does not count; commission one new review. Focused completion supplies the installed native tool's strict reviewed input; follow that exact advertised contract and record the human's completion words as required above. Broad action discovery intentionally omits completion. Original v2/v3 briefs are historical-only facts for independently verified archive, checkpoint and completion bindings; they have no operational decoding or recovery route. Pinboard rechecks the same accepted brief reference and disposition under lock before publication and commit.

When an authorized repository disposition includes creating or updating a pull request, use `$technical-writing` in quiet editorial mode for its description. Ground the description in the accepted definition and brief, the exact candidate and diff, implementation evidence, verification, and the accepted review. Make the requested outcome recognizable before implementation detail. Preserve material caveats and unknowns, and do not interview the user when those sources already determine truthful content.

Also compare the frozen candidate with the project's current limitations and the brief's recorded assessment. Reject a candidate that introduces, widens, preserves, masks, or deepens an unacknowledged material limitation, even under generic implementation authority or behind a locally correct compensating layer. A newly accepted or materially changed limitation is bound to the current definition and existing brief provenance, represented as a cross-boundary contract with `update-required` architecture impact and complete coverage, and reflected in the named current-truth owner, without another brief field or consent receipt. A missing decision is a brief omission or unresolved product decision, never worker discretion.

The owning task owns review publication: after the candidate-read-only reviewer returns a complete verdict, write it to the active attempt's `review.md`, then link its purpose before announcing or applying acceptance, return for correction, checkpoint acceptance, accept-review-and-continue, or terminal completion. Later mentions follow the readable-artifact rule; do not link immutable copies archived by acceptance transitions.

### Reconcile late direction and replace the definition and brief

Before presenting a candidate, accepting review, offering repository disposition, or wrapping up, account for every user direction and repository change after the current accepted brief or exact candidate was established. Distinguish work that implements the current brief from a change to accepted semantics. When semantics changed, do not present, submit, accept, or complete against the superseded identity: replace the complete item definition, publish a matching canonical brief, rebind the active or paused attempt to that current scope and its accepted Git lineage, produce a new exact candidate, and obtain a new exact-candidate review.

When the human adds direction while a worker is active, compare it with the complete accepted brief. A clarification already covered by the brief may go directly to the same worker. A new material requirement changes accepted semantics: do not send it as implementation authority or wait for `result.md` to reconcile it. Preserve the worker's evidence, replace the complete item definition and matching canonical brief, and rebind the active attempt before another candidate submission. Rebind fences the old worker's Pinboard authority but does not stop its native process: stop it through its native handle or wait for it to finish, and confirm it no longer writes to the checkout before dispatching a fresh worker there, leaving dispatch pending if that cannot be confirmed. Then continue through supported dispatch and fresh worker authority against the revised brief, and obtain a new exact-candidate review.

Use the lifecycle route that matches the current state. Before submission, revision makes the active attempt stale: publish the matching brief and rebind it, keeping it active. While a candidate is in review—even after a favorable verdict—return it for correction with a reason saying accepted scope superseded it rather than that the implementation is defective, then revise, publish, rebind, implement, submit, and review again. After `accept-review-and-continue` returned the attempt to active, revise, publish, and rebind without a review-state return. A paused attempt follows the same publication and rebind path while staying paused, even when live dependencies keep resume unavailable. After terminal completion, preserve its history and treat later direction as new work.

When acceptance requires exact-head CI, resolve the needed commit and publication authority early enough to follow the [single-pass candidate sequence](../../pinboard-deliver/SKILL.md#implement-and-verify): prepare the commit before submission, then publish it unchanged after favorable review and verify its CI before acceptance. Otherwise, repository disposition may follow candidate acceptance. Keep code acceptance, Pinboard state, commit state, branch integration, remote publication, and deliberate deferral distinct. Before asking the human to wrap up, refresh only the decision-relevant facts: review outcome; dirty or committed state; current branch and checkout or worktree; intended target; known filename overlap or conflict risk; and remote delivery status when it affects the choice. State observations, uncertainty, and limitations. A separate worktree avoids competing writes in one checkout but does not make later integration conflict-free.

When repository disposition remains unresolved, recommend the best-supported next action with alternatives whose repository effects are explicit, using the [question presentation](../SKILL.md#match-detail-to-the-question) with two to four choices. When remote publication is available, include `commit the candidate, push its branch, and open a draft PR` beside any useful commit-only, named-branch integration, or publication choices, without implying the draft-PR path is required, and perform only the selected action. Unless the agreed outcome keeps the work isolated, do not routinely offer leaving it unchanged, uncommitted, isolated, or for later; acknowledge an explicit request to defer. Otherwise the choice stays on the `Still open:` line until the human chooses a concrete disposition.

### Repository disposition and local closure

At the repository decision, state the human's exact choice and the remaining sequence: verify the selected disposition, perform only authorized cleanup, then apply the authorized terminal transition. Offer one bundled decision when its exact targets and consequences are established. Each named effect has separate authority; execute the selected sequence in order and verify each effect before advancing. A merge or green checks alone authorizes no deletion or completion. If an effect fails or remains uncertain, stop before later destructive or terminal effects and report completed and pending facts separately.

For explicit local-only closure of an already favorably reviewed candidate, carry out the named effects through this bounded path. Attribute a human-reported merge to the human and verify the local relation needed for cleanup or completion; that report needs no GitHub or merge-actor investigation. An excluded installation and a difference between source guidance and the advertised native contract create no version-audit prerequisite. Keep the protected candidate and its bound brief, result and review bytes unchanged. Reuse observations within the same closure sequence while their decision-relevant facts remain current; reread after a relevant effect, changed target, evidence change, occupancy change, stale receipt or failed observation. This reuse never replaces fresh action selection or the executable's locked rechecks.

1. Read exact item status and inspect the named attempt with `reconciliation: null`. A current `ready` verdict and `reconcile-repository` mean the exact candidate already has commissioned review; reuse it despite the board state `review`. If current coverage is missing or invalid, retain the worktree and branches and report the missing review before any cleanup or completion: unresolved review still uses the worktree. Follow [review and completion](#review-and-completion) only with review authority. Close intent supplies neither review commissioning nor candidate reconstruction authority.
2. Resolve the intended local target and read item-status operation `integration` once for that target. `content-present` supports `candidate-integrated` with the returned `target_revision`, including rebase and squash integration. Preserve the original review subject; this proves neither review of surrounding commits nor remote freshness. `content-not-present`, `no-change` or a failed read is inconclusive: establish the actual relation before cleanup or completion. Do not infer another relation, create an empty PR or broadly rereview unchanged code. A local-only instruction adds no fetch, push, PR, hosted-check or remote-deletion effect.
3. If cleanup was requested or authorized, establish the exact worktree and applicable branch targets against the verified integration target. Read worker authority for this attempt and establish the cleanup conditions below, including other task or attempt occupancy and needed work outside the protected candidate's diff. The positive integration check covers only that reviewed diff; an unknown or failed condition leaves requested cleanup and completion pending. If cleanup was neither requested nor authorized, retain those targets and proceed to the terminal phase when the other completion conditions hold.
4. Inspect with `candidate-integrated`, the verified target revision and the phase/effect observations below. Use `cleanup` only for required cleanup; use `terminal` after cleanup succeeds or when none is required. Follow the returned continuation. A denied or unknown required effect selects permission recovery; an observation describes current authority and capability, never grants it.
5. For authorized cleanup whose conditions all hold, remove the exact disposable worktree, then its local branch, then any explicitly authorized still-present remote branch. Verify each effect before advancing; an already absent branch is no remaining deletion effect. Use a surviving checkout for subsequent repository calls. After cleanup, inspect the terminal phase with current observations; refresh only facts the cleanup changed or made uncertain.
6. Request the exact fresh project `complete` action, fill its current completion contract with the human's exact completion decision, protected candidate and recorded reviewer's identity, and apply it only under explicit completion authority. The contract preserves commissioned-review bindings, accepted terminal scope and checkpoint coverage. Follow the returned effect and retry disposition; do not replay a committed or uncertain effect. Immediately before the closing reply, read exact item status as required by [wrap-up](../SKILL.md#wrap-up-with-facts). Report local integration and terminal status as distinct facts. When the requested effects and terminal status are verified, end the turn without more tool work, investigation or proposed follow-ups; an unverified remote actor or excluded installation is no remaining work.

Reconciliation always contains exactly three effect observations in `source-checkout`, `shared-work-root`, `git-metadata` order. For the integrated local closure path:

| Phase | `source-checkout` | `shared-work-root` | `git-metadata` |
| --- | --- | --- | --- |
| `cleanup` | observed required status | `not-required` | observed required status |
| `terminal` | `not-required` | observed required status | `not-required` |

An observed required status is exactly `allowed`, `denied` or `unknown`. Supply `not-required` only where the phase requires no effect, even if that resource is writable. In particular, `shared-work-root: allowed` is invalid for cleanup. The [runtime request contract](runtime-adapters.md#current-mcp-request-shapes) owns the full native input shape and other reconciliation routes.

Cleanup requires all of these facts:

- no active coding-agent task or Pinboard attempt uses the worktree;
- no needed uncommitted changes remain in it;
- no needed branch commits are absent from the accepted integration target;
- the worktree and each applicable local or remote branch target are exact; and
- the human explicitly authorized deletion of each applicable target.

A review-state attempt with no live worker authority no longer uses its isolated worktree once its exact favorably reviewed candidate is present at the verified integration target. Retained lineage and protected evidence alone do not block removal. An active attempt, live worker, unintegrated candidate or unresolved review still uses it; another occupant remains a separate condition. When requested cleanup fails a condition or leaves it unknown, retain the worktree and branches, leave the item nonterminal and name the evidence or decision needed next. Close intent alone authorizes no cleanup. When cleanup is neither requested nor authorized, deletion authority is no prerequisite to otherwise authorized completion.

If the human already authorized the exact cleanup and completion sequence, execute it in the same turn without another routine confirmation. Ask only for a missing effect authority. Do not manufacture integration or publication as a prerequisite when the human knowingly accepts another disposition; use that disposition's supported reconciliation route instead of this already-integrated local path.

For an accepted intermediate checkpoint, use the checkpoint acceptance path above. Its paused item and attempt remain nonterminal, checkpoint evidence remains immutable under the same attempt, and terminal item history remains absent until a later full-outcome completion. For an accepted intermediate review inside an unfinished checkpoint, use `accept-review-and-continue:<attempt>` instead; it records the passing review without accepting the checkpoint and leaves the fenced attempt ready to continue after a worker reacquires it.

Use `return-for-correction:<attempt>` for an implementation defect against an accepted owner or when newly accepted semantics supersede the protected review candidate. In the second case, record scope supersession rather than calling the implementation defective, then follow the [complete definition-and-brief replacement route](#reconcile-late-direction-and-replace-the-definition-and-brief). For a brief omission, authority contradiction, unresolved product decision, or new capability that has not become accepted scope, preserve the review evidence and stop before any lifecycle transition until the existing upstream owner resolves it; do not turn the review feedback into implementation scope or invent a state, transition, or alternate acceptance path. For an implementation defect, record the exact correction reason instead of completing the item, manufacturing a new attempt, or editing lifecycle files. Report the outcome compactly with the reason's lead sentence only: `Returned for correction — <lead sentence>; the same attempt and review evidence are preserved and ready for a named worker to reacquire. No acceptance occurred.` If the executable does not offer that action for a valid review return, preserve the review evidence and report the workflow blocker; do not bypass the missing transition.
