# Coding-agent runtime adapters

Pinboard exposes agent workflows through local stdio MCP and retained human and maintenance operations through CLI. Both use one SQLite authority, action vocabulary, brief schema and skill tree. Use this reference only to translate shared workflow operations into the current coding agent's native outer capabilities. The surrounding skill remains the semantic owner.

`<launcher-root>` is the resolved directory containing `scripts/pinboard`. MCP declarations invoke that launcher with exactly `--mcp`; Claude startup hooks use their exact selectors described below, and direct CLI operations use CLI arguments. When `<launcher-root>` is a prepared `<pinboard-source>` checkout, the launcher uses `<pinboard-source>/.venv`. When it is an installed plugin version, the launcher uses `<launcher-root>/.pinboard-runtime/environment`. `<managed-project>` and its exact work root are request data, never runtime or dependency locations. Runtime selection follows the resolved launcher root, not the human or agent audience.

## Packaged connection and first setup

Codex's explicit root `mcp-codex.json` declares `sh ./scripts/pinboard --mcp` with `cwd: "."`, resolved under the plugin root. Claude's separate root `mcp-claude.json` declares `${CLAUDE_PLUGIN_ROOT}/scripts/pinboard --mcp`; the client expands that root in the command. Both start the existing `pinboard-mcp` entry through the same runtime owner. No additional MCP startup arguments are supported; every tool call carries exact project and work roots.

Resolve those roots before the first call. The project root is the exact selected checkout. Unless the user or an existing Pinboard receipt selected another work root, a normal checkout uses `<project-root>/.codex/pinboard`. A containing temporary directory, fixture root, checkout parent, or project root itself is not the work root. A linked worktree reuses only the exact shared work root supplied by its accepted workflow or resolved through the retained root command; do not guess it from the worktree path.

If a version is unprepared, MCP startup exits before the server starts and puts its strict same-launcher preparation action on stderr, never protocol stdout. Deliberate CLI setup may run `<launcher-root>/scripts/pinboard --prepare-runtime` with uv and write access only to that version's `.pinboard-runtime`. Follow the exact preparation result, then use the client's supported MCP reconnect or plugin reload mechanism before attempting a covered tool. Setup and CLI-only operations retain their direct launcher route. A missing required MCP tool stops that operation and never authorizes shell fallback.

The server's existing SDK registration supplies entry and discovery instructions in standard MCP initialization, before deferred tool schemas. For intake or coordination, it routes attributed-call construction through the complete existing workflow skill: intake for new work, coordination for existing work. The selected skill owns sequencing and consultation of this reference's runtime identity procedure. Follow those connection instructions first; this reference provides the detailed host procedure and request, startup and recovery contracts. If connection discovery instructions are absent, use the procedure below.

Pinboard wire identities, such as intake's `pinboard_overview` and `pinboard_proposal_create`, identify the required operations. The current host may advertise different full callable names for them. Resolve the native name before selecting a deferred tool schema:

1. Find the required operation in the host's actual tool announcement or native inventory and copy its full callable name, including the connector prefix. Resolve each host's names independently.
2. When the full name is known, use the host's exact-name selection with that full name. When it is unresolved, use supported keyword discovery to find the advertised callable.
3. If exact selection returns no match, reconcile the selected name with the actual advertised inventory. When a short wire name was selected, retry with the advertised full callable name. An unmatched short-name selection or an incomplete broad search does not establish a missing connection.
4. Inspect the returned callable identity and schema against the required operation, then invoke that native callable with exact project and work roots under its negotiated contract.

## Current MCP request shapes

The twenty tool identities share one installed surface. Ten tools carry their exact selected leaf inside one strict `request` object: `pinboard_brief_contract`, `pinboard_brief_sources`, `pinboard_item_definition`, `pinboard_brief_review`, `pinboard_order`, `pinboard_parallel_preview`, `pinboard_actions`, `pinboard_preparation_authority`, `pinboard_attempt_authority`, and `pinboard_transition`. For attempt status, use `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "status", "attempt_id": "<exact attempt>"}}`. The roots, role or operation, and selected leaf fields all belong inside `request`. Unknown outer or inner fields and flat calls are rejected unchanged. The other ten tools retain their advertised ordinary object arguments. Discover and follow each current negotiated schema rather than copying a historical call.

`pinboard_dispatch` takes ordinary `project_root`, `work_root` and one strict `dispatch` leaf, without a `request` wrapper. Its registration description makes all three leaves, their common receipt/environment fields and their distinct review inputs explicit when a host loses construction details in callable metadata. The negotiated schema and typed decoder remain authoritative; this description does not repair the host's schema translator. Use only `action_id` and `subject_revision` from the fresh project dispatch action for `receipt`, and explicit `prompt: null` for canonical construction. A dispatch action's lifecycle `payload_schema` is not the dispatch request contract. Ordinary, reviewed and correction construction remain distinct; initial ready review cannot substitute for candidate-bound correction review.

`pinboard_candidate_observe` takes ordinary exact `project_root`, `work_root`, and `attempt_id` arguments. It reads the named nonterminal attempt's branch/base context and the selected checkout's actual tracked working-tree identity, preimage and binary-diff metadata. `omitted_untracked_paths` reports Git-visible nonignored files excluded from that identity. The result is an observation, not protected evidence or acceptance. Preparation of only intended new paths is a separate authorized Git operation; reobserve afterwards and use existing own-leased submission. Observation changes no source, Git index, artifact, ledger or authority. It adds no committed-candidate mode; clean exact-current-commit submission remains separate.

`pinboard_candidate_restore` takes ordinary object arguments: exact `project_root`, `work_root`, `attempt_id`, and inspected `candidate`. Candidate recovery returns a native `restore` invocation with the chosen work root and exact candidate preserved; `project_root: null` is explicitly unresolved. Supply the caller-selected exact clean checkout on the recorded branch and preimage before invoking it. The tool restores only the current accepted snapshot context, not arbitrary archived checkpoints; an inspected candidate superseded by a newer submission rejects before Git. Source effects finish after entry and report only actual `source-checkout` changes or a committed post-mutation failure with `do-not-retry`. Restoration acquires no authority, changes no ledger or lifecycle, creates no checkout and launches no task.

`pinboard_review_job` takes exact roots and one `review` leaf. Ordinary `initial`, `package-initial`, `correction`, and `package-correction` remain repair-free. Missing genuine selected-v1 patch evidence returns a native `recovery` invocation preserving the current protected candidate, checkpoint history, and correction history when supplied. Fill only its unresolved `review.candidate_patch` with base64-encoded exact historical patch bytes matching `expected_patch_sha256`, not the current protected candidate. The required-patch `package-initial-recovery` and `package-correction-recovery` leaves accept only that same-attempt linked retained-v1 package, publish canonical revision-one historical evidence, then freshly prepare ordinary review. Current v2/v3 packages cannot use them. Later rejection or infrastructure failure preserves every earlier publication/reference/ledger surface and forbids replay; successful historical repair does not permit a patch-only new correction start or strengthen historical assurance. Run full validation separately before selecting package evidence.

`pinboard_order` takes exact roots, the existing strict `order` record (`schema: pinboard-live-order/v1`, complete `expected_order` and authorized `requested_order`) and trusted `actor_task_id`/`actor_host_id` inside `request`. It needs no preparation or worker lease and grants no launch authority. Its result preserves the committed receipt or unchanged rejection; known committed warnings name the exact retained CLI view-repair command. The structured `recovery` points to fresh `pinboard_overview` arguments for current-state reconciliation, not proof that this caller committed or recovery of its lost receipt. Equal order after a valid no-op cannot distinguish a committed call from one that never ran. There is no exactly-once guarantee; never blindly replay a lost reply or committed warning.

`pinboard_parallel_preview` takes exact roots and `selection: selected` with nonempty unique supported `item_ids`, or explicit `selection: all-safe` without item IDs, inside `request`. Selected reads focused current facts; all-safe reads current portfolio constraints without proposal bodies or retained history. Neither leaf changes artifacts, views, lifecycle, authority or native tasks. Structural safety does not certify readiness or replace human batch permission and fresh launch checks.

Use `pinboard_item_definition` operation `current` with exact roots and `item_id` for the complete accepted definition and its current identity. Its `history` leaf additionally requires an explicit `limit` from 1 to 100 and `before_revision`: begin with `null`, then use the returned `next_before_revision` as the exclusive cursor while it is non-null. Both leaves are read-only and require no lease.

Use `pinboard_brief_review` operation `publish` with exact roots, `brief_artifact_ref_id`, and a complete structured `pinboard-work-brief-review-needs-correction/v1` record bound to that accepted brief. The `status` leaf takes roots and the exact reference only; it returns the canonical accepted brief and verified latest negative evidence, if any. Wrap returned `correction.status_request` inside `request` when calling the same tool. The correction target names `pinboard_brief_publish` and its exact roots; add the complete corrected brief as `brief`. Neither negative evidence nor its absence proves ready review, changes lifecycle, or acquires authority.

Focused project `pinboard_actions` discovery for the exact `complete` action supplies the current completion contract. If an active checkpointed attempt needs candidate protection, that focused MCP result supplies the executable authority, submission, and rediscovery recipe using these request shapes and the caller's exact roots. Make that focused discovery read when the transition result does not include a recovery recipe. Discovery neither acquires authority, submits evidence nor completes automatically.

## Brief construction and source preparation

Use `pinboard_brief_contract` with a strict `request` containing exact roots and `operation: full`, or `operation: starter` with `boundary: local` or `cross-boundary`. Copy the returned complete starter, choose its structural variants, and fill unresolved values from accepted facts. Construction resolves no roots or ledger and grants no readiness or authority.

Use `pinboard_brief_sources` with exact roots inside `request`. `plan` takes a structured `manifest` and positive `max_batch_bytes`; `plan-to-file` adds one explicit `destination`. `emit` takes a structured `plan` and nonnegative `batch_index`; `emit-file` takes `plan_path` and `batch_index`. Planning and emission resolve the selected source checkout once and never open work state. Prefer a direct plan for small inputs or a saved plan when transporting it again would be wasteful. Read each verified batch once in order. Plan-to-file creates or identically reuses its exact immutable destination; a differing destination rejects unchanged. A visible output followed by synchronization failure reports committed `selected-output` and `do-not-retry`; inspect that destination, never replay the failure. Required roots are context, not permission to create durable state.

## Prompt verification and worker startup

Dispatch and review-job publication create no native worker. Call only their returned `native_launch.tool` with exactly the strict runtime-specific `native_launch.arguments` from the `pinboard-native-agent-launch/v2` envelope. Do not add, remove, or rewrite an argument, or substitute `prompt_reference`, its path, the verified prompt body, or a reconstructed launch message. The independently required `prompt_reference` identifies immutable provenance; it is not another launch input. A worker or reviewer launched from different arguments is invalid; stop it and launch a fresh context from the unchanged recipe instead of coaching or resuming it. Follow the recipe prompt's exact verifier before reading the immutable prompt. Current recipes name `pinboard_artifact_verify`. Immutable historical CLI-origin envelopes retain their original verifier as evidence, not a supported current invocation. Require the accepted identity, verification schema, selector, size, digest, and bytes to agree before acting. Prompt identity and execution semantics are shared; the envelope owns runtime selection, exact host arguments, verifier, and startup presentation.

After prompt verification, a worker loads the complete delivery skill through the host-specific route above and reads the complete canonical brief, including any bootstrap, before acquiring its own authority. Obtain the launched worker's own trusted post-launch identity through that runtime and preserve the returned lease and generation together. A missing required MCP tool or identity stops its operation; a historical brief's retired CLI bootstrap does not restore that route. Never manufacture identity, temporary payload files, or substitute shell calls for a missing connection. A denied invocation does not authorize editing saved permission policy.

The Claude manifest explicitly registers `./hooks/claude-hooks.json`. Native SessionStart events select `"${CLAUDE_PLUGIN_ROOT}/scripts/pinboard" --claude-session-start`; native SubagentStart events independently select `"${CLAUDE_PLUGIN_ROOT}/scripts/pinboard" --claude-subagent-start`. SessionStart matches all native initiation sources; SubagentStart matches all agent types. Both accept no additional arguments and share the prepared launcher-root runtime. The plugin supplies no shared default hook configuration for Codex discovery, and registration grants no client trust.

The parent entry validates the current SessionStart record and samples the machine name with `socket.gethostname()`. It adds only `Pinboard native parent task_id: "<actual session_id>"; host_id: "<actual machine name>"` and a concise attribution instruction through native additional context. The host's SessionStart delivery refreshes those values on startup, resume and other native session refreshes; an emitted hook result alone does not prove native ingestion or agent adherence. The worker entry independently adds only `Pinboard native worker task_id: "<actual agent_id>"` to that worker's startup context and supplies no host value; its verified dispatch host remains separate.

Each entry decodes its exact Claude-owned event, validates required fields and ignores unrelated additive host fields. Ignored extensions, cwd and transcript paths are never forwarded. Pinboard-owned outputs, requests and artifacts remain strict regardless of sender. Missing or malformed required fields, a wrong event kind or invalid identity emit no attribution and only a payload-free diagnostic; machine-source failure cannot supply a guessed host. Neither entry reads project state, creates a task, acquires a lease, authenticates credentials or changes permissions. Prepare that plugin version before native launch; attribution does not replace prompt verification, canonical brief reading, own leased acquisition or actual runtime approvals.

Newly generated MCP launch envelopes carry wrapped acquisition and continuation inputs under the [current request contract](#current-mcp-request-shapes); artifact verification keeps its ordinary arguments. Immutable historical prompts remain evidence, not a flat-call compatibility route.

## Native human questions

Apply the main skill's [question policy](../SKILL.md#match-detail-to-the-question) through tools actually exposed in the current runtime. In Codex, prefer `request_user_input_async` when available and permitted for the question, so independent authorized work can continue while the answer is pending. Use `request_user_input` only when its current mode and purpose restrictions allow the question; a Plan-only tool is unavailable in Default mode, and a tool that excludes permission requests cannot collect them. Follow the selected tool's question and choice limits. If neither tool is exposed or permitted, use the main skill's ordinary-text fallback.

In another coding agent, use its available native question capability only as permitted by that tool's current instructions; otherwise use the same text fallback. Native question support is not a desktop-only assumption or a promised capability of every host. Execution permission escalation remains in the host's actual approval mechanism, including the source-setup recovery below.

## Source-worktree setup recovery

Run the repository's exact setup command in the selected checkout through normal runtime execution first. On failure, use its diagnostics or one cheapest additional observation to distinguish a sandbox permission restriction from a missing prerequisite, actual locked-install failure, network failure, or a defect in the tool being changed.

For a diagnosed sandbox permission restriction during already-authorized source setup, request the runtime's permission review for one retry of that exact command in the same checkout. Do not add a separate conversational confirmation. Runtime approval still controls whether the retry executes:

- In Codex, use the execution tool's `sandbox_permissions: "require_escalated"` with a justification naming the observed restriction and the authorized setup command. Request only that invocation; do not add a persistent approval rule.
- In Claude Code, use the current runtime's native permission request for that invocation when available. Do not invent a permission API or treat a dispatch declaration as an execution grant.

If permission is denied or unavailable, the retry fails, the cause is not a sandbox restriction, or recovery would change accepted scope, stop setup and report the exact observation. Ask the human to abort, authorize one bounded retry or investigation, or revise the accepted scope and evidence. Do not repeat the retry, relocate caches, edit global configuration, bypass approval, or weaken locked setup to continue.

After successful setup, continue with the prepared checkout and preserve the result as setup evidence. This route changes only source-worktree setup recovery. Installed-runtime preparation and protected ledger writes retain their own recovery contracts; ordinary installed Pinboard commands use the prepared plugin runtime without uv or managed-project environments.

## Codex protected project writes

Fresh default initialization is special: approve the exact `<launcher-root>/scripts/pinboard init` command once because it first idempotently adds only `/.codex/pinboard/` to the shared repository's `.git/info/exclude`, then creates `.codex/pinboard/`. Do not grant persistent `.git` write access. Pinboard never edits `.gitignore`, and sibling `.codex` paths remain visible to Git. If a later initialization step fails, inspect the exact effect before issuing a fresh command: `committed-effect` names `repository-git-exclude` when this invocation added it and also names `ledger` when it published the database before failing. A repeat that commits neither surface is an unchanged rejection.

For routine Pinboard commands from a normal checkout at the default work root, select a Codex permission profile that extends `:workspace` and whose only protected workspace override writes relative `.codex/pinboard`. From a linked worktree, use only a direct write rule for the exact resolved absolute shared-repository `.codex/pinboard` directory; do not add the shared repository as a workspace root. For an explicit `--work-root`, grant write access to that exact selected directory instead. Remove legacy `sandbox_mode` and `sandbox_workspace_write` settings because they override permission profiles. The narrow profile must not write sibling `.codex` content, `.git`, the rest of the shared repository, or the installed plugin cache; packaged plugin code and skills are immutable runtime inputs, while the selected work-root tree is project data.

On `SQLITE_READONLY`, use the structured database path, operation, retry disposition, effect disposition, changed surfaces, and recovery naming the exact rule that needs write access: relative `.codex/pinboard` only for a normal default checkout, otherwise the exact absolute effective work root. Correct the narrow profile before issuing a fresh command. Never replay an operation whose result reports a committed immutable artifact; inspect current state and continue through the operation-specific recovery instead.
