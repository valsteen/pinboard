# Coding-agent runtime adapters

Pinboard exposes agent workflows through local stdio MCP and retained human and maintenance operations through CLI. Both use one SQLite authority, action vocabulary, brief schema and skill tree. Runtime adapter guidance translates shared workflow operations into the current coding agent's native outer capabilities; the surrounding skill remains the semantic owner. This shared reference holds the rules that apply to every runtime. Read it together with your own runtime's reference, and only that one:

| Current runtime | Its reference |
| --- | --- |
| Codex | [runtime-codex.md](runtime-codex.md) |
| Claude Code | [runtime-claude-code.md](runtime-claude-code.md) |
| Antigravity CLI (`agy`) | [runtime-antigravity.md](runtime-antigravity.md) |

Each runtime reference gives that runtime's connection, operation table (running Pinboard, task and host identity, checkout isolation, worker and reviewer launch, skill loading, worker continuation, permission declarations, waiting and optional messaging), close confirmation, native questions and permission retry.

`<launcher-root>` is the resolved directory containing `scripts/pinboard`. Ordinary MCP declarations invoke that launcher with exactly `--mcp`; runtime hooks use their exact selectors described in their runtime's reference, and direct CLI operations use CLI arguments. CLI capture accepts only normal CLI targets and cannot wrap either protocol startup path. A caller may instead start one dedicated captured MCP process with the complete explicit pair described below. When `<launcher-root>` is a prepared `<pinboard-source>` checkout, the launcher uses `<pinboard-source>/.venv`. When it is an installed plugin version, the launcher uses `<launcher-root>/.pinboard-runtime/environment`. `<managed-project>` and its exact work root are request data, never runtime or dependency locations. Runtime selection follows the resolved launcher root, not the human or agent audience.

## Handling another runtime's attempt

A board is shared, so an agent in one runtime may coordinate, review, recover or reconcile an attempt that a worker in another runtime started. Use the attempt's recorded checkout facts (its `project_root`, branch, base revision and shared work root) and Pinboard tools for that attempt. Never use the other runtime's native handles, such as its task names, agent IDs or conversation IDs, and never follow its runtime reference for your own actions: native continuation, stop and wait apply only to workers your own runtime launched. When the other runtime's worker must be stopped or continued, report that to the human or its owning task instead.

## Public contracts and source scope

When Pinboard coordinates another project, use its advertised tools, verified artifacts and loaded public skill contracts. Its installed implementation, tests, private modules, generated code and database internals are outside that assignment; do not inspect them to derive protocol behavior, canonicalization or missing values. Pinboard source inspection remains available when the accepted assignment explicitly covers Pinboard development or a separate human-authorized Pinboard investigation.

If a required value or capability is unavailable, stop the affected operation before its dependent publication, lifecycle change or implementation. Preserve the exact project/work roots, accepted artifact identity and checkpoint when known; name the missing field or tool, the attempted operation and its consequence. Report observed target and auxiliary effects separately, or state that they are unknown; a missing input never proves that earlier calls had no effects. Use the exact supported recovery from the producing response or public contract. If none supplies the input, report that gap and the complete structured error to the human or owning coordinator. Resume only when a supported tool, verified artifact or documented contract supplies it. Do not invent, approximate or omit values, weaken independent judgment, reconstruct undocumented hashes, or use another agent, process or client as a proxy.

## Packaged connection and first setup

Each runtime's own reference names its packaged MCP declaration. Every declaration starts the existing `pinboard-mcp` entry through the same runtime owner. Ordinary declarations accept no additional arguments, and every tool call carries exact project and work roots. For an explicitly approved exact-evidence run, start a separate process as `<launcher-root>/scripts/pinboard --mcp --capture-evidence-dir <existing-directory> --safe-to-persist-exactly`. The selected directory applies only to that process; startup proves writable immutable publication before accepting callbacks, and partial declarations reject before startup without altering the installed manifests.

Resolve those roots before the first call. The project root is the exact selected checkout. Unless the user or an existing Pinboard receipt selected another work root, a normal checkout uses `<project-root>/.pinboard`. Read the exact selected initialized root; an unavailable root supplies no authority to choose another location. Explicit work roots retain their ordinary resolution and initialization rules. A released v6 ledger uses `migrate-schema` preview and apply at its selected real root while quiescent. A containing temporary directory, fixture root, checkout parent, or project root itself is not the work root. A linked worktree reuses only the exact shared work root supplied by its accepted workflow or resolved through the retained root command; do not guess it from the worktree path.

If a version is unprepared and uv is available, MCP startup invokes the same `--prepare-runtime` path and starts the server after readiness is verified. A runtime's SessionStart hook can also invoke that preparation; the version-local lock serializes both callers. Missing uv, contention or failed preparation leaves the MCP connection attempt unavailable and puts its strict same-launcher recovery on stderr, never protocol stdout. The hook reports its own preparation facts and the exact manual command as additional context; it cannot establish the current connection status. Deliberate CLI setup may run `<launcher-root>/scripts/pinboard --prepare-runtime` with uv and write access only to that version's `.pinboard-runtime`. Follow the exact preparation result and check tool availability. Use the client's supported MCP reconnect or plugin reload mechanism if the connection remains unavailable after preparation. Setup and CLI-only operations retain their direct launcher route. A missing required MCP tool stops that operation and never authorizes shell fallback.

The server's existing SDK registration supplies entry and discovery instructions in standard MCP initialization, before deferred tool schemas. For intake or coordination, it routes attributed-call construction through the complete existing workflow skill: intake for new work, coordination for existing work. The selected skill owns sequencing and consultation of the runtime reference's task and host identity procedure. Follow those connection instructions first; this reference provides the detailed host procedure and request, startup and recovery contracts. If connection discovery instructions are absent, use the procedure below.

Pinboard wire identities, such as intake's `pinboard_overview` and `pinboard_proposal_create`, identify the required operations. The current host may advertise different full callable names for them. Resolve the native name before selecting a deferred tool schema:

1. Find the required operation in the host's actual tool announcement or native inventory and copy its full callable name, including the connector prefix. Resolve each host's names independently.
2. When the full name is known, use the host's exact-name selection with that full name. When it is unresolved, use supported keyword discovery to find the advertised callable.
3. If exact selection returns no match, reconcile the selected name with the actual advertised inventory. When a short wire name was selected, retry with the advertised full callable name. An unmatched short-name selection or an incomplete broad search does not establish a missing connection.
4. Inspect the returned callable identity and schema against the required operation, then invoke that native callable with exact project and work roots under its negotiated contract.

Do not infer that subagents are unavailable because an unrelated, nested, shell, MCP, or dynamically listed tool surface omits their controls. Report a missing subagent capability only after the runtime's native launch surface is actually absent or unsupported, or an actual required native launch returns an unavailable or unsupported result.

No adapter authorizes one client to control another or use another client's connection as a fallback.

## Current MCP request shapes

The native tools share one installed surface. These tools carry their exact selected leaf inside one strict `request` object: `pinboard_brief_contract`, `pinboard_brief_sources`, `pinboard_fixture_review`, `pinboard_startup_text`, `pinboard_brief_source_plan_output`, `pinboard_item_definition`, `pinboard_obligation_coverage`, `pinboard_item_status`, `pinboard_brief_review`, `pinboard_pr_review`, `pinboard_order`, `pinboard_parallel_preview`, `pinboard_actions`, `pinboard_preparation_authority`, `pinboard_attempt_authority`, `pinboard_transition`, `pinboard_cancel`, and `pinboard_initiative`. For attempt status, use `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "status", "attempt_id": "<exact attempt>"}}`. The roots, role or operation, and selected leaf fields all belong inside `request`. Unknown outer or inner fields and flat calls are rejected unchanged. The remaining tools retain their advertised ordinary object arguments. Discover and follow each current negotiated schema rather than copying a historical call.

`pinboard_close` is one of those remaining tools and has a single project role, so it takes no `request` wrapper and no `role`: `{"project_root": "<exact checkout>", "work_root": "<exact work root>", "receipt": {"action_id": {"kind": "close", "subject": "<item>"}, "subject_revision": "<from pinboard_actions>"}, "payload": {"outcome": "done", "reason": "<one line>", "human_decision": "<the human's explicit close decision in their own words>"}, "actor_task_id": "<task>", "actor_host_id": "<host>"}`. `human_decision` is required, nonempty and single-line; without the human's own words, ask the human and stop rather than writing them. Whether the human is asked to confirm each close depends on the runtime; its own reference says how. Report a denied close to the human and seek no other route. `pinboard_transition` has no close leaf and refuses a close receipt unchanged, naming `pinboard_close`.

Use `pinboard_item_status` with `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "item", "item_id": "<exact item>"}}` for one item's `pinboard-item-status/v3` result: state, labeled intake-time `intake_context`, the current attempt with its `branch` and `pause_reason`, the current attempt's `review_verdict` (`none`, `returned-for-correction`, `ready`, `accepted-and-continued`, or `checkpoint-accepted`), a terminal item's `closure` with its closing action, committed time, and, for a completion, closing attempt, and `board` with the absolute `markdown` and `html` paths of the generated board page under the selected work root, named whether or not those files exist yet. Use operation `branch` with an exact `branch` instead of `item_id` for `pinboard-branch-owners/v1`, which lists every item and attempt that recorded that branch. Use operation `integration` with an exact `item_id` and `target` (a local branch, remote-tracking ref, tag, or full commit id; Pinboard never fetches) for `pinboard-item-integration/v1`, which names the target's resolved `target_revision`, the reviewed candidate `source` (`protected-review`, `accepted-checkpoint` with its `checkpoint`, or `completion`) with its `compared_from_revision`, and `presence`: `content-present`, `content-not-present`, or `no-change`. All three leaves reject through `pinboard-mcp-item-status-result/v3`; the integration leaf adds `INTEGRATION_TARGET_UNRESOLVED`, `INTEGRATION_CANDIDATE_UNAVAILABLE`, `INTEGRATION_CANDIDATE_EVIDENCE_INVALID`, and an unchanged Git-checkout rejection carrying its `PROJECT_GIT_*` code; `BRANCH_OWNER_NOT_FOUND` also covers a branch recorded before a rebind, and `TRANSITION_RECEIPT_DAMAGED` names a consumed receipt whose outcome does not decode, with a diagnosis-only recovery: `pinboard validate` for a pause or paused-rebind receipt, otherwise a report of the named receipt and defect to the human.

`pinboard_dispatch` takes ordinary `project_root`, `work_root` and one strict `dispatch` leaf, without a `request` wrapper. Its registration description makes all six worker-launch leaves and the separate replacement-readiness leaf, their exact common fields and distinct review inputs explicit when a host loses construction details in callable metadata. The negotiated schema and typed decoder remain authoritative; this description does not repair the host's schema translator. Use only `action_id` and `subject_revision` from the fresh project dispatch action for `receipt`, and explicit `prompt: null` for canonical construction. Action discovery omits `payload_schema` for dispatch because no lifecycle-transition payload applies; construct its separate request through `pinboard_dispatch`. Ordinary and reviewed construction serve initial work. `local-correction` takes a local review bound to the accepted brief and an independent reviewer; `correction` retains the effective cross-boundary contract review. `reuse-correction` carries a fresh independent candidate-bound assessment and reuses accepted ready coverage only while the accepted brief and every reviewed source remain exact. All correction leaves bind the current return receipt, accepted starting snapshot, and exact reason. Initial ready review alone cannot substitute for candidate-bound correction review.

`pinboard_candidate_observe` takes ordinary exact `project_root`, `work_root`, and `attempt_id` arguments. It reads the named nonterminal attempt's branch/base context and the selected checkout's actual tracked working-tree identity, preimage and binary-diff metadata. `omitted_untracked_paths` reports Git-visible nonignored files excluded from that identity. The result is an observation, not protected evidence or acceptance. Preparation of only intended new paths is a separate authorized Git operation; reobserve afterwards and use existing own-leased submission. Observation changes no source, Git index, artifact, ledger or authority. It adds no committed-candidate mode; clean exact-current-commit submission remains separate.

`pinboard_correction_context` takes ordinary exact `project_root`, `work_root`, `attempt_id`, and `correction_history_id` arguments. Its read-only result returns the complete effective correction brief, exact brief/checkpoint/authority-set hashes, canonical return reason, accepted starting candidate artifact identity, complete snapshot fields with base64 diff bytes, and advisory `reuse_eligible` and `reuse_blockers`. Use it before independent correction-source review. Dispatch rechecks current source, accepted ready review, and snapshot identity after review; the read alone grants no authority and cannot freeze the checkout.

`pinboard_return_context` takes ordinary exact roots, `attempt_id`, and a strict `selection` with `kind: historical` or `kind: current-candidate` and the caller-selected `return_history_id`. Historical selection returns the exact original canonical return receipt and verified starting-snapshot identity and content, after rebind or rebase, and while a later pause or protected review leaves the selected return historical. It decodes and verifies only the selected receipt/snapshot evidence and grants no current correction authority. Finding the original submission may traverse unrelated revision-index entries between submission and return under the current schema; lookup work grows with those intervening receipts. This accepted limitation also affects the shared correction/replacement recovery reader; reopen when focused recovery becomes noticeably slow. No project export or full validation is required. Current-candidate selection additionally requires the current active return and the returned branch, HEAD and accepted base; it supplies plain effective review evidence plus the current tracked candidate and sorted omitted untracked path names. Untracked bytes remain outside candidate identity. Independently assess that complete subject before `candidate-correction` dispatch. Its `brief_review` is `pinboard-current-correction-source-review/v1`, with `boundary: cross-boundary` and a full `CorrectionSourceReview` as `source_review`, or `boundary: local` and a `LocalCorrectionSourceReview`; both carry the exact observed `current_candidate` binding. Existing exact-checkout correction and coverage-reuse shapes remain available. The read publishes nothing, and dispatch repeats current-return, historical-snapshot, lineage, candidate/path and source checks around publication.

`pinboard_candidate_restore` takes ordinary object arguments: exact `project_root`, `work_root`, `attempt_id`, and inspected `candidate`. Candidate recovery returns a native `restore` invocation with the chosen work root and exact candidate preserved; `project_root: null` is explicitly unresolved. Supply the caller-selected exact clean checkout on the recorded branch and preimage before invoking it. The tool restores only the current accepted snapshot context, not arbitrary archived checkpoints; an inspected candidate superseded by a newer submission rejects before Git. Source effects finish after entry and report only actual `source-checkout` changes or a committed post-mutation failure with `do-not-retry`. Restoration acquires no authority, changes no ledger or lifecycle, creates no checkout and launches no task.

`pinboard_attempt_inspect` takes ordinary exact roots, `attempt_id`, and required nullable `reconciliation`. Pass `null` for ordinary inspection. For a favorably reviewed candidate, `null` returns an ordinary review-state continuation of kind `reconcile-repository` that names the reviewed candidate and the repository reconciliation needed next; it is not a failed read. Then pass the outer coordinator's nonempty target revision, exact integration relation, legal repository phase, and exactly three effect observations in source-checkout, shared-work-root, git-metadata order to select one repository continuation. The adapter observes those repository and permission facts and performs only the returned continuation; Pinboard does not grant permissions or run Git, checkout, shared-work-root, cleanup, disposition, or terminal effects. A paused continuation carries `pause_reason`: the reason recorded by the current pause, carried forward by a paused rebind, or `null` for a checkpoint pause or an unrecorded reason. `pinboard_item_status` reports the same `pause_reason` on its current attempt.

`pinboard_review_job` takes exact roots and one `review` leaf. Ordinary `initial`, `package-initial`, `correction`, and `package-correction` remain repair-free and reject before prompt publication when the exact current candidate already has a valid ready-review record. Caller-selected retired v1/v2 checkpoint packages reject unchanged before publication. Their verified terminal archives preserve exact readable history and incoming completion coverage, but cannot authorize review, correction or restoration. Current v3 packages require their exact accepted candidate evidence and independent closure, including original brief and ready-review bindings; an archive waives none of those checks. Run full validation separately before selecting package evidence. The `record-ready` leaf is separate: it requires exact current candidate, snapshot, accepted-brief, result and review digests, `reviewer_prompt_sha256` copied from the `prompt_reference.sha256` that a launch leaf returned for that exact candidate, brief and `result.md`, the identity of the reviewer launched from that prompt, `verdict: ready`, and nonempty acceptance evidence. It takes no runtime or background fields, never launches a reviewer, and returns only the canonical `pinboard-candidate-review/v2` record and exact publication accounting. A digest that names no reviewer prompt published for that subject—a missing, worker, foreign or older-result prompt—rejects unchanged with `REVIEWER_PROMPT_NOT_COMMISSIONED`; run the review job for the current candidate first. Terminal completion through either payload leaf rejects unchanged with `CANDIDATE_REVIEW_REQUIRED` until such a recorded review names the completion's `reviewer_task_id`; its observations name the missing exact review binding and one read-only attempt inspection. The closure refusal does not commission or launch a reviewer.

`pinboard_order` takes exact roots, the existing strict `order` record (`schema: pinboard-live-order/v1`, complete `expected_order` and authorized `requested_order`) and trusted `actor_task_id`/`actor_host_id` inside `request`. It needs no preparation or worker lease and grants no launch authority. Its result preserves the committed receipt or unchanged rejection; known committed warnings name the exact retained CLI view-repair command. The structured `recovery` points to fresh `pinboard_overview` arguments for current-state reconciliation, not proof that this caller committed or recovery of its lost receipt. Equal order after a valid no-op cannot distinguish a committed call from one that never ran. There is no exactly-once guarantee; never blindly replay a lost reply or committed warning.

`pinboard_parallel_preview` takes exact roots and `selection: selected` with nonempty unique supported `item_ids`, or explicit `selection: all-safe` without item IDs, inside `request`. Selected reads focused current facts; all-safe reads current portfolio constraints without proposal bodies or retained history. Neither leaf changes artifacts, views, lifecycle, authority or native tasks. Structural safety does not certify readiness or replace human batch permission and fresh launch checks.

Use `pinboard_item_definition` operation `current` with exact roots and `item_id` for the complete accepted definition and its current identity. Its `history` leaf additionally requires an explicit `limit` from 1 to 100 and `before_revision`: begin with `null`, then use the returned `next_before_revision` as the exclusive cursor while it is non-null. Both leaves are read-only and require no lease.

Use `pinboard_brief_review` operation `publish` with exact roots, `brief_artifact_ref_id`, and a complete structured `pinboard-work-brief-review-needs-correction/v1` record bound to that accepted brief. The `status` leaf takes roots and the exact reference only; it verifies the accepted bytes and returns the canonical brief, `accepted_brief_sha256`, `checkpoint_sha256`, `reviewed_authority_set_sha256`, and verified latest negative evidence, if any. Both status variants carry the same bindings: copy them for initial ready or negative review; the accepted-brief digest equals `accepted_brief.sha256`, and the other digests use the existing canonical checkpoint and ordered-authority codec. These facts establish the review subject, never the review conclusion. Corrupt or unreadable accepted bytes return `ARTIFACT_BYTES_INVALID` with unchanged target effects and `do-not-retry`; preserve the named resource for human diagnosis. Wrap returned `correction.status_request` inside `request` when calling the same tool. The correction target names `pinboard_brief_publish` and its exact roots; add the complete corrected brief as `brief`. Neither negative evidence nor its absence proves ready review, changes lifecycle, or acquires authority.

Focused project `pinboard_actions` discovery for the exact `complete` action supplies the current completion contract. When closure lacks a protected current candidate or the accepted checkpoint still continues, that focused MCP result reports the pending condition, includes the exact accepted `remaining_work` for a continuing checkpoint, and supplies one read-only `pinboard_attempt_inspect` input with the caller's exact roots. Follow the inspection to establish what remains before choosing further authorized work. Discovery supplies no acquisition, submission, dispatch or scope-replacement recipe and never reconstructs a candidate automatically.

Historical definition queries and portable export preserve the original v1 schema and full fields without a checkout policy or synthesized obligations. These records are historical evidence, never current execution authority. Activation, rebind, resume and dispatch require a genuine current supported definition: origin-free v2 or origin-bearing v3.

`pinboard_cancel` accepts one strict top-level `request` containing the `preview` or `confirm` operation and exact project/work roots. Preview requires `item_id`. Confirm additionally requires the preview's exact `binding`, the separate human reply as `human_confirmation`, and trusted current `actor_task_id` and `actor_host_id`. The preview token and quoted words do not authenticate human authorship. Follow the [separate chat confirmation procedure](setup-and-transitions.md#cancel-after-separate-exact-item-confirmation); generic transitions accept no cancellation leaf.

## Brief construction and source preparation

Use `pinboard_brief_contract` with a strict `request` containing exact roots and `operation: full`, or `operation: starter` with `boundary: local` or `cross-boundary`. Copy the returned complete starter, choose its structural variants, and fill unresolved values from accepted facts. Construction resolves no roots or ledger and grants no readiness or authority.

Use read-only `pinboard_brief_sources` with exact roots inside `request`: `plan` takes a structured `manifest` and positive `max_batch_bytes`; `emit` takes the returned structured plan and nonnegative `batch_index`. The complete inline plan and each emitted batch must fit the presented-result limit. If a plan exceeds it, divide the manifest into smaller selections and use `plan` and `emit` for each without a write or human replanning. Read each verified batch once in order, and resume at the first unread `batch_index` from the same plan after an interruption. Use write-capable `pinboard_brief_source_plan_output` for `plan-to-file` only when a durable plan is explicitly needed, with one destination; then read batches through the read-only `emit-file` leaf using `plan_path` and `batch_index`. Planning and emission resolve the selected source checkout and never open work state. Plan-to-file creates or identically reuses only its exact immutable destination; a differing destination rejects unchanged. A visible output followed by synchronization failure reports committed `selected-output` and `do-not-retry`; inspect that destination, never replay the failure. Required roots are context, not permission to create durable state.

### Recover a lost brief-publication result

When `pinboard_brief_publish` may have committed but its result was lost, recover with `pinboard_brief_lookup` using ordinary arguments `project_root`, `work_root`, `attempt_id` and positive `artifact_revision` from the original publication request. Do not replay publication. The read selects only that exact accepted brief, including an unbound correction, and verifies its selector, size and SHA-256 before returning `pinboard-verified-artifact-reference/v1`. It changes no files, settings, traces, references, binding or lifecycle, even when optional tracing is on.

Compare the recovered identity, digest and size with the intended canonical brief before continuing separately authorized preparation. When the intended bytes are unavailable, report the verified receipt and leave that comparison unresolved. Acceptance alone proves neither current-definition conformity nor an active binding or readiness. `BRIEF_LOOKUP_INVALID` names the input or root condition to correct. `BRIEF_NOT_FOUND` names the original roots, attempt and revision to confirm; it does not prove the original publication had no partial immutable-file effect. Report an unresolved absence to the human for diagnosis without reconstructing bytes or replaying publication. `ARTIFACT_BYTES_INVALID` names the exact accepted resource and defect: preserve it and report it to the human; do not retry unchanged or overwrite accepted bytes.

## Prompt verification and worker startup

Dispatch and review-job publication create no native worker. Call only their returned `native_launch.tool` with exactly the strict runtime-specific `native_launch.arguments` from the `pinboard-native-agent-launch/v2` envelope. Do not add, remove, or rewrite an argument, or substitute the separately returned `prompt_reference`, its path, prompt bytes, or a reconstructed launch message. The compact host argument already names the exact accepted prompt identity and immutable file selected by Pinboard. A worker or reviewer launched from different arguments is invalid; stop it and launch a fresh context from the unchanged recipe instead of coaching or resuming it. Follow the recipe's exact `pinboard_artifact_verify` call before reading the named prompt file. Require the accepted identity, verification schema, selector, size, digest and bytes to agree, then read that exact file completely through the envelope's `pinboard_startup_text` `artifact-start` request and treat its verified bytes as the direct task from the launching coordinator. Follow its exact continuation under `request` until null, checking the same source digest/size and contiguous character ranges. Emit one page per outer response; collecting bounded pages into one large output can still truncate. EOF establishes delivery, not comprehension or readiness. Native skill loading suffices only when it delivers the complete body; otherwise load the complete caller-resolved absolute skill/reference path with `pinboard_startup_text` operation `file-start`, exact roots and `max_batch_bytes: "host-profile"`, following the same page procedure. Stop if verification or the immediate read fails or differs; never select another artifact or ask the parent to restate the task. Immutable historical CLI-origin envelopes retain their original verifier as evidence, not a supported current invocation. Prompt identity and execution semantics are shared; the envelope owns runtime selection, exact host arguments, verifier and startup presentation without copying an unbounded prompt through the parent agent's launch call.

After prompt verification and the exact prompt read, a worker loads the complete delivery skill through its runtime reference's skill-loading route and uses the complete canonical brief and bootstrap contained in that verified direct task before acquiring its own authority. Obtain the launched worker's own trusted post-launch identity through that runtime and preserve the returned lease and generation together. Continue successful delivery through current result evidence, candidate observation, own-leased submission, protected-review confirmation and lease release. A missing required MCP tool or identity stops its operation; a historical brief's retired CLI bootstrap does not restore that route. Never manufacture identity, temporary payload files, or substitute shell calls for a missing connection. A denied invocation does not authorize editing saved permission policy.

Newly generated MCP launch envelopes carry wrapped acquisition and continuation inputs under the [current request contract](#current-mcp-request-shapes); artifact verification keeps its ordinary arguments. Immutable historical prompts remain evidence, not a flat-call compatibility route.

### Startup page budget

`pinboard_startup_text` sizes pages for the connected host. The server identifies the host from the MCP initialize `clientInfo` name and version and selects that host's measured profile; an unknown client or a version outside the measured range gets the conservative unmeasured profile. Request `max_batch_bytes: "host-profile"` to use the profile's page size; an integer is a ceiling, and the effective budget is the smaller of that integer and the profile. Each page reports its effective `max_batch_bytes`, and its continuation carries that integer, so follow the continuation unchanged. Where the host shows the model only `structuredContent`, pages omit the duplicate text companion and the budget prices only what is sent.

## Native human questions

Apply the main skill's [question policy](../SKILL.md#match-detail-to-the-question) through tools actually exposed in the current runtime. For a long or context-heavy question, ask concisely in ordinary chat, end the turn, and stop tool work until the human answers; do not use a timed, countdown, or asynchronous popup. Silence, expiry, preselection, and an unread prompt supply no response or approval.

Each runtime's own reference names its native question route. A runtime without one uses its available native question capability only as permitted by that tool's current instructions, or the same text fallback. Native question support is not a desktop-only assumption or a promised capability of every host. Execution permission escalation remains in the host's actual approval mechanism, including the source-setup recovery below.

## Source-worktree setup recovery

Run the repository's exact setup command in the selected checkout through normal runtime execution first. On failure, use its diagnostics or one cheapest additional observation to distinguish a sandbox permission restriction from a missing prerequisite, actual locked-install failure, network failure, or a defect in the tool being changed.

For a diagnosed sandbox permission restriction during already-authorized source setup, request the runtime's permission review for one retry of that exact command in the same checkout. Do not add a separate conversational confirmation. Runtime approval still controls whether the retry executes. Each runtime's own reference names its permission-request route for that one invocation.

If permission is denied or unavailable, the retry fails, the cause is not a sandbox restriction, or recovery would change accepted scope, stop setup and report the exact observation. Ask the human to abort, authorize one bounded retry or investigation, or revise the accepted scope and evidence. Do not repeat the retry, relocate caches, edit global configuration, bypass approval, or weaken locked setup to continue.

After successful setup, continue with the prepared checkout and preserve the result as setup evidence. This route changes only source-worktree setup recovery. Installed-runtime preparation and protected ledger writes retain their own recovery contracts; ordinary installed Pinboard commands use the prepared plugin runtime without uv or managed-project environments.
