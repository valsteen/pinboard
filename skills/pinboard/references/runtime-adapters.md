# Coding-agent runtime adapters

Pinboard exposes agent workflows through local stdio MCP and retained human and maintenance operations through CLI. Both use one SQLite authority, action vocabulary, brief schema and skill tree. Use this reference only to translate shared workflow operations into the current coding agent's native outer capabilities. The surrounding skill remains the semantic owner.

`<launcher-root>` is the resolved directory containing `scripts/pinboard`. Ordinary MCP declarations invoke that launcher with exactly `--mcp`; Claude and Antigravity hooks use their exact selectors described below, and direct CLI operations use CLI arguments. CLI capture accepts only normal CLI targets and cannot wrap either protocol startup path. A caller may instead start one dedicated captured MCP process with the complete explicit pair described below. When `<launcher-root>` is a prepared `<pinboard-source>` checkout, the launcher uses `<pinboard-source>/.venv`. When it is an installed plugin version, the launcher uses `<launcher-root>/.pinboard-runtime/environment`. `<managed-project>` and its exact work root are request data, never runtime or dependency locations. Runtime selection follows the resolved launcher root, not the human or agent audience.

## Public contracts and source scope

When Pinboard coordinates another project, use its advertised tools, verified artifacts and loaded public skill contracts. Its installed implementation, tests, private modules, generated code and database internals are outside that assignment; do not inspect them to derive protocol behavior, canonicalization or missing values. Pinboard source inspection remains available when the accepted assignment explicitly covers Pinboard development or a separate human-authorized Pinboard investigation.

If a required value or capability is unavailable, stop the affected operation before its dependent publication, lifecycle change or implementation. Preserve the exact project/work roots, accepted artifact identity and checkpoint when known; name the missing field or tool, the attempted operation and its consequence. Report observed target and auxiliary effects separately, or state that they are unknown; a missing input never proves that earlier calls had no effects. Use the exact supported recovery from the producing response or public contract. If none supplies the input, report that gap and the complete structured error to the human or owning coordinator. Resume only when a supported tool, verified artifact or documented contract supplies it. Do not invent, approximate or omit values, weaken independent judgment, reconstruct undocumented hashes, or use another agent, process or client as a proxy.

## Packaged connection and first setup

Codex's explicit root `mcp-codex.json` declares `sh ./scripts/pinboard --mcp` with `cwd: "."`, resolved under the plugin root. Claude's separate root `mcp-claude.json` declares `${CLAUDE_PLUGIN_ROOT}/scripts/pinboard --mcp`; the client expands that root in the command. Antigravity's root `mcp_config.json`, named by its native `.antigravity-plugin/plugin.json` discovery, declares command `sh` with arguments `${PLUGIN_ROOT}/scripts/pinboard --mcp`, because Antigravity expands `${PLUGIN_ROOT}` only in arguments, environment and working directory, not in the command. All three start the existing `pinboard-mcp` entry through the same runtime owner. Ordinary declarations accept no additional arguments, and every tool call carries exact project and work roots. For an explicitly approved exact-evidence run, start a separate process as `<launcher-root>/scripts/pinboard --mcp --capture-evidence-dir <existing-directory> --safe-to-persist-exactly`. The selected directory applies only to that process; startup proves writable immutable publication before accepting callbacks, and partial declarations reject before startup without altering the installed manifests.

Resolve those roots before the first call. The project root is the exact selected checkout. Unless the user or an existing Pinboard receipt selected another work root, a normal checkout uses `<project-root>/.pinboard`. Read the exact selected initialized root; an unavailable root supplies no authority to choose another location. Explicit work roots retain their ordinary resolution and initialization rules. A released v6 ledger uses `migrate-schema` preview and apply at its selected real root while quiescent. A containing temporary directory, fixture root, checkout parent, or project root itself is not the work root. A linked worktree reuses only the exact shared work root supplied by its accepted workflow or resolved through the retained root command; do not guess it from the worktree path.

If a version is unprepared and uv is available, MCP startup invokes the same `--prepare-runtime` path and starts the server after readiness is verified. Claude Code's and Antigravity's SessionStart hooks can also invoke that preparation; the version-local lock serializes both callers. Missing uv, contention or failed preparation leaves the MCP connection attempt unavailable and puts its strict same-launcher recovery on stderr, never protocol stdout. The hook reports its own preparation facts and the exact manual command as additional context; it cannot establish the current connection status. Deliberate CLI setup may run `<launcher-root>/scripts/pinboard --prepare-runtime` with uv and write access only to that version's `.pinboard-runtime`. Follow the exact preparation result and check tool availability. Use the client's supported MCP reconnect or plugin reload mechanism if the connection remains unavailable after preparation. Setup and CLI-only operations retain their direct launcher route. A missing required MCP tool stops that operation and never authorizes shell fallback.

The server's existing SDK registration supplies entry and discovery instructions in standard MCP initialization, before deferred tool schemas. For intake or coordination, it routes attributed-call construction through the complete existing workflow skill: intake for new work, coordination for existing work. The selected skill owns sequencing and consultation of this reference's runtime identity procedure. Follow those connection instructions first; this reference provides the detailed host procedure and request, startup and recovery contracts. If connection discovery instructions are absent, use the procedure below.

Pinboard wire identities, such as intake's `pinboard_overview` and `pinboard_proposal_create`, identify the required operations. The current host may advertise different full callable names for them. Resolve the native name before selecting a deferred tool schema:

1. Find the required operation in the host's actual tool announcement or native inventory and copy its full callable name, including the connector prefix. Resolve each host's names independently.
2. When the full name is known, use the host's exact-name selection with that full name. When it is unresolved, use supported keyword discovery to find the advertised callable.
3. If exact selection returns no match, reconcile the selected name with the actual advertised inventory. When a short wire name was selected, retry with the advertised full callable name. An unmatched short-name selection or an incomplete broad search does not establish a missing connection.
4. Inspect the returned callable identity and schema against the required operation, then invoke that native callable with exact project and work roots under its negotiated contract.

## Antigravity adapter

Antigravity CLI (`agy`) loads the repository root as a native plugin through `.antigravity-plugin/plugin.json`, the root `mcp_config.json` and the root `hooks.json`; it does not convert the Claude manifest. It names the Pinboard server `pinboard_pinboard` and runs every MCP call, for every server, through its own `call_mcp_tool` tool with `ServerName`, `ToolName` and `Arguments`. Three setup facts shape every route below:

- Antigravity runs Pinboard tools only after the user adds `mcp(pinboard_pinboard/*)` to `permissions.allow` in `~/.gemini/antigravity-cli/settings.json`, as [INSTALL.md](../../../INSTALL.md#antigravity) describes. Pinboard never writes that file. Without the rule, an interactive session prompts for each call and headless `agy -p` denies it. Report a denial as that missing setup step; do not edit settings, pass `--dangerously-skip-permissions`, or retry through another route.
- In headless `agy -p`, a refused action in an `invoke_subagent` worker or reviewer is never delivered: the child stalls and the parent waits with no message, an accepted limitation recorded in [ARCHITECTURE.md](../../../ARCHITECTURE.md#known-limitations-and-operating-assumptions). Reviewers compute artifact digests through a shell command, so unattended headless review needs the hash-command allow rule, such as `command(shasum)`, that [INSTALL.md](../../../INSTALL.md#unattended-headless-runs) documents. Interactive sessions are expected to ask the user instead, which is unconfirmed.
- Antigravity injects only the first 24000 bytes of a skill body, and the main `pinboard` and `pinboard-deliver` skills are larger. Its skill catalog names each skill's absolute `SKILL.md` path. Before acting on a Pinboard skill or reference, read that complete file through `pinboard_startup_text` operation `file-start` with exact roots and `max_batch_bytes: 8000`, following each continuation until null. The injected body is never a loaded skill.

The root `hooks.json` registers two entries. Antigravity runs each hook with the plugin root as working directory:

- **SessionStart** runs `./scripts/pinboard --antigravity-session-start`. Antigravity fires it for a parent session and again for every `invoke_subagent` child, each with its own `conversationId`. The entry decodes the Antigravity-owned event, validates its required fields, ignores unrelated additive fields, samples `socket.gethostname()`, and injects one system message: `Pinboard native task_id: "<conversationId>"; host_id: "<machine name>"`, the attribution rule below, and the paged skill-loading instruction. It forwards no paths or prompt text and grants no authority. A malformed event injects nothing and leaves only a payload-free diagnostic. On an unprepared plugin version it runs the same `--prepare-runtime` path and reports that result as injected context, recommending a new agy session if the connection stays unavailable.
- **PreToolUse** on `call_mcp_tool` runs `./scripts/pinboard --antigravity-pre-tool-use`. Antigravity offers no narrower matcher, and it blocks a call whose hook fails or answers nothing, so the entry answers every well-formed call. It answers `force_ask` for `pinboard_close` on `pinboard_pinboard`, so the human confirms every close even under the allow rule; `allow` for every other Pinboard tool; and `ask` for every other server, so Antigravity's own approval settings, including that server's own allow rules, decide. A hook `allow` alone does not pass Antigravity's permission check; the user's allow rule does. Headless `agy -p` cannot show the forced prompt and denies it, so `pinboard_close` is unavailable there. When the plugin hook does not run, Antigravity's own approval settings decide for every tool, as Codex's do. On an unprepared plugin version the launcher still answers, with `force_ask` for any call naming `pinboard_close` and `ask` otherwise. A malformed event leaves only a payload-free diagnostic and a failed hook, which Antigravity treats as a block for that call.

## Claude confined evidence-write recovery

A `PreToolUse:Write` refusal that names the isolated worktree and says the attempt path is in the base repo checkout comes from Claude Code's built-in worktree guard. [Claude's isolation documentation](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation) describes location-based checks that block `Edit`, `Write`, and `NotebookEdit` in the main checkout, including for subagents of an isolated session. Pinboard's separate PreToolUse hook matches only `mcp__plugin_pinboard_pinboard__.*` and emits `allow`; it does not govern `Write`.

Ignored `.pinboard` files under the main checkout are still in that checkout, so the guard can refuse the exact shared-work-root `result.md`, `blocker.md`, or `review.md` destination. Keep that destination: the refusal's suggested worktree-local `.pinboard` path is not the shared board and would not record its evidence. Human authorization for the evidence write does not disable the guard; Claude documents that it cannot be turned off.

Use the existing recovery below for this refusal; do not relocate attempt evidence, edit saved permission policy, remove the checkout, or retry through another path.

- **Confined worker.** Write the complete intended file to your own session scratchpad. Return to the owning task naming the refused exact attempt path and the scratch path, and state that the evidence is not yet recorded.
- **Owning session in its launch directory.** Copy those exact bytes to the named attempt path with one approved command, such as `cp <scratch-path> <attempt-path>`, and verify that both files have the same SHA-256. Then continue the same worker through its native handle so it can finish from the recorded evidence.
- **Confined owning session.** Ask the human whether to leave the worktree with `ExitWorktree` action `keep`. Its tool description states that `keep` leaves the worktree directory and branch on disk and restores the session to the directory it had before `EnterWorktree`. After that exit, write or copy the evidence from the launch directory as above.
- **No active worktree session.** `ExitWorktree` acts only on a worktree entered with `EnterWorktree` in the current session; otherwise it reports that no worktree session is active and changes nothing, and `keep` does not restore the launch directory. In that case stop, keep the scratch copy, and give the human the refused exact attempt path, the scratch path, and the scratch file's SHA-256 so they can copy it from a session in the launch directory and verify the digest.

## Current MCP request shapes

The native tools share one installed surface. These tools carry their exact selected leaf inside one strict `request` object: `pinboard_brief_contract`, `pinboard_brief_sources`, `pinboard_fixture_review`, `pinboard_startup_text`, `pinboard_brief_source_plan_output`, `pinboard_item_definition`, `pinboard_obligation_coverage`, `pinboard_item_status`, `pinboard_brief_review`, `pinboard_pr_review`, `pinboard_order`, `pinboard_parallel_preview`, `pinboard_actions`, `pinboard_preparation_authority`, `pinboard_attempt_authority`, `pinboard_transition`, `pinboard_cancel`, and `pinboard_initiative`. For attempt status, use `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "status", "attempt_id": "<exact attempt>"}}`. The roots, role or operation, and selected leaf fields all belong inside `request`. Unknown outer or inner fields and flat calls are rejected unchanged. The remaining tools retain their advertised ordinary object arguments. Discover and follow each current negotiated schema rather than copying a historical call.

`pinboard_close` is one of those thirteen and has a single project role, so it takes no `request` wrapper and no `role`: `{"project_root": "<exact checkout>", "work_root": "<exact work root>", "receipt": {"action_id": {"kind": "close", "subject": "<item>"}, "subject_revision": "<from pinboard_actions>"}, "payload": {"outcome": "done", "reason": "<one line>", "human_decision": "<the human's explicit close decision in their own words>"}, "actor_task_id": "<task>", "actor_host_id": "<host>"}`. `human_decision` is required, nonempty and single-line; without the human's own words, ask the human and stop rather than writing them. The tool registration carries `_meta` `anthropic/requiresUserInteraction: true`, for which Claude Code v2.1.199 or later documents a per-call confirmation prompt that neither an allow rule nor the Pinboard PreToolUse allow skips, and a denial in `dontAsk` mode and non-interactive runs; report a denied close to the human and seek no other route. Codex ignores that metadata and applies its own approval settings, and older Claude Code versions do not prompt. Antigravity asks the human because Pinboard's PreToolUse hook answers `force_ask` for `pinboard_close`, which an allow rule does not skip; headless `agy -p` runs cannot show that prompt and deny the close. When that hook does not run, Antigravity's own approval settings decide, as Codex's do. `pinboard_transition` has no close leaf and refuses a close receipt unchanged, naming `pinboard_close`.

Use `pinboard_item_status` with `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "item", "item_id": "<exact item>"}}` for one item's `pinboard-item-status/v3` result: state, labeled intake-time `intake_context`, the current attempt with its `branch` and `pause_reason`, the current attempt's `review_verdict` (`none`, `returned-for-correction`, `ready`, `accepted-and-continued`, or `checkpoint-accepted`), a terminal item's `closure` with its closing action, committed time, and, for a completion, closing attempt, and `board` with the absolute `markdown` and `html` paths of the generated board page under the selected work root, named whether or not those files exist yet. Use operation `branch` with an exact `branch` instead of `item_id` for `pinboard-branch-owners/v1`, which lists every item and attempt that recorded that branch. Use operation `integration` with an exact `item_id` and `target` (a local branch, remote-tracking ref, tag, or full commit id; Pinboard never fetches) for `pinboard-item-integration/v1`, which names the target's resolved `target_revision`, the reviewed candidate `source` (`protected-review`, `accepted-checkpoint` with its `checkpoint`, or `completion`) with its `compared_from_revision`, and `presence`: `content-present`, `content-not-present`, or `no-change`. All three leaves reject through `pinboard-mcp-item-status-result/v3`; the integration leaf adds `INTEGRATION_TARGET_UNRESOLVED`, `INTEGRATION_CANDIDATE_UNAVAILABLE`, `INTEGRATION_CANDIDATE_EVIDENCE_INVALID`, and an unchanged Git-checkout rejection carrying its `PROJECT_GIT_*` code; `BRANCH_OWNER_NOT_FOUND` also covers a branch recorded before a rebind, and `TRANSITION_RECEIPT_DAMAGED` names a consumed receipt whose outcome does not decode, with a diagnosis-only recovery: `pinboard validate` for a pause or paused-rebind receipt, otherwise a report of the named receipt and defect to the human.

`pinboard_dispatch` takes ordinary `project_root`, `work_root` and one strict `dispatch` leaf, without a `request` wrapper. Its registration description makes all six worker-launch leaves and the separate replacement-readiness leaf, their exact common fields and distinct review inputs explicit when a host loses construction details in callable metadata. The negotiated schema and typed decoder remain authoritative; this description does not repair the host's schema translator. Use only `action_id` and `subject_revision` from the fresh project dispatch action for `receipt`, and explicit `prompt: null` for canonical construction. Action discovery omits `payload_schema` for dispatch because no lifecycle-transition payload applies; construct its separate request through `pinboard_dispatch`. Ordinary and reviewed construction serve initial work. `local-correction` takes a local review bound to the accepted brief and an independent reviewer; `correction` retains the effective cross-boundary contract review. `reuse-correction` carries a fresh independent candidate-bound assessment and reuses accepted ready coverage only while the accepted brief and every reviewed source remain exact. All correction leaves bind the current return receipt, accepted starting snapshot, and exact reason. Initial ready review alone cannot substitute for candidate-bound correction review.

`pinboard_candidate_observe` takes ordinary exact `project_root`, `work_root`, and `attempt_id` arguments. It reads the named nonterminal attempt's branch/base context and the selected checkout's actual tracked working-tree identity, preimage and binary-diff metadata. `omitted_untracked_paths` reports Git-visible nonignored files excluded from that identity. The result is an observation, not protected evidence or acceptance. ## Source-worktree setup recovery

Run the repository's exact setup command in the selected checkout through normal runtime execution first. On failure, use its diagnostics or one cheapest additional observation to distinguish a sandbox permission restriction from a missing prerequisite, actual locked-install failure, network failure, or a defect in the tool being changed.

For a diagnosed sandbox permission restriction during already-authorized source setup, request the runtime's permission review for one retry of that exact command in the same checkout. Do not add a separate conversational confirmation. Runtime approval still controls whether the retry executes:

- In Codex, use the execution tool's `sandbox_permissions: "require_escalated"` with a justification naming the observed restriction and the authorized setup command. Request only that invocation; do not add a persistent approval rule.
- In Claude Code, use the current runtime's native permission request for that invocation when available. Do not invent a permission API or treat a dispatch declaration as an execution grant.
- In Antigravity, use its native command permission prompt for that invocation when available. Do not add a `permissions.allow` rule for it; a headless run that cannot prompt stops setup.

Ask the human to abort, authorize one bounded retry or investigation, or revise the accepted scope and evidence. Do not repeat the retry, relocate caches, edit global configuration, bypass approval, or weaken locked setup to continue.

After successful setup, continue with the prepared checkout and preserve the result as setup evidence. This route changes only source-worktree setup recovery. Installed-runtime preparation and protected ledger writes retain their own recovery contracts; ordinary installed Pinboard commands use the prepared plugin runtime without uv or managed-project environments.
