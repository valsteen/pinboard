# Coding-agent runtime adapters

Pinboard exposes agent workflows through local stdio MCP and retained human and maintenance operations through CLI. Both use one SQLite authority, action vocabulary, brief schema and skill tree. Use this reference only to translate shared workflow operations into the current coding agent's native outer capabilities. The surrounding skill remains the semantic owner.

`<launcher-root>` is the resolved directory containing `scripts/pinboard`. Ordinary MCP declarations invoke that launcher with exactly `--mcp`; Claude startup hooks use their exact selectors described below, and direct CLI operations use CLI arguments. CLI capture accepts only normal CLI targets and cannot wrap either protocol startup path. A caller may instead start one dedicated captured MCP process with the complete explicit pair described below. When `<launcher-root>` is a prepared `<pinboard-source>` checkout, the launcher uses `<pinboard-source>/.venv`. When it is an installed plugin version, the launcher uses `<launcher-root>/.pinboard-runtime/environment`. `<managed-project>` and its exact work root are request data, never runtime or dependency locations. Runtime selection follows the resolved launcher root, not the human or agent audience.

## Packaged connection and first setup

Codex's explicit root `mcp-codex.json` declares `sh ./scripts/pinboard --mcp` with `cwd: "."`, resolved under the plugin root. Claude's separate root `mcp-claude.json` declares `${CLAUDE_PLUGIN_ROOT}/scripts/pinboard --mcp`; the client expands that root in the command. Both start the existing `pinboard-mcp` entry through the same runtime owner. Ordinary declarations accept no additional arguments, and every tool call carries exact project and work roots. For an explicitly approved exact-evidence run, start a separate process as `<launcher-root>/scripts/pinboard --mcp --capture-evidence-dir <existing-directory> --safe-to-persist-exactly`. The selected directory applies only to that process; startup proves writable immutable publication before accepting callbacks, and partial declarations reject before startup without altering the installed manifests.

Resolve those roots before the first call. The project root is the exact selected checkout. Unless the user or an existing Pinboard receipt selected another work root, a normal checkout uses `<project-root>/.pinboard`. A legacy-only `.codex/pinboard` project requires the exact installed `pinboard migrate-work-root` recovery before ordinary use; do not open it directly or initialize a competing board. A containing temporary directory, fixture root, checkout parent, or project root itself is not the work root. A linked worktree reuses only the exact shared work root supplied by its accepted workflow or resolved through the retained root command; do not guess it from the worktree path.

If a version is unprepared, MCP startup exits before the server starts and puts its strict same-launcher preparation action on stderr, never protocol stdout. In Claude Code, the plugin's SessionStart hook runs that same preparation during the first session when uv is available and then asks for one MCP reconnect; otherwise it reports the cause and the exact manual command as additional context. Deliberate CLI setup may run `<launcher-root>/scripts/pinboard --prepare-runtime` with uv and write access only to that version's `.pinboard-runtime`. Follow the exact preparation result, then use the client's supported MCP reconnect or plugin reload mechanism before attempting a covered tool. Setup and CLI-only operations retain their direct launcher route. A missing required MCP tool stops that operation and never authorizes shell fallback.

The server's existing SDK registration supplies entry and discovery instructions in standard MCP initialization, before deferred tool schemas. For intake or coordination, it routes attributed-call construction through the complete existing workflow skill: intake for new work, coordination for existing work. The selected skill owns sequencing and consultation of this reference's runtime identity procedure. Follow those connection instructions first; this reference provides the detailed host procedure and request, startup and recovery contracts. If connection discovery instructions are absent, use the procedure below.

Pinboard wire identities, such as intake's `pinboard_overview` and `pinboard_proposal_create`, identify the required operations. The current host may advertise different full callable names for them. Resolve the native name before selecting a deferred tool schema:

1. Find the required operation in the host's actual tool announcement or native inventory and copy its full callable name, including the connector prefix. Resolve each host's names independently.
2. When the full name is known, use the host's exact-name selection with that full name. When it is unresolved, use supported keyword discovery to find the advertised callable.
3. If exact selection returns no match, reconcile the selected name with the actual advertised inventory. When a short wire name was selected, retry with the advertised full callable name. An unmatched short-name selection or an incomplete broad search does not establish a missing connection.
4. Inspect the returned callable identity and schema against the required operation, then invoke that native callable with exact project and work roots under its negotiated contract.

## Claude confined evidence-write recovery

A Claude session that entered a managed worktree with `EnterWorktree` is confined to it, and a write to an exact attempt `result.md`, `blocker.md`, or `review.md` path under the shared work root can be refused. Use only this recovery; do not relocate attempt evidence, edit saved permission policy, remove the checkout, or retry through another path.

- **Confined worker.** Write the complete intended file to your own session scratchpad. Return to the owning task naming the refused exact attempt path and the scratch path, and state that the evidence is not yet recorded.
- **Owning session in its launch directory.** Copy those exact bytes to the named attempt path with one approved command, such as `cp <scratch-path> <attempt-path>`, and verify that both files have the same SHA-256. Then continue the same worker through its native handle so it can finish from the recorded evidence.
- **Confined owning session.** Ask the human whether to leave the worktree with `ExitWorktree` action `keep`. Its tool description states that `keep` leaves the worktree directory and branch on disk and restores the session to the directory it had before `EnterWorktree`. After that exit, write or copy the evidence from the launch directory as above.
- **No active worktree session.** `ExitWorktree` acts only on a worktree entered with `EnterWorktree` in the current session; otherwise it reports that no worktree session is active and changes nothing, and `keep` does not restore the launch directory. In that case stop, keep the scratch copy, and give the human the refused exact attempt path, the scratch path, and the scratch file's SHA-256 so they can copy it from a session in the launch directory and verify the digest.

## Current MCP request shapes

The twenty-two tool identities share one installed surface. Twelve tools carry their exact selected leaf inside one strict `request` object: `pinboard_brief_contract`, `pinboard_brief_sources`, `pinboard_item_definition`, `pinboard_item_status`, `pinboard_brief_review`, `pinboard_pr_review`, `pinboard_order`, `pinboard_parallel_preview`, `pinboard_actions`, `pinboard_preparation_authority`, `pinboard_attempt_authority`, and `pinboard_transition`. For attempt status, use `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "status", "attempt_id": "<exact attempt>"}}`. The roots, role or operation, and selected leaf fields all belong inside `request`. Unknown outer or inner fields and flat calls are rejected unchanged. The other ten tools retain their advertised ordinary object arguments. Discover and follow each current negotiated schema rather than copying a historical call.

Use `pinboard_item_status` with `{"request": {"project_root": "<exact checkout>", "work_root": "<exact work root>", "operation": "item", "item_id": "<exact item>"}}` for one item's `pinboard-item-status/v2` result: state, labeled intake-time `intake_context`, the current attempt with its `branch` and `pause_reason`, the current attempt's `review_verdict` (`none`, `returned-for-correction`, `ready`, `accepted-and-continued`, or `checkpoint-accepted`), and a terminal item's `closure` with its closing action, committed time, and, for a completion, closing attempt. Use operation `branch` with an exact `branch` instead of `item_id` for `pinboard-branch-owners/v1`, which lists every item and attempt that recorded that branch. Use operation `integration` with `item_id` and an exact `target` (a local branch, remote-tracking ref, tag, or full commit that does not begin with `-`, read as stored locally without fetching) for `pinboard-item-integration/v1`: the target as supplied, its resolved `target_revision`, the compared `source` (`protected-review`, `accepted-checkpoint` with its `checkpoint_id`, or `completion`, each with its attempt, candidate, and compared-from revision), and `presence` (`content-present`, `content-not-present`, or `no-change`). Call only their returned `native_launch.tool` with exactly the strict runtime-specific `native_launch.arguments` from the `pinboard-native-agent-launch/v2` envelope. Do not add, remove, or rewrite an argument, or substitute the separately returned `prompt_reference`, its path, prompt bytes, or a reconstructed launch message. The compact host argument already names the exact accepted prompt identity and immutable file selected by Pinboard. A worker or reviewer launched from different arguments is invalid; stop it and launch a fresh context from the unchanged recipe instead of coaching or resuming it. Follow the recipe's exact `pinboard_artifact_verify` call before reading the named prompt file. Require the accepted identity, verification schema, selector, size, digest and bytes to agree, then read that exact file completely and treat its verified bytes as the direct task from the launching coordinator. Stop if verification or the immediate read fails or differs; never select another artifact or ask the parent to restate the task. Immutable historical CLI-origin envelopes retain their original verifier as evidence, not a supported current invocation. Prompt identity and execution semantics are shared; the envelope owns runtime selection, exact host arguments, verifier and startup presentation without copying an unbounded prompt through the parent agent's launch call.

After prompt verification and the exact prompt read, a worker loads the complete delivery skill through the host-specific route above and uses the complete canonical brief and bootstrap contained in that verified direct task before acquiring its own authority. Obtain the launched worker's own trusted post-launch identity through that runtime and preserve the returned lease and generation together. Continue successful delivery through current result evidence, candidate observation, own-leased submission, protected-review confirmation and lease release. ## Source-worktree setup recovery

Run the repository's exact setup command in the selected checkout through normal runtime execution first. On failure, use its diagnostics or one cheapest additional observation to distinguish a sandbox permission restriction from a missing prerequisite, actual locked-install failure, network failure, or a defect in the tool being changed.

For a diagnosed sandbox permission restriction during already-authorized source setup, request the runtime's permission review for one retry of that exact command in the same checkout. Do not add a separate conversational confirmation. Runtime approval still controls whether the retry executes:

- In Codex, use the execution tool's `sandbox_permissions: "require_escalated"` with a justification naming the observed restriction and the authorized setup command. Request only that invocation; do not add a persistent approval rule.
- In Claude Code, use the current runtime's native permission request for that invocation when available. Do not invent a permission API or treat a dispatch declaration as an execution grant.

If permission is denied or unavailable, the retry fails, the cause is not a sandbox restriction, or recovery would change accepted scope, stop setup and report the exact observation.
