# Antigravity runtime adapter

<!-- roles: all -->

These are the antigravity instructions for the role named at the top of this document. Shared rules are inline above.

<!-- roles: all -->

## Connection and setup

<!-- roles: all -->

Antigravity loads the repository root as a native plugin through `.antigravity-plugin/plugin.json`, the root `mcp_config.json` and the root `hooks.json`; it does not convert the Claude manifest. `mcp_config.json` declares command `sh` with arguments `${PLUGIN_ROOT}/scripts/pinboard --mcp`, because Antigravity expands `${PLUGIN_ROOT}` only in arguments, environment and working directory, not in the command. It starts the shared `pinboard-mcp` entry through the same runtime owner as the other runtimes. Antigravity names the Pinboard server `pinboard_pinboard` and runs every MCP call, for every server, through its own `call_mcp_tool` tool with `ServerName`, `ToolName` and `Arguments`. Three setup facts shape every route below:

<!-- roles: all -->

- Antigravity runs Pinboard tools only after the user adds `mcp(pinboard_pinboard/*)` to `permissions.allow` in `~/.gemini/antigravity-cli/settings.json`, as [INSTALL.md](../../../INSTALL.md#antigravity) describes. Pinboard never writes that file. Without the rule, an interactive session prompts for each call and headless `agy -p` denies it. Report a denial as that missing setup step; do not edit settings, pass `--dangerously-skip-permissions`, or retry through another route.
- In headless `agy -p`, a refused action in an `invoke_subagent` worker or reviewer is never delivered: the child stalls and the parent waits with no message, an accepted limitation recorded in [ARCHITECTURE.md](../../../ARCHITECTURE.md#known-limitations-and-operating-assumptions). Reviewers compute artifact digests through a shell command, so unattended headless review needs the hash-command allow rule, such as `command(shasum)`, that [INSTALL.md](../../../INSTALL.md#unattended-headless-runs) documents. Interactive sessions are expected to ask the user instead, which is unconfirmed.
- Antigravity's system prompt lists each skill's name, absolute `SKILL.md` path and description and tells the model to read `SKILL.md`; the body reaches the model only through that read. Read the complete selected role/runtime startup document, and any conditionally required companion skill from its actual resolved absolute path with native `read_file` first: when a file exceeds `read_file`'s 46,080-byte per-call limit (including the generated startup documents), continue `read_file` at `ByteOffset=46080` and later 46,080-byte offsets until the final section is loaded. Installed and linked plugin skills live outside the workspace, where headless `agy -p` without a `read_file` allow rule refuses a native `read_file`; fall back to `pinboard_startup_text` operation `file-start` with the file's absolute path, exact roots and `max_batch_bytes: "host-profile"`, following each continuation until null, only if native `read_file` is unavailable or refused. Keep `pinboard_startup_text` operation `artifact-start` with `max_batch_bytes: "host-profile"` for SHA-256-verified worker and reviewer launch prompts after `pinboard_artifact_verify`. Never manually edit `max_batch_bytes` inside a returned `pinboard_startup_text` `continuation` object (changing `continuation.max_batch_bytes` causes `STARTUP_TEXT_CONTINUATION_INVALID`). A catalog entry, a mention or a partial read is never a loaded skill.

<!-- roles: all -->

When loading the selected startup document or a conditionally required companion skill together with the lazy MCP tool schemas needed for that turn (such as `pinboard_overview.json`, `pinboard_item_status.json`, and `pinboard_attempt_authority.json` under `/Users/<user>/.gemini/antigravity/mcp/pinboard_pinboard/`), batch those `read_file` calls in parallel in a single turn rather than reading them sequentially. If a lazy MCP tool schema file is missing or unreadable, stop the affected operation and report the exact missing resource rather than guessing schema fields.

<!-- roles: all -->

Antigravity shows the model only an MCP result's text block and saves a text block above about 4 KB to `.system_generated/steps/<N>/output.txt` instead of showing it inline; the result then shows only that file's path. Pinboard's Antigravity page size, seeded with a measured default, therefore lets each `pinboard_startup_text` page spill into one such file of at most 46,080 bytes, which one native `read_file` call reads whole; a page of about 4 KB or less, such as a short final page, stays inline. Read each spilled page file with one `read_file`, continuing at `ByteOffset=46080` when a larger stored page size makes the file exceed that limit, then follow its `continuation` exactly. When Antigravity spills a larger MCP tool result (such as `pinboard_overview` on a large board) to `.system_generated/steps/<N>/output.txt`, read that spilled file directly with `read_file` (using parallel `ByteOffset` reads when the file exceeds 46,080 bytes) instead of treating spilled files as forbidden; it is the exact structured output of the Pinboard MCP tool call already made, not an unverified `.pinboard/views/` file or SQLite database. If a spilled `.system_generated/steps/<N>/output.txt` file is missing or unreadable, stop the affected operation and report the exact missing resource rather than guessing fields or re-running mutating calls.

## Hooks

<!-- roles: all -->

The root `hooks.json` registers two entries. Antigravity runs each hook with the plugin root as working directory:

<!-- roles: all -->

- **SessionStart** runs `./scripts/pinboard --antigravity-session-start`. Antigravity fires it for a parent session and again for every `invoke_subagent` child, each with its own `conversationId`. The entry decodes the Antigravity-owned event, validates its required fields, ignores unrelated additive fields, samples `socket.gethostname()`, and injects one system message: `Pinboard native task_id: "<conversationId>"; host_id: "<machine name>"`, the attribution rule below, the native-`read_file`-first skill-loading instruction (with `ByteOffset=46080` continuation above 46,080 bytes and `pinboard_startup_text` `file-start` fallback when `read_file` is unavailable or refused) and a pointer to the selected role/runtime startup document. It forwards no paths or prompt text and grants no authority. A malformed event injects nothing and leaves only a payload-free diagnostic. On an unprepared plugin version it runs the same `--prepare-runtime` path and reports that result as injected context, recommending a new agy session if the connection stays unavailable.
- **PreToolUse** on `call_mcp_tool` runs `./scripts/pinboard --antigravity-pre-tool-use`. Antigravity offers no narrower matcher, and it blocks a call whose hook fails or answers nothing, so the entry answers every well-formed call. It answers `force_ask` for `pinboard_close` on `pinboard_pinboard`, so the human confirms every close even under the allow rule; `allow` for every other Pinboard tool; and `ask` for every other server, so Antigravity's own approval settings, including that server's own allow rules, decide. A hook `allow` alone does not pass Antigravity's permission check; the user's allow rule does. Headless `agy -p` cannot show the forced prompt and denies it, so `pinboard_close` is unavailable there. When the plugin hook does not run, Antigravity's own approval settings decide for every tool, as Codex's do. On an unprepared plugin version the launcher still answers, with `force_ask` for any call naming `pinboard_close` and `ask` otherwise. A malformed event leaves only a payload-free diagnostic and a failed hook, which Antigravity treats as a block for that call.

## Operations

<!-- roles: all -->

| Operation | Antigravity |
| --- | --- |
| Run Pinboard | Discover the connected `pinboard_pinboard` tools and call each through `call_mcp_tool` with exact roots in its `Arguments`. For CLI-only operations, `<launcher-root>` is the plugin root resolved from this startup document’s actual location; run `PINBOARD_RUNTIME=antigravity "<launcher-root>/scripts/pinboard" ...`. |
| Verified record inputs | For oversized completed briefs or reviews, use only the connected declared file inputs with the exact selected path and raw SHA-256; retain inline controls and all independent checks. Missing capability still stops its operation. |

<!-- roles: coordinator -->

| Operation | Antigravity |
| --- | --- |
| Task and host identity | A parent session uses the injected `Pinboard native task_id` and `host_id`. A worker or reviewer started through `invoke_subagent` receives its own injected `task_id` from its own SessionStart and uses it with the host named in its verified dispatch prompt, never the injected `host_id` or the parent's identity. If the injected context is absent, stop the affected operation; never invent identity, borrow another conversation's, or enumerate environment variables. |
| Checkout isolation | The owning session stays in its workspace, the primary checkout. Before brief construction for an isolated policy, it creates or selects a registered linked worktree on its own branch from the resolved integration baseline through ordinary Git, uses that checkout's absolute path as `project_root` with the unchanged shared `work_root`, and reads the branch and full base revision there. A launched subagent shares the parent's workspace, so its confinement to the assigned checkout is instruction-based: it addresses the checkout by the absolute `project_root` in its launch message and never writes source in the primary checkout. Because each `run_command` call runs in a fresh shell in the session's workspace and Antigravity's "always allow" command rules prefix-match the binary and subcommand only when no `cd <worktree> && ...` chain, wrapper binary (`env`, `timeout`, `xargs`, `eval`), command substitution or shell variable expansion precedes the command, every session (parent, worker or reviewer) addresses its target checkout explicitly with prefix-matchable command shapes: put the target binary first and pass the checkout through the tool's own directory flag or checkout-path argument, or invoke a self-locating repository script directly by its absolute checkout path, rather than chaining `cd <worktree> && ...`. For example: `uv --directory <worktree> run --locked ...`, `git -C <worktree> ...`, `ruff check --no-cache <worktree>`, `ruff format --check --no-cache <worktree>`, `/absolute/path/to/<worktree>/scripts/check-types`, and `/absolute/path/to/<worktree>/scripts/prepare-worktree`. On macOS Seatbelt, when a checkout's `.venv/bin/python` resolves to a uv-managed interpreter under `~/.local/share/uv/python`, a sandboxed `run_command` (`BypassSandbox: false`) fails with `Operation not permitted (os error 1)` (for example `Failed to read Python installation directory ... ~/.local/share/uv/python: Operation not permitted (os error 1)`). Once that failure is observed in a session, run that checkout's `uv` and `scripts/check-types` commands with `run_command` `BypassSandbox: true` for the rest of the session, where each unsandboxed call remains subject to Antigravity's command approval; never bypass `uv` by invoking `.venv/bin/python` or `.venv/bin/pyrefly` directly with hand-crafted flags, injecting `PYTHONPATH`, or editing `~/.gemini` settings. A worker writes attempt evidence at the exact work-root paths. Pinboard validates the declared checkout but creates or switches none. |
| Permission declarations | Map already authorized access into the dispatch record and Antigravity's approval settings. Pinboard tools need the user's allow rule above. File edits and commands follow Antigravity's own permission mode, and headless runs deny anything they cannot prompt for. Pinboard records declarations but neither grants nor enforces them, and never edits `~/.gemini` settings. |
| Workers and reviewers | Check that `invoke_subagent` is available, then call the returned `native_launch.tool` with exactly `native_launch.arguments`: `TypeName: "self"`, a one-line `Role`, and the complete shared launch message as `Prompt`. The `self` type starts a separate conversation with the parent's workspace, model and tools and none of the parent's transcript. The arguments deliberately omit `Model` and `Workspace`; another workspace would be a different source root. The envelope's `background` echoes the dispatch environment, while `invoke_subagent` takes no background flag and always runs the child asynchronously. Apply the same rule to candidate-read-only reviewers. A worker or reviewer subagent must send its final completion or blocker report to the parent conversation with `send_message` before stopping; plain response text is not relayed to the parent. If a launch used different arguments but changed neither source nor lifecycle, stop it and retry once from the unchanged recipe. If `invoke_subagent` is absent, stop native execution. |
| Brief sources | Any agent loading sources through a source plan—whether a coordinator preparing a cross-boundary brief, its brief reviewer, a worker under `pinboard-deliver`, or a coordinator expanding a status layer—still plans through `pinboard_brief_sources` operation `plan`, or `pinboard_brief_source_plan_output` operation `plan-to-file` when the inline plan is too large, so the plan supplies each selected source's `selector`, `start_line`, `end_line` and `selected_sha256`. Read each selected source from that plan, not through `emit` or `emit-file`: call native `read_file` on the selector's file under the selected checkout's absolute path with `StartLine` and `EndLine` set to the plan's span (or no span for a whole file), batching independent reads in one turn, and continue with a later `StartLine` or `ByteOffset` when one call stops at 46,080 bytes. Make no `emit` or `emit-file` call for source content. Keep each selector and `selected_sha256` as the read receipt. This native read does not verify the bytes it shows against the plan digest: for brief preparation, brief review and worker delivery, a source that changes after planning and stays changed is still rejected by `pinboard_dispatch`'s reviewed-authority digest check, whereas status-expansion source plans have neither read-time `emit` verification nor a subsequent `pinboard_dispatch` check, so describe the read as unverified rather than claiming a read-time check. |
| Startup loading | A launched worker or reviewer reads the complete generated role/runtime document named by its verified native envelope. The complete native-read and startup-text fallback procedure is inline here. A mention, catalog entry or verified brief is not complete loading; missing complete content stops startup. |
| Worker continuation | Continue the same child only through the messaging or subagent-management capability Antigravity advertises for that child's returned conversation ID, and only for direction already covered by its accepted brief. A material new requirement follows [definition and brief replacement](review-and-disposition.md#reconcile-late-direction-and-replace-the-definition-and-brief) and the [same-attempt rebind route](preparation-and-dispatch.md#checkout-and-baseline). Confirm through that capability that the child has stopped writing before launching a replacement in the same checkout; if that cannot be confirmed, leave the launch pending. A new `invoke_subagent` call is a different worker. |
| Waiting | After `invoke_subagent`, end the turn without polling or timers. Antigravity wakes the parent with the child's completion message. A prepared dispatch prompt is not a launched worker. Likewise, in any Antigravity session (coordinator, worker or reviewer), when a `run_command` call does not finish within `WaitMsBeforeAsync` and backgrounds as a task (`task-*`), end the turn immediately (call no further tools in that turn) and continue only after the system delivers the task completion notification; do not poll `manage_task` or issue overlapping `read_file` or `run_command` calls while the backgrounded command is running. Before ending its final turn, a worker or reviewer subagent must call `send_message` with the parent's conversation ID as `Recipient`. |
| Optional messaging | Unavailable. Antigravity has no supported Pinboard intake delivery route: keep the saved ledger result, report delivery as unavailable, and do not ask the human to relay it or mimic another client's transport. |

## Close confirmation

<!-- roles: coordinator -->

Antigravity asks the human before `pinboard_close` because Pinboard's PreToolUse hook answers `force_ask` for it, which an allow rule does not skip; headless `agy -p` runs cannot show that prompt and deny the close. When that hook does not run, Antigravity's own approval settings decide, as Codex's do.

## Native human questions

<!-- roles: all -->

Apply the shared [native human questions](runtime-adapters.md#native-human-questions) rule. In Antigravity, ask in ordinary chat whenever the main policy selects it; its `ask_question` tool may carry a short, bounded choice when its current instructions permit. A headless `agy -p` run has no human to answer, so stop and report the question instead.

## Source-worktree setup permission retry

<!-- roles: coordinator worker -->

For the one retry that the shared [source-worktree setup recovery](runtime-adapters.md#source-worktree-setup-recovery) permits, use Antigravity's native command permission prompt for that invocation when available. Do not add a `permissions.allow` rule for it; a headless run that cannot prompt stops setup.
