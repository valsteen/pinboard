# Claude Code runtime adapter

Use this reference when Claude Code is the current runtime. It translates the shared workflow operations into Claude Code's native capabilities; [the shared runtime adapters](runtime-adapters.md) hold every rule that applies to all runtimes, including request shapes, startup paging and cross-runtime handling. The surrounding skill remains the semantic owner.

## Connection

Claude's root `mcp-claude.json` declares `${CLAUDE_PLUGIN_ROOT}/scripts/pinboard --mcp`; the client expands that root in the command. It starts the shared `pinboard-mcp` entry through the same runtime owner as the other runtimes. Claude Code's SessionStart hook can also prepare an unprepared plugin version; the version-local lock serializes it with MCP startup. If the connection remains unavailable after preparation, reconnect it with `/mcp` or restart Claude Code.

## Operations

| Operation | Claude Code |
| --- | --- |
| Run Pinboard | Discover the connected Pinboard MCP tools and pass exact roots. For CLI-only operations, use the substituted absolute `${CLAUDE_PLUGIN_ROOT}` as `<launcher-root>` and run `PINBOARD_RUNTIME=claude "${CLAUDE_PLUGIN_ROOT}/scripts/pinboard" ...`. |
| Task and host identity | For parent operations, use the current `Pinboard native parent task_id` and `host_id` supplied by the installed SessionStart hook. They are the actual native event's local `session_id` and the executing machine's `socket.gethostname()`, refreshed when the host delivers SessionStart. If that context is absent, use trusted current local session context exposed directly by the invoking runtime, or read only `CLAUDE_CODE_SESSION_ID` through that parent's own Bash tool, together with trusted runtime host values. A connection-dependent Remote Control link is not this local source; an MCP server's startup environment may be stale after implicit resume. A launched worker instead uses the actual `agent_id` supplied by its own installed SubagentStart hook and the verified dispatch host, never the parent session or machine attribution. If required trusted context is unavailable, stop the affected operation; never invent identity or enumerate environment variables. |
| Checkout isolation | The owning session stays in its launch directory, the primary checkout. Before brief construction for an isolated policy, it creates or selects a registered linked worktree inside that directory at `.claude/worktrees/<bounded-name>`, on its own branch from the resolved integration baseline, using the runtime's ordinary Git execution such as `git worktree add -b <branch> .claude/worktrees/<bounded-name> <baseline>`. It uses that checkout's absolute path as `project_root` with the unchanged shared `work_root`, and reads the branch and full base revision there. Do not enter the checkout with `EnterWorktree` for a Pinboard attempt: an entered session is confined to that worktree and cannot write the shared work root, so it could not record `review.md` and its workers could not record `result.md` or `blocker.md`. Staying in the launch directory keeps every owning-session work-root write, including `review.md`, available to ordinary file tools. A later worker uses that assigned checkout; creating the worker does not replace the owning session's pre-brief checkout selection. A session already confined to an entered worktree follows the [confined evidence-write recovery](#claude-confined-evidence-write-recovery). Pinboard validates the declared checkout but creates or switches none. |
| Workers and reviewers | Check the advertised native subagent surface, then call the returned `native_launch.tool` with exactly `native_launch.arguments`. The recipe selects `Agent`, supplies the complete `prompt`, and deliberately omits `isolation`, because a second worktree is a different source root. The worker or reviewer therefore starts in the owning session's launch directory, not in its assigned checkout. It addresses that checkout by the absolute `project_root` in its launch message, runs repository commands with that checkout as working directory, never calls `EnterWorktree`, and never writes source in the primary checkout. It writes attempt evidence at the exact work-root paths with ordinary file tools. Freshness means a new agent context, not another checkout. Apply the same rule to workers and candidate-read-only reviewers. If a launch used different arguments but changed neither source nor lifecycle, stop it and retry once from the unchanged returned recipe; never add repair guidance or rebind Pinboard to an accidental checkout. Results return to the owning context. If the required callable is absent, stop native execution. |
| Skill loading | Invoke the native `Skill` tool for the advertised `pinboard:pinboard-deliver`. If that loader is unavailable, read the actual resolved `pinboard-deliver/SKILL.md` file, not its directory. A mention or verified brief is not a loaded skill; unavailable complete content stops startup. |
| Worker continuation | Follow the actual native Agent result's continuation operation and exact worker handle, including `SendMessage` when that return advertises it and the callable capability is available, only for direction already covered by that worker's accepted brief. A material new requirement follows [definition and brief replacement](review-and-disposition.md#reconcile-late-direction-and-replace-the-definition-and-brief) and the [same-attempt rebind route](preparation-and-dispatch.md#checkout-and-baseline) before implementation continues; a direct message cannot authorize it. Rebind fences Pinboard authority, not the Claude process: use that worker's actual native handle to stop it or await its completion, and confirm it has stopped writing before launching a replacement in the same checkout. If the native stop or wait cannot be confirmed, leave that launch pending. A new Agent launch is a different worker even when its prompt claims the old identity. Missing same-worker continuation stops that route; do not invent identity or substitute another launch. |
| Permission declarations | Map already authorized access into the dispatch record and Claude permission controls. For an autonomous repository-writing worker, use Claude's normal edit-accepting mode; `dontAsk` can deny file writes instead of prompting. In an observed worker run in the Pinboard source repository, in auto permission mode, source edits in a linked checkout under `.claude/worktrees/` inside the owning session's launch directory needed no additional directory grant and caused no permission prompt or refusal; that is an observed result, not a runtime guarantee. A selected linked checkout or a shared work root outside the launch directory must be in Claude's allowed directories before dispatch; otherwise the owning task stops before dispatch and names that exact directory instead of launching a worker that cannot write it. Pinboard records declarations but neither grants nor enforces them. |
| Waiting | Wait on the launched subagent or background task until it completes or needs attention. A prepared dispatch prompt is not a launched worker. |
| Optional messaging | Only when delivery was explicitly requested and an agent team is already active, resolve the exact named teammate and use `SendMessage` with the proposal ID, source identity, shared work root, and confirmed item-view link when available. Apply the main Pinboard skill's readable-artifact rule to every item or evidence reference in that message. If that teammate changes or the send fails, re-resolve the same target once; never redirect. If the exact target or capability remains unavailable, keep the saved ledger result, report delivery as unavailable, and do not ask the human to relay it. |

Do not enable Claude agent teams, open another session, create another worktree, or widen permissions merely to mimic a Codex transport. Messaging reduces latency; it never gates persistence, ownership, review, or completion.

## Close confirmation

The `pinboard_close` registration carries `_meta` `anthropic/requiresUserInteraction: true`, for which Claude Code v2.1.199 or later documents a per-call confirmation prompt that neither an allow rule nor the Pinboard PreToolUse allow skips, and a denial in `dontAsk` mode and non-interactive runs. Report a denied close to the human and seek no other route. Older Claude Code versions do not prompt.

## Hooks

The Claude manifest explicitly registers `./hooks/claude-hooks.json`. Native SessionStart events select `"${CLAUDE_PLUGIN_ROOT}/scripts/pinboard" --claude-session-start`; native SubagentStart events independently select `"${CLAUDE_PLUGIN_ROOT}/scripts/pinboard" --claude-subagent-start`. Native PreToolUse events matching `mcp__plugin_pinboard_pinboard__.*` select `"${CLAUDE_PLUGIN_ROOT}/scripts/pinboard" --claude-pre-tool-use`. SessionStart matches all native initiation sources; SubagentStart matches all agent types. All three accept no additional arguments and share the prepared launcher-root runtime. The PreToolUse entry emits exactly one allow decision for a well-formed Pinboard tool event and nothing otherwise; it reads no project state or settings, and Claude Code still evaluates deny and ask rules regardless of the hook. In Claude Code v2.1.199 or later, `pinboard_close` still asks the human, because that confirmation comes from Claude Code honoring the tool's `anthropic/requiresUserInteraction` metadata, which a hook allow does not skip. Registration grants no client trust.

The parent entry validates the current SessionStart record and samples the machine name with `socket.gethostname()`. It adds only `Pinboard native parent task_id: "<actual session_id>"; host_id: "<actual machine name>"`, a concise attribution instruction and a pointer to this reference through native additional context. The host's SessionStart delivery refreshes those values on startup, resume and other native session refreshes; an emitted hook result alone does not prove native ingestion or agent adherence. The worker entry independently adds only `Pinboard native worker task_id: "<actual agent_id>"` to that worker's startup context and supplies no host value; its verified dispatch host remains separate.

Each entry decodes its exact Claude-owned event, validates required fields and ignores unrelated additive host fields. Ignored extensions, cwd and transcript paths are never forwarded. Pinboard-owned outputs, requests and artifacts remain strict regardless of sender. Missing or malformed required fields, a wrong event kind or invalid identity emit no attribution and only a payload-free diagnostic; machine-source failure cannot supply a guessed host. None of the three entries reads project state, creates a task, acquires a lease, authenticates credentials or changes saved permission policy; only the PreToolUse entry emits an approval decision. Prepare that plugin version before native launch; attribution does not replace prompt verification, canonical brief reading, own leased acquisition or actual runtime approvals.

## Claude confined evidence-write recovery

A `PreToolUse:Write` refusal that names the isolated worktree and says the attempt path is in the base repo checkout comes from Claude Code's built-in worktree guard. [Claude's isolation documentation](https://code.claude.com/docs/en/worktrees#how-claude-code-enforces-isolation) describes location-based checks that block `Edit`, `Write`, and `NotebookEdit` in the main checkout, including for subagents of an isolated session. Pinboard's separate PreToolUse hook matches only `mcp__plugin_pinboard_pinboard__.*` and emits `allow`; it does not govern `Write`.

Ignored `.pinboard` files under the main checkout are still in that checkout, so the guard can refuse the exact shared-work-root `result.md`, `blocker.md`, or `review.md` destination. Keep that destination: the refusal's suggested worktree-local `.pinboard` path is not the shared board and would not record its evidence. Human authorization for the evidence write does not disable the guard; Claude documents that it cannot be turned off.

Use the existing recovery below for this refusal; do not relocate attempt evidence, edit saved permission policy, remove the checkout, or retry through another path.

- **Confined worker.** Write the complete intended file to your own session scratchpad. Return to the owning task naming the refused exact attempt path and the scratch path, and state that the evidence is not yet recorded.
- **Owning session in its launch directory.** Copy those exact bytes to the named attempt path with one approved command, such as `cp <scratch-path> <attempt-path>`, and verify that both files have the same SHA-256. Then continue the same worker through its native handle so it can finish from the recorded evidence.
- **Confined owning session.** Ask the human whether to leave the worktree with `ExitWorktree` action `keep`. Its tool description states that `keep` leaves the worktree directory and branch on disk and restores the session to the directory it had before `EnterWorktree`. After that exit, write or copy the evidence from the launch directory as above.
- **No active worktree session.** `ExitWorktree` acts only on a worktree entered with `EnterWorktree` in the current session; otherwise it reports that no worktree session is active and changes nothing, and `keep` does not restore the launch directory. In that case stop, keep the scratch copy, and give the human the refused exact attempt path, the scratch path, and the scratch file's SHA-256 so they can copy it from a session in the launch directory and verify the digest.

## Native human questions

Apply the shared [native human questions](runtime-adapters.md#native-human-questions) rule through the question capability Claude Code actually exposes, only as that tool's current instructions permit; otherwise use the main skill's ordinary-text fallback.

## Source-worktree setup permission retry

For the one retry that the shared [source-worktree setup recovery](runtime-adapters.md#source-worktree-setup-recovery) permits, use the current runtime's native permission request for that invocation when available. Do not invent a permission API or treat a dispatch declaration as an execution grant.
