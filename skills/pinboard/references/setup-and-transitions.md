# Setup and transitions

Load this phase for setup, state contracts, mutations or nested intake. The [main conversation core](../SKILL.md) owns human decisions and replies. Use [runtime adapters](runtime-adapters.md) for identity, exact request shapes and host permissions.

## Start from executable state

Before selecting a deferred Pinboard tool schema, follow the discovery instructions supplied by the initialized connection. If those instructions are absent, read and follow the [native discovery procedure](runtime-adapters.md#packaged-connection-and-first-setup). Load that shared runtime reference when an operation needs its detailed request, startup or recovery contract, including the [current MCP request contract](runtime-adapters.md#current-mcp-request-shapes). It owns exact request-envelope placement; workflow authority and lifecycle decisions remain here.

Use the connected Pinboard MCP surface for item status, item definition and history, brief construction and source preparation, proposal creation, brief publication, overview, saved priority, structural parallel preview, action discovery, attempt inspection, correction context, artifact verification, candidate observation and restoration, preparation and attempt authority, lifecycle transition, human-confirmed close through `pinboard_close`, dispatch, review-job, and human-owned PR review, with exact project and work roots on every call. Transitions carry a fresh exact receipt and structured leaf payload; dispatch carries its project receipt and structured environment; review-job carries its exact candidate and caller-selected history identities. Follow the runtime adapter's native callable restoration instructions. Restoration requires the current accepted snapshot context and exact inspected candidate; it neither selects archived history nor creates or launches a checkout. Follow returned effect, retry, and changed-surface accounting.

For requested Pinboard setup, follow the main skill's [private adoption rule](../SKILL.md#route-common-requests) through loaded skills and the existing private initialization below. `pinboard init` initializes the selected work root; default initialization adds its exact local Git exclusion. It does not install project guidance. Keep project-specific guidance edits and explicit contributor-documentation requests within their separately authorized purpose.

1. For CLI-only operations, invoke `<launcher-root>/scripts/pinboard`, where `<launcher-root>` is the directory two levels above this skill (`../../scripts/pinboard` relative to it); integration-specific discovery belongs in the runtime adapters, while the launcher-relative executable and CLI contract are common. A prepared Pinboard source checkout uses `<pinboard-source>/.venv`; an installed plugin uses only its marker-backed `<launcher-root>/.pinboard-runtime/environment`. Ordinary launch never invokes uv or consults the managed project's `.venv`, Python dependencies, or uv project. When the launcher returns `pinboard-launcher-result/v1` with `runtime-preparation-required`, run its exact same-launcher `--prepare-runtime` action once with uv available and only the narrow launcher-root write access it names, then retry the original command. That result always reports `pinboard_started: false`, says whether `.pinboard-runtime` changed, and preserves upstream diagnostics; it never proves the requested command ran. Follow its retry requirement for a preparation failure and never construct an ad hoc uv command, cache override, installed-cache locator, or managed-project environment workaround. When the user selected an explicit project root, place `--project-root <root>` before the subcommand on every invocation. Add `--work-root <path>` only when the user separately selected a non-default Pinboard directory; never reuse the project root as the work root or silently fall back to the current directory's default board. For a linked worktree, preserve the shared default ledger and use only its exact resolved absolute `.pinboard` directory in Codex permission recovery; never substitute the checkout-relative path or the whole shared repository.
2. For ordinary project-status orientation, call `pinboard_overview` with the exact roots. Treat its revision-stamped result as the complete default input. A request to read explicitly named context and wait is narrower than project-status orientation and uses only those named reads. When the user has already supplied an exact mutation and its semantic inputs, do not add an overview preflight merely because this skill triggered; use the narrow action query directly.
3. If the exact selected root is unavailable, report `WORKFLOW_UNAVAILABLE`. Initialize `.pinboard` with `<launcher-root>/scripts/pinboard init --json` only when the user explicitly requests coordinated-work setup. Read only that selected root; do not scan another location or choose a replacement board. An explicit `--work-root` remains at its user-selected location under ordinary root rules. A released v6 ledger uses `migrate-schema` preview and apply at the selected real root while quiescent. When a successful fresh initialization reports optional repository-care skills, relay them once in the user-facing result by presenting `$repository-readiness`, `$slop-cleanup`, and `$maintaining-agent-guidance` as optional next steps. The pointer and Codex setting recommendation are advice only: do not invoke a skill, create work, edit configuration, infer that a repository-care recommendation applies, or infer the effective project setting from them.

4. Require the returned authority to be exactly `sqlite-v7`. If validation fails or another authority is reported, stop state-consuming work and use the recovery procedure in `references/state-and-recovery.md`; never infer a fallback from generated views or archived files.
5. Inspecting SQLite state needs no lease. Prepare one exact leaf payload from the advertised `pinboard_transition` schema. Query the exact action through `pinboard_actions` as project, then call `pinboard_transition` with its complete returned receipt, structured payload, and invoking task and host identity. SQLite checks and commits the complete transition atomically. The negotiated transition leaf schema and action's inline input contract own exact contract diagnosis. Close is not a `pinboard_transition` leaf; apply a discovered close action only through `pinboard_close` as described under [Apply a transition](#apply-a-transition). The retained `close` CLI command is the human's own terminal route, not an agent fallback.
6. Preparation and attempt work use their own renewable leases. For a ready item only, call `pinboard_preparation_authority` with operation `start`, item, task, host, TTL, and exact roots. It selects the current definition and either creates the first claim or transfers an inactive retained claim in one transaction. Renew, release, or revoke preparation authority through that tool. For ready-item recovery and contract diagnosis, use preparation `status` and `start`; for an existing attempt, use attempt `status` and `acquire` when its continuation calls for worker authority. Neither tool exposes a `transfer` leaf. Inspect the named attempt through `pinboard_attempt_inspect` and follow its derived continuation rather than reconstructing ownership from conversation. Acquire worker authority through `pinboard_attempt_authority` with the launched worker's own task and host. A live conflicting holder rejects unchanged; forced revocation requires explicit user authority. Lifecycle state alone does not prove that user input is required; ask only when the recorded condition exposes a product choice the human has not made. If a required precondition is unavailable through a supported read, preserve that missing path as a product defect instead of inventing a value or reading raw SQLite state.

A paused item already has an attempt. Inspect that attempt first, use its current condition and legal actions to explain any human choice, and continue the same attempt. If its accepted scope or Git lineage is stale, publish the matching replacement brief and rebind before selecting its legal resume action. Do not start new preparation for it or diagnose a missing `transfer` operation. At a material choice, say where the work stands, why the person is needed, the practical supported options, what the agent will do after the choice, and what will count as complete; otherwise continue quietly.

When a native invocation, role, authority requirement, artifact shape or retry rule is unclear, use that connected tool's negotiated input and output schema and the exact action's inline input contract. An action's kind, `semantics.effect` and `input_contract.payload_schema` tell its route: a `mutating` action with a payload schema is applied through `pinboard_transition`, except `close`, which is applied only through `pinboard_close`; `dispatch` goes to `pinboard_dispatch`; `inspect` and `continue` are reads or runtime continuation; and `report-blocker` is advisory blocker evidence. Never pass an advisory action with a null payload schema to `pinboard_transition`. Treat each selected leaf's authority and postcondition independently: acquisition consumes direct identity facts and returns the lease it creates. Do not inspect implementation source or guess fields from neighboring tools. For retained CLI operations only, use `<launcher-root>/scripts/pinboard tool-contract --json` and one operation selector returned by that static index; follow its exact `cli_usage`, including global roots before the subcommand. CLI discovery includes root resolution, setup, status, validation, view repair, project export, human closure and static code lookup. For an unfamiliar stable code, use `<launcher-root>/scripts/pinboard code-catalog --json --code CODE`; follow the returned result's exact effect, retry, resource and next step over generic catalog recovery.

For retained CLI commands that support `--json`, treat `pinboard-rejected-operation/v1` as the recovery boundary. `status: rejected` and `state_changed: false` mean this invocation committed no Pinboard effect; correct the input, reacquire authority, or use one returned fresh action exactly as classified. `status: committed-effect` names durable surfaces already changed before the operation stopped; inspect current state and do not replay the mutation. A recovery action with `generation: null` uses direct project authority, while a non-null generation and lease must be copied together. Do not infer success or safety from the prose message when these fields are present.

For native calls, follow the selected tool's strict result schema, effect, retry and changed-surface facts. A `failed-after-publication` or `committed-effect` result names already published surfaces; preserve its exact selectors and inspect current state instead of replaying the call. A committed warning does not undo its receipt. An unchanged rejection may be corrected or refreshed only as its contract permits.

## Ownership

- Let `state.sqlite3` own lifecycle, dependencies, attempts, preparation and attempt leases, proposals, history, and accepted artifact references.
- Let `views/` remain generated human-readable output. Never edit it as authority.
- Let accepted brief and evidence artifacts own execution semantics and review receipts; resolve them through their SQLite artifact references.
- Let proposal fact columns preserve the original intake evidence while disposition columns record the later decision and same-identity items own queue state and position.
- Let public project documentation own stable architecture and domain truth.

Project transitions are direct atomic SQLite changes with task and host audit attribution supplied by the invoking trusted local task. Those strings are not authenticated credentials. Disjoint preparation leases reserve exact ready-item definitions before activation, and disjoint attempt leases authorize active item-local work concurrently. Expiry, release, revocation, and higher fencing generations invalidate retained leased actions.

## Apply a transition

Before the first default initialization or when a routine mutation reports `SQLITE_READONLY`, follow the shared runtime adapter's [Codex protected project writes](runtime-adapters.md#codex-protected-project-writes) rule. Keep one-time Git exclusion authority separate from routine project-data access.

1. Identify one action as `<kind>:<subject>`. Read its returned `use_case`, `effect`, `permitted_roles`, `subject_kind`, `lifecycle_precondition`, and `practical_result` instead of inferring from the verb. The stable `effect` field says whether the action accepts a lifecycle transition payload; it does not summarize every outer command effect, and dispatch may publish or reuse review evidence while leaving lifecycle unchanged. Treat the exact action record's `authorization` as the runtime authority to forward; the kind-level permitted roles do not replace it. When semantic input is not already settled, use the advertised exact transition leaf schema and prepare its structured payload before selecting the action. `revise-item:<item>` replaces one complete definition after exact revision-and-digest matching; never synthesize a partial patch. `report-blocker:<attempt>` is a worker advisory with no mutation payload; `block:<attempt>` is the project transition for an active attempt; `block-item:<item>` is the project transition for a ready item without an attempt. Blocking may name only dependencies already accepted in the current definition and never changes dependencies itself.
2. For one project change, call `pinboard_actions` with exact roots, role `project`, and structured `action_id` containing the exact kind and subject. Copy its returned action identity and `subject_revision` together as the transition receipt; supply the invoking task and host identity.
3. For an attempt- or preparation-local change, call `pinboard_actions` with exact roots, role `worker` or `preparer`, exact lease and generation, and structured action identity. Copy the returned identity and revision together. Forward the lease and generation unchanged; do not infer authorization from a neighboring role or reconstruct a partial receipt from prose.
4. Call `pinboard_transition` with those exact roots, role, receipt, authority fields, and structured leaf payload. A committed result returns the exact action identity, committed revision, history receipt, effect, changed surfaces, retry disposition, and any generated-view warning. A warning does not undo the authoritative transition. Preserve that receipt and call `pinboard_attempt_inspect` for the derived continuation; never replay a committed transition to obtain it.
5. On `STALE_ACTION`, discard the receipt, reselect only the same exact action, and retry silently while its semantics and payload are unchanged, retained state is safe, and existing authorization can refresh or reacquire the capability. Stop when the action disappears, its semantics, role, or payload changes, authority cannot be refreshed, state is invalid, or the lease or turn deadline cannot fit another attempt, and report only the resulting blocker, changed outcome, unsafe state, or required decision. A freshly selected receipt rejected without an intervening ledger revision is an executable contradiction: preserve the evidence and report it.
6. On `ACTION_NOT_AVAILABLE`, do not replay the same command, switch roles, or skip to another lifecycle state. Validate once and refresh only the same exact action under fresh authority. If it disappeared, follow the resulting state and report it only when the user's outcome or next action changed. If it is now available, apply its fresh receipt once under the `STALE_ACTION` rule; treat only an unexplained rejection without an intervening ledger revision as an executable contradiction.
7. If a task is interrupted before a receipt is visible, never replay its retained action. Follow the interrupted-transition recovery in `references/state-and-recovery.md`; authoritative state distinguishes no change from one complete committed transition, and a fresh lease generation fences the abandoned action.
8. Report the practical effect of the returned transition in terms of the human's picture. Run `<launcher-root>/scripts/pinboard validate` immediately after any non-tool edit to supporting attempt artifacts.

The executable rejects stale definition identities, expired or replaced lease holders, illegal states, invalid dependencies, and inconsistent references. Actions that require current accepted scope remain unavailable to attempts pinned to an older definition; rebind is the explicit active-or-paused recovery that accepts a matching current-definition brief and corrected Git lineage together. It does not decide whether evidence is true, whether work is valuable, or what product behavior should mean.

For an explicit terminal human decision about live work without an accepted attempt, discover the exact project `close` action through `pinboard_actions`, then call `pinboard_close` with ordinary top-level arguments—`project_root`, `work_root`, `receipt` holding only that action's `action_id` and `subject_revision`, `payload` with `outcome`, `reason` and `human_decision`, `actor_task_id` and `actor_host_id`—instead of manufacturing lifecycle states. `human_decision` is the human's explicit close decision in their own words on one line, such as their reply "yes, drop it, the parser rewrite covers it"; never write it yourself, and when you do not have it, ask the human and stop. Claude Code v2.1.199 or later asks the human to confirm every `pinboard_close` call, and Codex and earlier Claude Code versions may not ask; a denied call, including in a non-interactive run, means the human has not confirmed, so report that and seek no other route. `pinboard_transition` refuses a close receipt unchanged. The tool applies one direct atomic project transition and records the decision with the close. Do not add an overview preflight. Use `done` when the recorded decision or outcome is complete and may satisfy dependents. Use `dropped` only when the work is intentionally abandoned and has no live dependents. Never use `close` to bypass review for an accepted attempt, including after pause or block. Resume or rebind the same attempt and keep its normal evidence-backed review path; a genuine change to accepted semantics requires deliberate item revision, matching brief review, and rebind. The returned revision is the durable mutation receipt, so do not create a temporary payload file or replay the transition to prove that it committed. Still perform the fresh exact `pinboard_item_status` operation `item` read required by [workflow-ending replies](../SKILL.md#wrap-up-with-facts).

## Nested intake and concern revision

Proposal creation persists immutable facts and a same-identity ready item. It appends at the back by default or uses an explicitly requested one-based position, and relation semantics may add a dependency or proposal origin. It creates no attempt, pauses no current work, and completes nothing. When intake is embedded in ongoing work, keep a compact continuation anchor in the current task context before invoking it:

- the pre-intake objective;
- the next action already promised;
- the exact active or paused item, attempt, proposal, or durable selector that owns the facts after context compaction.

After persistence and optional notification handling, return to that anchor in the same turn. Re-read the durable selector when compaction made conversational memory uncertain; do not create a scheduler or recovery record. Before the final response, reconcile every announced pending action as completed, durably deferred at an exact owner, or blocked by one exact decision. The anchor is the agent's own state; what the human sees is the [concern receipt](../SKILL.md#reconcile-material-concerns-before-reporting-them) and, when something remains open for them, the `Still open:` line.

Conditional follow-up language such as “if this is a production defect, follow it up” authorizes one bounded disposition only after current evidence proves the named condition. If it is false or unproved, make no ledger write; if the exact observation and consequence are already recorded in a live linked owner, reuse that owner. If the condition is proved and the exact concern is new, create at most one `follow-up` or `independent` intake proposal through `$pinboard-intake`, choosing the relation from the evidence, and never turn this authority into a prerequisite, preparation, activation, implementation, notification, or unrelated intake. Record the evidence, relation to current work, and smallest useful next decision, then return to the continuation anchor.

Deliberate steering is distinct from intake. Insert a genuine prerequisite only at a safe boundary, pause or block the displaced objective through its legal transition, and name the ordinary `resume:<item>` action that restores it. Recovery is for interrupted or inconsistent state, not the normal route back to preserved work.

When the concern belongs to an existing admitted item but its accepted semantics are incomplete, read the current definition and discover the project `revise-item` action and call `pinboard_transition` with one complete replacement, exact expected identity, source task, reason, receipt, and roots. A retained attempt then remains pinned and stale; use its legal review-correction path when a candidate is protected, publish a matching revised canonical brief, and rebind the active or paused attempt before continuation. When no admitted item owns the concern, use `$pinboard-intake` if the user has explicitly authorized preservation.

When an active attempt discovers a prerequisite:

1. preserve its current result and verification;
2. use `$pinboard-intake` to propose the prerequisite;
3. report the advisory `report-blocker:<attempt>` from the worker context, then have the owning task select the exact project transition: use `block:<attempt>` only when its named dependencies already exist in the current definition, or `pause:<attempt>` when preserving work without such a condition; revise the complete definition first when a newly accepted dependency is required, and never use the intake-only `block-item:<item>` action for active work;
4. implement the accepted prerequisite independently from the current integration base;
5. resume the preserved attempt only after its freshness check passes.
