# Status and selection

Load this phase before answering status, saved-work selection, planning context or requested detail. The [main conversation core](../SKILL.md) owns the human picture and questions. Inspection alone grants no implementation or lifecycle authority.

For a current-attempt review claim, read `pinboard_item_status` operation `item` with the exact roots and item, and use its current `review_verdict`. It selects the nonterminal attempt; a terminal item has no current attempt and may return `none` despite favorable historical review. Overview omission and current `none` never prove a historical review gap. When the claim concerns an earlier candidate or merged commits, verify the selected available historical evidence for that exact subject and time. Preserve verified coverage; qualify unavailable or conflicting coverage instead of asserting no review or inventing a new gate. An informal outcome note can point to evidence to inspect, but cannot authorize commissioned ready recording or completion. For every worker claim, read `pinboard_attempt_authority` operation `status` for the exact attempt; overview's `preparation` concerns preparation only, and its release or revocation says nothing about that worker. Use successful returned observations, never a malformed request, error, title or state label, to make these claims. If an exact read is unavailable, leave that fact unknown and report only what was observed.

- **Where do we stand, what next, what can run together:** read `pinboard_overview`, and `pinboard_parallel_preview` only when the user asks what can run together or in parallel. Report items in saved order with their dependency reasons, keeping default status and orientation replies (`$pinboard`, `/pinboard`, “where do we stand?”, “quick status”) within the main skill's ~150-word budget: on a large board, always list every item waiting on the human, every active, in-review, or paused item, and the immediate next ready items in saved order, then summarize the remaining ready, blocked, and deferred items with a count rather than listing every item on the board. Do not call `pinboard_initiative` (`roadmap`) for a default status or orientation reply unless the user asks about initiatives or the roadmap. An active attempt means work was started; say whether anyone is working on it only after reading its attempt authority status. Keep leases, preparation claims, revisions, and attempt IDs out of the reply unless the human asks to inspect or troubleshoot Pinboard.
- **Save for later:** use `$pinboard-intake`. Without a board nothing can be saved: say so and offer Pinboard setup; never create board files by hand.
- **Pick up paused work:** read `pinboard_item_status` operation `item`. Keep its current `pause_reason` separate from the attempt's latest `decision_batch`. When that batch is pending, present every decision with its options, recommendation, what it unblocks and deferral cost; record exact human answers or explicit deferrals with reopening conditions against their IDs. Resume only after every pending ID is resolved. A resolved latest batch remains recorded context through later transitions and plain pauses; do not ask those questions again. Scope-changing answers follow the [replacement and rebind route](../SKILL.md#record-and-resolve-decision-batches). When a plain pause names a human decision, ask it with your recommended default and wait for that answer before dependent work or resume.
- **Merge a named change:** handle a plain merge request as a repository action on the existing change, preserving its current review and authority requirements; do not create new intake merely to perform the merge.
- **Was it merged, is anything left:** read the exact item status and inspect a current attempt when present before naming remaining review. A `ready` verdict is a verified commissioned review of its named candidate; `reconcile-repository` means that review is recorded and repository disposition remains. When the human reports a rebase, squash merge or merge, resolve the intended target and run item-status operation `integration` before calling the earlier review insufficient because commit identities changed. `content-present` verifies that candidate's accepted diff at the returned local `target_revision`: say the review covered the original candidate and its reviewed content reached the target. It does not establish review of every surrounding commit. `content-not-present` and `no-change` are inconclusive; inspect changed content or selected historical evidence before naming a gap. A verified gap is in `main` but unreviewed, and you recommend review of that landed change. Unknown or conflicting coverage stays qualified, and remote identity stays observed or unverified. Merged work owing review is review work, not implementation in flight. Keep required current-subject commissioning and ready recording separate from historical narration.
- **Close, complete, or mark done:** first check that the human explicitly asked to close this item. If you fixed or implemented it yourself and they did not ask, report the change and where it landed, ask whether to close it, and stop. `close` applies only to live work without an attempt and runs only through `pinboard_close`, whose `human_decision` carries the human's explicit close decision in their own words; if you do not have those words, ask and stop. Claude Code v2.1.199 or later asks the human to confirm every `pinboard_close` call; Codex and earlier Claude Code versions may not ask. Antigravity asks through Pinboard's PreToolUse `force_ask` decision, so the close is unavailable in headless `agy -p` runs; when that hook does not run, Antigravity's own approval settings decide. If the call is denied, report that the human must confirm the close and seek no other route. When the item has an attempt, read its current verdict and inspect that attempt. When the human reports integration, check the named target through the route above before describing any review still owed. If commissioned ready review is already recorded, say what it covered and reuse that valid review through the fresh completion contract when the agreed outcome and authorized disposition are satisfied. Changed commit identities alone do not require another review or another close confirmation. If completion refuses because work or evidence remains, report its actual accepted remaining work or missing current candidate, review, or evidence and follow the focused inspection. Preserve an eligible current review when read-only investigation or explicit retention settles existing scope, recording that decision separately from the bound brief, result and review. Closure authorizes no automatic candidate reconstruction or implementation launch. If the required record is missing, explain the review still owed and offer that route: completion requires a reviewer commissioned through `pinboard_review_job`, its ready verdict recorded with `record-ready`, and that reviewer's identity. Content presence alone cannot replace that record. Status-only requests authorize these reads and a reply, never completion or review commissioning. Never pause, block, defer, or resume work, or run the CLI `close`, to approximate a close or completion.
- **Fix, start, or implement a saved item now:** say in one sentence what will be produced and where it will land, ask only a question whose answer would change the result, with your recommendation, then follow [Prepare delegated attempts](preparation-and-dispatch.md#prepare-delegated-attempts). Do not edit or commit source for the item directly unless the human chooses to work outside Pinboard.

- for each attempt in review, its item-status `review_verdict` and `pinboard_attempt_inspect` with `reconciliation: null`: a valid `ready` verdict and `reconcile-repository` mean review is recorded, so gather the named repository observations and check reported integration before presenting any unresolved disposition. `review-subagent` means it waits for a reviewer;
- for each active attempt, `pinboard_attempt_authority` operation `status`—an active holder is a running worker, none means nobody is working on it; a preparation record cannot replace this read—and its item status `review_verdict`, where `returned-for-correction` means a correction is owed; when its `rebound_since_return` is true the return is history, and [replacement-brief recovery](review-and-disposition.md#recover-after-a-brief-replacement) records a new return before correction;
- for each paused item, its `pinboard_item_status` operation `item` result, whose current `pause_reason` and any pending `decision_batch` say what it waits on;
- in Git, `git branch --no-merged <target>`. For an unmerged branch with no live item, find the items and attempts that own it with `pinboard_item_status` operation `branch`, then read the owning item's status; a terminal item's `closure` says when and by which action it closed, its recorded `outcome_evidence` says whether the human deliberately retained or deferred the unmerged change and where a kept experiment's scratch board is. Preserve that settled decision; product absence alone creates no new adoption choice. Present a landing choice only when it remains unresolved, and assess exact review coverage separately. For a live item whose branch is already merged, check whether a review covered it and whether `origin/<target>` contains the merge. `pinboard_item_status` operation `integration` with that `target` reports whether the item's reviewed candidate diff is `content-present` there, including after a rebase or squash merge; `content-not-present` does not prove the change is absent.

Default `$pinboard`, `/pinboard`, “where do we stand?”, “quick status”, and equivalent orientation questions to the single `overview` result plus the reads that [the human's picture](../SKILL.md#keep-the-humans-picture-current) requires; never call `pinboard_initiative` (`roadmap`) unless the user asks about initiatives or the roadmap. Keep the reply within [the main skill's ~150-word budget](../SKILL.md#keep-the-humans-picture-current). Lead with what waits on the human, then work in progress (active, in-review, and paused items) with who acts next, then the immediate next ready items in saved order with dependency reasons. On a large board, list every item waiting on the human, every active/in-review/paused item, and the immediate next ready items, then give a count of the remaining ready, blocked, and deferred items rather than listing every item on the board; link the generated board page on the closing line for the full queue. Give each listed item one line of at most twelve words—the item, where it stands in the human's terms, and your default when it waits on them—and leave out facts you did not read. Those lines are the answer's open items, so a status answer has no `Still open:` line and asks at most one question. Link every mentioned item under the [readable-artifact rule](../SKILL.md#match-detail-to-the-question). Intake candidates already appear in that order. The revision stamp is freshness evidence, not reply content. Read selected historical evidence or an earlier decision only when needed to substantiate a review claim or distinguish a settled choice from an open one; do not preload full history, project notes, GitHub, CI or delivery state for this default answer. Acquire no lease merely to explain the live picture.

Keep inspection, validation, repair, and project-export claims distinct. `pinboard_item_status` operation `item` and both `pinboard_item_definition` leaves read only the named item facts; the item leaf also carries the current attempt's `branch`, a paused attempt's `pause_reason`, each current attempt's latest `decision_batch` with any recorded resolution, the current attempt's `review_verdict`, a terminal item's `closure`, and intake-time next action and notes only as labeled original context in `intake_context`. Item-status operation `branch` scans retained attempts for every item and attempt that recorded that exact branch; a branch recorded before a rebind is not found. Item-status operation `integration` with `item_id` and `target` reads only that item's reviewed candidate evidence and runs one read-only Git content check against the named local target without fetching. Use definition operation `current` for complete accepted fields and revision/digest identity, never a title or status substitute. Use operation `history` only when history is requested, with an explicit 1–100 limit and `before_revision: null` initially, continuing with the returned exclusive `next_before_revision` while it is non-null. These reads, like direct attempt- and preparation-authority status, need no lease.

`pinboard_attempt_inspect` reads one named attempt context and verifies its accepted brief. Its required nullable `reconciliation` is `null` for ordinary inspection, or the outer coordinator's target revision, exact integration relation, legal repository phase, and ordered source-checkout, shared-work-root, and git-metadata effect observations. For a favorably reviewed candidate, `null` returns the ordinary `reconcile-repository` continuation naming the observations needed next, and those observations then select one repository continuation; Pinboard never performs the repository or permission effect. Every nonterminal continuation carries the latest `decision_batch` and its recorded resolution when present; a paused continuation separately carries the current pause's recorded `pause_reason`. `pinboard_review_job` reads that attempt context, accepted brief, and current `result.md`; an optional caller-selected package adds the exact checkpoint history receipt and package artifact, and optional correction context adds the exact return receipt and current `review.md`, all in one focused read transaction. Review launch leaves may publish an immutable reviewer prompt, accept its artifact reference, and advance the ledger; the non-launching `record-ready` leaf verifies the exact attempt, candidate snapshot, accepted brief, result and review digests, independent reviewer, and favorable verdict, then publishes or reuses the canonical candidate review. Neither path mutates lifecycle, candidate state, attempt authority, repository files, or Git. `pinboard_parallel_preview` with explicit selected `item_ids` reads only those items, their direct launch constraints, and applicable authority; its explicit all-safe leaf is project-wide. Retained CLI `status`, `pinboard_overview`, `pinboard_actions`, and that all-safe preview each project one current SQLite snapshot without validating accepted artifacts or generated views. Use `<launcher-root>/scripts/pinboard validate` when integrity matters: it verifies the snapshot and accepted artifact bytes, validates each v2-linked checkpoint or reviewed-completion package against its historical receipt and immutable evidence, and reports generated-view drift as repairable warnings without repairing; `<launcher-root>/scripts/pinboard views rebuild` is that separate write. Use `<launcher-root>/scripts/pinboard export --json` only to materialize one strict `pinboard-project-export/v3` package of the supported project-facts subset from one snapshot and verified artifacts; it applies the same package validation, exposes valid checkpoint and completion packages as typed portable evidence beside their generic artifact entries, keeps authority local, and contacts no receiving tool.

End every compact overview with one short offer to expand the useful layers: recommendation and item context; completed decisions; delivery and CI; or full history. Make it a single line, either a natural sentence or, as the text fallback of the [question presentation](../SKILL.md#match-detail-to-the-question), `Quick reply: 1 why next · 2 decisions · 3 delivery/CI · 4 full history`, never both. The same closing line of a status or task-list answer carries one link to the board page, using the `html` path from the overview's `board` object under the [readable-artifact rule](../SKILL.md#match-detail-to-the-question); add no separate board section.

Do not invent slash commands for these follow-ups. `$pinboard` is an explicit entry point for invoking the skill in a new or unrelated context, where terse prompts such as `$pinboard quick status` or `$pinboard full history` are valid. It is not a required subcommand inside an ongoing pinboard conversation.

Fetch only the selected expansion:

- For a recommendation or deeper rationale, use the overview itself when it contains enough evidence. Otherwise read only the exact live item records that are plausible choices. Apply the ordering below only then.
- For completed decisions, read terminal item history only. Do not add GitHub or delivery checks.
- For delivery or CI, inspect Git and GitHub only. Do not reconstruct ledger history.
- For full history, say that the answer will be slower, then read the complete relevant ledger and accepted artifact context. Add delivery state only if the user includes it.

When an expansion needs several known project files or headings, plan their selected sizes with `pinboard_brief_sources` before loading their bodies, then read each non-overlapping emitted batch once. For other known facts, use a bounded batch when the available tool supports it. If output truncates, continue at the first unread boundary without replaying returned content. Do not turn one requested layer into an exploratory command-per-item walk. If the user explicitly asks for a zero-tool or last-known answer, reuse the most recent overview from the current conversation and label it as not refreshed. Never present it as current. A requested expansion is not permission to preload the other layers.

This proportional behavior applies to mutation as well as status. After a successful command returns a revision-stamped receipt, do not run a redundant overview merely to confirm what the command already proved. Run broader verification only when the operation lacks a sufficient postcondition or the user asks for it.

## Interpret the available actions

Translate executable actions into ordinary repository and product language; the exact action record serves execution only. Whenever the explanation names an item, decision, or evidence artifact with confirmed readable Markdown, apply the shared readable-artifact link rule.

When selecting work, explain:

1. the current product or repository trajectory;
2. what changed after the last accepted item;
3. which items are ready and why;
4. which items are blocked and the exact unresolved condition;
5. which ordering is mechanically determined by dependencies;
6. which choice genuinely requires human priority;
7. the recommended next item and why now.

Respect the saved live priority order from `overview` before making a heuristic recommendation. Its `next_unstarted` context names the first unstarted item and unsatisfied dependency targets; read the matching item row for lifecycle, replacement and preparation facts, and report an existing blocker rather than silently recommending a lower item. Active, review and previously started attempts remain current work, not new starts. Priority does not change dependencies, preparation authority, available actions or independent parallel eligibility.

Read each returned dependency condition as its exact target. A string identity requires the whole prerequisite to be `done` or `superseded`; `{"item":"producer","checkpoint":"usable-api"}` can also be satisfied by a matching committed checkpoint acceptance. Status, overview, preview, and generated item, board, and roadmap output retain that distinction and its acceptance status. An active producer can therefore have satisfied a consumer's checkpoint dependency while still owing its own remaining work. Acceptance recorded on any retained producer attempt survives later brief changes, rebind, or cancellation; do not infer a blocker merely from the producer's current state. Whole-item dependencies continue to wait for whole-item completion or supersession.

Save only an explicit human priority decision through `pinboard_order`: put the complete current live sequence from `pinboard_overview` in `order.expected_order` and the complete authorized permutation in `order.requested_order`, with `order.schema: pinboard-live-order/v1`, exact roots, and trusted `actor_task_id`/`actor_host_id` inside `request`, preserving unmentioned relative order unless the human decided otherwise. A stale rejection needs a fresh overview and reconciliation with the same decision; a committed warning keeps the receipt and names exact CLI view-repair recovery, never order replay. A fresh overview verifies saved order, but after a lost reply it cannot prove this caller committed, because a valid no-op leaves the same order; never blindly replay the mutation.

When the human asks for a new priority recommendation, prefer, in order:

1. evidence preservation or avoidance of an irreversible transition;
2. prerequisites required by the current product objective;
3. runtime, consumer, or user-visible product evidence;
4. foundation work that is concretely cheaper now;
5. optional hardening only after its recorded reopen condition occurs.

Do not turn that ordering into a score. A recommendation remains an explanation, not an automatic product decision.


A dropped item is cancelled work, not successful completion. It is absent from the live queue but retains its definition, attempt and evidence. Exact item status names its `cancel` closure; exact retained-attempt inspection presents `dropped` with no executable continuation, and branch-owner output says `cancelled`. A dropped prerequisite keeps whole-item and unaccepted checkpoint targets unsatisfied; an already recorded matching checkpoint acceptance still satisfies that target. Report the retained repository disposition separately; cancellation proves neither absorption nor integration.

## Initiatives and the roadmap

For an initiative question, use `pinboard_initiative` operation `read` with exact roots and `initiative_id`. For the complete project roadmap, use operation `roadmap` with roots only. This deliberate aggregate read includes complete initiative history, current and terminal members, unassigned live work and relevant external prerequisite context; ordinary quick status and bare `$pinboard` / `/pinboard` orientation use the focused routes above and never call `pinboard_initiative` unless the user asks about initiatives or the roadmap.

The same tool exposes strict `create`, `revise`, `member-add`, `member-remove`, `decision` and `assess` leaves. Discover their exact schema before constructing a change. Writes retain `human`, supplied `date`, `reason`, and actor task/host attribution. Existing-initiative writes compare `expected_revision`; assessments also name the current `evaluation_context`. A goal or success-signal edit creates a fresh unassessed context, while unrelated metadata preserves it. General decisions are separate from goal assessments.

Membership and wave placement grant no lifecycle or execution authority. Delivered means successful item completion; cancelled, superseded and removed memberships earn no delivery credit. Read the page's explicit totals selection and snapshot revision. Every ledger commit regenerates the roadmap, including artifact-only and unrelated changes; complete selected history grows the offline page and per-commit work. Reload the file after regeneration. A committed view warning requires the supported `pinboard views rebuild` repair, never replay of the mutation. Revisit the history/refresh policy only for measured material delays.
