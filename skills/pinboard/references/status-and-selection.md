# Status and selection

Load this phase before answering status, saved-work selection, planning context or requested detail. The [main conversation core](../SKILL.md) owns the human picture and questions. Inspection alone grants no implementation or lifecycle authority.

- **Where do we stand, what next, what can run together:** read `pinboard_overview`, and `pinboard_parallel_preview` for work at the same time. Report items in saved order with their dependency reasons. An active attempt means work was started; say whether anyone is working on it only after reading its attempt authority status. Keep leases, preparation claims, revisions, and attempt IDs out of the reply unless the human asks to inspect or troubleshoot Pinboard.
- **Save for later:** use `$pinboard-intake`. Without a board nothing can be saved: say so and offer Pinboard setup; never create board files by hand.
- **Pick up paused work:** read `pinboard_item_status` operation `item`; its `pause_reason` names what the work waits on. When that is a human decision, ask it with your recommended default, and change no source or lifecycle state until the human answers.
- **Merge a named change:** handle a plain merge request as a repository action on the existing change, preserving its current review and authority requirements; do not create new intake merely to perform the merge.
- **Was it merged, is anything left:** check Git for the change, then `pinboard_item_status` operation `item`, whose `review_verdict` says whether a review is recorded for the current attempt. A merged change without a covering review is in `main` but unreviewed: recommend that a separate reviewer check the commit as it landed before the work is closed.
- **Close, complete, or mark done:** first check that the human explicitly asked to close this item. If you fixed or implemented it yourself and they did not ask, report the change and where it landed, ask whether to close it, and stop. `close` applies only to live work without an attempt and runs only through `pinboard_close`, whose `human_decision` carries the human's explicit close decision in their own words; if you do not have those words, ask and stop. Claude Code v2.1.199 or later asks the human to confirm every `pinboard_close` call; Codex and earlier Claude Code versions may not ask. If the call is denied, report that the human must confirm the close and seek no other route. When the item has an attempt, explain that its change needs review before completion and offer that route: completion requires a reviewer commissioned through `pinboard_review_job`, its ready verdict recorded with `record-ready`, and that reviewer's identity. Never pause, block, defer, or resume work, or run the CLI `close`, to approximate a close or completion.
- **Fix, start, or implement a saved item now:** say in one sentence what will be produced and where it will land, ask only a question whose answer would change the result, with your recommendation, then follow [Prepare delegated attempts](preparation-and-dispatch.md#prepare-delegated-attempts). Do not edit or commit source for the item directly unless the human chooses to work outside Pinboard.

- for each attempt in review, `pinboard_attempt_inspect` with `reconciliation: null`: `reconcile-repository` means it was reviewed favorably and the agent must first gather the named repository observations; only then present an unresolved landing choice to the human, and `review-subagent` means it waits for a reviewer;
- for each active attempt, `pinboard_attempt_authority` operation `status`—an active holder is a running worker, none means nobody is working on it—and its item status `review_verdict`, where `returned-for-correction` means a correction is owed; when its `rebound_since_return` is true the return is history, and [replacement-brief recovery](review-and-disposition.md#recover-after-a-brief-replacement) records a new return before correction;
- for each paused item, its `pinboard_item_status` operation `item` result, whose `pause_reason` says what it waits on;
- in Git, `git branch --no-merged <target>`. For an unmerged branch with no live item, find the items and attempts that own it with `pinboard_item_status` operation `branch`, then read the owning item's status; a terminal item's `closure` says when and by which action it closed, its recorded `outcome_evidence` says whether the human kept the change unmerged and where a kept experiment's scratch board is, and that useful change stays open. For a live item whose branch is already merged, check whether a review covered it and whether `origin/<target>` contains the merge. `pinboard_item_status` operation `integration` with that `target` reports whether the item's reviewed candidate diff is `content-present` there, including after a rebase or squash merge; `content-not-present` does not prove the change is absent.

Default “where do we stand?”, “quick status”, and equivalent orientation questions to the single `overview` result plus the reads that [the human's picture](../SKILL.md#keep-the-humans-picture-current) requires. Lead with what waits on the human, then work in progress with who acts next, then ready items in saved order with dependency reasons. Give each item one line of at most twelve words—the item, where it stands in the human's terms, and your default when it waits on them—and leave out facts you did not read. Those lines are the answer's open items, so a status answer has no `Still open:` line and asks at most one question. Link every mentioned item under the [readable-artifact rule](../SKILL.md#match-detail-to-the-question). Intake candidates already appear in that order. The revision stamp is freshness evidence, not reply content. Do not read history, project notes, GitHub, CI, delivery state, or old decisions for this default answer, or acquire a lease merely to explain the live picture.

Keep inspection, validation, repair, and project-export claims distinct. `pinboard_item_status` operation `item` and both `pinboard_item_definition` leaves read only the named item facts; the item leaf also carries the current attempt's `branch`, a paused attempt's `pause_reason`, the current attempt's `review_verdict`, a terminal item's `closure`, and intake-time next action and notes only as labeled original context in `intake_context`. Item-status operation `branch` scans retained attempts for every item and attempt that recorded that exact branch; a branch recorded before a rebind is not found. Item-status operation `integration` with `item_id` and `target` reads only that item's reviewed candidate evidence and runs one read-only Git content check against the named local target without fetching. Use definition operation `current` for complete accepted fields and revision/digest identity, never a title or status substitute. Use operation `history` only when history is requested, with an explicit 1–100 limit and `before_revision: null` initially, continuing with the returned exclusive `next_before_revision` while it is non-null. These reads, like direct attempt- and preparation-authority status, need no lease.

`pinboard_attempt_inspect` reads one named attempt context and verifies its accepted brief. Its required nullable `reconciliation` is `null` for ordinary inspection, or the outer coordinator's target revision, exact integration relation, legal repository phase, and ordered source-checkout, shared-work-root, and git-metadata effect observations. For a favorably reviewed candidate, `null` returns the ordinary `reconcile-repository` continuation naming the observations needed next, and those observations then select one repository continuation; Pinboard never performs the repository or permission effect. A paused continuation carries the current pause's recorded `pause_reason`. `pinboard_review_job` reads that attempt context, accepted brief, and current `result.md`; an optional caller-selected package adds the exact checkpoint history receipt and package artifact, and optional correction context adds the exact return receipt and current `review.md`, all in one focused read transaction. Review launch leaves may publish an immutable reviewer prompt, accept its artifact reference, and advance the ledger; the non-launching `record-ready` leaf verifies the exact attempt, candidate snapshot, accepted brief, result and review digests, independent reviewer, and favorable verdict, then publishes or reuses the canonical candidate review. Neither path mutates lifecycle, candidate state, attempt authority, repository files, or Git. `pinboard_parallel_preview` with explicit selected `item_ids` reads only those items, their direct launch constraints, and applicable authority; its explicit all-safe leaf is project-wide. Retained CLI `status`, `pinboard_overview`, `pinboard_actions`, and that all-safe preview each project one current SQLite snapshot without validating accepted artifacts or generated views. Use `<launcher-root>/scripts/pinboard validate` when integrity matters: it verifies the snapshot and accepted artifact bytes, validates each v2-linked checkpoint or reviewed-completion package against its historical receipt and immutable evidence, and reports generated-view drift as repairable warnings without repairing; `<launcher-root>/scripts/pinboard views rebuild` is that separate write. Use `<launcher-root>/scripts/pinboard export --json` only to materialize one strict `pinboard-project-export/v1` package of the supported project-facts subset from one snapshot and verified artifacts; it applies the same package validation, exposes valid checkpoint and completion packages as typed portable evidence beside their generic artifact entries, keeps authority local, and contacts no receiving tool.

End every compact overview with one short offer to expand the useful layers: recommendation and item context; completed decisions; delivery and CI; or full history. Make it a single line, either a natural sentence or, as the text fallback of the [question presentation](../SKILL.md#match-detail-to-the-question), `Quick reply: 1 why next · 2 decisions · 3 delivery/CI · 4 full history`, never both.

Do not invent slash commands for these follow-ups. `$pinboard` is an explicit entry point for invoking the skill in a new or unrelated context, where terse prompts such as `$pinboard quick status` or `$pinboard full history` are valid. It is not a required subcommand inside an ongoing pinboard conversation.

Fetch only the selected expansion:

- For a recommendation or deeper rationale, use the overview itself when it contains enough evidence. Otherwise read only the exact live item records that are plausible choices. Apply the ordering below only then.
- For completed decisions, read terminal item history only. Do not add GitHub or delivery checks.
- For delivery or CI, inspect Git and GitHub only. Do not reconstruct ledger history.
- For full history, say that the answer will be slower, then read the complete relevant ledger and accepted artifact context. Add delivery state only if the user includes it.

When an expansion needs several known project files or headings, plan their selected sizes with `pinboard_brief_sources` before loading their bodies, then read each non-overlapping emitted batch once. For other known facts, use a bounded batch when the available tool supports it. If output truncates, continue at the first unread boundary without replaying returned content. Do not turn one requested layer into an exploratory command-per-item walk. If the user explicitly asks for a zero-tool or last-known answer, reuse the most recent overview from the current conversation and label it as not refreshed. Never present it as current. A requested expansion is not permission to preload the other layers.

This proportional behavior applies to mutation as well as status. After a successful command returns a revision-stamped receipt, do not run a redundant overview merely to confirm what the command already proved. Run broader verification only when the operation lacks a sufficient postcondition or the user asks for it.

## Interpret the available actions

Translate executable actions into ordinary repository and product language; the exact action record serves execution only. Whenever the explanation names an item, decision, or evidence artifact with confirmed readable Markdown, apply the shared readable-artifact link rule.

When selecting work, explain:

1. the current product or repository trajectory;
2. what changed after the last accepted item;
3. which items are ready and why;
4. which items are blocked and the exact unresolved condition;
5. which ordering is mechanically determined by dependencies;
6. which choice genuinely requires human priority;
7. the recommended next item and why now.

Respect the saved live priority order from `overview` before making a heuristic recommendation. Its `next_unstarted` context names the first unstarted item and live dependencies; read the matching item row for lifecycle, replacement and preparation facts, and report an existing blocker rather than silently recommending a lower item. Active, review and previously started attempts remain current work, not new starts. Priority does not change dependencies, preparation authority, available actions or independent parallel eligibility.

Save only an explicit human priority decision through `pinboard_order`: put the complete current live sequence from `pinboard_overview` in `order.expected_order` and the complete authorized permutation in `order.requested_order`, with `order.schema: pinboard-live-order/v1`, exact roots, and trusted `actor_task_id`/`actor_host_id` inside `request`, preserving unmentioned relative order unless the human decided otherwise. A stale rejection needs a fresh overview and reconciliation with the same decision; a committed warning keeps the receipt and names exact CLI view-repair recovery, never order replay. A fresh overview verifies saved order, but after a lost reply it cannot prove this caller committed, because a valid no-op leaves the same order; never blindly replay the mutation.

When the human asks for a new priority recommendation, prefer, in order:

1. evidence preservation or avoidance of an irreversible transition;
2. prerequisites required by the current product objective;
3. runtime, consumer, or user-visible product evidence;
4. foundation work that is concretely cheaper now;
5. optional hardening only after its recorded reopen condition occurs.

Do not turn that ordering into a score. A recommendation remains an explanation, not an automatic product decision.
