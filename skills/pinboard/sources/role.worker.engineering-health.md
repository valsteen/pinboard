# Optional engineering-health baseline

Use this baseline only when the accepted item or canonical work brief explicitly selects it. A task looking complex, crossing several modules, or benefiting from more assurance is not enough. The accepted brief still owns the exact contract and mandatory verification; this reference does not create either.

## Close one representative contract

Before expanding a cross-boundary behavior across sibling variants, choose the cheapest supported value that can disprove agreement between the production owners and its real consumer.

1. Name the representative value, the observable consumer effect, and the production path between them.
2. Exercise that path through the application-owned boundary instead of proving each layer from separately constructed fixtures. When the path persists state, write it through the production operation and reload it from a fresh store before observing the consumer.
3. Put runtime evidence at the first real boundary capable of exposing disagreement: deserialization, persistence, an external system, an untyped value, relational state, or concurrency.
4. Expand sibling variants only after the representative path succeeds. Re-run the proof when a changed owner or representation can invalidate it.

The proof should be the smallest integration evidence that can falsify the contract. It is not a request for an exhaustive end-to-end suite.

## Count static guarantees fairly

Use concrete types, nominal identifiers, closed unions, exhaustive matching, and strict type-checker results as evidence for states supported code cannot construct. Do not add malformed domain objects, duplicate runtime guards, or tests solely to execute a statically unreachable branch.

Static evidence does not replace runtime evidence where values enter from deserialization, storage, external systems, untyped or cast boundaries, relational state, or concurrency.

## Treat repeated contradictions as architecture evidence

Correct a first representation mismatch at the owner that violated the contract, then rerun the representative proof. If the same boundary repeatedly produces incompatible representations after focused corrections, stop sibling expansion and return the contradiction to the accepted architecture or product owner. Do not normalize away facts in an adapter, multiply defensive review cases, or add downstream guards merely to keep the current path green.

Record the representative value, production path, static guarantees used, runtime boundary evidence, and outcome in the existing result and review evidence. Do not create a parallel artifact or schema.

## Stop at the baseline

The baseline is satisfied when the representative path succeeds, its owners agree on one supported representation, and no repeated contradiction remains unresolved. It does not add:

- complexity metrics, thresholds, or recovery automation;
- a cumulative architecture-fitness checkpoint;
- pre-execution architecture-decision compression;
- a generic architecture checklist;
- new ownership for architecture-impact declarations or closed-union recovery.

Those concerns require their own accepted scope and reopen evidence.
