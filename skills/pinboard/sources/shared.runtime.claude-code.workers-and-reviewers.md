Check the advertised native subagent surface, then call the returned `native_launch.tool` with exactly `native_launch.arguments`: `description` and the complete shared launch message as `prompt`. The recipe selects `Agent` and deliberately omits `isolation` (because a second worktree is a different source root) and `run_in_background` (because the advertised `Agent` tool schema declares neither argument); the outer envelope's `background` field echoes the requested dispatch or review-job background boolean. Whether `Agent` runs in the foreground or asynchronously in the background is observed from the `Agent` tool result: a foreground run returns the subagent's completed output directly in that tool result, whereas an asynchronous background launch returns an immediate `async_launched` result (`Async agent launched successfully...` with `agentId` and `output_file`) and delivers a later task-completion notification when the subagent finishes. The worker or reviewer therefore starts in the owning session's launch directory, not in its assigned checkout. It addresses that checkout by the absolute `project_root` in its launch message, runs repository commands with that checkout as working directory, never calls `EnterWorktree`, and never writes source in the primary checkout. It writes attempt evidence at the exact work-root paths with ordinary file tools. Freshness means a new agent context, not another checkout. Apply the same rule to workers and candidate-read-only reviewers. If a launch used different arguments but changed neither source nor lifecycle, stop it and retry once from the unchanged returned recipe; never add repair guidance or rebind Pinboard to an accidental checkout. Results return to the owning context. If the required callable is absent, stop native execution.
