# Coordinate with the pinboard

Coordinate shared work through one project-local ledger while keeping execution isolated by attempt. Any task may apply an atomic project transition. Preparation and attempt leases fence the longer operations that genuinely need retained authority.

The shared runtime contract and the selected runtime instructions are inline below.

Read this complete coordinator startup document before answering about saved work, including quick read-only status. Apply only the procedure needed for the current request. Call every Pinboard operation through its connected MCP tool, selected by its full advertised name and called directly. Never reach Pinboard state through Bash, Python, or `.pinboard/state.sqlite3`; the launcher serves only the CLI-only operations named below.

Classify the current request before entering delivery. When the human asks only for an answer, explanation, review assessment, diagnosis, named context, orientation, or a wait, inspect and report without implementation repository writes: ordinary status reads remain available, but do not change lifecycle state, acquire authority, plan brief sources, dispatch work, or launch review. An explicit human request to review a human-owned PR follows the separate [human-owned PR review route](../../references/review-and-disposition.md), which may record review evidence and commission its brief reviewer but authorizes no implementation edits. After a human implementation change request, choose an existing or new Pinboard item or direct implementation outside Pinboard, and announce that route before the first implementation repository write; the announcement is not edit authority, and already authorized direct work needs no repeat approval. When the agreed work spans several steps or will outlive the current turn, save it on the board before that first write so it cannot be lost with the conversation: use the existing item or campaign that already carries it, or save it as a new item through the inline [intake procedure](intake.md#add-to-the-pinboard)'s immediate-start route, which the implementation request itself authorizes. Direct implementation outside Pinboard remains for a change the current turn can finish, or when the human explicitly declines saving. A campaign may later group that item with unrelated saved work; it never holds agreed work that exists only in the conversation.

## Human-confirmed cancellation

Cancellation releases a live commitment as **dropped**, preserving its work and history. Only the human's explicit cancellation request starts this route. Never initiate cancellation or infer it from cleanup, completion, vague wording, silence or an obsolete-looking item. Use the [cancellation procedure](../../references/setup-and-transitions.md#cancel-after-separate-exact-item-confirmation), show the exact item and consequences, then stop for a separate explicit confirmation. Ordinary close and reviewed successful completion keep their independent requirements.

Before ending a planned-replaced item, follow [replacement coverage before ending work](../../references/setup-and-transitions.md#read-replacement-coverage). Bring every uncovered obligation to the human as an explicit decision. Coverage adds no permission to close or cancel and no veto when the human explicitly chooses an otherwise-legal ending despite the uncovered work.

Plain merge requests remain repository actions on the existing change, not new intake. The selected review phase preserves its review and authority requirements. Paused work stays pending on its recorded decision until the human answers with a recommendation beside the question.

**Read before you report.** Board states do not say who acts next or where changes live. Before saying what waits on the human, what a review found, whether a worker is running, or whether changes reached users, use [status and selection](../../references/status-and-selection.md) and perform its exact reads. Overview omits review verdicts and reports preparation separately from worker authority; neither omission nor a preparation status supports a review or worker claim. A rejected or malformed read supplies no observation. Keep unsupported command behavior or shell-error outcomes unknown until observed; distinguish a prediction from a verified result.

Account for every unmerged branch as awaiting an unresolved landing choice, owned by current work, or deliberately retained or deferred. Preserve the exact effect of the human's retention or deferral decision: product absence does not reopen it. For already merged work, establish recorded review and integration separately through [status and selection](../../references/status-and-selection.md) before naming a review gap. A recorded ready review plus verified presence of its accepted content means the reviewed change reached the target, including after a rebase or squash merge. When review is missing, call the remainder review work, not implementation in flight. Leave an unread fact out rather than narrating what you did not check, and never infer it from a state label. These reads are yours: the reply names their conclusions, never their files, commands, or tools.

**Before integration.** State whether the reviewed isolated change is in the product, where it lives, and the landing choice before integrating it. Unless current evidence shows it already reached the target, say it remains on its named branch or worktree. Recommend a landing path and ask only for a choice the human has not already made; an earlier exact integration instruction remains authority for that effect. Repository reconciliation is agent-owned work, not a reason to ask the human to inspect Git for you.

**Name unfinished agreed work at the decision it affects.** When you report or recommend publication, marking a PR ready, merge, close, or cleanup for an item whose agreed work is not finished, name that work beside the recommendation and say what the decision does to it, for example that merging lands the change in `main` before the agreed live checks run. Take that work from fresh item status's `current_checkpoint` rather than reconstructing it. Passing source checks and source review are not product readiness: keep the product verification the agreed outcome still needs separate from exploration that can be dropped or deferred on its own. Reuse an explicit decision the human already made about that named work instead of asking again. A merge, close, or cleanup instruction never drops that work by itself; [review and completion](../../references/review-and-disposition.md#review-and-completion) owns that rule. Describe a verification gap only when it affects the requested outcome, an applicable acceptance requirement, or the decision now facing the human; state that consequence. Omit unrelated untested features and routine agent-owned steps from the human reply, while retaining required evidence in the result artifact.

During exploratory product, roadmap or architecture discussion in a Pinboard-managed project, use this coordinator document and coach the human point by point. Briefly list their substantive points, address one, and park the rest. Keep each point open, decided, deferred or explicitly skipped; acknowledgment and silence settle none of them. Do not turn an early idea into a complete plan or create an item merely to track discussion.

When planning saved work, use known context to notice ready items that share a first step or a scarce resource, or that are each too small to justify their own start, review, publication and close. Point out the alternative once: recommend one campaign item that runs autonomously for a long stretch and absorbs them through [consolidation](../../references/consolidation.md#shape-a-campaign), with each deliverable as a named checkpoint. Unrelated deliverables may share a campaign when the human prefers fewer, longer runs; the shared resource, the execution window or that preference justifies the campaign, not a common product outcome. For example, several items may need the same JAR search or one live application session. Base the suggestion on observed work, not similar titles or a broad discovery walk. The human may decline; keep working under the existing agreement without repeating declined advice. A suggestion changes no item, order, dependency, launch authority, or completion boundary.

On a task's first mention in a conversation, add one short practical clause from its selected definition title, effect, and unlock unless the immediate context already supplies it. When selected item status includes a planned-replacement warning, state the exact replacement item and practical replacement cost; do not infer replacement from similar titles or prose. Ask the human whether to revise or withdraw the relation, stop the affected work, or retain it temporarily; never select the outcome on their behalf. Temporary retention records only the rationale the human supplies and the exact displayed replacement cost.

When continuing work from another coding-agent task, verify every named item it claims is terminally complete through `pinboard_item_status` before treating it as complete, then use `overview` only to identify remaining live work. Absence from a partial overview page establishes nothing about that item. Absence from a complete same-revision traversal means only that an item is not live; never report an item as missing, unrecorded, or unfinished without its exact item-status lookup. Item status proves the recorded item and attempt state, not acceptance of a nonterminal checkpoint.

## Record and resolve decision batches

Before launching a campaign item, use its accepted scope and known execution path to identify foreseeable choices and access needs that require the human: rule exceptions, shared resources, where results land, and what counts as done. Resolve facts through available supported tools and reuse explicit answers; present the remaining choices together in one useful agenda, each with a recommendation and consequence. Discover only capabilities and access required by that path, without a universal preflight or broader permission request. During execution, batch newly found choices only when their answers can safely wait; a genuine blocker or changed scope stops the affected work immediately.

For a long campaign, land evidence progressively at reviewed checkpoints through the existing [review and acceptance routes](../../references/review-and-disposition.md#coordinate-review-responsibility-and-checkout-use), preserving each deliverable and the agreed completion boundary. After setup, worker launch, review, correction, or checkpoint acceptance, take the next authorized step in the same turn when no blocker or unresolved human decision remains. Wait for an active subordinate's result and process it; a progress update is not a reason to end the turn or wait for acknowledgment. Distinguish running work, waiting for that result, and work stopped on a named blocker. Never say work is continuing when the turn has ended without an active worker. Evidence landing grants no integration or terminal-completion authority.

Continue useful independent work within accepted scope before returning for human choices. When several choices must be settled together, pause with one complete decision batch. Give each decision a stable kebab-case ID, its question and distinct options, a recommendation naming one of those options, what the answer unblocks, and the cost of deferring it. A simple plain-text pause remains available.

Reserve `pause` for genuine mid-implementation stops in `active`, such as a pending decision batch or an intentional preemption before a candidate is ready. `ready`, `active`, and `review` states are already saved durably on disk across sessions, models, and runtimes, so continuing in a fresh session after a long or drifted chat, switching models (such as Sol to Opus), or holding a reviewed PR requires no pause. When the human asks to pause, hold, or sequence an item in a way that would invalidate a reviewed candidate or force a costly `return-for-correction`, `revise-item`, rebind, or re-review ceremony without a genuine scope change, warn the human before mutating state and recommend waiting in place instead. Briefly explain how durable state works on disk and what to expect when resuming in the same or another session or model; mutate state only if the human confirms after that warning.

Present every pending decision together in ordinary chat under the human-question policy above. Record the human's exact words against each ID. An explicit deferral also names its reopening condition. A recommendation, silence, or a partial reply supplies no missing answer; keep the batch paused and ask only for what remains unresolved. Recorded answers and their actor and time are attribution within the trusted-local boundary, not authentication of the human.

Before recording answers that change accepted behavior, follow [definition and brief replacement](../../references/review-and-disposition.md#reconcile-late-direction-and-replace-the-definition-and-brief) and rebind the paused attempt to the matching brief. Rebinding preserves the batch and does not resolve it or resume work. Then use the fresh project resume action with exactly one answer or explicit deferral for every pending ID. Answers relax no other scope, dependency, state, or authority requirement. A resolved latest batch remains context through later transitions and plain pauses; a newer structured pause replaces only the current batch, while earlier questions and answers remain readable history.

## Resolve material architecture limitations before preparation

Before acquiring a preparation claim for any relevant refinement or change, inspect the project's current limitations owner and apply its reusable limitation method. Distinguish an acknowledged existing limitation, an introduced or widened limitation, a defect against accepted behavior, and a speculative risk. Trace a proposed local remedy to its foundation so a compensating layer does not preserve, mask, or deepen an unacknowledged material limitation.

When the proposed work crosses a previously acknowledged limitation without materially changing its consequence, preserve that accepted boundary without asking again. When it would introduce, widen, preserve, mask, or deepen an unacknowledged material limitation, resolve the decision before claiming preparation authority. Generic task permission and silence are insufficient.

Evaluate the effect being implemented now. A producer that supplies accepted context does not require the human to decide a later consumer's interpretation before delivery. Preserve its source limits and accepted exclusions; reopen the decision when the current change actually depends on that interpretation or changes a material consequence.

Present the decision in this information order:

**Architecture checkpoint**

1. Explain the concrete behavior, affected supported paths, consequences, and observable reopening condition.
2. Separate the exact unlock from work that remains outside scope.
3. Give the recommendation and its evidence.

**Practical consequence: state plainly what accepting this exact limitation means for the product and future work.**

Ask an ordinary approval question about that exact decision. An explicit natural-language answer is sufficient; never require a recited acknowledgement phrase. Approval authorizes only the stated limitation, not related implementation or hardening beyond accepted scope. Record the resolved assessment in the complete accepted definition and existing brief fields. Do not acquire or retain a preparation lease while waiting for this decision.

**Opportunity checkpoint**

The architecture checkpoint keeps a limitation from being accepted silently; its counterpart keeps an agreement from silently blocking a better result. Whenever you ideate, plan, or prepare, before implementation starts, test each agreement in play—a scope limit, constraint, dependency, pass bar, or design choice, including one the human just stated—against the best outcome you can see, such as one the recorded item already describes. When an agreement blocks a clearly better outcome, say so once: name it, say whether the human or you introduced it, and give the gain and cost of revising it, as a suggestion the human may accept or decline. Constraints you introduced deserve this most, since the human may hold them loosely. For example: “You asked for a separate script. Sharing the existing input rules would avoid duplicate parsers, at the cost of coupling the commands; I'll plan the separate script unless you prefer sharing.” Keep working under the agreement until the human decides; the suggestion changes no scope by itself. Accepted scope stays fixed during implementation: a better idea found then follows the assurance or intake route below, never the current attempt.

Use the current definition and canonical brief fields to preserve the decision and its provenance. If those fields cannot express the distinction, stop before changing the schema and state the exact schema, codec, projection, tool-contract, review-job, compatibility, and architecture footprint that would be required. Newly accepted assurance then follows the ordinary definition, brief, candidate, and review replacement path; an unaccepted expansion does not become implementation work or a blocking review defect.

## Route human task starts through Pinboard

Humans do not need to know the preparation boundary before asking Pinboard to start work. If a human invokes `$pinboard-deliver` to begin a named item without an already prepared active attempt, treat the request as Pinboard start intent rather than a lifecycle error. Give one gentle, non-blocking clarification: `$pinboard-deliver` is the implementer route after Pinboard prepares an active attempt; ordinary wording such as “Use Pinboard to work on <item>” is the intended start. Then continue through the normal Pinboard route when the item and requested outcome are clear. Ask one concrete question only when the intended item or outcome is genuinely ambiguous.

Do not blame the human, lecture about internal routing, expose backend or unrelated task state, or stop after the clarification when Pinboard can continue.

Keep `$pinboard-intake` and `$pinboard-deliver` as thin specialized callers that decide how to preserve or implement work and report through [the human's picture](common.md#keep-the-humans-picture-current) and the collaboration style above.

Use [preparation and dispatch](../../references/preparation-and-dispatch.md) before continuing that start.

## Outcome ownership

One coding-agent task owns one outcome through final human disposition. Keep product, scope, approval, review, and repository-disposition decisions in that task. Use subagents for bounded research, implementation, verification, and review whose results should return to it automatically. Create another task only for a genuinely independent outcome the human intends to follow in that task's own conversation; it is not a subordinate worker or return destination.

In multi-task use, recommend one task per distinct independent outcome; a campaign the human chose counts as one outcome.

An active implementation request covers candidate submission, review by a separate reviewer, and correction of in-scope findings through the supported workflow. Continue those steps in the owning turn without another general review approval or a human nudge. Keep explicit pauses, background requests, scope changes, missing capabilities, mandated executors and runtime access, repository disposition, and terminal completion under their existing authority rules. A request only to assess a review remains inspection-only.

Name the actor and expected next action in every user-facing review update. Describe the default path as `review by a separate Codex reviewer`, `review by a separate Claude Code reviewer`, or `review by a separate Antigravity reviewer`, matching the current runtime and including whether that review is ready, underway, accepted, or returned for correction. Say `ready for your review — <decision requested>` only when the human is actually expected to review or decide something. Do not use bare `independent review` as a user-facing destination when the actor would be unclear.

## Safe boundaries

Process newly delivered intake only after the current review, transition, commit, or other atomic repository action ends. Delivery does not authorize interrupting or widening an active attempt.

Before nested intake, load the [continuation anchor](../../references/setup-and-transitions.md#nested-intake-and-concern-revision), keep the current objective and promised next action with its durable selector, then return after persistence.

Keep that same anchor before compaction or a long gap in active work. Recover exact roots, distinct item and attempt identities, candidate or return context, native task handles, and current authority before acting. Correct a known wrong root, selector, copied identity, or invocation from current evidence without asking the human to supply hidden tool output. For lost or invalid launches, follow [fresh launch-response recovery](../../references/preparation-and-dispatch.md#recover-a-worker-or-reviewer-launch-response); a verified prompt alone is not a native recipe.

## Wrap up with facts

At every consequential workflow-ending reply after implementation, review, a blocker or unresolved concern, pause or resume, repository disposition, follow-up, or terminal confirmation, call `pinboard_item_status` operation `item` with exact roots and item immediately before the reply and treat that fresh `pinboard-item-status/v5` result as the internal truth source. Report it through the human's picture: no raw item or attempt identifiers, redundant state labels, or code-block status receipt unless the user requests machine-readable status or troubleshooting requires them.

Use the fresh result to preserve the distinction between a paused accepted checkpoint, active continuation, a candidate in review, and a terminal work item. Item status contains at most the current nonterminal attempt and contains none for a terminal item; a terminal item's `closure` names only the closing attempt of a completion. Mention another historical terminal attempt only when useful, and source it from the terminal transition continuation or exact attempt inspection. When the kept changes of an owning item came from an experiment on a scratch board, record that board's absolute work root in the item's terminal outcome evidence at closure, so a later agent reaching the item directly or through its branch finds the board before making review or adoption claims. If the fresh read fails or returns an inconsistent shape, report in ordinary prose that canonical status is unavailable and do not infer it from prose, Git, a pull request, or generated views.

At a consequential handoff or wrap-up, use a compact vertical decision view when it helps the human understand or choose the next action, with only the relevant short rows: **Delivered** for the verified agreed outcome, saying where it lives and whether it reached the integration target; **Remaining work** for unfinished product or review work; **Administrative steps** for verified recording or cleanup still owed; **Evidence or doubt** for a consequential uncertainty; **Follow-ups** for each raised concern resolved now, owned by an exact durable item, or still unresolved; and **Next action** or **Your decision** for the next actor and action or one genuine human decision. The view replaces the `Still open:` line; do not repeat its rows there. Ordinary technical discussion stays conversational.

Build that view from the accepted outcome and fresh item, attempt, review, repository, and follow-up evidence relevant to this work; Git and PR facts are evidence for Git-backed work, not a universal completion test. When a conversation covers multiple items, name each decision-relevant outcome separately and omit unrelated status. For paused or blocked work, name the condition preventing the next step, who can clear it, whether the human must decide now, and the next supported step; do not call review the next step while its required evidence or preparation is blocked. A merged PR, archived coding-agent task, or nonterminal Pinboard status alone establishes neither product completion nor an administrative-only remainder: call the remainder administrative only after verifying that the accepted product and review work is delivered and naming the exact recording or cleanup steps left. Never describe an ownerless concern as saved.

Qualify every other ending claim by the fact that actually ended—implementation candidate ready, checkpoint accepted, review accepted, repository integrated, cleanup performed, or coding-agent turn ended—under the status-word rule. Carry out obvious authorized remaining work before asking the human to act. Ask one concrete question only when the next step needs a product, architecture, requirements, limitation, or material-risk decision, or genuinely missing authority, including for repository disposition, cleanup, terminal transition, or bounded blocker recovery; otherwise name the agent-owned next step and continue it. Once fresh status reports a terminal work item and all authorized repository effects succeeded, state that no further action remains and whether its changes reached the integration target. Whenever fresh status reports a terminal item, also link the board page once from that result's `board` object under the readable-artifact rule; in-progress handoffs carry no board link. Omit closure framing from ordinary discussion and healthy in-progress updates.

Use the state-and-recovery section only for lease revocation, invalid SQLite state, interrupted transitions, or work inherited from an unavailable session.
